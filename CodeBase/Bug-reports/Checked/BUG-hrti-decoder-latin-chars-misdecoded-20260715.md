# Bug Report: HRTI-декодер некорректно декодирует латинские буквы A-O, Q и символ `/` как русские буквы

## Summary

Декодер HRTI (Hashed RTI) в `internal/rti/hrti.go` систематически декодирует латинские буквы `A`–`O`, `Q` и символ `/` (слэш) как соответствующие русские буквы из-за неисправимой коллизии `ord % 128` и стратегии «всегда предпочитать русскую букву». Также русская буква `Р` (U+0420) декодируется как пробел. Это приводит к искажению всех строковых полей, содержащих латинский текст (имена форм, имена файлов, имена атрибутов, пути), деля их нечитаемыми.

Примеры искажённого декодирования из HRTI-файла `cert_10002405568_20042026_21072026_транш_рамка_2.5.hrti`:

| Поле | Тип | Декодировано (баг) | Ожидаемое |
|------|-----|---------------------|-----------|
| `FormName` | `DSFIELDNAMEVAR` | `TуontractэltцundуrdьinePmnt^ц` | `TContractSetFundCrdLinePmntPF` |
| `AutoComment` | `DSCOMMENT` | `уonsumer\RяS^уяRP^уonsRam.smf` | `Consumer\RSRPRConsRam.smf` |
| `AttrName` | `DSFIELDNAMEVAR` | `уheckьimitцorяver` | `CheckLimitForOver` |
| `AttrName` | `DSFIELDNAMEVAR` | `уheckьimitцorTranche` | `CheckLimitForTranche` |

## Root Cause Analysis

### Алгоритм TDsHash и природа коллизии

TDsHash кодирует символы по формуле:

```
NewIndex = ((Ord(char) XOR M1) + M2) mod 128
CipherChar = cLetters[NewIndex]
```

Декодер обращает формулу:

```
v = ((cIdx - M2 + 128) % 128) XOR M1
```

Где `v = original_ord mod 128`. Для ASCII (0–127) `v == ord` — однозначное декодирование. Для русских букв (Unicode > 127) `v = ord % 128`, что **коллизирует** с определёнными ASCII-кодами.

### Таблица коллизий

Каждая пара ниже имеет одинаковый `ord % 128`, что делает их неразличимыми без контекста:

| ASCII | ord | Русская буква | Unicode | ord % 128 |
|-------|-----|---------------|---------|-----------|
| ` ` (space) | 32 | `Р` | U+0420 | 1056 % 128 = **32** |
| `/` (slash) | 47 | `Я` | U+042F | 1071 % 128 = **47** |
| `A` | 65 | `с` | U+0441 | 1089 % 128 = **65** |
| `B` | 66 | `т` | U+0442 | 1090 % 128 = **66** |
| `C` | 67 | `у` | U+0443 | 1091 % 128 = **67** |
| `D` | 68 | `ф` | U+0444 | 1092 % 128 = **68** |
| `E` | 69 | `х` | U+0445 | 1093 % 128 = **69** |
| `F` | 70 | `ц` | U+0446 | 1094 % 128 = **70** |
| `G` | 71 | `ч` | U+0447 | 1095 % 128 = **71** |
| `H` | 72 | `ш` | U+0448 | 1096 % 128 = **72** |
| `I` | 73 | `щ` | U+0449 | 1097 % 128 = **73** |
| `J` | 74 | `ъ` | U+044A | 1098 % 128 = **74** |
| `K` | 75 | `ы` | U+044B | 1099 % 128 = **75** |
| `L` | 76 | `ь` | U+044C | 1100 % 128 = **76** |
| `M` | 77 | `э` | U+044D | 1101 % 128 = **77** |
| `N` | 78 | `ю` | U+044E | 1102 % 128 = **78** |
| `O` | 79 | `я` | U+044F | 1103 % 128 = **79** |
| `Q` | 81 | `ё` | U+0451 | 1105 % 128 = **81** |

### Локализация ошибки в коде

**Файл:** `internal/rti/hrti.go`, строки 121–136

```go
switch v {
case 32: // space vs Р
    b.WriteByte(' ')
case 37, 40, 41, 44, 46: // %, (, ), comma, dot — ASCII punctuation
    b.WriteByte(byte(v))
default:
    // Prefer Russian letter if available
    if russians, ok := mod128ToRussian[v]; ok && len(russians) > 0 {
        b.WriteRune(russians[0])   // ← ВСЕГДА выбирает русскую букву
    } else if v >= 32 && v <= 126 {
        b.WriteByte(byte(v))
    } else {
        b.WriteRune(r)
    }
}
```

**Баг 1 (строки 127–129):** Ветке `default` всегда предпочитает русскую букву, если для значения `v` найдено соответствие в `mod128ToRussian`. Это затрагивает **все** латинские буквы A–O, Q и символ `/`, которые имеют коллизии с русскими буквами. Латинский текст (имена форм, файлов, атрибутов) превращается в нечитаемую смесь русских букв.

**Баг 2 (строки 122–123):** Значение `v=32` всегда декодируется как пробел, но русская буква `Р` (U+0420, ord=1056, 1056%128=32) также даёт `v=32`. В результате `Р` в русских текстах заменяется на пробел.

**Баг 3 (строка 124):** Символ `/` (v=47) не включён в список ASCII-пунктуации (обработаны только `37, 40, 41, 44, 46`). Значение `v=47` попадает в `default`, где выбирается русская буква `Я` вместо `/`.

### Отсутствие контекста типа поля

Функция `decodeHRTIString` не получает информацию о типе декодируемого поля (`DSFIELDNAMEVAR`, `DSBRIEFNAME`, `DSCOMMENT` и т.д.). Функция `DecodeHRTIResult` (строки 184–234) вызывает `decodeHRTIIfNeeded` для всех строковых значений без передачи типа:

```go
call.Params[i].Value = decodeHRTIIfNeeded(call.Params[i].Value)  // тип не передаётся
```

Тип поля позволяет определить, содержит ли поле латинский текст (имена форм, файлов, атрибутов — типы `DSFIELDNAMEVAR`, `DSFIELDNAME`) или русский (комментарии, описания — типы `DSCOMMENT`, `DSBRIEFNAME`, `DSFULLNAME`). Без этой информации декодер не может корректно разрешить коллизию.

### Декодер не обрабатывает имена процедур

`DecodeHRTIResult` (строки 184–234) декодирует значения параметров, контекст возврата, блоки бизнес-лога и таблицы, но **не декодирует**:
- `call.Procedure` — имя процедуры
- `call.Params[i].Name` — имя параметра
- `call.Params[i].Type` — тип параметра

В HRTI-файлах эти поля могут быть закодированы. Однако регулярные выражения парсера (`reEnter`, `reExit`, `reParam`) используют `\w+` для захвата имён, что не совпадает с закодированными значениями, содержащими не-ASCII символы. Если имена процедур в HRTI закодированы, парсер вообще не распознает такие строки как `Enter`/`Exit`-записи.

---

## Impact

- **Критический:** Все латинские строки в HRTI-логах искажаются — имена форм, файлов, атрибутов, пути становятся нечитаемыми. Это делает невозможным анализ HRTI-логов, содержащих технические идентификаторы.
- **Средний:** Русская буква `Р` теряется в декодированном тексте, заменяясь на пробел.
- **Средний:** Символ `/` в путях файлов заменяется на `Я`, деля пути нечитаемыми.
- **Низкий:** Отсутствие декодирования имён процедур и параметров (если они закодированы) может приводить к неполному парсингу HRTI-логов.

## Suggested Fix

### Вариант 1: Контекстно-зависимое декодирование (предпочтительный)

Добавить параметр `fieldType string` в `decodeHRTIString` и `decodeHRTIIfNeeded`. В `DecodeHRTIResult` передавать тип поля:

```go
func decodeHRTIString(s string, fieldType string) string {
    // ... existing code ...
    
    // Выбор стратегии разрешения коллизии на основе типа поля
    preferLatin := isLatinFieldType(fieldType)
    
    switch v {
    case 32:
        if preferLatin {
            b.WriteByte(' ')
        } else {
            b.WriteRune('Р')
        }
    case 47: // /
        if preferLatin {
            b.WriteByte('/')
        } else {
            b.WriteRune('Я')
        }
    default:
        if preferLatin && v >= 32 && v <= 126 {
            b.WriteByte(byte(v))
        } else if russians, ok := mod128ToRussian[v]; ok && len(russians) > 0 {
            b.WriteRune(russians[0])
        } else if v >= 32 && v <= 126 {
            b.WriteByte(byte(v))
        } else {
            b.WriteRune(r)
        }
    }
}
```

Где `isLatinFieldType` определяет, что типы `DSFIELDNAMEVAR`, `DSFIELDNAME`, `DSPARAMNAME` содержат латинский текст:

```go
func isLatinFieldType(t string) bool {
    switch t {
    case "DSFIELDNAMEVAR", "DSFIELDNAME", "DSPARAMNAME", "DSTYPENAME":
        return true
    default:
        return false
    }
}
```

### Вариант 2: Эвристика по содержимому (fallback)

Если тип поля недоступен, применять эвристику: декодировать строку дважды (с prefer Latin и prefer Russian), затем выбрать вариант с большим количеством "осмысленных" символов. Для латинских идентификаторов характерно наличие строчных букв `a-z` (которые не имеют коллизий), заглавных `P-Z` (не имеют коллизий), цифр и спецсимволов.

### Вариант 3: Добавить `/` в список ASCII-пунктуации (минимальный фикс)

Как минимум, добавить `47` (слэш) в список ASCII-пунктуации на строке 124:

```go
case 37, 40, 41, 44, 46, 47: // %, (, ), comma, dot, slash — ASCII punctuation
```

Это исправит только символ `/`, но не латинские буквы A–O, Q.
