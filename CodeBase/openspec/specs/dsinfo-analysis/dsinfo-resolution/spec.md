# Разрешение контекста анализа по профилю dsinfo

## Purpose

Потребление профиля развёртывания dsinfo командами анализа: сопоставление
манифеста «Продукты Digital Q» с индексированными релизными линиями,
цепочка разрешения контекста (флаг/окружение/активный профиль/ветка по
умолчанию) и семантика fallback с явным предупреждением. Финальный срез
мультиветочной модели из `Modifications/dsinfo-product-branches-6f2a1c.md`.

## Requirements

### Requirement: Матчинг профиля на индексированные ветки

Система SHALL вычислять сопоставление каждой строки манифеста профиля
(`dsinfo_products`) с индексом: продукт — по `product_name` в `ds_products`,
линия — по `(product, branch_key)` в `ds_products_branch`. Сопоставление
SHALL быть двухуровневым: сначала точное совпадение `branch_key`, затем
fallback в пределах того же продукта — последовательность числовых
сегментов `branch_key` манифеста SHALL быть суффиксом последовательности
числовых сегментов `branch_key` индексированной линии (`fa-contracts-11-01-7`
↔ `sup/11-01-7`; цифры внутри буквенных сегментов имени продукта
игнорируются). Точное совпадение SHALL иметь приоритет; при нескольких
кандидатах fallback выбирается default-линия, затем больший id. Строка
получает статус `ok` (продукт и линия проиндексированы), `product_not_indexed`
или `branch_not_indexed`; в статусе `ok` сохраняется фактический
`branch_key` совпавшей линии. Сопоставление SHALL вычисляться при отображении
(на лету) и не SHALL изменять сохранённый снимок профиля.

Строки манифеста одного продукта (несколько пакетов/линий, например
fa-contracts-ext) SHALL сопоставляться независимо. Выбранная линия продукта
SHALL определяться так: если у продукта есть проиндексированные строки —
default-линия среди них, затем старшая версия (числовое сравнение сегментов),
затем больший id; fallback на default-ветку продукта применяется только при
отсутствии проиндексированных строк.

#### Scenario: Линия проиндексирована

- **GIVEN** профиль со строкой `fa-contracts`/`fa-contracts-11-01-7` и проиндексированная линия `fa-contracts-11-01-7`
- **WHEN** вычисляется сопоставление
- **THEN** строка имеет статус `ok` и ссылку на строку `ds_products_branch`

#### Scenario: Линия не проиндексирована

- **GIVEN** профиль со строкой `fa-agreement`/`fa-agreement-9-01-1` и продукт `fa-agreement` без линии `fa-agreement-9-01-1`
- **WHEN** вычисляется сопоставление
- **THEN** строка имеет статус `branch_not_indexed`

#### Scenario: Продукта нет в индексе

- **GIVEN** профиль со строкой `fa-adpsuv` и продукт `fa-adpsuv` не проиндексирован
- **WHEN** вычисляется сопоставление
- **THEN** строка имеет статус `product_not_indexed`

#### Scenario: Нестандартное имя линии

- **GIVEN** профиль со строкой `fa-contracts`/`fa-contracts-11-01-7` и проиндексированная линия с `branch_key` = `sup/11-01-7`
- **WHEN** вычисляется сопоставление
- **THEN** строка имеет статус `ok`, а совпавшая линия — `sup/11-01-7`
- **AND** при наличии также точной линии `fa-contracts-11-01-7` выбрана она

### Requirement: Таблица сопоставления в parse и show

Команды `dsinfo parse` и `dsinfo show` SHALL выводить таблицу
сопоставления: продукт, ссылка манифеста, совпавшая ветка, статус; и итог
вида «matched N/M products; K branches missing». N и M SHALL считаться по
уникальным продуктам манифеста (matched — продукт, у которого есть хотя бы
одна строка `ok`), K — число строк со статусом `branch_not_indexed`.
Повторный просмотр того же профиля после индексации недостающих веток
SHALL показывать обновлённые статусы без повторного разбора CSV.

#### Scenario: Parse с недостающими ветками

- **GIVEN** CSV-манифест с 62 продуктами, из которых линии проиндексированы для 14
- **WHEN** выполняется `dsinfo parse <csv>`
- **THEN** выведены dsinfo_id, таблица сопоставления и итог с числом недостающих веток

#### Scenario: Статусы обновляются после update

- **GIVEN** профиль со статусом `branch_not_indexed` у строки `fa-gaap`/`fa-gaap-11-01-4`
- **WHEN** линия проиндексирована (`codebase update`) и выполняется `dsinfo show <id>`
- **THEN** строка показывает статус `ok` без повторного parse

### Requirement: Цепочка разрешения контекста анализа

Команды анализа (`query`, `rti`, `trc`, `review`; CLI и MCP) SHALL принимать
необязательный контекст профиля, разрешаемый по цепочке убывания приоритета:
явный `--dsinfo <id>` (CLI) / `dsinfo_id` (MCP) > переменная окружения
`CODEBASE_DSINFO_ID` > активный профиль (`dsinfo use`) > отсутствие профиля
(ветка по умолчанию). Несуществующий или некорректный идентификатор SHALL
завершать команду ошибкой при применении контекста — когда команда
выполняет выбор копии или enrichment; на поверхностях вне границ профиля и
при отсутствии элементов для enrichment контекст не разрешается и
идентификатор не проверяется. Команды
`init`, `update`, `dsinfo ...`, `health`, `stats` не SHALL принимать
контекст. Применение контекста на командах анализа SHALL ограничиваться
поверхностями, перечисленными в требовании «Границы применения профиля по
поверхностям».

#### Scenario: Флаг перекрывает окружение и активный профиль

- **GIVEN** активный профиль 1, `CODEBASE_DSINFO_ID=2`, вызов с `--dsinfo 3`
- **WHEN** выполняется `query procedure --name MyProc --dsinfo 3`
- **THEN** контекст разрешения — профиль 3

#### Scenario: Окружение перекрывает активный профиль

- **GIVEN** активный профиль 1, `CODEBASE_DSINFO_ID=2`
- **WHEN** выполняется `query procedure --name MyProc` без флага
- **THEN** контекст разрешения — профиль 2

#### Scenario: Ничего не задано

- **GIVEN** ни флага, ни окружения, активный профиль не назначен
- **WHEN** выполняется команда анализа
- **THEN** профиль не применяется, lookup идёт в default-ветку (поведение среза branch-aware-lookup)

#### Scenario: Несуществующий идентификатор

- **GIVEN** вызов с `--dsinfo 999` и профиль 999 не существует
- **WHEN** выполняется команда анализа
- **THEN** команда завершается ошибкой, fallback не применяется молча

#### Scenario: Review с профилем

- **GIVEN** активный профиль 3 с линией `fa-contracts-11-01-7`
- **WHEN** выполняется `codebase review file.sql`
- **THEN** ветки чужих продуктов разрешаются по профилю 3
- **AND** ветка продукта проверяемого файла берётся из файла, а не из профиля

### Requirement: Семантика fallback с явным предупреждением

Профиль SHALL задавать приоритет выбора ветки, а не жёсткий фильтр: порядок
выбора копии в поверхностях, выполняющих выбор, — `not_generated` →
`profile_match` (продукт и линия профиля) → default-ветка (`is_default`) →
больший id. Для продукта из профиля lookup выбирает его линию; если линия не
проиндексирована — default-ветку продукта. Ответ SHALL сообщать
`branch_requested` (`branch_key` всех линий манифеста продукта, через
запятую) и `branch_used` (`branch_key` фактически выбранной линии).
Предупреждение SHALL вычисляться по фактическим элементам ответа после
выполнения запроса: оно формируется для элемента, чья `branch_used` не
входит в `branch_requested` (в том числе когда ветка не определена), не
формируется при `branch_used ∈ branch_requested` и при пустом ответе.
Предупреждение SHALL агрегироваться по тройке (продукт, запрошенные линии,
использованная линия) и не SHALL появляться для продуктов вне профиля;
текст сообщает показанную ветку без утверждения о том, что она default.

#### Scenario: Запрошенная линия проиндексирована

- **GIVEN** профиль с `fa-contracts`/`fa-contracts-11-01-7` и проиндексированная линия
- **WHEN** выполняется `query procedure --name MyProc --dsinfo <id>`
- **THEN** выбрана копия из `fa-contracts-11-01-7`, `branch_requested` = `branch_used`

#### Scenario: Запрошенная линия отсутствует

- **GIVEN** профиль с `fa-agreement`/`fa-agreement-9-01-1` и только develop-линия продукта
- **WHEN** выполняется запрос сущности продукта `fa-agreement`
- **THEN** выбрана develop-копия, `branch_used` = develop, `branch_requested` = `fa-agreement-9-01-1`
- **AND** ответ содержит предупреждение о возможном различии кода

#### Scenario: Линия проиндексирована, но сущности в ней нет

- **GIVEN** профиль с `fa-contracts`/`fa-contracts-11-01-7` (линия проиндексирована) и процедура `MyProc`, существующая только в develop
- **WHEN** выполняется `query procedure --name MyProc --dsinfo <id>`
- **THEN** выбрана develop-копия, `branch_requested` = `fa-contracts-11-01-7`, `branch_used` = develop
- **AND** ответ содержит предупреждение о возможном различии кода

#### Scenario: Несколько линий продукта в манифесте

- **GIVEN** профиль со строками `fa-contracts-ext`/`fa-contracts-ext-7-02-2` и `fa-contracts-ext-9-01-553`, из которых проиндексирована только 7-02-2
- **WHEN** выполняется запрос сущности продукта `fa-contracts-ext` с профилем
- **THEN** выбрана копия из линии 7-02-2
- **AND** `branch_requested` перечисляет обе линии, предупреждения нет

#### Scenario: Продукт вне профиля

- **GIVEN** профиль и сущность продукта, отсутствующего в манифесте профиля
- **WHEN** выполняется запрос с профилем
- **THEN** сущность выбирается по правилам default (профиль не фильтрует чужие продукты)

### Requirement: Границы применения профиля по поверхностям

Система SHALL применять контекст профиля только к поверхностям, выполняющим
выбор копии сущности: entity- и API-запросы (`query procedure`, таблицы и
схемы, индексы, методы, формы и компоненты, отчёты, JS/SMF, retcode,
фрагменты), поиск символов, лексический слой поиска по описаниям, enrichment
RTI/TRC и DB-lookup'и review для чужих продуктов (ветка продукта проверяемого
файла всегда берётся из файла). Поверхности, возвращающие все копии или не
имеющие продукта-кандидата (`query callers`, `query relations`, `query
inspect`, spec-команды `query spec ...`, semantic-слой desc-search), SHALL
возвращать результаты независимо от профиля. Присутствие контекста на таких
поверхностях не SHALL быть ошибкой и не SHALL добавлять предупреждений;
идентификатор профиля на них не разрешается и не проверяется.

#### Scenario: Callers с профилем

- **GIVEN** процедура с копиями в develop и релизной линии и заданный профиль с этой линией
- **WHEN** выполняется `query callers --procedure MyProc --dsinfo <id>`
- **THEN** возвращены вызывающие из обеих копий, как без профиля
- **AND** ответ не содержит предупреждений о ветках

#### Scenario: Spec-команда с профилем

- **GIVEN** профиль задаёт линию продукта, у которого есть отдельная spec-конфигурация
- **WHEN** выполняется `query spec search --query договор --dsinfo <id>`
- **THEN** поиск идёт по default-конфигурации, как без профиля

#### Scenario: Semantic-слой поиска описаний

- **GIVEN** заданный профиль
- **WHEN** выполняется `query desc-search --text кредит`
- **THEN** лексический слой учитывает профиль, semantic-слой — нет

#### Scenario: Review с профилем

- **GIVEN** проверяемый файл продукта `fa-contracts` в ветке `fa-contracts-11-01-7` и профиль с линией `fa-contracts-11-01-7`
- **WHEN** выполняется review и правило обращается к сущности чужого продукта
- **THEN** ветка чужого продукта разрешается по профилю
- **AND** для продукта `fa-contracts` используется ветка из файла

### Requirement: Приоритет продуктов профиля в enrichment без известного продукта

Enrichment RTI/TRC, где продукт вызова заранее не известен (имя процедуры
ищется глобально), SHALL применять профиль как приоритет кандидатов:
сначала копии в продуктах и линиях профиля (ось `profile_match` после
`not_generated`), затем остальные — по правилам среза branch-aware-lookup.
Результат enrichment SHALL содержать `product` и `branch_used` — `branch_key`
выбранной копии.

#### Scenario: Имя в двух продуктах, один в профиле

- **GIVEN** процедура `UTIL_DateFmt` в `fa-contracts` (11-01-7) и `fa-payments` (develop); профиль содержит только `fa-contracts`/`fa-contracts-11-01-7`
- **WHEN** выполняется enrichment вызова `UTIL_DateFmt` с профилем
- **THEN** выбрана копия `fa-contracts` из линии 11-01-7, результат содержит product/branch

#### Scenario: Без профиля поведение прежнее

- **GIVEN** тот же индекс и вызов без контекста профиля
- **WHEN** выполняется enrichment
- **THEN** выбор по правилам default (идентично срезу branch-aware-lookup)

## Notes

- Профиль — снимок: ссылки на ветки вычисляются при использовании, поэтому
  переиндексация новых линий обновляет статусы без повторного parse.
- Решения обсуждения 2026-10-27: порядок осей — `not_generated` строго первым
  (гигиена generated-артефактов), затем `profile_match`; границы применения
  профиля зафиксированы явно; матчинг веток — точный плюс fallback по
  числовым сегментам хвоста (цифры в имени продукта игнорируются).
- Решения по code review (2026-10-27): предупреждения вычисляются по
  фактическому ответу (коллектор по элементам), а не по всему профилю;
  `branch_requested` — полный список линий продукта, предупреждение только
  при `branch_used ∉ branch_requested`; идентификатор профиля валидируется
  при применении контекста, на границах — не проверяется.
- `develop`-линия индекса имеет `branch_key = develop`, которого манифест не
  порождает; для develop-кода профиль всегда даёт fallback с предупреждением —
  это ожидаемо.
- `--strict`-режим (жёсткая фильтрация по веткам) отклонён: приоритет с
  пометкой fallback достаточен и не ломает анализ при частично
  проиндексированном банке (решение обсуждения 2026-10-24).
- Секция «Модули» профиля (`dsinfo_modules`) дополнительно связывает BPL
  банка с продуктом — потенциальное уточнение для клиентских RTI-событий,
  вне объёма этого среза.
