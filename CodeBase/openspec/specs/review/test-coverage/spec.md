# Review Test Coverage

## Purpose

Определяет обязательное unit-покрытие каждого правила каталога review: положительный и отрицательный кейсы, исполняемые без СУБД, и детерминированные подмены для правил, зависящих от метаданных индекса или каталога.

## Requirements

### Requirement: Unit-тест для каждого правила каталога

Каждое правило, зарегистрированное в каталоге review, MUST иметь хотя бы один unit-тест, который исполняется командой `go test ./internal/review/...` без тега `integration` и без подключения к PostgreSQL и проверяет поведение самого правила, а не только его включение в набор правил.

#### Scenario: Правило без unit-теста

- **GIVEN** правило присутствует в каталоге review
- **WHEN** выполняется `go test ./internal/review/...`
- **THEN** существует тест, вызывающий применение этого правила к SQL-тексту
- **AND** тест не требует переменных окружения или БД

#### Scenario: Правило с единственным integration-тестом

- **GIVEN** правило покрыто только тестом с тегом `integration`
- **WHEN** выполняется обычный `go test ./internal/review/...`
- **THEN** правило всё равно имеет unit-тест, исполняемый в этом прогоне

### Requirement: Положительный и отрицательный кейсы

Unit-тест правила MUST содержать минимум один положительный кейс (ожидается finding) и минимум один отрицательный кейс (finding отсутствует), чтобы фиксировать не только обнаружение, но и отсутствие ложных срабатываний.

#### Scenario: Есть только положительный кейс

- **GIVEN** правило имеет unit-тест, проверяющий только ожидаемый finding
- **WHEN** правило начинает срабатывать на корректном SQL
- **THEN** тест должен обнаружить регрессию
- **AND** для этого в наборе кейсов присутствует отрицательный кейс

#### Scenario: Проверка результата negative-кейса

- **GIVEN** отрицательный кейс правила
- **WHEN** правило применяется к корректному SQL-тексту
- **THEN** количество findings равно нулю

### Requirement: Детерминированные подмены вместо БД

Правила, которым для решения нужны метаданные индекса, каталога процедур или привязки к продукту, MUST тестироваться через детерминированные тестовые подмены, не обращающиеся к реальной БД.

#### Scenario: Правило зависит от каталога процедур

- **GIVEN** правило сравнивает вызовы процедур с каталогом продуктов
- **WHEN** выполняется unit-тест
- **THEN** каталог предоставляется тестовой подменой
- **AND** результат не зависит от состояния PostgreSQL

#### Scenario: Правило зависит от метаданных индекса

- **GIVEN** правило проверяет соответствие условий индексу
- **WHEN** выполняется unit-тест
- **THEN** набор индексов предоставляется тестовой подменой
- **AND** тест воспроизводим без индексации кодовой базы

### Requirement: Проверка идентичности finding

Unit-тест правила MUST проверять не только количество findings, но и идентичность правила, уровень серьёзности и, для позиционных проверок, привязку к строке исходного текста.

#### Scenario: Проверка позиционного правила

- **GIVEN** правило сообщает номер строки или объект
- **WHEN** положительный кейс даёт finding
- **THEN** тест проверяет правило, серьёзность и номер строки
- **AND** при использовании макросов проверяется привязка к исходной строке
