# Spec Search

## Purpose

Полнотекстовый поиск по спецификациям в два слоя: лексический (tsvector 'russian' + pg_trgm по всем уровням сущностей спек) и семантический (TF-IDF + LSA на capability-уровне, k настраивается), с раздельными секциями результата и пороговой фильтрацией семантической выдачи. Управление LSA-моделью: обучение при пост-обработке индексации, инвалидация по fingerprint корпуса и параметров (детерминированный хеш) с кумулятивным порогом амортизации, хранение словаря и векторов в БД, матрицы проекции и состояния — в файлах рядом с БД.

## Requirements

### Requirement: Лексический слой поиска

Система SHALL обеспечивать точный полнотекстовый поиск по `spec_capabilities` (title A-вес, purpose/notes B), `spec_requirements` (requirement_name A, body_text B), `spec_scenarios` (given/when/then B), `spec_usecases` (title A, description B) через `tsvector`, конфигурацию 'russian' и GIN-индексы. Технические идентификаторы (`API_*`, `FCD_*`, имена таблиц) дополнительно ищутся через `pg_trgm` similarity — как в текстах спек, так и в `spec_code_mentions`. Поиск поддерживает фильтры: продукт, уровень сущности (capability|requirement|scenario|usecase), статус (для changes).

#### Scenario: Поиск по бизнес-термину

- **GIVEN** проиндексированные спеки с требованием «Арест аналитического счёта»
- **WHEN** выполняется поиск по запросу «арест счёта»
- **THEN** найдены capability и требования, содержащие термин, с указанием продукта, slug и границ строк

#### Scenario: Поиск технического идентификатора

- **GIVEN** спеки, упоминающие `API_CCred_BindClassifier` в текстах сценариев
- **WHEN** выполняется поиск по имени без точного совпадения падежа/контекста
- **THEN** trgm-слой находит упоминания в текстах спек, включая тексты сценариев, а не только секции Related code

### Requirement: Семантический слой — TF-IDF + LSA

Система SHALL строить семантический слой поиска через TF-IDF + LSA: токенизация с тремя категориями терминов (русские слова — нижний регистр, нормализация ё→е и стемминг; технические идентификаторы — как есть, единым токеном; гибриды вида `758П`/`275-ФЗ` — как есть), словарь с фильтрацией minDF/maxDF, TF-IDF с log-нормализацией (учитывающей кратности терминов, включая удвоенный title) и smooth IDF, SVD-разложение (gonum) на все термины словаря. LSA применяется на уровне capability (embed_level = 'spec'): каждый capability получает k-мерный вектор; k настраивается (`lsa_k`, default 512 — поднимает редкие термины в топ выдачи); requirement-уровень покрывается только лексическим слоем.

#### Scenario: Семантическая близость через ко-встречаемость

- **GIVEN** корпус спек, где «арест» и «блокировка» встречаются в одних документах
- **WHEN** выполняется поиск «блокировка счёта» семантическим слоем
- **THEN** capability про арест счёта попадает в секцию семантически близких с косинусной оценкой

#### Scenario: Технический идентификатор как единый токен

- **GIVEN** тексты спек со словами `CON_STP_MassAccrual` и обычной русской лексикой
- **WHEN** строится словарь
- **THEN** `CON_STP_MassAccrual` — один токен словаря (не разбит на части), русский текст — стеммированные токены

#### Scenario: Редкий термин требования находится семантически

- **GIVEN** термин встречается только в текстах требований нескольких capability и проходит minDF
- **WHEN** выполняется семантический поиск по этому термину
- **THEN** capability с этим термином в требованиях входят в топ-5 семантической выдачи (замер k-тюнинга: k=512 против k=128 поднимает позицию с #18 до #5)

### Requirement: Состав LSA-документа

Система SHALL формировать LSA-документ каждой capability как единственный документ уровня capability (embed_level = 'spec', отдельные эмбеддинги требований не создаются) из: заголовка (title), назначения (purpose), примечаний (notes), имён и текстов всех дочерних требований, имён и текстов всех сценариев (given/when/then). Агрегирование MUST быть детерминированным: одинаковый корпус даёт одинаковый по составу и порядку текстов документ.

#### Scenario: Термин из требования входит в документ

- **GIVEN** capability, чьё требование содержит термин «заметка», отсутствующий в title/purpose/notes этой capability
- **WHEN** формируется LSA-документ capability
- **THEN** текст требования входит в документ, и термин участвует в словаре LSA, если проходит фильтр minDF

#### Scenario: Тексты сценариев входят в документ

- **GIVEN** capability с требованием, имеющим сценарии с текстами given/when/then
- **WHEN** формируется LSA-документ capability
- **THEN** имя каждого сценария и его тексты given/when/then включены в документ

#### Scenario: Детерминированность агрегирования

- **GIVEN** один и тот же корпус спек, прочитанный дважды
- **WHEN** формируются LSA-документы
- **THEN** состав и порядок текстов в документах идентичны при каждом чтении

### Requirement: Обучение и пересчёт LSA-модели

Система SHALL обучать LSA-модель при пост-обработке индексации и определять её актуальность по fingerprint — детерминированному хешу корпуса (состав LSA-документов всех capability) и параметров модели (minDF, maxDF, k, версия токенизатора, версия состава документа). Модель переобучается, когда fingerprint текущего корпуса отличается от fingerprint обученной модели И накопленное с прошлого обучения число изменений сущностей спек (включая удаления) достигло порога `lsa_retrain_threshold`; при нулевом пороге — при любом отличии fingerprint. Прогон без отличия fingerprint не переобучает модель и не увеличивает счётчик изменений. При ошибке обучения состояние актуальности не меняется, повторная попытка выполняется следующим прогоном. Словарь (term, doc_freq, idf) и векторы документов хранятся в таблицах `spec_vocab` / `spec_embeddings`; матрица проекции Vᵀ и fingerprint сериализуются рядом с файлом модели у БД. Пересчёт детерминирован: одинаковый корпус и параметры дают одинаковую модель.

#### Scenario: Идемпотентный прогон

- **GIVEN** обученная модель и `codebase update`, не изменивший ни одной сущности спек
- **WHEN** выполняется пост-обработка
- **THEN** fingerprint совпадает, модель не переобучается, счётчик изменений не растёт

#### Scenario: Пересчёт после массовых изменений

- **GIVEN** обученная модель и `codebase update`, изменивший 50+ сущностей спек (порог 50)
- **WHEN** выполняется пост-обработка
- **THEN** модель переобучена на актуальном корпусе, векторы в `spec_embeddings` обновлены, счётчик изменений сброшен

#### Scenario: Порог не достигнут

- **GIVEN** обученная модель, нулевой счётчик накопленных изменений и порог 50
- **WHEN** `codebase update` изменил 1 spec-файл, суммарно затронувший 10 сущностей спек
- **THEN** модель не переобучается, накопленное число изменений становится 10

#### Scenario: Накопление изменений между прогонами

- **GIVEN** обученная модель, накопленные 45 изменений и порог 50
- **WHEN** очередной прогон изменил 5 и более сущностей спек
- **THEN** модель переобучается, счётчик изменений сбрасывается в ноль

#### Scenario: Изменение параметра модели

- **GIVEN** обученная модель и нулевой порог
- **WHEN** в конфигурации изменён параметр модели (например, minDF)
- **THEN** fingerprint отличается от fingerprint обученной модели, модель переобучается

#### Scenario: Удаление spec-файла

- **GIVEN** обученная модель и нулевой порог
- **WHEN** удалён spec-файл с сущностями спек
- **THEN** корпус изменился, fingerprint отличается, модель переобучается без удалённых сущностей

#### Scenario: Ошибка обучения

- **GIVEN** fingerprint отличается и порог достигнут
- **WHEN** во время переобучения произошла ошибка (например, SVD)
- **THEN** состояние актуальности не меняется, ошибки фиксируются в логе, следующий прогон повторяет попытку

### Requirement: Раздельные секции результата

Система SHALL выдавать результат поиска двумя раздельными секциями — «точные совпадения» (лексический слой, ранжирование ts_rank + trgm similarity) и «семантически близкие» (LSA, косинусная оценка) — без слияния ранжирований; документы, найденные обоими слоями, показываются в обеих секциях. Каждый результат содержит продукт, slug/имя, уровень сущности, границы строк и текст-фрагмент. Секция «семантически близкие» MUST фильтроваться настраиваемым абсолютным порогом косинуса и относительным cutoff (доля от максимального косинуса секции), применяемыми до ограничения лимита. Если секция пуста после фильтрации или термины запроса отсутствуют в словаре LSA, ответ MUST содержать диагностические метаданные: причину пустоты, число отсеянных результатов и применимый порог; при терминах запроса вне словаря — подсказку воспользоваться точным слоем.

#### Scenario: Двухсекционный ответ

- **GIVEN** обученная модель и спеки, где часть совпадений точные, часть — только семантические
- **WHEN** выполняется `codebase query spec search --text "ограничение расходных операций"`
- **THEN** ответ содержит секцию точных совпадений (с ts_rank) и секцию семантически близких (с cosine score), перекрывающиеся документы видны в обеих

#### Scenario: Модель не обучена

- **GIVEN** индекс спек, но LSA-модель ещё не построена
- **WHEN** выполняется поиск
- **THEN** возвращается только секция точных совпадений с пометкой, что семантический слой недоступен

#### Scenario: Отсечение по порогам до лимита

- **GIVEN** обученная модель и semantic-кандидаты с косинусами 0.8 (максимум), 0.5, 0.3 при относительном cutoff 0.5 и лимите 10
- **WHEN** выполняется семантический поиск
- **THEN** кандидат 0.3 (ниже cutoff 0.4) отсечён до применения лимита, в секции остаются кандидаты 0.8 и 0.5

#### Scenario: Пустая секция с диагностикой

- **GIVEN** обученная модель и semantic-кандидаты, все ниже абсолютного порога
- **WHEN** выполняется поиск
- **THEN** секция семантически близких пуста, ответ содержит метаданные: число отсеянных результатов и применимый порог

#### Scenario: Термины запроса вне словаря

- **GIVEN** обученная модель, запрос «Заметка по клиенту», где стем «заметк» отсутствует в словаре LSA
- **WHEN** выполняется поиск
- **THEN** ответ содержит подсказку, что часть терминов запроса вне словаря LSA, с отсылкой к секции точных совпадений

### Requirement: Доступ через CLI и MCP

Система SHALL предоставлять поиск через MCP-инструмент `codebase_query_spec_search` и зеркальную CLI-подкоманду `codebase query spec search` с параметрами: текст запроса, слой (exact|semantic|both, по умолчанию both), фильтры продукта/уровня, лимит. Большие ответы MCP проходят существующую пагинацию; CLI поддерживает `--json`/`--ndjson` envelope как прочие query-команды.

#### Scenario: MCP-вызов поиска

- **GIVEN** запущенный MCP-сервер и проиндексированные спеки
- **WHEN** вызывается `codebase_query_spec_search` с `text = "отключение SMS-уведомлений"`
- **THEN** возвращены доменные данные (count, items с секциями exact/semantic) без CLI envelope
