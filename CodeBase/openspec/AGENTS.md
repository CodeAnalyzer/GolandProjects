# Правила работы с OpenSpec

## Структура каталогов

```
<project>/                # Корень проекта
├── README.md            # Карта проекта: обзор, модули, точки входа
└── openspec/
    ├── config.yaml       # Конфигурация OpenSpec (пути, настройки)
    ├── specs/            # Спецификации — источник истины (как система работает сейчас)
    │   └── <domain>/     # Спеки разбиты по доменам
    │       └── <feature>/
    │           └── spec.md   # Файл спецификации домена/функции
    └── changes/          # Изменения — единицы работы
        ├── <change-name>/    # Текущее (незавершённое) изменение
        │   ├── proposal.md   # Зачем (why): обоснование изменения
        │   ├── design.md     # Как (how): технический подход
        │   ├── tasks.md      # Шаги (steps): чек-лист задач
        │   └── specs/        # Дельта-спецификации (что меняется)
        │       └── <domain>/ # Зеркалит структуру openspec/specs/
        │           └── <feature>/
        │               └── spec.md   # Дельта к соответствующему spec-файлу
        └── archive/          # Завершённые и слитые обратно изменения
            └── <date>-<change-name>/
```

### Структура specs/ внутри change

Папка `changes/<change-name>/specs/` **зеркалит** структуру `openspec/specs/`.
Каждый файл в change — дельта к соответствующему spec-файлу продукта, лежит по
тому же относительному пути. Если change затрагивает несколько spec-файлов —
в `specs/` будет несколько файлов, каждый по своему пути:

```
changes/<change-name>/specs/
└── <domain>/
    ├── <sub-domain>/
    │   └── <sub-sub-domain>/
    │       └── spec.md          # дельта к <domain>/<sub-domain>/<sub-sub-domain>
    └── <sub-domain2>/
        └── <sub-sub-domain2>/
            └── spec.md          # дельта к <domain>/<sub-domain2>/<sub-sub-domain2>
```

При `openspec archive <change-name>` валидатор находит каждый дельта-файл по
пути, сопоставляет с основным spec-файлом по тому же пути и применяет
ADDED/MODIFIED/REMOVED к соответствующим требованиям.

## Принципы

1. **Спеки — источник истины.** Спецификация (`openspec/specs/`) описывает, как система работает сейчас. Состоит из требований (типа «система SHALL истекать сессии через 30 минут») и сценариев (конкретные примеры given/when/then).

2. **Изменение — это единица работы.** Когда нужно добавить, изменить или удалить поведение, следует создать изменение: папку в `openspec/changes/`, содержащую всё об этой работе в одном месте. Одно изменение — одна папка — одна фича.

3. **Дельта-спецификации описывают, что меняется.** Внутри изменения не переписывают всю спецификацию. Пишут небольшую дельту: `ADDED` — новое требование, `MODIFIED` — изменённое, `REMOVED` — удалённое.

4. **Артефакты строятся друг на друге.** Изменение содержит несколько документов, создаваемых в естественном порядке. Каждый документ имеет **обязательные секции** — валидатор CLI проверяет их наличие:
   - **proposal.md** (why) — зачем нужно изменение. Обязательные секции:
     - `## Why` — проблема, мотивация, ожидаемый эффект.
     - `## What Changes` — что меняется (новые возможности, модификации, удаления).
     - `## Capabilities` — затрагиваемые capabilities:
       - `### New Capabilities` — новые (kebab-case path); если нет — оставить пустым или «(нет)».
       - `### Modified Capabilities` — существующие, чьи **требования** меняются (не реализация); путь должен совпадать с путём в `openspec/specs/`.
     - `## Impact` — затронутый код, API, зависимости, системы.
   - **specs/** (what) — дельта-спецификации: какие требования добавляются/меняются/удаляются. Формат — в секции «Дельта-спецификации» ниже.
   - **design.md** (how) — технический подход. Обязательные секции:
     - `## Context` — текущее состояние и ограничения. Не повторяет proposal.
     - `## Goals / Non-Goals` — цели и явно вне области.
     - `## Decisions` — ключевые решения с обоснованием и альтернативами.
     - `## Risks / Trade-offs` — известные риски.
   - **tasks.md** (steps) — чек-лист задач. Формат: группы `## 1.`, `## 2.` с чек-боксами `- [ ] 1.1 ...`.

   > **Связь с концепцией.** Если доработка сопровождается концепцией (skill `concept-writer`), то `proposal.md` и `design.md` — это краткая выжимка из концепции со ссылкой на файл концепции. Дублировать весь текст концепции не нужно: `design.md` может содержать сводку и ссылку на раздел «Технические детали» концепции. `tasks.md` берётся из раздела «Сводная таблица файлов для изменения» концепции.

5. **Архивирование возвращает изменение обратно в истину.** Когда работа завершена, дельта-спецификации сливаются с основными спецификациями, а папка изменения перемещается в `changes/archive/` с меткой даты. Теперь спецификации описывают новую реальность. Цикл завершён.

6. **Карта проекта** описана в `README.md` в корне продукта (например `CodeBase/README.md`). Спеки в `openspec/specs/` разбиты по доменам.

## Структура файла spec.md

Каждый основной файл `spec.md` (в `openspec/specs/`) устроен одинаково:

- `# Название` — заголовок документа (h1). Не проверяется валидатором, но рекомендуется для читаемости.
- `## Purpose` — короткое описание, о чём спека (1–3 предложения, минимум 50 символов). **Обязательная секция** — без неё валидатор бросает ошибку `Spec must have a Purpose section`.
- `## Requirements` — **обязательная секция-контейнер** для требований. Без неё валидатор бросает ошибку `Spec must have a Requirements section`. Требования вне этой секции помечаются как невидимые (`requirement-outside-requirements`).
  - `### Requirement: Название` — каждое требование с **ровно 3 решётками**, вложено под `## Requirements`. Под требованием — его описание: «Система SHALL ...».
  - `#### Scenario: Название` — сценарии с **ровно 4 решётками**, вложены под требованием.
- `## Related code` — список технических артефактов (процедуры, таблицы, файлы). Не проверяется валидатором, но рекомендуется для связи спеки с кодом.
- `## Notes` — примечания, связи с другими spec. Не проверяется валидатором.

> **Запрет delta-заголовков в main spec.** Заголовки `## ADDED Requirements`, `## MODIFIED Requirements`, `## REMOVED Requirements`, `## RENAMED Requirements` **запрещены** в основных spec-файлах — они обрезают секцию `## Requirements` и помечаются ошибкой `delta-header`. Эти заголовки допустимы только в дельта-файлах внутри `changes/<name>/specs/`.

Количество решёток критически важно — валидатор OpenSpec выдаёт ошибку, если перепутать уровни.

## Стиль сценариев

Сценарий должен быть написан в **behavior-oriented** стиле (описывает ЧТО, а не КАК). Правило: тестировщик, который не видел кода, должен понять и проверить спеку.

Каждый сценарий — короткая история из трёх частей:

- **GIVEN** (Дано) — начальная ситуация, предусловие.
- **WHEN** (Когда) — действие, которое происходит.
- **THEN** (Тогда) — что должно получиться в итоге.

Дополнительные предусловия и результаты добавляются через **AND**.

### Формат буллетов

Каждая строка сценария — буллет через дефис с ключевым словом в **bold**:

```markdown
- **GIVEN** <предусловие>
- **AND** <дополнительное предусловие>
- **WHEN** <действие>
- **THEN** <ожидаемый результат>
- **AND** <дополнительный результат>
```

Под каждое требование — **минимум один сценарий**. Хорошо — несколько: успех, ошибка, крайний случай.

## Ключевые слова в требованиях

Валидатор OpenSpec распознаёт **только английские** ключевые слова `SHALL` и `MUST` (regex `/\b(SHALL|MUST)\b/`). Русские `ДОЛЖНА`/`ДОЛЖЕН`/`СЛЕДУЕТ`/`МОЖЕТ` **не распознаются** и приводят к warning `Requirement "..." should contain SHALL or MUST` (в режиме `--strict` — к ошибке и провалу валидации).

Ключевое слово проверяется в **теле** требования (строка после `### Requirement:`), а не в заголовке. Если `SHALL`/`MUST` есть только в заголовке — будет подсказка перенести его в body.

| Слово | Значение | Статус |
|-------|----------|-------|
| SHALL / MUST | Обязательное требование | Не выполнено = баг. **Распознаётся валидатором.** |
| SHOULD | Рекомендация | Нужно выполнять, если нет веских причин не делать. Не проверяется валидатором. |
| MAY | Необязательная возможность | Сделали — отлично, нет — тоже не нарушение. Не проверяется валидатором. |

> **Русский перевод** (`ДОЛЖНА`, `ДОЛЖЕН`, `СЛЕДУЕТ`, `МОЖЕТ`) приведён в таблице ниже для понимания семантики, но **в файлах spec.md нужно писать английские `SHALL`/`MUST`**. Шаблон: `Система SHALL <описание на русском>`.

| Английское | Русский аналог | Семантика |
|------------|----------------|-----------|
| SHALL / MUST | ДОЛЖЕН / ДОЛЖНА | Обязательное требование |
| SHOULD | СЛЕДУЕТ | Рекомендация |
| MAY | МОЖЕТ | Необязательная возможность |

## Дельта-спецификации

Внутри изменения (папка `changes/<name>/specs/`) дельта описывает только то, что меняется — без переписывания всей спецификации.

### Формат заголовков (требование CLI)

Дельта-файл `spec.md` внутри change отличается от основного spec-файла:
требования группируются под заголовками операций **множественного числа,
уровень 2**, а сами требования идут под ними **уровнем 3**:

- `## ADDED Requirements` → `### Requirement: <название>`
- `## MODIFIED Requirements` → `### Requirement: <название>` (название должно совпадать с существующим требованием в основном spec-файле)
- `## REMOVED Requirements` → `### Requirement: <название>` (название должно совпадать с существующим требованием)
- `## RENAMED Requirements` → `### Requirement: <новое название>` (со ссылкой на старое)

Под каждым `### Requirement:` — описание и `#### Scenario:` (уровень 4), как в основном spec-файле.

> **Важно:** заголовки `## ADDED Requirement:` (единственное число) — НЕ принимаются валидатором. Только множественное число: `## ADDED Requirements`, `## MODIFIED Requirements`, `## REMOVED Requirements`.

Секция `## Purpose` в дельта-файле **не нужна** для существующих capabilities — она только для новых.

### MODIFIED: полный текст требования

При `MODIFIED` воспроизводится **полный текст требования** (не только изменённая часть) — при `openspec archive` он заменяет старый текст целиком. Добавляются новые сценарии; старые сценарии, которые всё ещё актуальны, воспроизводятся тоже.

## Команды CLI

Команды выполняются из корня `openspec/` проекта.

| Команда | Назначение |
|---|---|
| `openspec validate <change-name>` | Валидировать change (дельты + proposal/design/tasks) |
| `openspec validate <spec-path>` | Валидировать основной spec |
| `openspec validate --all` | Валидировать все changes и specs |
| `openspec validate --changes` | Валидировать все changes |
| `openspec validate --specs` | Валидировать все specs |
| `openspec show <change-name> --json --deltas-only` | Показать распознанные дельты (для отладки) |
| `openspec list` | Список активных changes |
| `openspec list --specs` | Список specs |
| `openspec archive <change-name>` | Заархивировать завершённый change: применить дельты к specs и перенести папку в `changes/archive/<date>-<change-name>/` |
| `openspec templates` | Показать пути к шаблонам proposal/design/tasks/spec |
| `openspec instructions --change <change-name>` | Инструкции по артефактам change |

> **Шаблоны CLI.** Точные шаблоны артефактов можно посмотреть командой `openspec templates` — она покажет пути к файлам шаблонов в установленном пакете. Шаблоны — источник истины для формата; это правило — его краткое описание.

## Валидация

OpenSpec включает валидатор, который проверяет структуру файлов:

- Правильность уровней заголовков (`##`, `###`, `####` — ровно по одному на каждый уровень).
- Наличие `## Purpose` в каждом основном `spec.md` (в дельта-файлах не требуется для существующих capabilities). Без неё — ошибка `Spec must have a Purpose section`.
- Наличие `## Requirements` в каждом основном `spec.md` — **обязательная секция-контейнер**. Без неё — ошибка `Spec must have a Requirements section`. Требования (`### Requirement:`) вне этой секции помечаются как невидимые.
- Запрет delta-заголовков (`## ADDED/MODIFIED/REMOVED/RENAMED Requirements`) в основных spec-файлах — ошибка `delta-header`. Эти заголовки только в дельтах внутри `changes/`.
- Наличие хотя бы одного сценария под каждым требованием.
- Наличие `SHALL` или `MUST` в теле каждого требования (не в заголовке). Отсутствие — WARNING в обычном режиме, ERROR в `--strict`. Русские `ДОЛЖНА`/`ДОЛЖЕН` не распознаются.
- Корректность ключевых слов в дельтах (`## ADDED Requirements`, `## MODIFIED Requirements`, `## REMOVED Requirements` — множественное число).
- Соответствие дельт существующим требованиям (нельзя `MODIFIED` на несуществующее требование — название должно совпадать).
- Наличие обязательных секций в `proposal.md` (`## Why`, `## What Changes`, `## Capabilities`, `## Impact`).
- Наличие хотя бы одной дельты в change (если change без дельт — чистый рефакторинг/документация — нужно `skip_specs: true` в `.openspec.yaml`).

Типичные ошибки валидатора:
- `Spec must have a Purpose section` — в основном `spec.md` нет секции `## Purpose`.
- `Spec must have a Requirements section` — в основном `spec.md` нет секции `## Requirements` (требования лежат напрямую под `## Purpose`).
- `Main spec contains delta header "## ADDED Requirements"` — delta-заголовок в основном spec-файле. Перенесите его в дельту внутри `changes/` или замените на `## Requirements`.
- `Requirement header "..." appears outside the main ## Requirements section` — `### Requirement:` найден вне секции `## Requirements` и будет проигнорирован.
- `No delta sections found` — заголовки дельт не в формате `## ADDED Requirements` (мн. ч., уровень 2).
- `Change must have a Why section` — в `proposal.md` нет секции `## Why`.
- `Heading level mismatch` — перепутано количество решёток.
- `No scenarios under requirement` — требование без сценария.
- `Modified requirement not found` — дельта ссылается на несуществующее требование (название не совпадает с основным spec-файлом).
- `Requirement "..." should contain SHALL or MUST` — в теле требования нет английского `SHALL`/`MUST` (русские ключевые слова не распознаются).

## Кодировка файлов

Все файлы OpenSpec (`spec.md`, `proposal.md`, `design.md`, `tasks.md`, `config.yaml`) создаются в кодировке **UTF-8**.
