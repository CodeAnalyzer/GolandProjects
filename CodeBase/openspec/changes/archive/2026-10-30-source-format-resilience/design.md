# Design: source-format-resilience

## Context

Детектор кодировок (`internal/encoding/encoding.go`) знает только CP866/WIN1251/UTF8.
UTF-16LE с кириллицей состоит из байтов `≤ 0x7F` (кириллица U+04xx → байты `xx 04`),
поэтому существующая детекция фундаментально не способна его увидеть: ASCII fast-path
отдаёт prior (для `.sql` — CP866), NUL проходит через CP866-декодер насквозь и роняет
batch-вставку (`pq: … 0x00`). `DetectXMLEncoding` верит декларации `encoding="UTF-8"`
без `utf8.Valid` — CP1251-файл с UTF-8-декларацией падает в Go xml-декодере
(`invalid UTF-8`). Default-ветка dsxml-парсера (`internal/parser/dsxml/parser.go`,
`objectXML` с `XMLName "Object"`) жёстко ждёт корень `<Object>` — InfoPath-события
fa-ratings с корнем `<event>` роняют файл. `xmlRootName` уже вычисляется до dispatch
(skip `message`/`fasdocument` существует), `classifyPath` уже возвращает `kind=event`
для `/Event/` — точки интеграции готовы. Строка `files` коммитится до парсинга
(`indexer.go`: `saveFileCtx` → `processFileCtx`), поэтому упавший файл замалчивается
пре-фильтром mtime+size до изменения самого файла.

Полный разбор кейсов и фикстуры — `Bug-reports/BUG-utf16-files-not-decoded-20261028.md`;
заключение по коду (2026-10-30) подтвердило все четыре дефекта и механизм консервации.

## Goals / Non-Goals

**Goals:**

- Все четыре класса экзотики (UTF-16, ложная декларация, `<event>`, неизвестный
  корень) индексируются или корректно пропускаются — errors_count прогона на
  рабочем дереве → 0 (после правки fmcore-файла владельцами).
- NUL никогда не доезжает до PostgreSQL ни по одному пути вставки.
- Деградация мягкая: непонятный формат теряет сущности файла, но не роняет прогон.
- Регресс существующих кодировок (CP866/CP1251/UTF-8, детекция по содержимому)
  отсутствует; перф-бюджет — один линейный проход по буферу на файл, без лишних
  аллокаций.

**Non-Goals:**

- Механика автоматического ретрая законсервированных пре-фильтром файлов
  (упавший до фикса файл вернётся в индекс принудительным перепрохом: touch,
  DELETE строк `files` или `update --modified=false`).
- Recovery битых XML (автозакрытие тегов) — опциональная группа задач E; при
  исключении A–D самодостаточны (см. Risks).
- Правка исходников FA (upstream: pgonline, fmcore, fa-stockmarket) — сообщается
  владельцам, вне кода.
- Определение точных порогов NUL-эвристики как контракта спеки — спека
  формулирует поведение, пороги — решение ниже.

## Decisions

### D1. Воркер детектит кодировку, точки входа декодят; `Content` остаётся сырым

BOM-детект (`FF FE`/`FE FF`/`EF BB BF`) и NUL-эвристика выполняются в
`fswalk`-воркере по уже прочитанному буферу — до ASCII fast-path и до
диспетчеризации по расширению (включая `.xml`/`.md`/`.yaml`/`.t01`). Результат —
только метаданные: `FileInfo.Encoding` = `UTF16LE`/`UTF16BE` (+ `EncodingRefined`);
`FileInfo.Content` остаётся сырыми байтами, SHA-256 продолжает считаться по сырым
байтам. Декодирование выполняют точки входа формата: SQL/H/T01/PAS/JS/DFM/RPT/MD/
YAML — существующим `decodeIndexedFileContent` → `DecodeBytes` (получает UTF-16
ветки); XML — `dsxml.ParseBytes` → `DetectXMLEncoding` (получает BOM/NUL-шаг);
SMF/TPR — их внутренний перебор кодировок расширяется UTF-16-попыткой первой.

Обоснование: сегодня XML/SMF/TPR уже получают сырой `Content` и обходят
`file.Encoding` — «декод в воркере» потребовал бы флага «контент уже декодирован»
и ломал бы SMF/TPR-перебор (UTF-8-контент прочитался бы как WIN1251). Модель
«детект в воркере + декод в точке входа» не меняет ни одного существующего пути:
каждая точка самодостаточна (XML-парсер работает и при прямом `ParseFile` без
walker'а), воркер лишь заполняет метаданные. Альтернатива — учить каждую
эвристику отдельно без воркера — отвергнута: `files.encoding`/`EncodingRefined`
для SQL-файлов уже вычисляются в воркере, единый пре-детект сохраняет одну точку
правды.

### D2. NUL-эвристика без BOM: пороги по префиксу буфера, ASCII-зависимость

Проверяются первые 4096 байтов: если доля NUL ≥ 30% и ≥ 90% NUL лежит на
позициях одной чётности — файл UTF-16 (LE при нечётных смещениях, BE при чётных).
NUL в UTF-16LE дают ASCII-сегменты (латиница, пробелы, переводы строк — младший
байт 0x00); кириллица U+04xx имеет старший байт `0x04`, не NUL. Реальный
pgonline-тест `TC01` проходит порог (49% NUL), потому что SQL-код
ASCII-доминирует; чисто кириллический текст без BOM порог может не пройти —
зафиксировано как ограничение (Risks): такой файл детектируется прежними
правилами как prior, NUL-strip в store страхует от 0x00-краха. Легитимный
однобайтовый файл с редкими NUL обеих чётностей отсекается обоими условиями.
Пороги — константы пакета с тестами на границах; спека фиксирует только
поведение (классификация по преобладающей чётности).

### D3. Кодировки UTF16LE/UTF16BE — значения enum + строковые значения files.encoding

`Encoding` получает константы `UTF16LE`/`UTF16BE`; `DecodeBytes`/`ReadFile`
декодируют через `golang.org/x/text/encoding/unicode` (BOM удаляется). Для
`UTF8` `DecodeBytes` дополнительно удаляет ведущий BOM `EF BB BF` (сегодня
возвращается как есть — U+FEFF попадает в контент). В `files.encoding` пишутся
строки `UTF16LE`/`UTF16BE` — колонка текстовая, миграция схемы не нужна.
consumers, switch-ащиеся по кодировке, получают default-ветку UTF-8-путь
(декод идёт до парсера в точке входа формата).

### D4. Валидация XML-декларации — utf8.Valid + эвристика по содержимому

При `encoding="utf-8"`: `utf8.Valid(data)` → верим; иначе — не верим декларации
и определяем кодировку маркерными диапазонами (`DetectFromBytesWithPrior`-эвристика
с prior WIN1251 для XML). GSOD-кейс (CP1251-байты) → WIN1251 → корректный декод.
UTF-16 без BOM ловится NUL-шагом того же детектора (D1). Для `.xml` воркер
дополнительно вызывает `DetectXMLEncoding` и записывает фактическую кодировку в
`files.encoding` (иначе GSOD-файл остался бы с фиктивным `UTF8`, а
`EncodingRefined` не отразил бы перекодировку). Альтернатива «падать с понятной
ошибкой» отвергнута: цель — проиндексировать файл.

### D5. eventXML — отдельная структура в default-ветке dsxml

`eventXML` (корень `event`, kebab-теги) добавляется в switch после `xmlRootName`:
`case rootName == "event"` → маппинг по таблице из баг-репорта. `required`
парсится из смешанной записи (`true`/`false` у table, `1`/`0` у field) — свой
unmarshaler для булева-или-числа. `architect-approval = "OK"` → `ArchApproval = 1`
(числовой флаг objectXML). `module-depend` игнорируется: в `model.APIContract`,
DDL `api_contracts` и `BatchInsertAPIContracts` колонки нет, а её добавление —
DDL + bump `CurrentSchemaVersion` ради поля без потребителей в lookup'ах.
Возвращаем к нему Open Question: добавить колонку при появлении потребителя.
`return-resultset`/`retvals`/`contexts` — без сущностей (в фикстурах пусты); при
появлении непустых `<param>` структура уточняется (Open Question).
kind/owner_module — из пути существующими `classifyPath`/`ownerModuleFromPath`.

### D6. Graceful-skip — консистентность корня и path-ветки + канал skip

Dispatch в `ParseContent` остаётся по пути (`/BObject/.../Table/` →
standaloneTableXML, `/Param/` → standaloneParamXML, иначе → default/objectXML).
Skip-проверка после вычисления `rootName` сверяет корень с ожиданием выбранной
path-ветки: default-ветка принимает `object`/`event` (+ существующие skip'ы
`message`/`fasdocument`), `/Table/`-ветка — `table`, `/Param/`-ветка — `param`;
несоответствие (`<table>` вне `/Table/`, `<object>` в `/Table/`, корень вне
известного набора) → пустой результат без ошибки. Канал: `ParseResult`
получает признак `Skipped` (+ причина), индексер по нему инкрементирует
`ScanStats.XMLSkipped` — без канала индексер не отличит skip от пустого
`<Object>`. Синтаксическая ошибка XML по-прежнему ошибка файла: `xmlRootName`
падает только на битой разметке, поэтому различие надёжно без второго прохода.
Альтернатива «полный переход на dispatch по rootName» отвергнута: меняет
поведение существующих путей (например, `<Table>` вне `/Table/` стал бы
standalone-таблицей вместо ошибки) — расширение скоупа без заявленной
потребности.

### D7. NUL-strip — точка в store, предикат вместо безусловной замены

Санитизация выполняется в batch-insert слое store для текстовых значений:
`strings.IndexByte(s, 0) < 0` → без копирования; иначе `strings.ReplaceAll`.
Safety-net независим от декодера: даже нераспознанная экзотика не роняет файл
ошибкой 0x00. Альтернатива «чинить только в query_fragments» отвергнута: NUL
может доехать любым текстовым полем (описания процедур, symbols).

### D8. Recovery (E) — автозакрытие при «element closed by», включено в дельту

Решение по итогам ревью: группа выполняется. При синтаксической ошибке
`element <A> closed by </B>` выполняется собственный линейный скан контента
(`recoverUnclosedElements`): стек открытых имён; при закрывающем теге, не
совпадающем с вершиной, но присутствующем глубже, перед ним вставляются
закрывающие теги всех элементов поверх совпадающего (лимит 32 вставки на
файл, при превышении и при orphan-close контент не меняется). Исправленный
контент переразбирается; `ParseResult` несёт `Recovered` + `RecoveryNote`,
индексер пишет предупреждение в лог (не в `errors_count`). Точка входа —
ошибка `xmlRootName` в `ParseContent`: если после фикса корень не
читается, наружу уходит исходная ошибка. Комментарии/CDATA/PI/декларации
пропускаются сканером; атрибуты со `>` внутри кавычек не поддерживаются
(в DSArchitect-XML не встречаются, worst case — отсутствие вставок и
исходная ошибка). Дельта-требование добавлено в `specs/indexing/dsxml-parsing`
(ADDED «Recovery незакрытых элементов XML»); сценарий «Битый XML остаётся
ошибкой» переориентирован на нечинимые случаи (обрезанный файл).

### D9. Charset-ветки xml-декодера и SMF/TPR-перебор — доведение UTF-16 до всех точек

(1) `xmlCharsetReader` (dsxml) получает pass-through для `utf-16`/`utf-16le`/
`utf-16be`/`ucs-2`: контент уже предекодирован в UTF-8 на шаге
`DetectXMLEncoding`, но декларация в тексте файла остаётся `encoding="UTF-16"` —
Go-декодер вызывает CharsetReader и сегодня падает `unsupported xml charset`.
Заодно ветка `cp866`: `DetectXMLEncoding` уже возвращает CP866 по декларации, но
CharsetReader её не умеет — внутренняя несогласованность существующего кода.
(2) SMF/TPR-парсеры перебирают кодировки сами (`WIN1251/CP866/UTF8`) — в начало
перебора добавляется UTF-16 BOM/NUL-детект + декод; иначе UTF-16 `.smf`/`.tpr`
останутся сломаны (воркер их `Content` не декодирует, см. D1).
(3) `DetectMarkdownEncoding` получает тот же BOM/NUL-шаг (md-файлы в UTF-16,
включая повторное чтение с диска в `indexer_postprocess_spec_deps`).

## Risks / Trade-offs

- [Чисто кириллический UTF-16 без BOM не проходит NUL-порог (NUL дают только
  ASCII-сегменты, кириллица U+04xx → старший байт 0x04)] → ограничение эвристики
  зафиксировано: файл детектируется прежними правилами (prior), NUL-strip в
  store страхует от 0x00-краха; BOM-детект покрывает генераторы MS, которые
  почти всегда пишут BOM.
- [Ложное срабатывание NUL-эвристики на бинарном/смешанном файле] → двойное
  условие (доля ≥ 30% + чётность ≥ 90%) + тест на CP866-файле с редкими NUL;
  worst case — файл декодируется UTF-16 в нечитаемый текст и индексируется с
  мусорными сущностями, как сегодня, но без 0x00-краха.
- [A2: файл с единичными битыми UTF-8-байтами уходит в WIN1251 и становится
  mojibake целиком] → принимаемо: файл индексируется (сейчас — выпадает);
  масштаб в FA неизвестен, если после прогона EncodingRefined по XML аномально
  высок — порог уточним.
- [D3: новые значения files.encoding ломают consumers, switch-ащиеся по строке
  кодировки] → аудит call-sites `Encoding(file.Encoding)` при реализации;
  после декода в точке входа парсеры получают UTF-8 строку, ветка default-safe.
- [D6: skip может замаскировать будущую потерю сущностей при дрейфе формата] →
  счётчик XMLSkipped печатается во всех сводках (init/update, stats JSON) —
  аномальный рост виден.
- [D5: `<param>`-структура `<event>` не подтверждена реальным файлом;
  `module-depend` отброшен из-за отсутствия колонки] → зафиксировано как Open
  Question; пустые в фикстурах секции не парсятся.
- [Перф: NUL-strip на каждом текстовом значении] → предикат без аллокации при
  отсутствии NUL; замер на корпусе encoding-тестов.
- [Консервация: файлы, упавшие до фикса, не вернутся сами] → осознанный
  Non-Goal; верификация и возврат — принудительный перепрох (touch / DELETE
  строк `files` / `--modified=false`).

## Migration Plan

1. Реализация A/A2/B/C/D (группы 1–5 задач) → юнит-тесты на фикстурах →
   integration (вставка без NUL, регресс кодировок).
2. Локальная верификация: touch трёх классов файлов на рабочем дереве →
   errors_count не растёт, сущности на месте (`query api-contract --name
   OnAfterScr_MassDel`, desc-search по русским описаниям GSOD/событий).
3. Полный прогон update на рабочем дереве: errors_count = 13 → 3 (fmcore — до
   правки владельцами), EncodingRefined включает новые UTF-16/XML-детекты.
4. Откат: изменения локальны (детект + парсер + store-sanitize), отдельного
   состояния в БД нет; откат = предыдущий бинарник.

## Open Questions

- Структура непустых `<input-params>`/`<output-params>` в `<event>`-формате —
  уточнить при появлении файла с непустыми params (маппинг по аналогии с
  `<field>`); на решение A–D не влияет.
- `module-depend` событий: колонка `api_contracts.module_depend` + DDL-bump —
  только при появлении потребителя в lookup'ах/отчётах; сейчас игнорируется.
- Точный порог доли NUL (30%) и окно (4KB) — калибруется по корпусу
  encoding-тестов и рабочему дереву; поведение спеки не меняется.
