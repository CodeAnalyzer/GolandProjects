## 1. Вердикт

(`tRequisitParticipantSB`) реально закрывается имеющимися данными индекса, схема изменений

## 3. Ревью решений D1 / D2 / D4

### D1 — lower-индекс на `sql_index_definitions` + bump схемы `v7→v8`

**Вердикт: принять; добавить проверяемость (R3, R5).**

- Без `LOWER(table_name)`-индекса ветвь свидетельств по индексам не сможет использовать
  существующий `idx_sql_index_definitions_table_name` (предикат `LOWER(table_name)=ANY`).
  Новый индекс оправдан; бонусом он ускорит уже существующий
  `batchLoadIndexCandidates` (`review_lookup.go:609`, тоже `LOWER(i.table_name)`).
- Bump `CurrentSchemaVersion` обязателен (`db_schema.go:13`): fast-path `InitSchemaCtx`
  (`db_schema.go:1260-1265`) иначе молча пропустит новый DDL на существующих БД —
  это ровно readonly-schema-policy из `AGENTS.md`.
- Тесты схемы завязаны на `store.CurrentSchemaVersion` динамически
  (`schema_integration_test.go:28`), поэтому сам bump тесты не ломает.
- Замечания:
  - R3: сниппет SQL в `design.md` (ветвь `sql_index_definitions`) не содержит фильтра
    `definition_kind IN ('create_index','macro_create_index')`, а `tasks.md 1.2` — содержит.
    Привести к единому виду (семантика одинакова, но расхождение сбивает реализатора).
  - R5: «индекс используется планировщиком» — это предположение, а не факт. В рамках 1.1
    проверить `EXPLAIN` ветви по `sql_index_definitions`, а не только `\d`. И добавить
    автотест миграции (см. R5 ниже), а не только ручной `\d`.

### D2 — свидетельства только из индекса, не из проверяемого файла (анти-самоподтверждение)

**Вердикт: intent принять, формулировку и тест — исправить (R1).**

Проблема: проверяемый файл **сам проиндексирован** (review берёт его через `getIndexedFile`,
иначе `ErrFileNotIndexed`). Его `M_ADD_FIELD('tTypo', …)`/`ALTER TABLE … ADD` попадут в
`sql_column_definitions`, а `CREATE INDEX`/`M_CRT_INDEX` — в `sql_index_definitions`. Поэтому
при актуальном индексе «свидетельство только из индекса» **не** исключает самоподтверждение:
DB-запрос вернёт и строки проверяемого файла. Свойство «same-file не считается» выполняется
только когда индекс устарел (файл изменён после `update`).

Следствия:
- Тезис в `design.md` D2 («same-file `M_ADD_FIELD` … не должен подтверждать сам себя»)
  в общем случае неверен. Верное утверждение: «свидетельство берётся из **снимка индекса**,
  а не из текущего текста; при устаревшем индексе same-file свидетельство не видно».
- Предложенный тест в `tasks.md 2.2` («same-file `M_ADD_FIELD` **без записи индекса** →
  finding») проверяет только stale-index сценарий и создаёт ложную уверенность.

Бинарное закрытие:
- Принять как есть **с исправлением обоснования**: реальная защита — снимок индекса + падение
  патча с опечаткой на установке (second-order), а не исключение same-file. Добавить явный
  тест, документирующий фактическое поведение: same-file свидетельство, **присутствующее в
  индексе**, finding подавляет.
- Полноценное same-file-исключение (сравнение `file_id` источника с `files.id` проверяемого
  файла) **не рекомендуется**: метод возвращает только имена, это усложняет сигнатуру/prewarm
  и даёт FN для DML-файлов, которые сами добавляют колонку/индекс используемой таблицы
  (редко, но легитимно). Оставить как осознанный остаточный риск, зафиксировав его в design.

### D4 — гейт `indexExistsInDB` по создающему источнику

**Вердикт: принять; уточнить приоритет кэш/`db==nil` и покрыть интеграционно (R2, R6, R8).**

- Семантика гейта корректна и согласуется со спекой: таблица без создателя в разрешённой
  области → индексный набор неполон → проверка неверифицируема → молчим и в ветви хинтов,
  и в `M_DELETE_PTABLE*`. «Одна причина — один finding»: дефект существования остаётся за
  `tableExistsInMetadata` (fail-closed при ошибке БД — `cachedLookupTableCreator` возвращает
  `false`), а индексный гейт при ошибке БД подавляет (fail-open). Асимметрия осознанная.
- `prewarm` создателей при `indexExistsInDB` нужен (`runner.go:214` → `|| indexExistsInDB`):
  иначе гейт в проде уйдёт в lazy-путь по каждому имени.
- **R2 (противоречие в тест-плане):** `tasks.md 3.1` одновременно требует «при `r.db == nil`
  гейт инертен (true)» и unit-тест «кэш создателей `false` + хинт → **нет** finding».
  Если хелпер возвращает `true` при `db==nil` **до** чтения кэша, тест «кэш false → нет
  finding» на `&Runner{}` не пройдёт; если кэш читается **до** `db==nil`, то существующие
  тесты (`review_rule_coverage_test.go:234`, `review_block_comment_test.go:190`) с пустым
  кэшем и `db==nil` обязаны остаться «инертными» (finding сохраняется). Нужна явная
  спецификация приоритета:
  1) есть запись в непустом `tableCreatorCache` (включая `false`) → вернуть её;
  2) иначе `db == nil` → `true` (инертно);
  3) иначе `cachedLookupTableCreator`.
  Это единственная непротиворечивая комбинация; её и зафиксировать в `design.md`/`tasks.md`.
- **R6 (проверяемость):** при `db==nil`-seam все unit-тесты `indexExistsInDB` идут мимо гейта,
  поэтому подавление гейтом нельзя доказать unit-тестами «в вакууме». Нужен интеграционный
  тест через `RunSQLFileCtx` (реальный DB): (а) нет создателя + хинт → нет finding;
  (б) создатель есть + отсутствующий индекс → finding; (в) `M_DELETE_PTABLE_INDEX` на
  таблице без создателя → нет finding; (г) DSArchitect-таблица → гейт пройден.
- **R8 (DSArchitect/scope):** `BatchLookupTableCreators` скоупит API-таблицы через
  `api_contracts.file_id`/`api_business_object_tables.file_id` + `areaFilter`. Сценарий
  «Индекс таблицы, объявленной в DSArchitect, проверяется» обязан быть покрыт тестом,
  доказывающим, что в разрешённой области гейт проходит (иначе API-таблицы без
  product/branch в `files` будут молча подавлены — регресс `indexExistsInDB` для них).
- **R7 (осознаваемый fail-open):** гейт намеренно игнорирует свидетельства, поэтому у старой
  базовой таблицы, существующей по патчу, реально отсутствующий/опечатанный индекс **не**
  будет найден. Это заявленная цена снижения FP; зафиксировать как известное ограничение
  (в `design.md` ## Risks) явно, а не только через спеку.

## 4. Прочие замечания

### R4 — Контроль замера D6 устарел (методология)
`design.md` D6 и `tasks.md 5.1` сравнивают с «100 имён / 239 файлов (build 1684)». Текущая
сборка — `build 1718` (`cmd/root.go:29`), и между 1684 и 1718 поведение `tableExistsInMetadata`
менялось (в частности, атрибуция view → `viewUsageInServerCode`, сейчас это часть main-spec).
Сравнение с устаревшим контролем может «подтвердить» эффект, которого нет, или скрыть регресс.
Требование: снять **свежий baseline ДО** правки на том же снимке индекса/той же сборке, затем
**после**, и сравнивать между собой (плюс показать контроль 100/239 как историческую справку,
не как критерий приёмки). Разбор ушедших имён и эскалацию «похоже на опечатку» оставить.

### R5 — Нет автотеста миграции `v7→v8`
`tasks.md 1.1` ограничивается ручным `\d`. Добавить интеграционный тест по образцу
`TestInitSchema_MemoryTablesV7` (`schema_integration_test.go:611`): `testutil.ResetSchemaVersion`
→ `InitSchemaCtx` → `pg_indexes` содержит `idx_sql_index_definitions_table_name_lower`, а
`indexdef` содержит `LOWER(table_name)`. Опционально добавить индекс в `requiredIndexes`
(`schema_integration_test.go:75`).

### R9 — Согласованность `review-scope`
D5 оставляет `review/review-scope` без изменений. Формально ок (областная привязка свидетельств
описана в самой дельте `deploy-stoppers`), но текст `review-scope` говорит о «созданной»
сущности, а новый сценарий — про «изменённую». Не блокер; при желании — одно уточняющее слово
в `review-scope`, иначе оставить как есть (расхождения поведения нет).

### R10 — Сценарий «Индекс есть только в другой ветке» и гейт
Сценарий `indexExistsInDB` «Индекс `IX_Contract_Name` только в `develop` → finding» неявно
предполагает, что **таблица** имеет создателя в разрешённой области. С новым гейтом при
отсутствии in-scope создателя finding не будет. Уточнить в фикстуре/сценарии, что создатель
таблицы в целевой ветке есть (иначе сценарий станет ложным).
