# Design: Улучшение качества LSA-слоя семантического поиска спек

## Context

См. `proposal.md` (Why) — мотивация и воспроизведённый эксперимент («Заметка по клиенту» → кросс-продуктовый шум 0.43–0.51, релевантная capability `legal` отсутствует в semantic-топе).

Текущее состояние (ключевые точки кода):

- `internal/indexer/indexer_postprocess_spec_lsa.go` — документ = `title + purpose + notes` (строки 59, 129); решение о переобучении: `changedCount := stats.SpecCapabilities` за прогон, ранний выход при `changedCount < nDocs && changedCount < LSARetrainThreshold`.
- `internal/store/db_lsa.go` — `LoadAllSpecCapabilitiesForLSA` грузит только `id, title, purpose, notes`.
- `internal/specsvc/specsvc.go:1172-1207` — semantic: фильтр `Rank <= 0.01` → сортировка → limit.
- `internal/specfts/tokenizer.go` — стоп-слова без доменных, стеммер однопроходный, «счёт»/«счет» дают разные стемы.
- `internal/specfts/vocab_tfidf.go` — `minDF=3`, `maxDF=0.3`, TF = 1+log(count) + L2-нормализация строк; комментарий `Document.Text` уже декларировал включение body_text требований (дизайн опережал реализацию).
- `internal/config/config.go` — `LSARetrainThreshold <= 0 → 50`: задать «0 = всегда» конфигом невозможно (расхождение со старой спекой уже существовало).

Исходные материалы: план `Modifications/lsa-quality-improvement-7e3a2c.md` и ревью `Modifications/lsa-quality-improvement-7e3a2c-review.md` (9 находок; главные: stale retrain, minDF режет редкие термины, порядок cutoff/limit, недетерминированная агрегация, отсутствие benchmark).

## Goals / Non-Goals

**Goals:**

- Релевантная capability попадает в semantic-топ для контрольных запросов; шум отсекается порогами.
- Модель гарантированно консистентна корпусу и параметрам (fingerprint), без ручных инвалидаций.
- Регрессионная защита: golden-тест на синтетическом корпусе + контрольные запросы.

**Non-Goals:**

- requirement-уровневые эмбеддинги (requirement-слой остаётся только лексическим).
- Смена стеммера/алгоритма токенизации, кроме нормализации ё→е.
- Доменные стоп-слова и понижение maxDF — вне скоупа, отдельный follow-up по данным benchmark (находка ревью #7/#8: без измерений это замена одного шума другим).
- Включение `related_code` в LSA-документ — follow-up.
- Embeddings-модели отличные от TF-IDF+LSA.

## Decisions

Все решения ниже зафиксированы по итогам explore-сессии; «lean» означает выбор, подтверждённый пользователем.

### D1. Состав LSA-документа (спека: ADDED «Состав LSA-документа»)

Документ = `title×2 + purpose + notes + [requirement_name + body_text]* + [scenario_name + given + when + then]*`.

- title дублируется дважды (взвешивание против размывания коротких capability длинными сценариями; log-TF демпфирует, но якорные термины title заслуживают усиления).
- Веса — деталь моделирования, в спеке фиксируется только состав.
- Альтернатива «без весов» отклонена: ревью #4 обосновал риск длинных документов; дублирование — самый дешёвый контр-приём.

### D2. Политика переобучения: гибрид fingerprint + кумулятивный порог (спека: MODIFIED «Обучение и пересчёт LSA-модели»)

```
postProcessSpecLSA
   ▼
быстрый путь: за прогон 0 spec-изменений И параметры == сохранённым → выход
   ▼
загрузить корпус (детерминированно) → H = SHA-256(тексты ‖ параметры ‖ версии)
   ▼
модели нет → ОБУЧИТЬ → state = (H, pending=0)
   ▼
H == state.H → выход (идемпотентно, pending не растёт)
   ▼
state.pending + Δ_прогона ≥ threshold?
   ├── нет  → state.pending += Δ → выход
   └── да   → ОБУЧИТЬ → state = (H, pending=0)
```

- **Fingerprint** (решение «в хеш входят тексты + параметры»):
  ```
  SHA-256 потоково по (\x00-разделители против коллизий конкатенаций):
    composition_version   — const в коде; bump при изменении состава (D1 поднимет сам → первый прогон после деплоя переобучит)
    tokenizer_version     — const в коде; bump при изменении токенизации/стемминга (D5 поднимет)
    min_df, max_df, k     — из конфига
    для каждой capability (ORDER BY id):
      id ‖ title ‖ purpose ‖ notes
      ‖ agg(requirement_name, body_text  ORDER BY req_order, id)
      ‖ agg(scenario_name, given, when, then  ORDER BY req_order, scn_order, id)
  ```
  Хеш считается в Go по загруженным строкам — тестируемо без БД.
- **Кумулятивный порог**: `pending` накапливается между прогонами, Δ_прогона = изменённые сущности (capability + requirement + scenario, включая удалённые). Семантика порога меняется с «за один прогон» на «с прошлого обучения» — чинит дрейф (50 правок за 10 прогонов никогда не переобучали модель).
- **Дефолт threshold = 100** (уточнён замером, см. benchmark.md: SVD 97 c на корпусе 2322 capability — выше порога 30 с). Изначально планировался 0; замер показал стоимость и дефолт поднят до 100 ≈ 2–3 типичные правки spec.md. Явный `0` в конфиге легален и отключает амортизацию. Затирающий дефолт `<=0 → 50` убран: поле — `*int` (nil = 100, 0 = «при любом изменении»).
- **Хранение state**: sidecar `spec_lsa_state.json` рядом с файлом модели: `{fingerprint, pending, params, num_docs, trained_at}`. Атомарная запись (tmp+rename), бинарник модели не трогаем. «Модель удалена, state остался» → обучить, state=(H,0).
- **Ошибка обучения**: state не меняется вовсе → каждый следующий прогон ретраит (самоисцеление важнее; загрузка корпуса дешёвая относительно SVD).
- Альтернативы: (a) чистый fingerprint — отклонена как невозможность амортизации на больших корпусах; (b) расширенный счётчик `SpecCapabilities + SpecRequirements + SpecScenarios` — отклонена: не чинит дрейф между прогонами, удаления и parameter-staleness.

### D3. Загрузка корпуса: детерминированная агрегация

Новый `LoadAllSpecCapabilitiesWithReqsForLSA` в `db_lsa.go`: два коррелированных подзапроса `string_agg(... ORDER BY ...)` + `concat_ws(' ', ...)` для NULL-безопасности. Индексы `capability_id`, `requirement_id` уже существуют (`db_schema.go:855-857`). ORDER BY в агрегатах — жёсткое требование: bag-of-words безразличен к порядку, но fingerprint — нет (без ORDER BY хеш флапает → вечные ложные переобучения). В модель `SpecCapability` добавляется поле `LSAText string` (не `RelatedCode` — у него своя семантика).

### D4. Фильтрация semantic-секции (спека: MODIFIED «Раздельные секции результата»)

Чистая функция без БД:

```go
func filterSemanticHits(hits []SpecSearchHit, minCosine, relativeCutoff float64, limit int) []SpecSearchHit
// порядок: absolute → sort DESC → relative (cutoff × maxRank) → limit
```

- Конфиг: `lsa_min_cosine` (default 0.15, диапазон [0,1]), `lsa_relative_cutoff` (default 0.5, [0,1]); некорректные значения — ошибка загрузки конфига.
- Диагностика: при пустой секции — метаполе `{filtered_out: N, threshold: ..., reason: "threshold"|"oov"}`; при OOV-терминах запроса — hint со списком OOV-стемов и отсылкой к exact-слою.
- Абсолютное значение 0.15 — стартовое, калибруется по контрольным запросам (не фиксируется в спеке).

### D5. Нормализация ё→е в токенизаторе

`strings.ReplaceAll(токен, "ё", "е")` перед стеммингом: «счёт»/«счет» сливаются в один стем, двойные стоп-листы ё-форм не нужны. `tokenizer_version` в fingerprint поднимается — модель сама переобучится. Риск коллизий стемов прикрывается тестами токенизатора.

### D6. minDF — по данным (гейт этапа)

Замер на боевом корпусе (benchmark.md): df(«заметк») = 4 — проходит minDF=3; размер словаря 11200 термов. **Решение: minDF остаётся 3 без изменений.** Прежняя невидимость «заметки» была вызвана составом документа (термин только в текстах требований), а не minDF. Высокочастотные «клиент» (44%), «счет» (51%), «параметр» (52%) отфильтровываются maxDF 0.3 — OOV-hint (D4) подсвечивает их в ответе с отсылкой к exact-слою.

### D7. Benchmark: golden-тест + ручной чек-лист

- Синтетический мини-корпус (~120 capability, чтобы пройти `LSAMinCorpus=100`) с заложенными зависимостями: ко-встречаемость «арест»↔«блокировка», редкий термин «заметка» (df≥minDF в синтетике), «клиент» как высокочастотный шум. Golden-файлы: словарь, косинусы контрольных запросов, состав документов.
- Ручной чек-лист на боевом корпусе FA: «Заметка по клиенту», «блокировка счёта», «лимит карточки», «обработка платежного документа», «параметры операции», техимена (`API_*`); метрики: позиция ожидаемой capability в топ-k, число нерелевантных в топ-5, minCosine релеванта. Для каждого запроса — с фильтром продукта и без.
- Туда же замер стоимости полного переобучения (гейтит целесообразность threshold > 0; дефолт 0 уже принят).

### D8. SVD: фикс обрезки VT и k=512 (по данным k-тюнинга)

**Найден давний баг** (не из этого change, но блокировал его цель): `SVD()` клампил колонки Vᵀ до `min(nDocs, nTerms)` — при nTerms > nDocs (боевой корпус: 11200 термов / 2322 доков) термины с алфавитным индексом ≥ nDocs выпадали из проекции запроса. Все контрольные термины (заметк=4539, арест=2856, лимит=5601) были вне матрицы → косинусы 0.0. Прежний «шум 0.43–0.50» и пустая semantic-секция — артефакты этого бага. Фикс: VT строится на все nTerms; добавлена `AlgorithmVersion = 2` в fingerprint и `algorithm` в state — смена алгоритма переобучает безусловно (амортизация не действует). Смена **параметров** (min_df/max_df/k) также переобучает безусловно: это действие оператора, амортизация предназначена только для дрейфа корпуса.

**k=512**: k-тюнинг (`Tests/lsaktune`, один полный SVD + обрезки) показал монотонное улучшение редких терминов с ростом k при неизменной стоимости SVD:

| Запрос → ожидание | k=64 | k=128 | k=256 | k=384 | k=512 |
|---|---|---|---|---|---|
| «Заметка по клиенту» → legal | #64 | #18 | #13 | #7 | **#5** |
| «блокировка счёта» → card-block | #4 | #5 | #3 | **#1** | **#1** |
| «лимит карточки» → limit/* | #3 | #1 | #1 | #1 | #1 |
| «параметры операции» → operation/* | #1 | #1 | #1 | #1 | #1 |

Выбран k=512 (default): legal входит в топ-5, card-block #1; файл модели растёт 11 → 46 МБ, эмбеддинги ×4 — приемлемо. k остаётся настраиваемым; спека фиксирует «k настраивается, default 512».

## Risks / Trade-offs

- [Fingerprint требует загрузки корпуса на каждом прогоне] → загрузка — один SQL с агрегатами, дешёвая относительно SVD; быстрый путь (0 изменений + параметры совпадают) пропускает загрузку вовсе.
- [string_agg по двум коррелированным подзапросам дороже плоского SELECT] → индексы уже есть; корпус спек — тысячи, не миллионы строк; при необходимости — LATERAL JOIN.
- [title×2 может сместить ранжирование против ожиданий] → golden-тест фиксирует поведение; вес убирается одной правкой состава.
- [Снижение minDF раздувает словарь и замедляет SVD] → замер размера словаря на этапе D6 — гейт; взрывной рост → остаёмся на 2 и закрываем кейс OOV-hint'ом.
- [ё→е меняет все стемы → разовое полное переобучение и сдвиг косинусов] → ожидаемо и покрыто fingerprint (tokenizer_version); golden-тесты пишутся уже под новую нормализацию.
- [threshold=0 по умолчанию = переобучение на каждый чих в спеках] → осознанный выбор для локального инструмента; при замере D7 > ~30 сек на боевом корпусе — поднять дефолт, не меняя контракт.
- [Пустая semantic-секция после порогов может удивить пользователей] → метаполе с причиной и числом отсеянных (D4) делает поведение объяснимым.

## Migration Plan

1. Деплой бинарника → первый прогон: fingerprint отсутствует/не совпадает (composition_version и tokenizer_version подняты) → полное переобучение, state создан.
2. Старый файл модели без state — валиден: «модели нет?» проверяется по state, отсутствие state = переобучение.
3. Откат: предыдущий бинарник игнорирует state-файл и работает по старой политике; state-файл можно удалить, следующий прогон старой версии переобучит как при init.
4. Ручных миграций БД нет: `spec_vocab` / `spec_embeddings` пересоздаются при обучении.

- Значение minDF (D6) — закрывается замером на этапе 3 задач.
