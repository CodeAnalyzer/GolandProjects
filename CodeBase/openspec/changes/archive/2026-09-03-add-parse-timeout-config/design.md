## Context

См. proposal.md — Why. Текущее состояние: `registerSDKCoreTools` в `server.go:71-80` применяет `query_timeout_sec` (30с) как глобальный дефолт ко всем MCP-инструментам, с единственным исключением для `codebase_review_sql` (120с). Операции парсинга TRC/RTI на больших файлах (1+ ГБ .trc) превышают 30с и падают с отменой контекста.

## Goals / Non-Goals

**Goals:**
- Отдельный таймаут для тяжёлых операций парсинга (`codebase_trc_parse`, `codebase_rti_parse`) в отличие от лёгких query-операций
- Настраиваемость по каждому анализатору (`[trc]`, `[rti]`), консистентно с существующей структурой конфига
- Обратная совместимость — старый `codebase.toml` без новых ключей работает с разумными дефолтами

**Non-Goals:**
- Индивидуальная настройка таймаута для каждого MCP-инструмента (избыточно, только parse требует особого обращения)
- Изменения CLI-пути (CLI использует `context.Background()`, пользователь может Ctrl+C)
- Изменения non-parse TRC/RTI инструментов (это DB-запросы, 30с достаточно)

## Decisions

### Решение 1: `parse_timeout_sec` в секциях `[rti]` и `[trc]` (не в `[mcp]`)

**Обоснование:** Таймаут парсинга — свойство анализатора, а не MCP-транспорта. У каждого анализатора уже есть своя секция конфига (`[rti]`, `[trc]`) со специфичными параметрами. Размещение `parse_timeout_sec` там консистентно с существующей структурой и позволяет независимую настройку.

**Рассмотренная альтернатива:** Добавить `parse_timeout_sec` в секцию `[mcp]` рядом с `query_timeout_sec` и `review_timeout_sec`. Отклонено, т.к. смешивает транспортный и анализаторный уровни и не масштабируется при появлении новых анализатор-специфичных таймаутов.

### Решение 2: `switch` по имени инструмента в `registerSDKCoreTools`

**Обоснование:** Текущий паттерн `if tool.Definition.Name == "codebase_review_sql"` не масштабируется. `switch` чище и читабельнее при добавлении новых особых случаев.

```go
timeout := time.Duration(cfg.MCP.QueryTimeoutSec) * time.Second
switch tool.Definition.Name {
case "codebase_review_sql":
    timeout = time.Duration(cfg.MCP.ReviewTimeoutSec) * time.Second
case "codebase_trc_parse":
    timeout = time.Duration(cfg.TRC.ParseTimeoutSec) * time.Second
case "codebase_rti_parse":
    timeout = time.Duration(cfg.RTI.ParseTimeoutSec) * time.Second
}
if timeout > 0 {
    ctx, cancel = context.WithTimeout(ctx, timeout)
    defer cancel()
}
```

**Рассмотренная альтернатива:** Registry-driven подход, где каждый инструмент декларирует свою категорию таймаута. Отклонено как over-engineering для 3 особых случаев — switch простой, явный и легко аудируется.

### Решение 3: Дефолт 300с (5 минут)

**Обоснование:** Файл .trc размером 1.4 ГБ парсится ~60-90с на типичном железе. 300с даёт запас 3-5x. Для RTI даже большие файлы (44 МБ) парсятся за секунды, но RTI-файлы бывают больше. 300с достаточно щедро, чтобы избежать ложных таймаутов, но при этом обеспечивает страховку от бесконечных зависаний.

**Рассмотренная альтернатива:** Дефолт 600с (10 минут). Отклонено как слишком щедро — если парсинг занимает больше 5 минут, вероятно что-то не так (I/O проблема, патологический файл).

## Risks / Trade-offs

- **[Риск] Дефолт 300с может быть недостаточен для очень больших файлов (>5 ГБ)** → Пользователь может установить `parse_timeout_sec = 0` для полного отключения таймаута или увеличить значение. Документировано в комментарии к параметру.
- **[Риск] Switch вырастёт если больше инструментов потребуют кастомных таймаутов** → Приемлемо пока; при превышении ~5 случаев можно рефакторить в map-based lookup. Сейчас не актуально.
- **[Компромисс] Два ключа конфига вместо одного** → Чуть сложнее конфиг, но разделение соответствует доменной структуре и позволяет независимую настройку по анализатору.
