# Design: branch-aware-lookup

## Context

Срез `branch-aware-indexing` дал ось ветки (`ds_products_branch`,
`files.ds_product_branch_id`), но все выборки сущностей остались
одномерными. Проблемные точки (из исходного дока, решение 5–6):

| Звено | Файл | Проблема |
|---|---|---|
| Резолв имён в графе | `internal/store/db_lookup_sql.go:36-47` | `DISTINCT ON` c `not_generated → product_match → id` — нет оси ветки |
| Пост-обработка вызовов | `internal/indexer/indexer_postprocess_sql_calls.go:19` | `FindLatestSQLProcedureIDsByNames(..., 0)` — без продукта и ветки |
| Пост-обработка фрагментов | `indexer_postprocess_fragments.go:49,55,149,221,313` | то же, `productID=0` |
| Детали процедуры | `internal/query/query_sql.go:480-489, 513-523` | `QueryRow` по имени **без ORDER BY** — недетерминизм уже сегодня |

Аналог приоритизации в проекте — `is_generated` (ORDER BY-приоритет в
`DISTINCT ON`), его и расширяем.

## Goals / Non-Goals

**Goals:**

- Детерминированный выбор копии сущности при любом числе веток.
- Приоритет: entity-запросы — `not_generated` → default-ветка → id;
  резолв связей — ярус ветки источника → default-ветка продукта → другие
  продукты (явный scope запроса — срез `dsinfo-integration`).
- `branch_used` (нормализованный `branch_key`) в результатах
  entity/API-запросов.
- Граф: рёбра в пределах scope источника; batch-механика сохраняется.
- Списки и поиск без дублей веток: одна строка на сущность/capability
  продукта; дедуп скрытых копий виден через `branch_used`.

**Non-Goals:**

- Флаг `--dsinfo`, профиль развёртывания, `branch_requested`/fallback-
  предупреждения — срез `dsinfo-integration` (осознанно разведены, чтобы
  не модифицировать одни требования дважды).
- Жёсткая фильтрация по ветке (`--strict`-режим) — вне объёма.
- Пересчёт рёбер при смене профиля: рёбра привязаны к веткам при
  индексации, профиль влияет только на выбор при запросе.

## Decisions

### D1. `LookupScope` вместо позиционного productID

```go
type LookupScope struct {
    ProductID int64 // 0 = любой
    BranchID  int64 // 0 = default-ветка/глобально
}
```

Заменяет `productID int64` во всех `FindLatest*` (SQL procedures/tables/
columns, PAS classes, DFM forms, API contracts/events — ~10 функций) и
пробрасывается из мест вызова. Альтернатива «добавить branchID рядом с
productID» отвергнута: два позиционных int64 рядом — готовые ошибки
перепутывания; структура самодокументируется и расширяется (в срезе C
добавится DsinfoID на уровне сервиса, не хранилища).

### D2. ORDER BY-приоритет

К существующему `not_generated` добавляются оси (по образцу `is_generated`):

```sql
ORDER BY
  not_generated  DESC,
  branch_match    DESC,  -- f.ds_product_branch_id = :scope_branch
  product_match   DESC,  -- f.ds_product_id = :scope_product
  default_branch  DESC,  -- ds_products_branch.is_default
  id              DESC
```

`branch_match`/`product_match` — булевы выражения в SELECT списке
(`DISTINCT ON`/`ORDER BY`). Эти оси применяются в `FindLatest*`
хранилища (резолв связей), где scope задаётся файлом-источником; в
query-слое явного scope нет, поэтому там порядок вырождается в
`not_generated → default-ветка → id` (ветка запроса — срез C). Для
`GetProcedureDetails`/`GetProcedureResult` добавляется явный
`ORDER BY ... LIMIT 1` — сейчас порядок не определён (баг и на
одно-веточном индексе при UPLOAD-дубликатах). Выборка `branch_used` —
JOIN `ds_products_branch` по `files.ds_product_branch_id` и
нормализованный `branch_key` (единая единица для query и specsvc;
отображаемое `branch_name` в результаты не попадает).

### D3. Правило без явной ветки

`BranchID=0` → приоритет `is_default` ветки продукта. Если у продукта нет
default-ветки (нет develop) — выигрывает старший id (свежая). Для
entity-запросов без известного продукта: `ProductID=0, BranchID=0` →
глобальный максимум по тому же порядку. Результаты всегда несут
`branch_used` (+`product`), при NULL-ветке (не-git файлы) — пустое поле.

### D4. Граф: scope источника, три яруса кандидатов

Пост-обработка берёт для каждого pending-элемента `(product, branch)`
файла-источника (через `files` родительской сущности) вместо константного
`0`. Множество кандидатов ограничено ярусами (иначе «кто последний»
протащит ребро в чужую линию уже на ORDER BY-приоритете — нужна фильтрация,
а не только сортировка):

```
tier 1: копия в ветке источника
tier 2: копия в default-ветке того же продукта
tier 3: копии в других продуктах (их default-ветки, затем id DESC)
   ✗   остальные ветки того же продукта — исключены из кандидатов
```

Tier 3 сохраняет прежнее поведение для общих DDL-утилит других продуктов.
Не-git файл (ветка NULL) вырождается в tier 2 + tier 3. Внутри яруса
приоритет копий определяется осями `not_generated → branch_match →
product_match → default_branch → id DESC`; фильтрация ярусами отсекает
чужие ветки, порядок выбирает лучшую копию среди допустимых. Включены все
точки резолва: вызовы процедур, фрагменты, PAS↔DFM, API-макросы и
**spec_code_mentions** (`indexer_postprocess_spec.go` передаёт сегодня
productID ≠ 0 — спеки SP-worktree'ов среза A резолвим в их ветку, а не в
develop). Pending-пачки группируются по scope → по одному batch-запросу на
группу (обычно 1–3 группы: develop + линии) — N+1 не возвращается.
Неразрешённые в кандидатах имена остаются pending/NULL. Инкрементальный
update: при переиндексации файла его рёбра пересоздаются с актуальным
scope.

**Осознанное исключение:** `FindLatestSQLColumnDefinitionType` (и
`BatchFindColumnDefinitionTypes`) сохраняет поведение «файл проверяемого
файла → ветка → продукт → default → id» без tier-WHERE. Это
review-фолбэк типов колонок: проверяемый файл обязан видеть определения
любой ветки (иначе типы, объявленные в другой линии, ложно не находятся);
первая ось — точный `file_id`, поэтому чужое ребро не подмешивается.

### D4a. Дедупликация списков и поиска

После среза A списковые и поисковые поверхности отдают по строке на копию:
`SearchSymbol` (`internal/query/query.go:325`) — 3 строки на имя (3
линии), то же в списках entity queries, exact-слоях desc-search и
spec-поиска, spec-навигации (спеки релизных линий — отдельные
spec_configs одного продукта). Правило: копии, отличающиеся только веткой
одного продукта, схлопываются в одну строку по приоритету default-ветки;
ключ дедупа — естественный ключ сущности (имя; для PAS-методов — класс и
имя; для API-контрактов — имя и вид) + продукт; для поиска по содержимому
без ключа (query fragments) схлопываются побайтово идентичные копии.
Дедупликация SHALL быть двухфазной: фаза 1 выбирает ветку для ключа
(`DISTINCT ON`), фаза 2 возвращает ВСЕ строки выбранной ветки. Поэтому
одноимённые сущности внутри одной ветки сохраняются (состав результатов
на одно-веточном индексе не меняется), а связи-дубли (например, метод с
несколькими фрагментами) не размножают строку. Выбранная строка несёт
`branch_used` (+`product`). Разные продукты и одноимённые методы разных
классов не схлопываются. На одно-веточном индексе дедуп — no-op
(регрессионные тесты). Дедуп применяется и к агрегатам: `usages` таблицы
считаются в пределах выбранной ветки, enrichment (файлы/колонки/процедуры)
ограничен продуктом и веткой выбранной копии.

### D5. Обратная совместимость контрактов

`branch_used`/`product` — новые необязательные поля JSON (`omitempty`);
`format_version` не меняется (обратное совместимое расширение). На
одно-веточном индексе `branch_match` всегда true для единственной ветки —
результаты идентичны прежним (проверяется регрессионными тестами).

## Risks / Trade-offs

- [Расширение сигнатур ~10 функций] — механический рефакторинг; защита —
  компилятор + интеграционные тесты на выбор копии.
- [Группировка pending по scope разбивает batch'и] — групп мало (веток
  единицы); патологический рост проверяется тестом на 3+ scope.
- [`is_default` отсутствует у продукта] — fallback на старший id; поведение
  зафиксировано тестом.
- [Рёбра, оставшиеся неразрешёнными] — видимы в статистике пост-обработки;
  это честнее ложного ребра; при добавлении ветки позже — резолв при
  следующем update.
- [Дедуп скрывает копии других веток из списков] — выбранная копия видна
  через `branch_used`; профиль среза `dsinfo-integration` выбирает линию
  осознанно, точечный просмотр копий остаётся через `spec_config` и
  файловые пути.

## Migration Plan

Без миграции данных: изменение только логики выборки. Рёбра, созданные до
среза на мультиветочном индексе (если update успел пройти), пересоздаются
следующим полным `update` с корректным scope; до этого срез B+A должны
идти подряд (см. tasks среза A, 7.3).
