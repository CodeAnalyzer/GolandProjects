# Дизайн: add-description-search

## Context

Парсер SQL работает построчно; многострочные `/* */`-комментарии уже вырезаются
из потока трекингом `inBlockComment` (`internal/parser/sql/sql_parser.go:911-921`),
до основной обработки строки — сюда встаёт аккумулятор описания. Регистрация
процедуры сегодня происходит на `procBeginRe` (строка 1133; `DCL_PROC_BEGIN`,
`__BEGIN_PROCEDURE__`) и на `procDeclRe` (`create proc`, строка 1199);
ветка `procCreateRe` (`API_CREATE_PROC`, строка 1125) только сбрасывает стейтмент —
регистрацию делает последующий `__BEGIN_PROCEDURE__`, когда комментарий уже
вырезан. Конец сигнатуры (`as`, параметры собраны) фиксируется флагом
`inProcSignature` (строка 1178).

FTS-инфраструктура спек отработана: выражения векторов с весами A/B
(`internal/store/db_insert_spec.go:13-20`), GIN-индексы
(`internal/store/db_schema.go:898-901`), идемпотентный бэкфилл
(`EnsureSpecSearchVectors`). Описания контрактов уже в БД
(`api_contracts.short_description/full_description`); API-поиски фильтруют
только по `contract_name ILIKE` (`internal/query/api_query.go`).

Фактура FA (замеры в `Modifications/semantic-search-descriptions.md` и разведке):
~98% процедур имеют header-описание; три стиля декларации; описание всегда
блок-комментарий между декларацией и телом; у API-стиля `as` нет.

## Goals / Non-Goals

Goals:

- Описания процедур и контрактов доступны единому FTS-поиску с первого шага.
- Правило захвата — одно для всех стилей декларации (окно «декларация → тело»).
- Дедупликация API-пар в выдаче без потери данных при индексации.
- Переиспользование спековой FTS-инфраструктуры (векторы, индексы, бэкфилл).

Non-Goals:

- Процедуры в `.h`-файлах (отдельное предложение
  `Modifications/index-h-file-sql-procedures.md`).
- Поиск по описаниям SMF/DFM (captions).
- Merge-выдача «контракт+реализация одной строкой» (можно добавить позже,
  дедуп-решение ему не противоречит).
- Общее LSA-пространство «спеки + описания» — отдельные модели по D8.

## Decisions

### D1. Окно захвата: «декларация → первая кодовая строка», первый блок-комментарий

Альтернатива из исходного предложения («комментарий, непосредственно
предшествующий маркеру начала») отклонена фактами: в FA описание стоит
**после** `as`, у `ChangeCalendar_CopyPrc` нет `__BEGIN_PROCEDURE__` вовсе,
у двух образцов между комментарием и `__BEGIN_PROCEDURE__` стоит `begin`.
Единое правило: окно открывается на строке декларации (`DCL_PROC_BEGIN`,
`create proc`, `API_CREATE_PROC`), параметры и `as` окно не закрывают,
первый блок-комментарий = описание, первая кодовая строка /
`__BEGIN_PROCEDURE__` закрывает окно. `--`-комментарии описанием не считаются.

### D2. Точка захвата — трекинг блок-комментариев (строки 911-921)

Аккумулятор встаёт в существующий `inBlockComment`-трекинг: при
`awaitingDescription` строки комментария копятся до `*/`. Для `API_CREATE_PROC`
ветка (строка 1125) должна открывать окно (создавать pending-состояние), т.к.
регистрация процедуры происходит позже — на `__BEGIN_PROCEDURE__`, когда
комментарий уже вырезан. Состояния: `awaitingDescription` → `capturing` →
готово/тело. Альтернатива («задним числом» искать комментарий перед маркером
по исходному тексту) отклонена: дублирует вырезание, хуже тестируется.

### D3. Очистка: имя файла, декоративные линии, 8 КБ

Решения пользователя (разведка 2026-10-04): первая строка вырезается, если
матчится `^\w+\.(sql|h)$` (дублирует `rel_path`); декоративные линии — строки
только из `-`/`=`; лимит 8 КБ с обрезкой хвоста; «внутри лимита — целиком»
(@param/@resultTable-документация сохраняется). Кодировка прозрачна: парсер
получает уже декодированный текст (`internal/encoding`, CP866 для `.sql`).

### D4. Схема и векторы — по образцу спек

- `sql_procedures.description TEXT` — миграция `ADD COLUMN IF NOT EXISTS`;
  модель `SQLProcedure.Description`; запись через существующий batch-insert.
- Векторы: `setweight(to_tsvector('russian', proc_name), 'A') ||
  setweight(to_tsvector('russian', coalesce(description,'')), 'B')`;
  для контрактов имя = A, `short_description || ' ' || full_description` = B.
- GIN на оба вектора + trgm-GIN на `sql_procedures.description` (частичные
  совпадения, как `idx_spec_requirements_body_trgm`).
- Бэкфилл — идемпотентный `UPDATE ... SET search_vector = <выражение> WHERE
  search_vector IS NULL` (по образцу `EnsureSpecSearchVectors`); события и
  callback-контракты покрываются тем же вектором `api_contracts`
  (`contract_kind` различается фильтром).

### D5. Дедупликация: контракт вытесняет процедуру (решение пользователя)

На стороне процедур UNION-запроса: `NOT EXISTS` (связь `implements_contract` →
контракт с непустым описанием). Хранение описаний — у всех процедур: описание
нужно `query procedure` независимо от поиска и является fallback'ом для
контрактов с пустыми описаниями. Отсечение при индексации отклонено: статус
«пустое описание у контракта» меняется, проверка обязана быть в момент выдачи.
Merge-строка «контракт + файл реализации» отложена (Non-Goal): добавляется
позже без пересмотра дедупа.

### D6. Выдача: ts_rank + сниппет + kind-фильтр

Ранжирование `ts_rank` по вектору (веса A/B внутри одной конфигурации
сопоставимы между сущностями); сниппет — `ts_headline('russian', ...)`;
kind-фильтр — предикат по источнику строки UNION
(`procedure | service | event | callback_event | used_service`).
`query procedure` дополняется колонкой `description` (обратная совместимость:
новое поле в существующих записях).

### D7. Слои: query → querysvc → cmd + MCP

`SearchDescriptions` в `internal/query/` (новый файл); тонкая обёртка в
`querysvc`; CLI `codebase query desc-search` (`--text`, повторяемый `--kind`,
`--limit`) с `--json`-envelope по machine-readable контракту; MCP-инструмент
`codebase_query_desc_search` в `internal/mcp/tools.go` со штатной пагинацией.

### D8. LSA: отдельная desc-модель на отдельном корпусе (решение разведки)

Корпус — **только описания** (`sql_procedures.description` + `api_contracts`
short/full), **без спек**. Общий корпус отклонён по четырём причинам:
(1) регрессия откалиброванного spec-поиска — подмешивание 10-60 тыс. документов
сдвигает IDF/латентное пространство молча; (2) гетерогенность жанров
(нормативные спеки vs техническая проза с `@param`-шумом) размывает словарь при
фиксированном K; (3) покорпусная машина переобучения и генерации не должны
связывать жизненные циклы правок спек и кода; (4) кросс-доменность «спека ↔ код»
уже покрыта FTS и `spec_code_mentions`. Соответствует формулировке исходного
предложения («второй sidecar для корпуса описаний»).

### D9. Механика desc-LSA — переиспользование `specfts`

- Документ корпуса: имя сущности с двойным весом + описание
  (`LSADocText(name, "", "", description)` — симметрично spec-варианту).
- Sidecar-пара `desc_lsa_model.bin` + `desc_lsa_state.json` рядом с БД;
  fingerprint `CorpusFingerprint(docs, params)` — тот же.
- Машина переобучения по образцу `postProcessSpecLSA`
  (`internal/indexer/indexer_postprocess_spec_lsa.go:94`): retrain /
  skip-idempotent / defer-до-порога; CorpusDelta = изменённые процедуры +
  контракты за прогон.
- Публикации — новые таблицы `desc_vocab`/`desc_embeddings`
  (generation-ключ, транзакционная публикация, удержание текущего+предыдущего
  по образцу `PublishSpecLSAGeneration`/`DeleteSpecLSAGenerationsExcept`).
- Конфиг — секция по образцу `SpecConfig`-LSA (`internal/config/config.go:82-92`):
  `lsa_enabled`, `lsa_k` (default 512), `lsa_min_df`, `lsa_max_df`,
  `lsa_min_corpus`, `lsa_retrain_threshold`, `lsa_model_path`, `lsa_min_cosine`,
  `lsa_relative_cutoff` — независимые значения для desc-корпуса.
- Query-слой: точная загрузка эмбеддингов поколения + трансформация запроса
  (как в spec_search); хиты `semantic` с cosine-рангом, фильтры
  MinCosine/relative-cutoff; гибрид с exact-хитами, источник хита в выдаче.

## Risks / Trade-offs

- [Джанк-описания из `#define`-продолжений в `.sql`] → окно захвата требует
  `inProcedure`/pending-декларацию; continuation-строки макросов вне процедур
  окно не открывают. Проверить тестом «макрос с DCL_PROC_BEGIN в теле».
- [Описания процедур пусты до перепарсинга] → задокументировать: контрактная
  часть ищется сразу после бэкфилла; процедуры — после полной пересборки
  (`update --modified=false`, ~1.5ч на FA) или инкрементального update.
- [Рост размера БД] → описание ≤ 8 КБ × ~10-50 тыс. процедур — единицы сотен
  МБ worst case; фактически тексты в среднем < 1 КБ. Приемлемо.
- [ts_headline дорог на больших выборках] → применяется только к отсечённому
  `LIMIT`-набору после ранжирования.
- [Сопоставимость рангов процедура/контракт] → одна конфигурация `'russian'`,
  одинаковая схема весов; при необходимости — калибровка коэффициентом в
  отдельной итерации.
- [SVD на корпусе 10-60 тыс. документов] → gonum SVD справлялся на spec-корпусе
  при K=512; следить за временем стадии `desc-lsa` в scan stats; при деградации —
  амортизация порогом retrain-threshold (уже в машине переобучения).
- [Мелкие описания = короткие документы, слабая LSA] → имя с двойным весом
  добавляет якорные термины; MinDF/MaxDF/K — конфигурируемые, калибровка на
  FA-прогоне (задача верификации); до обучения — graceful exact-only.
- [Два sidecar-файла] → независимые пути в конфиге; публикация атомарная
  (переиспользуется replace_file_unix/windows из specfts).

## Migration Plan

1. `InitSchema` идемпотентно добавляет колонку, FTS-индексы и таблицы
   `desc_vocab`/`desc_embeddings` (существующие БД).
2. Бэкфилл векторов выполняется при старте update/init и идемпотентен.
3. Первое обучение desc-LSA происходит в той же полной пересборке, что и
   заполнение описаний (`update --modified=false`) — отдельного прогона не
   требуется; до обучения поиск работает в exact-only режиме.
4. Релизные заметки: описания процедур заполняются после перепарсинга —
   `codebase update --modified=false` (полная пересборка) или ожиданием
   естественного инкрементального обновления файлов.
5. Откат — бинарный: новые колонки/индексы/таблицы не мешают старой версии.
