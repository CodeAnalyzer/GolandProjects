# Design: mask-plpgsql-dollar-quoted-blocks

## Context

Пайплайн review (`internal/review/runner.go`, `runSQLFileCtx`): чтение файла
(CP866) → `replaceMacros` (#define, line-preserving, SourceMap) →
`ParseContent` → правила. Парсер — линейный автомат: понятия dollar-quoting
нет, `#ifdef`-гейты не вычисляются — PG-код парсится как T-SQL, правила
(MSSQL-ориентированные) дают FP. `reviewExecContext` хранит `content`
(expanded), `rawContent` (raw), `macroResult`, `lines`.

В `review_parser.go` есть прецеденты line-preserving маскирования:
`maskBlockCommentsKeepLines`, `maskSingleQuotedStringContent`,
`stripCommentsFromText`. Мотивация и цифры — proposal.md (27/27 FP на
ADM_STPPGEXECUTE, 34/38 на RPT_Exec, 228 файлов с dollar-quoting в FA, 45
смешанных; воспроизводимые команды подсчёта — tasks.md 4.3/4.5). Мотивация
выбора варианта «маскирование» — ниже, D1.

## Goals / Non-Goals

**Goals:**

- Убрать FP из plpgsql-областей, сохранив разбор MSSQL-веток смешанных
  файлов и все находки в файлах без dollar-quoting (0 diff).
- Минимальная аддитивная правка: один новый этап препроцессинга, никакого
  изменения контракта findings, CLI, БД, индексатора.

**Non-Goals:**

- `#ifdef`-проекция (эмуляция препроцессора) — кандидат-преемник; суперпозиция
  веток в смешанных файлах остаётся.
- PG-семейство правил (настоящий review PG-кода).
- Мусор PG-файлов в индексаторе (dblink_get_result как «таблица» и т.п.) —
  смежная задача.
- Обучение 47 правил PG-диалекту.

## Decisions

### D1: Маскирование областей, а не скип файлов / ifdef-проекция / правки правил

- Скип файла — отпал: 45 смешанных файлов (DCL_PROC_BEGIN + plpgsql), потеря
  реальных находок MSSQL-ветки (в RPT_Exec — все 4 легитимные).
- `#ifdef`-проекция — частично покрывает (гейты PG_CODE/PG_CONVERT/PG_STYLE
  только в 347/259/30 файлах; 213 с `#else`; вложенность, `#endif -- comment`,
  негейтовые каталоги pgKernel/Test PG) — требует частичного препроцессора,
  отложено как преемник.
- Диалект-awareness в правилах — 47 правил × специфика PG — whack-a-mole.
- Маскирование решает на уровне ниже правил: парсер и правила просто не видят
  PG-код. Один механизм закрывает все семейства правил.

### D2: Область маски — от `create`-заголовка до закрывающего тега, не только `$$…$$`

Маска только тел оставляет сигнатуру видимой → nullComparison стреляет на
`var_x DSTYPE = null` (4 из 27 FP — строки 61, 294–296 ADM_STPPGEXECUTE);
исключения правила знают только T-SQL-формы (`@p type = null`, `= null out`).
В корпусе обе формы записи дефолтов: `= null` и `DEFAULT NULL::` (RPT_Exec).
Поэтому:

```
create or replace procedure name(...)  ┐
  ...сигнатура, language plpgsql, as   │ маска (create-заголовок → тег)
$$ … тело … $$;                         ┘
```

Механика: при встрече открывающего dollar-quote — обратный скан до ближайшей
строки, матчащей `(?i)^\s*create\s+(or\s+replace\s+)?(function|procedure)\b`;
если между ней и тегом нет `;` (в PG-сигнатуре их нет) — маска начинается со
строки `create`, иначе — ограничивается телом dollar-quote. Обратный скан
ограничен (барьер — первый встреченный `;`). `do $$…$$;` — отдельного
расширения назад не требует: слово `do` не является целью ни одного правила,
маскируется только доллар-область.

### D3: Сканер — однопроходный автомат с состояниями, а не regex

Состояния: normal / in-single-quote / in-line-comment (`--`) /
in-block-comment (`/* */`, вложенность считается — как в PG) /
in-dollar-quote(tag). Dollar-quote распознаётся
только в normal. Тег: `$([A-Za-z_][A-Za-z_0-9]*)?$` — пустой (`$$`) либо
с первым символом буква/подчёркивание, как unquoted-идентификатор PG;
последовательности вида `$1$` (позиционные параметры) область не открывают.
Закрытие — парный тег с тем же именем. В состоянии in-single-quote удвоение
`''` не закрывает литерал.

**Guard на `$$$`-серии.** Серия из трёх и более подряд идущих `$` не
открывает и не закрывает область — сканер пропускает серию целиком (симметрично
в поиске открывающего и закрывающего тега). Причина: в корпусе есть
`$$$`-маркеры клиентских макросов Diasoft в обычном коде, вне литералов и
комментариев (ClientMacros.sql — `$$$NPPBEGIN$$$`, `$$$FAKE_…`; файл в
`#ifndef PG_CONVERT`-ветке, т.е. это T-SQL-код). Без guard'а сканер хаотично
маскировал бы раздел макро-маркеров и искажал разбор `#define`/вызовов.
Реальные dollar-quote корпуса всегда начинаются с `$$`/`$tag$`, за которыми
идёт не-`$` контент; `$$$` встречается в 4 файлах FA (ClientMacros.sql —
нормальный код, остальные — внутри `'…'`-литералов, защищены состоянием
in-single-quote) и ни разу — внутри dollar-quoted тела.

Ограничение: двойные кавычки `"…"` (PG-идентификаторы) не отслеживаются
отдельным состоянием — в проверенных файлах корпуса `$$` внутри `"…"` не
встречается; при появлении автомат расширяется состоянием in-double-quote.

Причина: грабли корпуса — `$$$$$$$$` внутри строкового литерала
(Cons_CorrectLastPay.sql:374): наивный поиск `$$` даст ложное открытие и
поглотит код. Regex по строкам не отслеживает многострочные литералы и
комментарии.

### D4: Точка встраивания — до `replaceMacros`, `rawContent` не трогаем

`masked := maskDollarQuotedBlocks(raw)` выполняется на raw-контенте сразу
после чтения; `replaceMacros(masked)`; `rawContent` остаётся немаскированным
(для `debugProfileEnabled` и любых будущих сырых анализов). Обоснование
порядка: **основной аргумент — line-preserving**: обе операции сохраняют
строки, число строк совпадает с raw, SourceMap и `mapExpandedLineToOriginal`
работают без изменений. Аргумент «тела `#define` с `$$` маскируются до
подстановки» — вторичный и условный: настоящих dollar-quote в телах `#define`
корпус не содержит (единственный кейс `#define … $$$…` — ClientMacros.sql,
закрывается `$$$`-guard из D3). Порядок «до replaceMacros» сохранён как более
простая цепочка raw → mask → expand; маскирование после `replaceMacros` от
`$$$`-маркеров всё равно не спасает (они живут и в expanded-контенте).

### D5: Отказ при незакрытом теге — fail-open

Если парный закрывающий тег не найден до EOF, область не маскируется
(контент остаётся как есть — текущее поведение). Незакрытый dollar-quote —
сломанный файл; fail-open не теряет находок в остальном файле.

### D6: Размещение кода

Новый файл `internal/review/review_plpgsql_mask.go`: функция
`maskDollarQuotedBlocks(content string) string` + таблица/автомат состояний.
Вызов — в `runSQLFileCtx` (`runner.go`). Тесты — рядом в `internal/review`
(синтетические кейсы по сценариям спеки + литеральные ловушки).

## Risks / Trade-offs

- [Risk] `$$` в T-SQL-коде вне литералов/комментариев/`$$$`-серий → ложное
  маскирование до следующего `$$` → потеря находок → Mitigation: форму
  `$$$`-маркеров закрывает guard D3; `$$$$$$$$`-подобные — состояние
  in-single-quote (Cons_CorrectLastPay.sql); контроль эквивалентности батчем
  по MSSQL-корпусу (0 diff) и целевой прогон ClientMacros.sql (tasks 4.5).
- [Risk] Нет парного тега → fail-open оставляет FP → Mitigation: осознанно
  (D5); на 228 dollar-quoting-файлах парность подтверждается приёмкой.
- [Risk] `create or replace` на нескольких строках / необычные формы →
  обратный скан не найдёт заголовок → маска только тела → остаточный FP
  nullComparison → Mitigation: приёмка на 45 смешанных файлах; при находке
  расширяется regex заголовка.
- [Risk] Барьер `;` обратного расширения проверяется по raw-тексту строк без
  учёта литералов и комментариев: `;` в строковом дефолте сигнатуры или в
  комментарии между `create`-заголовком и тегом отключает расширение → маска
  только тела → остаточный FP nullComparison. Класс дефекта — видимый FP (не
  потеря находок), в корпусе 0 вхождений (45 смешанных + 228 dq); при
  появлении реального кейса барьер переводится на лексически-осведомлённый
  скан региона заголовок→тег.
- [Trade-off] PG-код становится принципиально непроверяемым review — принято
  (non-goal), компенсируется будущим PG-семейством правил.

## Migration Plan

Не требуется: нет изменений схемы БД, CLI-флагов, контракта findings.
Развёртывание — пересборка бинарника; откат — предыдущий бинарник (review
stateless). Приёмка — на реальном корпусе FA (см. tasks.md).
