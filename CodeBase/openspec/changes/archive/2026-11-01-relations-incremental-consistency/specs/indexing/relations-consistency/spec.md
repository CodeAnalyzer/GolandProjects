## Purpose

Обеспечивает целостность графа связей между сущностями при инкрементальной индексации: после каждого прогона рёбра ссылаются только на существующие источники и цели, а результаты запросов графа не содержат фантомных вызывателей и не теряют реальные связи.

## ADDED Requirements

### Requirement: Инвариант целостности графа после прогона

После успешного завершения `Init` или `Update` система SHALL не оставлять в `relations` ни одного ребра, у которого `source_type`/`source_id` или `target_type`/`target_id` не соответствует существующей сущности. Инвариант применяется ко всем семействам рёбер, создаваемым по файлам: `calls_procedure`, `dispatches_to`, `dispatches_to_subscriber`, `references_table`, `selects_from`, `inserts_into`, `updates`, `deletes_from`, `builds_query`, `executes_query`, `has_field`, `has_param`, `uses_param`, `implements_contract`, `executes_contract`, `publishes_event`. Семейства, пересобираемые глобально каждый прогон (`subscribes_to_event`, `references_code`, `depends_on_capability`, `usecase_involves`, `change_modifies`), сохраняют текущее поведение и в per-file инвариант не входят.

#### Scenario: Инкрементальный прогон после изменения файлов

- **GIVEN** индекс, в котором ранее были проиндексированы вызыватели, вызываемые, файлы таблиц и XML-контракты
- **WHEN** выполняется `update` после изменения набора этих файлов
- **THEN** после завершения прогона в `relations` нет рёбер с отсутствующим источником или отсутствующей целью

#### Scenario: Прогон без изменений

- **GIVEN** индекс, удовлетворяющий инварианту
- **WHEN** выполняется `update`, не обнаруживший изменённых или удалённых файлов
- **THEN** набор рёбер не меняется и инвариант сохраняется

#### Scenario: Полная пересборка

- **GIVEN** пустая или заполненная база
- **WHEN** выполняется `Init` или `update --modified=false`
- **THEN** после завершения прогона инвариант целостности выполняется

#### Scenario: Сбой парсинга изменённого файла

- **GIVEN** файл изменён на диске, но его парсинг завершился ошибкой и новые сущности не созданы
- **WHEN** `Update` завершается
- **THEN** рёбра предыдущего поколения этого файла не остаются в `relations`
- **AND** в графе нет рёбер, ссылающихся на отсутствующие сущности

### Requirement: Согласование рёбер переиндексированных и удалённых файлов

При изменении содержимого файла система SHALL удалять рёбра, чьи источники принадлежат предыдущему поколению этого файла, и перестраивать их из нового содержимого. Для межфайловых рёбер система SHALL переносить цель на сущность нового поколения того же файла. Если цель не может быть сопоставлена с новой сущностью (сущность удалена, файл удалён или переименован), рёбра, ссылающиеся на неё, SHALL удаляться.

#### Scenario: Изменение файла-вызывателя

- **GIVEN** SQL-процедура `Caller` вызывает `Callee`; файл с `Caller` переиндексирован
- **WHEN** прогон завершён
- **THEN** для `Callee` не появляется вызыватель с именем `unknown` и пустым файлом
- **AND** рёбра `calls_procedure` соответствуют вызовам в новой версии `Caller`

#### Scenario: Изменение файла-вызываемого

- **GIVEN** процедура `Caller` в неизменённом файле вызывает `Callee`; файл с `Callee` переиндексирован
- **WHEN** прогон завершён
- **THEN** `Caller` по-прежнему виден в результатах вызовов `Callee`

#### Scenario: Изменение файла с определениями таблиц

- **GIVEN** query fragments и процедуры ссылаются на таблицу `tAccount`; файл, определяющий `tAccount`, переиндексирован
- **WHEN** прогон завершён
- **THEN** связи `references_table`/`selects_from`/`inserts_into`/`updates`/`deletes_from` живых источников указывают на новую сущность `tAccount`

#### Scenario: Изменение XML-контракта API

- **GIVEN** SQL-процедура реализует контракт `FCD_Loan_Get`; XML-файл контракта переиндексирован
- **WHEN** прогон завершён
- **THEN** связь `implements_contract` от процедуры указывает на новую сущность контракта

#### Scenario: Удаление файла

- **GIVEN** файл содержит процедуру, которая вызывает другие процедуры и сама вызывается из неизменённых файлов
- **WHEN** файл удалён с диска и выполнен `update`
- **THEN** рёбра, где удалённая процедура была источником, удалены
- **AND** рёбра, где удалённая процедура была целью, удалены

#### Scenario: Переименование процедуры

- **GIVEN** процедура `OldName` вызывалась из неизменённых файлов и в новой версии файла переименована в `NewName`
- **WHEN** прогон завершён
- **THEN** рёбра на `OldName` удалены и не отображаются как фантомы
- **AND** вызовы по имени `NewName` разрешаются по общим правилам резолва

#### Scenario: Переименование или перенос файла

- **GIVEN** файл с целевыми сущностями переименован или перемещён, поэтому путь файла изменился
- **WHEN** прогон завершён
- **THEN** рёбра, чью цель не удалось сопоставить по новому поколению, удаляются
- **AND** в графе не остаётся мёртвых целей

#### Scenario: Изоляция веток и продуктов

- **GIVEN** одна и та же сущность существует в нескольких ветках или продуктах
- **WHEN** переиндексируется файл одной ветки
- **THEN** перенос целей выполняется только в пределах пути этого файла (та же ветка и продукт)
- **AND** рёбра других веток и продуктов не перепривязываются

### Requirement: Идентичность цели при переносе

Перенос цели SHALL выполняться по стабильному identity-ключу сущности внутри файла: `sql_procedure` — `proc_name`, `sql_table` — `table_name`, `api_contract` — `contract_name` + `contract_kind`. Для старого id выбирается новая сущность с тем же путём файла и тем же ключом с максимальным id — это соответствует семантике резолверов `FindLatest...`. Содержимое, номера строк и `body_hash` в identity не входят. Типы целей, которые всегда находятся в том же файле, что источник (`query_fragment`, `report_field`, `report_param`), переносу не подлежат, так как их связи пересоздаются вместе с источником.

#### Scenario: Изменение тела процедуры

- **GIVEN** процедура `Calc` изменила тело, но сохранила имя и файл
- **WHEN** файл переиндексирован
- **THEN** входящие связи на `Calc` переносятся на новую сущность
- **AND** номера строк вызова в вызывателях не изменяются

#### Scenario: Дубли имён в файле

- **GIVEN** в одном файле несколько определений сущности с одинаковым именем
- **WHEN** выполняется перенос целей
- **THEN** выбирается последняя (max id) новая сущность с этим именем
- **AND** искусственные дубли рёбер не создаются

#### Scenario: Новая сущность отсутствует

- **GIVEN** старая цель имела имя, которого больше нет в новом поколении файла
- **WHEN** выполняется перенос целей
- **THEN** перенос для неё не выполняется, а рёбра на неё удаляются

### Requirement: Наблюдаемость согласования

Прогон SHALL логировать счётчики этапа согласования: сколько рёбер удалено по мёртвым источникам, сколько целей перенесено и сколько рёбер удалено из-за неустранимой цели, с разбивкой по типам сущностей.

#### Scenario: Прогон с изменениями

- **GIVEN** `update` обработал изменённые и удалённые файлы
- **WHEN** этап согласования завершён
- **THEN** в логе присутствуют счётчики purge, remap и deleted с разбивкой по типам

#### Scenario: Прогон без изменений

- **GIVEN** `update` не обнаружил изменённых файлов
- **WHEN** этап согласования завершён
- **THEN** счётчики сообщают нулевые значения

### Requirement: Результаты запросов графа без фантомов

После успешного прогона запросы графа SHALL не возвращать фантомные связи: `codebase_query_callers` не возвращает вызывателей с `caller_name='unknown'` или пустым файлом, а `codebase_query_relations` и `inspect` не возвращают синтетические имена вида `type:id` для семейств, покрытых инвариантом.

#### Scenario: Проверка вызывателей после переиндексации

- **GIVEN** после прогона у процедуры-цели есть только живые вызыватели
- **WHEN** выполняется `codebase_query_callers` для этой цели
- **THEN** среди результатов нет строк с `unknown` или пустым путём файла

#### Scenario: Проверка графа по типу

- **GIVEN** после прогона выполнено согласование рёбер
- **WHEN** выполняется `codebase_query_relations` с фильтром по типу сущности
- **THEN** результаты не содержат синтетических имён `type:id` для живых типов сущностей
