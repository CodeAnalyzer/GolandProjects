## Context

Мотивация — см. `proposal.md`. Текущее состояние, важное для реализации:

- `checkUseEqColumn` (`internal/review/review_rules.go`) собирает условия `WHERE`/`ON`/`HAVING` (функции `findConditionStart`, `hasConditionEnded`), вырезает комментарии и передаёт буфер в `analyzeConditionForEqColumn`.
- В `analyzeConditionForEqColumn` единый регэксп `reEqOperands = (@?\w+(?:\.\w+)?)\s*=\s*(@?\w+(?:\.\w+)?)` уже захватывает `@`-операнды; сразу после матча стоит безусловный пропуск, если хотя бы один операнд начинается с `@` (`review_rules.go:3370`).
- `indexWrong` строит набор колонок условия через `collectColumnsFromConditionExpression` → `extractUnqualifiedConditionColumns` → `reHelperUnqualifiedCondition = \b([a-zA-Z_]\w*)\b\s*(=|<>|...)` (`review_helpers.go:48`). `\b` срабатывает между `@` и буквой, поэтому `@BankProductID = ...` даёт колонку `BankProductID`.
- Go regexp (RE2) не поддерживает lookbehind, поэтому фильтр «не после `@`» нельзя выразить в самом регэкспе без смены семантики матчинга.

## Goals / Non-Goals

**Goals:**
- Поймать `@X = @X` именно в предикатах, не задев массовые named-args `EXEC` (проверено `rg`: 42 045 вхождений в 4 415 файлах fa-contracts).
- Убрать ложный `indexWrong` из-за `@`-префикса, не меняя логику выбора индекса для реальных колонок.
- Минимальная поверхность: без нового rule ID, без изменений формата JSON-вывода.

**Non-Goals:**
- Не детектировать семантически эквивалентные тавтологии (`@X = abs(@X)`, `@X = isnull(@X,@X)`, `1 = 1`).
- Не менять разбор условий, обработку комментариев/строк и правила `hasConditionEnded`.
- Не исправлять сам SQL в FA — change только про анализатор.
- Не менять severities и формат сообщений для существующих колонковых кейсов.

## Decisions

### D1. Расширяем `useEqColumn`, а не вводим новое правило

Самосравнение переменной проверяется в том же `analyzeConditionForEqColumn`, до существующего `@`-skip. Причины:

- анализатор уже ограничен `WHERE`/`ON`/`HAVING`, уже вырезает комментарии и уже отсеивает битовые операции — это ровно нужный контекст;
- severity 1 и семантика «сравнение с самим собой» совпадают;
- новое правило потребовало бы дублировать сбор условий, добавлять catalog/spec/тесты и лишний finding-тип при том же результате.

Альтернатива (отдельный `varSelfComparison`) отклонена по цене; если позже понадобится другая severity/сообщение — выделить можно без изменения детекции.

### D2. Порядок проверок в `analyzeConditionForEqColumn`

1. Оба операнда — ровно `@name` (один `@`, без точки), имена равны без учёта регистра → finding `useEqColumn` с сообщением `Заведомо истинное сравнение: <left> = <right>` (операнды в исходном написании, например `@BankProductID`).
2. Иначе — прежнее поведение: любой операнд с `@` пропускается.
3. Далее — существующая колонковая логика (`normalizeIdentifier`, `isNumericLiteral`, `isInSelectClause`).

`@@`-переменные (`@@spid`) в самосравнение не включаем: это системные значения, а не пользовательский параметр; для них остаётся текущий пропуск.

Механизм отсечения: `reEqOperands` матчит `@@spid` начиная со **второй** `@` (первая не даёт `\w+`), поэтому операнд выглядит как `@spid` и наивное сравнение «оба с `@` и имена равны» дало бы FP. Поэтому для каждого операнда проверяется символ непосредственно перед началом матча: если это `@`, операнд не считается пользовательской переменной (тот же приём, что в D3). Дополнительно требуется ровно один ведущий `@` и отсутствие точки в имени.

Самосравнение засчитывается только внутри выражения условия: позиция матча должна быть до начала первого оператора/макроса на **нулевой глубине скобок**, открывающегося после `WHERE`/`ON`/`HAVING` (`exec`, `API_EXEC`, `API_INIT_EVENT`, `M_*`, `$_IF`, `if`, `begin`, `select` и т.п.). Причина: сборщик условия может захватить такой хвост вплоть до `M_KEEPPLAN`/`go`, а в аргументах `@X = @X` — штатный синтаксис. Учёт глубины скобок не даёт принять строку-продолжение вида `isnull(@a,0) = @b` за начало нового оператора. Проверка построчная, существующая колонковая логика не затрагивается.

Ключ дедупликации — с префиксом (`var:@bankproductid`), чтобы не пересечься с колонковым `seen` в том же условии. Строка finding вычисляется тем же `positionToLine`, что и для колонок (операнд в многострочном условии).

### D3. Фильтр `@`-префикса — по индексу матча, а не регэкспом

`extractUnqualifiedConditionColumns` переводится на `FindAllStringSubmatchIndex`: для каждого матча проверяется символ непосредственно перед началом идентификатора; если это `@` — матч отбрасывается. Это закрывает и `@name`, и `@@name` (в `@@spid` символ перед `spid` — `@`), не требует lookbehind и не меняет поведение для обычных колонок.

Альтернативы: (а) регэксп с `(^|[^@\w])` — ломает перекрывающиеся совпадения и требует ручной работы с группами; (б) фильтр на уровне `collectColumnsFromConditionBranch` — менее локально и не покрывает будущие вызовы. Отклонены.

### D4. Приёмочные эталоны

- `BPConsConditionInsert.sql`: до — `indexWrong` 1 (строка 1720), `useEqColumn` 0; после — `indexWrong` 0, `useEqColumn` 1 (строка 1723, сообщение про `@BankProductID = @BankProductID`), остальные 32 finding не меняются.
- `BPConsCoolingOff_Transfer.sql`: `useEqColumn` 0 до и после — правильная форма `and BankProductID = @BankProductID` не считается колонковым самосравнением, и сканер `useEqColumn` для этого файла жив (блочный комментарий обрабатывается до `--`-строки). Для `indexWrong` этот файл эталоном **не является**: закрывающая строка шапки `------...---*/` (строка 20) начинается с `--`, и из-за порядка проверок в `checkIndexWrong` (`review_rules.go:268-280`) весь файл после неё пропускается сканером (независимый дефект, см. Risks). Корректность индексной формы `BankProductID = @BankProductID` покрывается синтетическим тестом (задача 2.3).
- Батч fa-contracts (выборка 1000 файлов + 2 эталона; полный набор 11 991 файл слишком медленный, ~0,4 с/файл): было 139 findings (2 `useEqColumn`, 137 `indexWrong`), стало 139 (3, 136); diff ровно `+BPConsConditionInsert.sql:1723 useEqColumn` и `-BPConsConditionInsert.sql:1720 indexWrong`. Ложные `diffTypesComparison`/`datatype` не появляются.

## Risks / Trade-offs

- [Ложное срабатывание на `@X = @X` в необычном, но легитимном предикате] → таких в FA нет (3 живых кейса, все — опечатки/заглушки); при появлении — точечный `//nolint`-механизма нет, решение принимать на уровне правила.
- [Фильтр по индексу матча можно применить не к тому символу при квалифицированных именах `alias.@x`] → такая конструкция невалидна в T-SQL; тест на `p.col` подтверждает, что колонка после точки не отбрасывается.
- [Расширение `useEqColumn` меняет поведение deploy-stopper'а: новые блокировки деплоя] → это цель изменения; сообщение явно указывает на тавтологию, а не на «столбец».
- [MODIFIED-требование при архивации заменит текст целиком] → в дельте воспроизведены оба требования полностью, включая прежние сценарии.
- [Независимый дефект сканеров: заголовочная строка `------*/` пропускается как `--`-комментарий до закрытия блока, поэтому правила с таким порядком проверок не видят файл после шапки] → в этот change не входит; приёмка по `BPConsCoolingOff_Transfer.sql` честно сужена до `useEqColumn`. Завести отдельный change: переставить обработку блочного комментария перед `--`-фильтром. Затронуты минимум `checkIndexWrong`, `checkUpdateOnlyVar`, `checkPTableSpid`, `checkForceOrder2Tbl`, `checkSaveTran`, `checkUseDrop`, `checkMathOperations`, `checkExistsWithAndInIf`, `checkIndexExistsInDB`, `checkVarcharSize`, `checkUseFuncInIndCol`; после фикса на Transfer.sql ожидается легитимный `indexWrong@40` (XIE1).
