# Design: update-full-rebuild-truncate

## Context

Источник проработки: `Modifications/update-full-rebuild-truncate-c41d7f.md` (замеры FA, список таблиц). При `codebase update --modified=false` pre-filter отключён (фикс из change `fix-sql-tables-update-pollution`, `runner.go:161`), все файлы читаются и хешируются, но каждый идёт по update-ветке «вставить нового + каскадно удалить старого» — на FA это 4ч39м против 1ч35м у `init` на чистой БД. `cmd/update.go` уже вызывает `db.InitSchema()` (идемпотентен), поэтому шаг инициализации схемы — status quo. FK-картина проверена: почти все entity-таблицы ссылаются на `files(id) ON DELETE CASCADE`; RTI/TRC-таблицы не имеют FK на усекаемые таблицы.

## Goals / Non-Goals

**Goals:**
- `update --modified=false` = «пересобрать индекс кодовой базы с нуля» за время, сопоставимое с init (~1.5ч на FA вместо ~4.5ч).
- Сохранение RTI/TRC-сессий и истории `scan_runs`.
- Честная, наблюдаемая семантика (метка прогресса, справка флага).

**Non-Goals:**
- Изменение семантики `--modified=true` (дефолтный инкрементальный update с pre-filter).
- Shadow-таблицы + rename для устранения окна пустого индекса — сложность не оправдана: окно ~1.5ч совпадает с поведением `init` на чистой БД.
- `VACUUM FULL` в пайплайне — TRUNCATE возвращает место немедленно (новые relfile-ы); при необходимости — отдельная ручная операция для разросшихся RTI/TRC-таблиц.
- Изменения RTI/TRC storage (`rti_prune`/`trc_prune`).

## Decisions

**D1. Носитель семантики — флаг `--modified=false`, не отдельная команда.**
После фикса pre-filter у `--modified=false` не осталось собственного значения (полный перепрох по update-ветке — непрактично медленный). Отдельная команда `rebuild` добавила бы третий способ пересборки рядом с `init` и `update`. Альтернатива «bulk DELETE всех строк вместо per-file каскадов» отклонена: оставляет мёртвые кортежи (нужен VACUUM), не убирает перезапись 1.17M+2.5M+1.7M строк; TRUNCATE дешевле и чище.

**D2. Явный список таблиц в TRUNCATE + CASCADE как страховка.**
FK-граф (`REFERENCES files(id) ON DELETE CASCADE` у ~35 таблиц) позволил бы усечь почти всё одним `TRUNCATE files CASCADE`, но таблицы без FK на `files` (`ds_products`, `ds_return_codes`, `relations`, `spec_vocab`, `spec_embeddings`) остались бы. Явный список из 52 таблиц читаем и самодокументируем; CASCADE — страховка от появления новых зависимостей. Тест фиксирует полный список и проверяет пустоту каждой таблицы, не полагаясь на CASCADE.

**D3. `scan_runs` не усекается — история сохраняется.**
В документе-источнике `scan_runs` был в списке усечения с пометкой «решить на реализации». FK направлен `files.scan_run_id → scan_runs(id)`, поэтому усечение `files` не требует усечения родителя: сиротские строки истории безвредны, `CreateScanRun` в `InitCtx` просто добавляет новую запись. Цена сохранения — нулевая, ценность — непрерывность истории прогонов (раньше терялась даже при ручном обходе). `stats_snapshot` усекается — это кэш, обновляемый `RefreshStats` в конце прогона (`cmd/update.go`).

**D4. Удаление LSA-sidecar — в делегирующем коде runner-а, до запуска пайплайна.**
Пути sidecar знает `indexer_postprocess_spec_lsa.go` (конфиг); `ResetCodebaseTables` (store-слой) файлами не занимается. Детерминированный ретрейн с нуля вместо загрузки устаревшей модели поверх опустевшего `spec_vocab`. Прерванный прогон: sidecar отсутствует до конца доигрывающего прогона — семантический поиск временно недоступен, лексический работает.

**D5. Ветвление в `UpdateCtx`, метка прогресса — параметр внутреннего пайплайна.**
`InitCtx` — выделение внутреннего `runInitPipeline(ctx, rootPath, parallel, progressLabel)`: `InitCtx` зовёт с `"init"`, ветка пересборки в `UpdateCtx` — с `"rebuild"`. Порядок в `UpdateCtx`: ветка `!onlyModified` проверяется **до** `GetLatestFilesByRootPath` (загрузка предыдущего состояния при пересборке не нужна). TRUNCATE и запуск пайплайна — последовательные шаги, не одна транзакция: пайплайн длится ~1.5ч.

**D6. Восстановление после прерванной пересборки — повторный запуск `--modified=false` (полный рестарт).**
Прерванная (Ctrl+C) пересборка оставляет частично заполненный индекс. Повторный `update --modified=false` стартует заново — TRUNCATE очищает частичное состояние, результат эквивалентен непрерывной пересборке; при отмене пользователю печатается подсказка перезапустить команду. Инкрементальный `--modified=true` для доигрывания непригоден: он восстанавливает сущности уже обработанных файлов (pre-filter пропускает их по fingerprint), но не relations-граф — pending-ссылки постпроцессоров (SQL/JS calls, PAS↔DFM, fragments) накапливаются в памяти при парсинге, не переживают перезапуск процесса и не восстанавливаются для pre-filtered файлов (подтверждено тестом: relations пропущенного файла не строятся). Это унаследованное ограничение — прерванный `init` ведёт себя так же. Альтернатива «восстанавливать pending из БД для pre-filtered файлов» — отдельная архитектурная работа, вне scope.

**D7. Мультирут-семантика — TRUNCATE действует на всю БД.**
В `files` нет `root_path` — привязка только через `scan_runs`. Если бы в одном индексе жили несколько root, пересборка снесла бы все. Практика — один root на БД (`codebase.toml`), поэтому семантика «пересобрать индекс (БД целиком)» принимается и фиксируется в справке флага.

## Risks / Trade-offs

- **[TRUNCATE необратим]** → операция явная (`--modified=false`); RTI/TRC-данные и история сканов не затрагиваются; прерванная пересборка возобновляется повторным rebuild (D6).
- **[Индекс пуст во время пересборки ~1.5ч]** → то же поведение, что у `init` на чистой БД; запросы в это время вернут пустые результаты. Shadow-tables отклонены (Non-Goals).
- **[Дубли, если делегация выполнится без TRUNCATE]** → сброс и делегация в одной ветке кода, сброс — первый шаг; интеграционный тест «сущности ровно в одном экземпляре после rebuild».
- **[FK-дрейф: у RTI/TRC-таблиц появится ссылка на усекаемые]** → CASCADE зацепит и удалит сессии; тест по `information_schema` фиксирует отсутствие таких FK и упадёт при их появлении.
- **[Пользователь ожидает «update», видит метку `rebuild`]** → принят как честный (D5); приглашения `"Updating started/completed"` в `cmd/update.go` остаются корректными.
