# Дизайн: fix-postgre-label-goto-batch-scope

## Context

`checkPostgreLabelGotoLevel` (`internal/review/review_rules.go:4747`) — построчный сканер: зачистка блочных/строчных комментариев и экранирование строковых литералов, затем сбор всех `goto` и всех меток (`word:`) **на весь файл** (`labels map[string][]int`) и сопоставление: finding при любом `labelLine <= gotoLine`. В T-SQL метка видима только в своём батче — сегменте между разделителями `go`; в Diasoft-стиле каждая процедура завершается меткой `_FINISH:`/`_EXIT:`/`_NEXT:`, поэтому метка первой процедуры «засвечивает» goto второй (Trunc_Inst.sql:103: метка@55 из proc 1 ≤ goto@103, реальная метка@109 ниже). Мотивация и замеры — proposal.md (37/39 FP на fa-generalledger).

Факты по корпусу fa-generalledger: строки `go` — всегда нижний регистр (9133 вхождений); форма `go N` — 0 вхождений. Каждая процедура в анализируемом контенте завершается либо литеральной строкой `go`, либо вызовом макроса-завершителя: `ARC_PROC_END(имя)` (archive.h:162, раскрытие `go … X_ANYMODE … go`; в fa-generalledger — только archiver.sql, 6 вызовов), `DCL_PROC_END(имя)` (MACROS.H:762, хвост `… end \ go \ X_ANYMODE(NAME) \ go \ grant … \ go`) или `PROC_END(имя)` (archive.h:168, идентичное ARC раскрытие; 8 вызовов в других продуктах FA, в fa-generalledger — 0). `replaceMacros`/`collectMacroDefinitions` (review_parser.go) резолвят только in-file `#define` и не раскрывают `#include`-заголовки, поэтому в анализируемом контенте граница батча остаётся литеральным вызовом макроса.

## Goals / Non-Goals

**Goals:**

- Сопоставлять `goto` только с метками своего батча; устранить кросс-процедурные FP (39 → 0 на fa-generalledger).
- Полностью сохранить TP-семантику: обратный переход в одном батче, метка и goto в одной строке, файл без `go` = один батч.
- Не менять формат finding (rule/severity/message/object) и поведение остальных правил.

**Non-Goals:**

- Не расширять триггер на произвольный `GOTO` (forward-переходы молчат — закреплено тестом `label below goto - ok` и сценарием «Прямой переход с меткой ниже»).
- Не вводить детекцию дублей меток внутри одного батча (область компилятора T-SQL).
- Не менять регистрозависимость имён меток (существующее поведение).
- Не трогать логику зачистки комментариев и остальные 13 построчных сканеров.

## Decisions

- **D1. Граница батча = строка `go` на зачищенной строке.** Проверка на `cleanLine` (после зачистки комментариев и маскирования строк): `^go(\s+\d+)?$` по `strings.TrimSpace(strings.ToLower(cleanLine))`. TrimSpace обязателен: реальные файлы FA — CRLF, `strings.Split(content, "\n")` оставляет `\r` в конце строки (`"go\r"`), который `TrimRight(" \t")` или сравнение без снятия `\r` не устранили бы — граница молча не сработала бы на корпусе. Альтернативы отклонены: трекинг `DCL_PROC_BEGIN`/`__BEGIN_PROCEDURE__` (макросы варьируются между поколениями кода, а `go` — стандартный T-SQL-разделитель и присутствует вокруг каждой процедуры); сопоставление с ближайшей меткой (игнорирует семантику области видимости); строгое равенство `go` (форма `go N` — валидный T-SQL «повторить батч N раз», в корпусе 0 вхождений, но поддержка бесплатна). Расхождение с SQL-парсером (`sql_parser.go` использует строгое `EqualFold(trimmed, "go")`) — намеренное расширение; зафиксировать комментарием в коде.
- **D2. Форма реализации — минимальная правка существующего прохода.** В единственном цикле добавляется счётчик батча, инкрементируемый на границе; `gotoRef` и записи меток получают `batchID`. Finding формируется при `label.batchID == goto.batchID && labelLine <= gotoLine`; в переборе позиций метки несовпадение батча — продолжение перебора, `break` — только по первому подошедшему (свой батч) кандидату. Двухпроходная реструктуризация отклонена: всё нужное уже вычисляется в текущем проходе.
- **D3. Порядок проверок в строке.** Проверка границы выполняется после зачистки комментариев и маскирования строк — `go` в комментарии или строковом литерале батч не разделяет; `/* header */ go` закрывает блок, остаток `go` разделяет (согласовано с требованием «Закрытие блочного комментария шапки в сканерах…»).
- **D4. Goto без метки в своём батче** (метка только в чужом) — пропускается как «метка не найдена», finding не формируется. До правки такой случай тоже не давал finding (чужая метка ниже молчала); меняется только поведение для чужой метки выше — сам FP.
- **D5. Точность формулировки спеки.** Дельта MODIFIED фиксирует фактический триггер (метка выше/на строке перехода в том же батче) вместо широкой «использование GOTO и меток», расходившейся с поведением (тест `label below goto - ok`, wantCount 0).
- **D6. Макросы-завершители процедуры как граница батча (добавлено по итогам code-review R1, решение — Вариант A).** Дополнительный разделитель: `^(arc_proc_end|dcl_proc_end|proc_end)\s*\(` по `TrimSpace(ToLower(cleanLine))`. Обоснование: оба оставшихся после `go`-скопинга findings (archiver.sql:215, 406) — кросс-процедурные FP того же класса (границы процедур заданы `ARC_PROC_END` из `#include <archive.h>`, который replaceMacros не раскрывает; единственная `EXIT_PROC:` в батче `Arc_ClrRest` — @419, ниже gotos). Открывающая скобка обязательна: отличает вызов макроса `PROC_END(имя)` от строки-метки `PROC_END:` (Exponent_ShiftNumber.sql:101; метка `PROC_END:` входит и в раскрытие самого `DCL_PROC_END`). Вызовы без скобок в FA не встречаются (0 вхождений). Альтернатива «научить replaceMacros резолвить `#include`» отклонена как изменение, влияющее на все правила review, — выходит за рамки change. `DCL_PROC_BEGIN`/`ARC_PROC_BEGIN` разделителем не объявлены: `go` в их раскрытии предшествует `create procedure`, END достаточно для отсечения утечки меток.

## Risks / Trade-offs

- [Риск] «Законный» обратный переход через границу батча потеряется → невозможен в валидном T-SQL (метка невидима за пределами батча); не является реальным риском.
- [Риск] `go` внутри строкового литерала (`'go'`) ложно разделит батч → исключено D3 (проверка на `cleanLine` с маскированием строк).
- [Ограничение] Маскировка строк построчная (`inString` сбрасывается на каждой строке): `go` внутри литерала, растянутого на несколько строк, ошибочно разделит батч (риск FN, не FP). В валидном T-SQL литерал не переносится строкой и в Diasoft-корпусе не встречается; при появлении потребуется состояние `inString` между строками. Отдельный скоуп не заводится.
- [Риск] Файлы с процедурами без `go`-разделителей → обрабатываются как один батч, поведение идентично текущему (дубли меток в одном батче — ошибка компиляции T-SQL, не наша зона); в корпусе такие файлы для данного правила не встречались.
- [Трейд-офф] Уменьшение общего числа findings — ожидаемый эффект: 39 → 0 на fa-generalledger. По итогам code-review R1 оба findings, остававшихся после `go`-скопинга (archiver.sql:215, 406), переклассифицированы из TP в остаточные кросс-процедурные FP того же класса и устраняются макро-границей (D6); обратные переходы в одном батче по-прежнему флагаются (тест «label above goto within macro batch - finding»).
- [Риск] Линия `PROC_END:`-метки ложно распознается как макро-граница → исключено обязательной скобкой в `reProcEndMacroSeparator` (закреплено тестом «PROC_END label is not a batch separator»).
