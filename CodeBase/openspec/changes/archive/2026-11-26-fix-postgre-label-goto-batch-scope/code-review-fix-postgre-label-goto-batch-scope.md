## Замечания

### R1. Major: `archiver.sql:215/406` — остаточные кросс-процедурные FP, а не TP

Доказательная цепочка:

- В файле 6 процедур, заданных макросами: `ARC_PROC_BEGIN/END` — 18–89 `Arc_CalcObjectCountGL`, 95–158 `Arc_VerifyResultsGL`, 168–425 `Arc_ClrRest` и далее.
- Метки `EXIT_PROC:` — строки 84, 153, 419 (а также 544, 1080, 1183). Внутри `Arc_ClrRest` (168–425) единственная `EXIT_PROC:` — строка 419, т.е. **ниже** gotos 215 и 406.
- Значит реальные цели `goto EXIT_PROC`@215 и @406 — метка @419 (переход **вперёд**), который правило не должно флагать (тест `label below goto - ok`, сценарий «Прямой переход с меткой ниже»).
- Findings возникают из-за меток @84/@153 из **других процедур**: литеральных `go` между процедурами 1–3 нет (первый `go` — строка 427).
- Почему `go` там нет: `archive.h:162-166` определяет `ARC_PROC_END(proc_name)` разворачивающимся в строки, среди которых `go`; `archiver.sql:4` содержит `#include <archive.h>`. Но `replaceMacros`/`collectMacroDefinitions` (`review_parser.go:775`, `:799`) раскрывают только **in-file** `#define` и не резолвят `#include`, поэтому `ARC_PROC_END(...)` в анализируемом контенте остаётся литеральным вызовом и `go` не появляется.
- Итог: по модели правила процедуры 1–3 попадают в один «батч», метка @84/@153 считается видимой → FP того же класса, что и 37 удалённых. Гипотетическая проверка: если трактовать строки `ARC_PROC_END`/`PROC_END`/`DCL_PROC_END` как границу батча, `archiver.sql` даёт **0** findings (единственная `EXIT_PROC` в батче `Arc_ClrRest` — @419 ниже). То есть текущие 2 — остаточный FP.

Влияние: по количеству мало (2 из 39), но отчёт приёмки фактически неточен: «2 TP сохранены» → на деле «37 FP устранено, 2 FP того же класса остались». Цель «устранить кросс-процедурные FP» достигнута на 37/39, а не полностью.

Следствие по смыслу замечания (бинарно):

- **Вариант A (полный фикс, больше скоупа):** учитывать макросы-разделители `ARC_PROC_END`/`PROC_END`/`DCL_PROC_END` как границу батча (или научить `replaceMacros` резолвить include). Тогда `archiver.sql` → 0; требуется повторный корпусный прогон и уточнение дельта-спеки (разделитель — не только литеральный `go`).
- **Вариант B (минимальный, рекомендую для текущего change):** код **не менять** — он точно реализует согласованный D1 («литеральный `go` на анализируемом контенте»); исправить отчёт приёмки: `archiver.sql:215/406` — остаточные кросс-процедурные **FP**, не TP; внести ограничение в `design.md` (`## Risks / Trade-offs`) про макросы-разделители из include и завести кандидат-последователь (Вариант A).

### R2. Minor: неточная посылка в `design.md` (Context)

Фраза «Каждый `DCL_PROC_BEGIN` в корпусе окружён `go`-разделителями» верна только после раскрытия include. В анализируемом контенте `replaceMacros` include не резолвит, поэтому для файлов вида `archiver.sql` это утверждение неверно и как раз порождает R1. Решение: уточнить формулировку (разделитель виден только при литеральном `go`/in-file макросе; include-макросы не раскрываются) — согласуется с исправлением acceptance по R1.

### R3. Nit

Отдельный тест на `go` с хвостовым `-- комментарием` отсутствует; поведение корректно по построению (отсечение `--` до проверки границы). Не требуется.
