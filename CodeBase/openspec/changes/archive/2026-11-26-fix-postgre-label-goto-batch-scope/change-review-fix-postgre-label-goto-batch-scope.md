## Замечания

### B1. Блокер: CRLF — границу батча делать через `strings.TrimSpace`

Реальные SQL-файлы FA — CRLF: `Trunc_Inst.sql` содержит 501 CRLF и 0 одиночных LF. `strings.Split(content, "\n")` оставляет `\r` в конце строки, т.е. строка разделителя выглядит как `"go\r"`. Дизайн (D1) пишет «Trim» неоднозначно: если реализация сделает `TrimRight(s, " \t")` или сравнит с `"go"` без снятия `\r`, проверка `^go(\s+\d+)?$` **никогда не сработает на реальном корпусе** — правка молча не изменит поведение, и ожидаемое 39 → 2 не будет достигнуто.

Решение (принято): фиксировать в D1/tasks явно `strings.TrimSpace(strings.ToLower(cleanLine))` (TrimSpace снимает `\r`, `\t`, пробелы) и добавить table-driven кейс с CRLF (`"L:\r\nselect 1\r\ngo\r\ngoto L\r\n"` → 0 findings) в задачу 2.1.

### B2. Остаточное ограничение: `go` внутри многострочного строкового литерала

Маскировка строк в сканере построчная (`inString` переинициализируется на каждой строке), поэтому литерал, растянутый на несколько строк, не маскируется, и строка `go` внутри него ошибочно разделит батч (риск нового FN, а не FP). В `Risks` дизайна покрыт только однострочный `'go'`.

Решение (принято как ограничение, не блокер): добавить в `## Risks / Trade-offs` пункт про многострочные литералы с пометкой «в Diasoft-генерённом коде не встречается; при появлении — потребуется состояние `inString` между строками». Отдельный скоуп на это не заводить.

### B3. Не блокер: `go N` расходится с определением батча в SQL-парсере

Парсер (`sql_parser.go:826,1327`) считает разделителем строго `strings.EqualFold(trimmed, "go")` (без `go N`), а дизайн вводит `^go(\s+\d+)?$` — более широкое правило. Это осознанное расширение (D1: 0 вхождений в корпусе, поддержка бесплатна), ломающего эффекта нет. Обоснование принимается; желателен однострочный комментарий в коде, что расхождение с парсером намеренное.

### B4. Минор: команда приёмки 3.2 не устраняет UTF-16

`cmd /c rg ... > Tests\Temp\gl_goto_files.txt` в PowerShell: `>` разбирает сама PowerShell (до передачи в `cmd`), поэтому файл всё равно получится UTF-16 и `--files` сломается. Перенаправление должно быть **внутри** строки `cmd`, иначе смысл `cmd /c` теряется.

Решение (принято): в задачи 3.2 записать
`cmd /c "rg -l --glob *.sql -i \bgoto\b D:\GITHUB\GolandProjects\FA\fa-generalledger > Tests\Temp\gl_goto_files.txt"`.

### B5. Минор: уточнить цикл сопоставления

При добавлении `batchID` к записям меток и `gotoRef` условие finding должно быть `label.batchID == goto.batchID && label.line <= goto.line`, а `break` — только по первому подходящему (свой батч) кандидату. Иначе возможен пропуск/дубль finding. Дизайн D2 это подразумевает; фиксируется как чек-пункт реализации, отдельной правки артефакта не требует.

### B6. Минор: README обновлять обязательно, а не «при необходимости»

Текущая строка README (`README.md:1085`, «`postgreLabelGotoLevel` — использование `GOTO` и меток») после правки становится неточной: правило ловит только обратный переход к метке выше в том же батче. Задача 4.1 оставлена опциональной («при необходимости»).

Решение (принято): сделать 4.1 обязательной с формулировкой «обратный переход `GOTO` к метке выше перехода в том же батче».

### B7. Нит: нет сценария для `go N`

Требование (дельта) допускает `go N`, но сценария на него нет; тест в 2.1 есть. Достаточно, т.к. минимум один сценарий под требованием соблюдён; при желании добавить сценарий «`go N` разделяет батчи».
