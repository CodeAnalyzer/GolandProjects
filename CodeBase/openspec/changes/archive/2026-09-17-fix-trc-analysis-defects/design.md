## Context

См. `proposal.md` — Why. TRC runtime имеет два пути: сохранённая сессия использует PostgreSQL-запросы, а `file_path` — срез разобранных `TRCEvent`. Сейчас эти пути расходятся в формуле длительности и enrichment. Выборка событий ограничивается до вычисления `filtered_count`, а TRC handlers в MCP часто отбрасывают ошибки `optional*` helpers.

Изменение затрагивает `internal/trc`, `internal/trcsvc`, MCP registry и CLI-представление результатов, но не меняет парсеры, таблицы или сохранённые данные.

## Goals / Non-Goals

**Goals:**

- Получать одинаковые агрегаты для одинаковых событий в PostgreSQL и Go.
- Сделать `count` числом завершённых вызовов процедур, а не числом событий с извлечённым именем.
- Разделить полное число совпадений и размер ограниченной выдачи событий.
- Не терять enrichment процедур из-за позиции их событий в сессии.
- Возвращать ошибки некорректных optional-аргументов всех существующих TRC MCP handlers.

**Non-Goals:**

- Добавление `event_scope`, фильтра агрегации по SPID или новых классов агрегации.
- Курсорная/offset-пагинация и расширение набора фильтров событий.
- Compare-procedures, SPID summary и анализ незавершённых Starting-событий.
- Изменение парсеров, схемы PostgreSQL, индексов или повторный парсинг сессий.
- Исправление обработчиков query, RTI, review и других MCP-профилей.

## Decisions

### 1. Одна completed-only семантика на уровне агрегаторов

`AggregateByProcedure` в file-mode пропускает все события, кроме `EventName == "SP:Completed"` с непустым `Procedure`. `LoadProceduresAggregated` добавляет эквивалентный SQL-предикат `event_name = 'SP:Completed'`. Отдельный параметр scope не вводится, поэтому CLI и MCP используют одну семантику.

Альтернатива — фильтровать события только в `ExecuteProcedures`. Она отклонена: низкоуровневые агрегаторы могли бы по-прежнему использоваться с разной семантикой, а parity было бы сложнее гарантировать.

### 2. Нулевая длительность участвует во всех метриках

В Go accumulator учитывает каждое выбранное значение `DurationMs`, включая 0: первый элемент инициализирует min/max, сумма делится на полный count. SQL использует обычные `sum`, `min`, `max`, `avg` без `FILTER (WHERE duration_ms > 0)`. Поскольку `trc_events.duration_ms` имеет `NOT NULL DEFAULT 0`, дополнительная обработка NULL не требуется, но `COALESCE` для пустого результата может сохраняться.

Альтернатива — исключить нулевые значения и в обоих режимах. Она отклонена: 0 является валидным результатом округления короткой длительности до миллисекунд, а исключение завышает среднее.

### 3. Фильтрация и подсчёт событий используют один предикат

Для saved-session серверный слой получает отдельную операцию подсчёта событий с тем же `TRCEventFilter`, что и ограниченная выборка. Построение SQL `WHERE` и аргументов выносится в общий внутренний helper, чтобы `SELECT rows` и `SELECT count(*)` не расходились при дальнейших изменениях существующих фильтров. Ошибки обоих count-запросов возвращаются вызывающему коду.

Для file-mode цикл просматривает все события: увеличивает `filtered_count` для каждого совпадения, но добавляет в результат только первые `limit`. Досрочный `break` после заполнения результата удаляется. `returned_count` всегда равен `len(events)`.

`total_count` остаётся числом всех событий источника; `filtered_count` считается без учёта `limit`. Пагинация отсутствует, поэтому неоднозначности относительно cursor нет.

Альтернатива — вычислять `filtered_count` как `len(events)` и только переименовать поле. Она отклонена, поскольку не исправляет невозможность узнать полный размер результата.

### 4. Enrichment строится по именам итоговых агрегатов

В `internal/trc/enrich.go` выделяется функция enrichment уникального списка имён процедур, переиспользующая существующие лимиты worker-ов и `EnrichProcedure`. `EnrichEvents` преобразует события в уникальные имена и делегирует этой функции. `ExecuteProcedures` в обоих режимах передаёт имена из уже рассчитанного `[]TRCProcAgg`, после чего применяет `EnrichAggregates`.

Это удаляет запрос первых 1000 произвольных событий saved-session и гарантирует одинаковый набор lookup-ов в обоих режимах. Ошибка отсутствия отдельной процедуры остаётся мягкой и даёт `Found=false`, как сейчас; ошибка всего процесса агрегации не создаётся.

Альтернатива — загружать из БД по одному sample-событию для каждой агрегированной процедуры. Она отклонена как лишняя зависимость enrichment от `trc_events` и дополнительный SQL-путь, отсутствующий в file-mode.

### 5. Строгая обработка optional-аргументов ограничена TRC handlers

Каждый TRC handler последовательно проверяет `error` от `optionalInt`, `optionalInt64` и `optionalString` до вызова `trcsvc`. TRC-параметр `limit` читается через helper, способный вернуть ошибку, вместо `optionalLimit`, который молча подставляет default при неверном типе. После успешного разбора существующая нормализация default/max остаётся в сервисном слое.

Числовые helpers отвергают JSON-числа с дробной частью и переполнением вместо усечения. Изменение самих helpers допустимо как усиление общей примитивной валидации, но систематическая переделка и тестирование non-TRC handlers не входят в change; только TRC handlers обязаны обработать возвращённую ошибку.

Альтернатива — создать копии helpers только для TRC. Она отклонена из-за дублирования правил разбора одних и тех же MCP-типов.

### 6. Коррекция контракта результата без пагинации

В `EventsResult` добавляется `ReturnedCount int` с JSON-именем `returned_count`. Поле присутствует в ответе всегда, включая пустой результат. CLI использует `ReturnedCount` для текста о количестве выведенных событий и отдельно показывает `FilteredCount`, не представляя ограниченную выдачу как полный результат.

## Risks / Trade-offs

- [Breaking change: агрегаты уменьшатся после исключения statement-событий] → отметить изменение в proposal и покрыть тестом смешанный набор `SP:Completed`/statement events.
- [Трейс без `SP:Completed` вернёт пустую агрегацию, даже если содержит RPC или statement events] → это намеренная семантика данного bugfix; настраиваемый scope остаётся отдельным будущим изменением.
- [Точный `COUNT(*)` добавляет запрос и стоимость для `trc events`] → использовать существующие индексируемые колонки фильтра; не загружать дополнительные строки в Go для saved-session.
- [File-mode обязан просмотреть весь файл после заполнения limit] → файл уже полностью разобран в память до фильтрации, поэтому меняется только линейный проход, необходимый для точного count.
- [Enrichment всех агрегатов создаёт больше lookup-запросов, чем sample первых 1000 событий] → дедупликация имён и существующий ограниченный worker pool предотвращают повторные и неограниченные запросы.
- [Усиление общих numeric helpers может затронуть malformed-вызовы других профилей] → корректные integer-вызовы не меняются; regression scope обработчиков и тестов ограничивается TRC.

## Migration Plan

1. Выпустить изменение как корректирующую смену семантики `codebase_trc_procedures` и `trc procedures`.
2. Повторный парсинг сессий и миграция БД не требуются: необходимые `event_name`, `procedure` и `duration_ms` уже сохранены.
3. При откате вернуть прежние предикаты агрегации и поля runtime; данные остаются совместимыми в обе стороны.
