# MCP Tool Profiles — Design

## Context

MCP-сервер CodeBase использует `github.com/modelcontextprotocol/go-sdk/mcp` SDK. Все инструменты регистрируются через `server.AddTool` в цикле по `buildToolRegistry(db)`. На запрос `tools/list` SDK возвращает JSON с описанием всех зарегистрированных инструментов. При 55 инструментах с `outputSchema` размер response составляет ~43 KB. Некоторые IDE MCP-клиенты имеют лимиты на размер JSON-RPC сообщения, что приводит к обрезке списка и недоступности инструментов для ИИ-агента.

Текущая точка входа: `cmd/mcp.go` → `mcp.RunStdio(version, commandLogger)` → `buildToolRegistry(db)` → цикл `server.AddTool`.

## Goals / Non-Goals

### Goals

- Один бинарник, несколько MCP-серверов в конфигурации IDE с разными профилями.
- Каждый профиль укладывается в лимиты IDE по размеру `tools/list`.
- Обратная совместимость: `codebase mcp` без флага работает как раньше (все 55 инструментов).
- Базовые инструменты (`ping`, `health`, `stats`, `read_more`) доступны во всех профилях.

### Non-Goals

- Динамическое включение/выключение инструментов через конфиг — только статические профили.
- Объединение query-инструментов в один универсальный — отдельная доработка.
- Удаление `outputSchema` — отдельная доработка (но профили сами по себе сокращают размер).
- Пагинация `tools/list` response — не поддерживается MCP-протоколом.

## Decisions

### 1. Флаг `--profile` на команде `mcp`

**Решение:** `codebase mcp --profile=rti` (строковый флаг, без default — отсутствие флага означает регистрация всех инструментов).

**Альтернатива:** подкоманды `codebase mcp-rti`, `codebase mcp-trc` — отвергнута: загрязняет namespace CLI, больше кода, менее гибко.

### 2. Маппинг профиль → инструменты

**Решение:** Статическая map `profileToolSets` в `registry.go`:

```go
var baseTools = map[string]bool{
    "codebase_ping": true, "codebase_health": true,
    "codebase_stats": true, "codebase_read_more": true,
}

var profileToolSets = map[string]map[string]bool{
    "query":  merge(baseTools, queryTools),
    "rti":    merge(baseTools, rtiTools),
    "trc":    merge(baseTools, trcTools),
    "review": merge(baseTools, reviewTools),
}
```

При пустом `profile` (флаг не указан) — все инструменты без фильтрации. Иначе — фильтрация registry по whitelist из `profileToolSets[profile]`.

**Альтернатива:** префиксный матчинг (`codebase_rti_*` для профиля `rti`) — отвергнута: хрупко, не позволяет включить `read_more` в RTI-профиль без отдельной логики.

### 3. Базовые инструменты во всех профилях

**Решение:** `ping`, `health`, `stats`, `read_more` включены в каждый профиль. `read_more` нужен для пагинации больших ответов, `ping`/`health` — для диагностики.

### 4. Фильтрация на уровне registry, не SDK

**Решение:** `buildToolRegistryForProfile(db, profile)` возвращает отфильтрованный map. SDK получает только нужные инструменты — `tools/list` автоматически содержит только их.

### 5. Ошибка при неизвестном профиле

**Решение:** `RunStdio` возвращает ошибку с перечислением валидных профилей. CLI выводит её через стандартный механизм Cobra.

### 6. Профиль в логировании tool-вызовов

**Решение:** `logMCPToolCall` добавляет поле `profile=%s` в каждую запись лога. При запуске без `--profile` пишется `profile=all`. Это позволяет отличить записи от разных MCP-серверов при одновременном запуске нескольких профилей в одной IDE.

## Risks / Trade-offs

- **Профиль не содержит нужный инструмент** — пользователь должен выбрать правильный профиль. Митигация: без флага доступны все инструменты, IDE может подключить несколько профилей одновременно.
- **Дублирование БД-подключений** — каждый MCP-сервер (профиль) открывает своё подключение к PostgreSQL. При 4 профилях — 4 коннекта. Митигация: `pgx` pool, `max_connections` в конфиге.
- **Рассинхронизация profileToolSets и registry** — новые инструменты могут не попасть в профиль. Митигация: тест, проверяющий что все инструменты из registry присутствуют хотя бы в одном профиле.
- **Конкурентная запись в лог-файл** — несколько процессов (разные профили) пишут в один `codebase_YYYYMMDD.log` с `O_APPEND`. Митигация: `profile=%s` в каждой записи позволяет отличить процессы; `log.Logger` использует mutex для атомарности `Write` внутри процесса.
