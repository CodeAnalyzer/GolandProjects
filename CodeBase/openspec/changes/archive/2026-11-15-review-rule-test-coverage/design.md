## Context

См. `proposal.md` — Why. Текущее состояние тестового слоя review:

- 59 правил в `internal/review/types.go` / `catalog.go`.
- 32 правила имеют прямой unit-тест; из них 30 покрывают оба кейса, `diffTypesComparison` — только positive, `foreignProcedureUsing` — только negative.
- Критерий «прямого unit-теста»: unit-файл (без тега `integration`) применяет правило целиком — вызывает check-функцию либо её statement-анализатор (`analyze*`/`extract*`) — и проверяет Rule ID, количество и/или Object. Тест чистой helper-функции без проверки Rule ID прямым покрытием не считается.
- 27 правил без прямого unit-теста: 12 покрыты helper-тестами с обеими сторонами, 7 — helper-тестами без проверки логики правила, 4 — только integration-тестами (`execNotExistsProc`, `procDuplicate`, `memoryUniqueIndexUpdate`, `foreignTablesUsing`), 4 — без тестов вообще (`procElseCase`, `truncTbl`, `useSelectAll`, `indexExistsInDB`).
- `TestEnabledRuleSet_*` есть для всех правил, но проверяет только состав набора и не считается покрытием поведения.
- Уже существует удачный приём: `newAPIRuleRunner` подкладывает `procProductIDCache` и `reviewExecContext`, позволяя тестировать API-правила без БД.

## Goals / Non-Goals

**Goals:**

- Довести каждое из 59 правил до unit-теста с positive+negative в обычном прогоне без БД.
- Переиспользовать существующие helper-тесты как основу, добавляя недостающий уровень «правило целиком».
- Сделать тесты устойчивыми к формулировкам сообщений: проверять правило, severity, количество и якорь строки, а не текст сообщения.
- Не дублировать уже существующее покрытие 30 правил с обоими кейсами.

**Non-Goals:**

- Не менять поведение и состав правил (допускаются только nil-guard'ы в lookup-ах при `db == nil` и тестовый seam в `checkDatatypeExecParams`, см. Decision 2).
- Не заменять integration-тесты (`review-scope`, ветки продуктов, индексы в БД) — они остаются для сквозной проверки.
- Не вводить внешние тестовые библиотеки и не менять CI-команды.
- Не добиваться 100% покрытия строк — цель по правилам, а не по метрике.

## Decisions

**1. Тестировать на уровне check-функции, а не полного Runner с БД.**
Для правил, не зависящих от БД, тест вызывает `Runner.checkX` с подготовленным `reviewExecContext` (content, lines, macroResult). Это быстрее, детерминированно и уже принято в `review_rules_test.go`. Альтернатива — всегда гонять `RunSQLFileCtx` с реальной БД — отклонена: медленно и требует integration-тег.

**2. Для зависимостей от метаданных — поля-кэши Runner и тестовые подмены.**
Правила `execNotExistsProc`, `procDuplicate`, `foreignTablesUsing`, `foreignProcedureUsing`, `memoryUniqueIndexUpdate`, `indexExistsInDB`, `deferredUpdate` тестируются через предзаполненные кэши: владельцы процедур — `procProductIDCache`, владельцы таблиц — `tableProductIDCache`, индексы — `indexCandCache`/`indexFieldsCache`, память — `memoryTableCache`. Образец — `newAPIRuleRunner`. Альтернатива — sqlmock/реальная БД — отклонена: лишняя зависимость и хрупкость.

Три lookup-а не имеют nil-guard и паникуют на cache miss при `db == nil`: `findAPITableNames` (используется `foreignPTablesUsing`), `lookupProcedureCreateFiles` (используется `procDuplicate`) и `cachedFindColumnDefinitionType` (используется datatype-ветками). Для них добавляются nil-guard'ы (`if r.db == nil { return ... }`) — это тестовый seam, согласованный с деградацией остальных cache-lookup'ов; при не-nil `db` поведение не меняется. Дополнительно `checkDatatypeExecParams` выходит при `db == nil` только если не задан `procParamsCache`, иначе ветка тестируется на предзаполненном каталоге параметров. Это единственные правки прод-кода в change.

**3. Единый table-driven хелпер для новых тестов.**
Вводится тестовый помощник вида `runRuleCases(t, ruleID, checkFn, []struct{name, content string; wantCount int; wantLine int; wantObject string})`. Он проверяет count, rule ID, severity и (опционально) строку/объект. Это снижает разнобой и гарантирует, что каждый набор содержит и `wantCount>0`, и `wantCount=0`. Существующие отдельные тесты не переписываются.

**4. Приоритет и группировка задач.**
Порядок: сначала 4 правила без тестов, затем 7 без rule-specific проверок, затем 4 integration-only, затем 12 helper-only, затем 2 односторонних. Такой порядок закрывает самые рискованные участки первыми. Группы «7 без rule-specific» и «12 helper-only» обе означают отсутствие rule-level теста; они разделены по характеру существующих helper-тестов (есть обе стороны vs нет проверки логики правила) и одинаковы по объёму работы.

**5. Negative-кейс обязателен и должен быть «соседним».**
Negative-кейс подбирается максимально близким к positive (например, то же выражение с корректным фильтром/алиасом), чтобы ловить FP, а не только smoke-отсутствие срабатывания. Для правил с макросами добавляется кейс с token-paste/раскрытием.

## Risks / Trade-offs

- [Тесты начнут проверять текст сообщений и станут хрупкими] → проверять `Rule`, `Severity`, `Line`, `Object`; текст сообщения — только через подстроку и лишь там, где смысл сообщения является контрактом.
- [Дублирование существующих helper-тестов] → в задачах фиксируется, какие helper-тесты уже есть, и добавляется только уровень правила.
- [Fake-кэши не отражают реальные SQL-резолвы] → scope/branch-логика остаётся на integration-тестах; unit-тесты проверяют только решение правила при заданных метаданных.
- [nil-guard в lookup-ах замаскирует отсутствие БД в проде] → guard срабатывает только при `db == nil`; в проде Runner всегда создаётся с БД, а guard покрыт отдельным unit-тестом.
- [Большой объём изменений в тестах] → изменения изолированы в `*_test.go`, не влияют на прод-код и могут идти пакетами по группам.
- [Тест выявит реальный дефект правила] → фиксируется отдельным change/fix; в рамках этого изменения тест помечается как ожидаемое падение нельзя — вместо этого задача блокируется до отдельного исправления.

## Migration Plan

Изменения в тестовом слое: поэтапное добавление тестов по группам, после каждой группы — `go test ./internal/review/...` и `go vet ./internal/review/...`. Прод-код затрагивается только nil-guard/seam-правками из Decision 2 (при не-nil `db` поведение не меняется). Откат — удаление добавленных тестовых файлов/кейсов; guard'ы можно оставить как nil-safe деградацию либо снять вместе с тестами.
