## Context

`FindMethodsByTable` (`internal/query/query_sql.go:377-419`) — единственное место в
`internal/query`, где встречена двухходовая цепочка JOIN'ов
`pas_methods → relations(r_query) → query_fragments → relations(r_table) → sql_tables`.
Запрос не содержит ни `DISTINCT`, ни `GROUP BY`, ни Go-дедупликации, поэтому
декартово произведение по промежуточным связям множит строки: каждый
query-фрагмент метода, ссылающийся на искомую таблицу, даёт отдельную строку
(плюс возможное пересечение `executes_query` ∩ `builds_query` на один фрагмент).

Контекст, влияющий на решение:
- `SELECT DISTINCT` — уже принятый паттерн в этом же файле (`:87`, `:125`, `:160`).
- Фильтр `LIMIT $2` применяется в SQL **до** Go-сканирования, поэтому Go-side
  дедупликация сама по себе не решает проблему «лимит съеден дубликатами».
- `MethodResult.TableUsage` заполняется из `st.table_name`.
- DB-тесты `internal/query` — интеграционные (`//go:build integration`,
  `store/testutil`); unit-тесты покрывают чистые query-building helpers.

См. `proposal.md` (Why) и `Bug-reports/BUG-methods-by-table-duplicate-rows-20261011.md`.

## Goals / Non-Goals

**Goals:**
- Одна строка на уникальный PAS-метод в `query methods --table` и корректный `count`.
- Минимальное, идиоматичное изменение, не затрагивающее форму ответа.
- Регрессионное покрытие, падающее до фикса и проходящее после.

**Non-Goals:**
- Изменение схемы БД/индексатора (данные корректны).
- Изменение JSON-контракта, полей `MethodResult` или семантики `--limit`.
- Рефакторинг цепочки JOIN'ов в `EXISTS` (рассмотрен как альтернатива, отклонён).
- Прочие инструменты (`FindCallers` и др. — fan-out не подтверждён).

## Decisions

### D1. Дедупликация — `SELECT DISTINCT` в SQL, а не в Go

Все выбираемые колонки функционально зависят от `pm.id`, кроме `st.table_name`,
зафиксированной условием `WHERE LOWER(st.table_name) = LOWER($1)`. Поэтому
`DISTINCT` схлопывает строки одного метода.

**Почему не Go-дедуп:** `LIMIT $2` вычисляется до передачи строк в Go — при
`limit=N` дубликаты расходуют лимит, и уникальных методов вернётся меньше N.
Дедупликация обязана происходить в SQL.

**Совместимость:** `DISTINCT` + `ORDER BY pu.unit_name, pm.method_name, pm.line_number`
корректен — все ORDER BY-выражения присутствуют в select-list (требование PostgreSQL).

### D2. Отклонён `GROUP BY pm.id`

PostgreSQL выводит функциональную зависимость только для колонок той таблицы,
чей PK сгруппирован. `pc.class_name` (`pas_classes`), `pu.unit_name` (`pas_units`),
`f.rel_path` (`files`), `st.table_name` (`sql_tables`) принадлежат другим таблицам,
их PK не сгруппированы → запрос с `GROUP BY pm.id` упадёт с
`column ... must appear in GROUP BY`. (Замечание в баг-репорте о допустимости
`GROUP BY` по PK здесь неприменимо.)

### D3. Отклонён `EXISTS`-подзапрос

`WHERE EXISTS (...)` структурно устраняет fan-out, но убирает `st.table_name` из
select-list: `TableUsage` пришлось бы заполнять из входного `tableName` в Go
(эхо запроса вместо значения из БД), что расширяет дифф и меняет источник поля без
необходимости. Для одной таблицы в `WHERE` выгода не оправдана.

### D4. Тест — интеграционный (`//go:build integration`)

Регресс требует БД: сценарий «метод + два query-фрагмента на `tAim` → одна
строка» проверяется на реальной схеме через `store/testutil`, по образцу
`query_relations_integration_test.go`. Вынос SQL в helper ради проверки строки на
`DISTINCT` отклонён как «улучшение ради улучшений» — слабая проверка реализации.

## Risks / Trade-offs

- **[Крайний случай регистра]** Если два физических ряда `sql_tables` с одним
  именем в разном регистре будут привязаны к одному методу, `DISTINCT` даст 2
  строки. На практике `references_table` привязывает фрагмент к конкретному
  `target_id`, поэтому fan-out — от числа фрагментов. → Приемлемо; при
  необходимости отдельная задача «фильтр по одному table id».
- **[Покрытие без БД]** Интеграционный тест не входит в `go test ./...` без
  `-tags integration` — регресс виден только при прогоне интеграционных тестов.
  Это существующая конвенция проекта для DB-зависимых query-тестов. → Принять;
  при желании добавить лёгкий unit-assert на текст запроса отдельной задачей.
- **[Дрейф ожидания TC-056]** Без правки `Tests/TEST_CASES.md` кейс останется
  FAIL из-за ожидания `count=3` вместо `count=2`. → Включено в tasks.
