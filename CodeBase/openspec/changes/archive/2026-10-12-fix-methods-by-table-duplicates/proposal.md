## Why

`query methods --table` / MCP `codebase_query_methods` (SQL `FindMethodsByTable`,
`internal/query/query_sql.go:377-419`) возвращает задвоенные строки на один и тот
же PAS-метод: запрос соединяет цепочку «метод → query-фрагменты → таблица» без
дедупликации, поэтому каждый query-фрагмент метода, ссылающийся на искомую
таблицу, умножает строку результата. Это даёт некорректный `count`, дубли в
выдаче агенту и неполный результат при `limit` (лимит расходуется на дубликатах).
Данные индекса корректны — дефект только в SQL инструмента (обнаружено при
прогоне TC-056, см. `Bug-reports/BUG-methods-by-table-duplicate-rows-20261011.md`).

## What Changes

- `FindMethodsByTable` возвращает ровно одну строку на уникальный PAS-метод,
  независимо от количества query-фрагментов метода, ссылающихся на искомую
  таблицу.
- Модифицируется требование «Поиск PAS-методов» в `query/entity-queries`:
  добавляется гарантия уникальности строк и сценарий дедупликации.
- Добавляется регрессионный тест: метод с двумя query-фрагментами на одну
  таблицу → одна строка.
- Актуализируется ожидание TC-056 в `Tests/TEST_CASES.md` (`count=3` → `count=2`),
  устранён дрейф ожидания.

Не breaking change: форма ответа (поля, JSON-конверт) не меняется, меняется только
устранение дубликатов и корректность `count`.

## Impact

- **Код**: `internal/query/query_sql.go` — `FindMethodsByTable` (SQL-запрос);
  новые тесты в `internal/query/`.
- **Интерфейсы**: CLI `query methods --table` (`cmd/query_commands.go:167`),
  MCP `codebase_query_methods` (`internal/mcp/registry.go:482`). Контракт вывода
  не меняется, `count` становится корректным.
- **Данные/БД**: изменений схемы нет; индексированные данные корректны.
- **Зависимости**: новые зависимости не добавляются.
- **Тест-артефакты**: `Tests/TEST_CASES.md` (TC-056).
