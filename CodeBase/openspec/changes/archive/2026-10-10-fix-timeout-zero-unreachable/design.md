# Design: fix-timeout-zero-unreachable

## Context

См. `proposal.md` — Why. Текущее состояние кода:

- `internal/config/config.go`: 4 поля — `RTIConfig.ParseTimeoutSec`, `TRCConfig.ParseTimeoutSec` (int, дефолт 300), `MCPConfig.QueryTimeoutSec` (30), `MCPConfig.ReviewTimeoutSec` (120). `Load()` нормализует `<= 0` в дефолты (строки 328–341, 366–371); `CreateDefault()` дублирует значения явно. Комментарии полей (`config.go:59,67`) уже обещают «(0 = без таймаута)» — ложь относительно поведения `Load()`.
- `internal/mcp/server.go`: единственный потребитель — `timeoutForTool` (108–119) возвращает `time.Duration`; обвязка в `registerSDKCoreTools` (88–94) применяет `WithTimeout` только при `timeout > 0`. Ветка «0 = без таймаута» реализована, но из конфиг-файла недостижима: `codebase mcp` всегда идёт через cobra `initConfigE()` → `config.Load()`.
- Тесты: `internal/mcp/server_test.go:676–752` — 5 тестов на `timeoutForTool`, все конструируют `Config` литералом, минуя `Load()`. `internal/config/config_spec_test.go:11–27` — прецедент правильной методологии (`writeTestConfig`: TOML-файл → `Load()`).

Ограничение, определяющее подход: go-toml v2 не может различить «ключ отсутствует» и «явный 0» для plain `int` — оба дают 0. Для `*int` отсутствующий ключ оставляет `nil`, присутствующий аллоцирует указатель. Паттерн уже обкатан в этом же файле: `SpecConfig.LSARetrainThreshold *int` («nil = 100, явный 0 = переобучать всегда», `config.go:90`), `LSAMinCosine`/`LSARelativeCutoff *float64` («0 = без фильтра»), с отклонением отрицательных/внедиапазонных значений в `Load()` и зелёными тестами.

## Goals / Non-Goals

**Goals:**

- Явный `0` в `codebase.toml` для 4 параметров таймаутов доезжает до `timeoutForTool` и отключает таймаут.
- Отсутствие параметра и явный `0` — разные состояния с разной семантикой (дефолт vs отключено).
- Отрицательные значения — fail-fast при загрузке конфига с именем параметра в ошибке (сегодня молча становятся дефолтом).
- Тест новой семантики проходит через `Load()` с реальным TOML-файлом (контракт конфиг-файла, а не структуры).

**Non-Goals:**

- Не вводим единую generic-механику «троичных настроек» для всех параметров конфига — меняем ровно 4 поля, где `0` осмыслен.
- Не трогаем остальные `<= 0`-нормализации в `Load()` (slow_threshold_ms и пр. — там `0` не имеет семантики отключения).
- Не добавляем per-tool конфигурацию таймаутов для отдельных инструментов (спектр: только существующие 4 параметра).
- Не меняем поведение при прямом программном конструировании `Config` вне `Load()` — там действуют те же правила разрешения (nil → дефолт).

## Decisions

### D1: `*int` вместо `int` — три состояния (домашний паттерн spec-LSA)

4 поля становятся `*int` с тегом toml без изменений. Семантика: `nil` = не задано → дефолт; указатель на `0` = отключено; указатель на `N > 0` = N секунд.

Альтернативы:
- *Sentinel-значение* (например, `-1` = отключить): не требует смены типа, но несовместимо со спеками («`0` означает отсутствие таймаута») и с уже написанным потребителем; ломает эргономику.
- *Вариант B (правка спек под код)*: отвергнут — хоронит полезную и уже реализованную семантику; противоречие врождённое (change 2026-09-03 записал его в спеки при реализации нормализации), чинить надо код, а не обещание.

Выбор `*int` следует прецеденту `SpecConfig`/`DescLSAConfig` в том же файле — новый читатель кода встречает уже знакомый паттерн.

### D2: nil НЕ нормализуется в `Load()` — дефолт резолвит потребитель

`Load()` удаляет `<= 0`-нормализацию этих 4 полей и вместо неё добавляет только валидацию: явное отрицательное значение → `fmt.Errorf` с именем параметра (по образцу `config.go:388–390`: `spec.lsa_retrain_threshold must be >= 0, got %d`). Разрешение `nil` → дефолт выполняет `timeoutForTool` (`internal/mcp/server.go`) через nil-чек.

Альтернатива: нормализация в `Load()` (nil → указатель на 300). Отвергнута по двум причинам: (1) рассинхрон с домашним паттерном — spec-LSA применяет дефолты через геттеры, «дефолт применяется через геттер», `config.go:386–387`; (2) литералы `Config{}` в тестах `server_test.go` и любом будущем коде будут содержать `nil`, поэтому читателю нужен nil-чек независимо от того, нормализует ли `Load()` — нормализация не экономит код, но добавляет вторую точку истины для дефолтов.

Побочный эффект принят: после `Load()` поле может остаться `nil` (в отличие от spec-LSA, где то же самое). `Save()` сериализует `nil` как отсутствие ключа — round-trip стабилен; `CreateDefault()` (см. D3) выдаёт явные значения, поэтому `init`-шаблон конфига содержит числа.

### D3: `CreateDefault()` — явные дефолты, не `nil`

`CreateDefault()` инициализирует поля указателями на 300/300/30/120. Генерируемый `init`-ом `codebase.toml` остаётся самодокументированным, а поведение «стартовый конфиг» не зависит от разрешения nil.

### D4: комментарии полей синхронизируются с новой семантикой

`config.go:59,67`: «(0 = без таймаута)» → «nil = 300, явный 0 = без таймаута» (и аналогично для `QueryTimeoutSec`/`ReviewTimeoutSec`: «nil = 30/120, 0 = без таймаута»). Это третье место ложного обещания после двух спек — фиксируем в tasks, чтобы не потерялось.

### D5: тест-методология — TOML → `Load()`, не литерал структуры

Новые тесты конфига используют `writeTestConfig`-подход из `config_spec_test.go` (временный TOML-файл → `Load()` → `Get()`). Хелпер `writeTestConfig` принимает произвольную секцию строкой, поэтому подходит для `[rti]`/`[trc]`/`[mcp]` без изменений. Существующие тесты `TestTimeoutForTool_*` в `internal/mcp/server_test.go` сохраняются как defensive-контракт `timeoutForTool`, но литералы переводятся на указатели (`ParseTimeoutSec: intPtrLocal(300)` — локальный хелпер, т.к. `intPtr` из config непроэкспортирован).

## Risks / Trade-offs

- [Появление второго читателя полей без nil-чека → паника разыменования] → Mitigation: комментарий на каждом поле фиксирует контракт «nil = дефолт»; grep-проверка в tasks (читатель один — `timeoutForTool`); тесты конструируют литералы с nil-полями.
- [`query_timeout_sec = 0` снимает таймаут со всех не-parse инструментов — пользователь может подвесить MCP-клиент] → Mitigation: это осознанная семантика, задокументированная в спеке (сценарий «Query-таймаут отключён»); значение по умолчанию не меняется.
- [Менее заметная ошибка конфига: раньше `-5` молча давало рабочий дефолт, теперь старт падает] → принято сознательно (fail-fast, единообразно с spec-LSA); сообщение ошибки называет параметр.
- [`Save()` после `Load()` конфига с отсутствующими ключами выпишет их без таймаут-полей] → безвредно: round-trip семантичен, отсутствие = дефолт.
- [Механическая правка литералов в `server_test.go` может пропустить новые места] → Mitigation: компилятор ловит несоответствие типов `int` vs `*int` — правка не может быть неполной, только неточной.

## Migration Plan

Изменение обратно совместимо для корректных конфигов (без ключей / положительные значения — поведение идентично). Конфиги с явным `0`: раньше молча дефолт, теперь отключение — именно заявленная цель; конфиги с отрицательными значениями (сегодня неработоспособные по смыслу) начинают отклоняться с внятной ошибкой. Откат — реверт коммита, миграции данных нет.
