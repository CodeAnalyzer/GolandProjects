# Proposal: fix-timeout-zero-unreachable

## Why

Две спеки (`infrastructure/configuration`, `mcp-server/mcp-transport-tools`) и комментарии полей в `internal/config/config.go` обещают «`0` = отключить таймаут», но `Load()` нормализует `<= 0` в дефолты (300/30/120), поэтому документированное поведение недостижимо через `codebase.toml` (BUG-mcp-timeout-zero-unreachable-20261009). Противоречие врождённое: change `2026-09-03-add-parse-timeout-config` одновременно записал это обещание в спеки и реализовал затирающую нормализацию. Потребитель (`timeoutForTool`) ветку «0 = без таймаута» уже реализует и тестирует — семантике не хватает только возможности доехать из конфиг-файла.

## What Changes

- 4 поля таймаутов (`RTIConfig.ParseTimeoutSec`, `TRCConfig.ParseTimeoutSec`, `MCPConfig.QueryTimeoutSec`, `MCPConfig.ReviewTimeoutSec`) переводятся с `int` на `*int` — три состояния: ключ отсутствует (`nil`) → дефолт, явный `0` → таймаут отключён, явное значение → значение.
- `Load()` перестаёт нормализовать эти поля в дефолты; вместо этого явные отрицательные значения отклоняются ошибкой загрузки конфига (по образцу `spec.lsa_retrain_threshold`, `config.go:388`).
- `timeoutForTool` (`internal/mcp/server.go`) разрешает `nil` в дефолт (300/30/120), `0` остаётся «без таймаута».
- `CreateDefault()` инициализирует поля явными дефолтами (не `nil`).
- Спеки уточняются до полной три-состоятельной семантики (отсутствует/`0`/отрицательное) — текущие формулировки «`0` означает отсутствие таймаута» становятся правдивыми и дополняются сценариями нуля и отклонения отрицательных значений.
- Тест «0 из TOML-файла доезжает до конфига» добавляется через `Load()` с реальным файлом (методология `config_spec_test.go`), а не литералом структуры.

Не-BREAKING для пользователей: конфиги без этих ключей и с положительными значениями ведут себя как раньше; меняется только обработка явного `0` (раньше молча → дефолт) и отрицательных (раньше молча → дефолт, теперь ошибка).

## Capabilities

### New Capabilities

(нет)

### Modified Capabilities

- `infrastructure/configuration`: требования «Настройки RTI и TRC» и «Настройки MCP» уточняются — `parse_timeout_sec`/`query_timeout_sec`/`review_timeout_sec` получают три состояния (отсутствует → дефолт, явный `0` → отключён, отрицательное → ошибка загрузки) вместо противоречивой пары «дефолт при отсутствии» + недостижимого «`0` = отсутствие таймаута».
- `mcp-server/mcp-transport-tools`: требование «Таймауты tool-вызовов» уточняет источник значений и семантику отключения (сценарий «Таймаут отключён» становится достижимым; добавляется аналогичный сценарий для query-таймаута всех не-parse инструментов).

## Impact

- Код: `internal/config/config.go` (типы полей, `Load()`, `CreateDefault()`, комментарии), `internal/mcp/server.go` (`timeoutForTool` — nil-safe разрешение), `internal/mcp/server_test.go` (литералы конфигов в тестах — механический переход на указатели), `internal/config/config_test.go` (новые тесты три-состоятельной семантики через `Load()`).
- Поведение: `codebase mcp` — явный `0` в секциях `[rti]`/`[trc]`/`[mcp]` отключает соответствующий таймаут; отрицательные значения fail-fast при старте любой CLI-команды с конфигом.
- Риски: `query_timeout_sec = 0` снимает таймаут со ВСЕХ не-parse инструментов (задокументированное следствие); прямое конструирование `Config{}` в коде вне `Load()` требует nil-безопасности у читателя (потребитель один).
- Зависимости: новые не вводятся; go-toml v2 поддержка `*int` уже используется полями `SpecConfig`/`DescLSAConfig`.
