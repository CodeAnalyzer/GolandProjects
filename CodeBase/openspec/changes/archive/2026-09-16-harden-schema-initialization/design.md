## Context

См. `proposal.md` — Why. Сейчас `RunStdio` создаёт подключение, выполняет полный `InitSchema`, затем запускает MCP SDK transport. Четыре профильных процесса OpenCode проходят этот путь параллельно. `InitSchemaCtx` исполняет более двухсот DDL-выражений через пул `sql.DB`; только одна поздняя data migration имеет собственную advisory-блокировку, поэтому начальный DDL остаётся конкурентным.

Ограничения:

- PostgreSQL advisory-lock принадлежит конкретной серверной сессии; независимые вызовы через `sql.DB` не гарантируют попадание на одно физическое соединение.
- Отмена переданного context должна прерывать как ожидание блокировки, так и DDL.
- stdout MCP-процесса зарезервирован для JSON-RPC; startup-диагностика должна идти через существующий журнал команд/ошибку Cobra.
- Существующая таблица `schema_migrations` уже хранит применённые одноразовые миграции и может хранить маркер совместимости без новой служебной таблицы.

## Goals / Non-Goals

**Goals:**

- Исключить гонки системного каталога при конкурентных вызовах `InitSchemaCtx`.
- Гарантировать освобождение блокировки при успехе, ошибке и отмене context.
- Сделать MCP startup read-only относительно схемы БД.
- Ввести явный, проверяемый маркер совместимости схемы с бинарной версией CodeBase.
- Сохранить профильную модель MCP и успешный JSON-RPC-контракт без изменений.

**Non-Goals:**

- Перевод всех существующих DDL на полноценную последовательность мелких версионированных миграций.
- Удаление `InitSchema` из всех read-only CLI-команд в рамках этого change; обязательное разделение применяется к MCP startup.
- Изменение формата MCP tools, профилей или логики индексирования.
- Автоматический retry MCP после обнаружения устаревшей схемы.

## Decisions

### 1. Сериализация через transaction-level advisory-lock на выделенном `sql.Conn`

`InitSchemaCtx` получает выделенный `*sql.Conn`, открывает на нём транзакцию и до первого DDL выполняет `pg_advisory_xact_lock(hashtextextended('codebase/schema-init', 0))`. Все schema statements и запись маркера версии выполняются через эту же транзакцию. Commit атомарно публикует изменения и освобождает lock; rollback при ошибке или отмене также освобождает lock.

Это предпочтительнее session-level `pg_advisory_lock`/`unlock`: transaction-level lock невозможно случайно оставить на соединении, возвращённом в pool, а выделенный `sql.Conn` исключает смену PostgreSQL-сессии. Выполнение DDL через ту же транзакцию также не требует резервного соединения и работает при `MaxOpenConns = 1`.

Альтернативы:

- Mutex в Go отклонён: он не координирует разные процессы.
- Session-level lock через `sql.DB.Exec` отклонён: lock и unlock могут попасть на разные соединения.
- Session-level lock на `sql.Conn` отклонён в пользу xact-lock: при сбое cleanup возможно вернуть в pool сессию с удерживаемым lock.
- Retry ошибки `pg_class_relname_nsp_index` отклонён: маскирует гонку и не гарантирует согласованную схему.

### 2. Маркер совместимости хранится в `schema_migrations`

В store вводится непрозрачная константа текущей версии схемы. После успешного полного прохода `InitSchemaCtx` добавляет соответствующую запись в `schema_migrations` в той же транзакции. Маркеры являются append-only: последующие версии получают новый идентификатор, старые не удаляются.

Совместимость определяется наличием маркера, требуемого текущим бинарным файлом. Это допускает запуск старого клиента на схеме с последующими additive-миграциями, пока его собственный маркер сохранён. Несовместимое удаление или изменение контракта в будущем должно сопровождаться отдельным решением о диапазоне поддерживаемых версий.

Альтернативы:

- Новая singleton-таблица `schema_metadata` отклонена: добавляет DDL только ради проверки и делает старые БД безусловно несовместимыми.
- Проверка полного списка таблиц/колонок отклонена: дублирует описание схемы в коде, дорога и легко рассинхронизируется.
- Использование версии бинарника отклонено: патч-релиз приложения не обязательно меняет схему.

### 3. Отдельная read-only операция проверки схемы

Store предоставляет операцию проверки, которая читает `schema_migrations` и ищет текущий маркер. Она классифицирует как минимум:

- таблица `schema_migrations` отсутствует — схема не инициализирована;
- таблица существует, но текущего маркера нет — требуется обновление;
- маркер присутствует — схема совместима;
- иная ошибка PostgreSQL — ошибка проверки/доступа к БД.

Операция не вызывает `InitSchemaCtx` и не выполняет DDL/DML. Ошибка содержит ожидаемый маркер и, если возможно, последний обнаруженный schema-marker, но не включает секреты подключения.

### 4. MCP startup использует только проверку

`RunStdio` после `NewDB` вызывает read-only проверку вместо `InitSchema`. При успехе registry и stdio transport запускаются как раньше. При ошибке функция возвращает обёрнутую диагностическую ошибку; существующий корневой логгер записывает её в `codebase_YYYYMMDD.log`, не загрязняя stdout.

Диагностика рекомендует:

- для отсутствующей схемы — `codebase init --config <path>`;
- для устаревшей схемы — `codebase update --config <path>`.

Поскольку проверка происходит до MCP initialize handshake, внешний клиент всё ещё может показать транспортное `Connection closed`; детальная причина гарантируется в журнале CodeBase. Изменение MCP-протокола или запуск частично работоспособного сервера ради передачи startup-ошибки не выбирается.

### 5. Тестирование разделяется по гарантиям

Интеграционный тест создаёт несколько независимых DB handles к одной тестовой БД и синхронно запускает `InitSchemaCtx`; все вызовы должны завершиться успешно, а текущий маркер — присутствовать. Отдельный тест удерживает тот же advisory-lock и проверяет, что ожидающий вызов завершается по deadline context.

Read-only проверка тестируется на пустой БД, схеме без текущего маркера и актуальной схеме. MCP startup тестируется через выделяемую startup-функцию до блокирующего запуска stdio transport; на несовместимой схеме она возвращает классифицированную ошибку и не создаёт объекты.

## Risks / Trade-offs

- [Большая транзакция удерживает DDL-lock до конца полного прохода] → `InitSchemaCtx` применяется в административных startup/update путях; интеграционные тесты и измерение времени контролируют отсутствие неприемлемой деградации. Долгосрочный переход к коротким versioned migrations уменьшит окно блокировок.
- [После обновления бинарника существующая БД не содержит новый маркер] → release/ошибка MCP явно требует однократно выполнить `codebase update`; миграционная проверка покрывается тестом.
- [Старый бинарник принимает более новую схему, если его маркер сохранён] → маркеры считаются декларацией backward compatibility; destructive migration должна вводить отдельную политику диапазона совместимости.
- [OpenCode продолжает показывать только `-32000` при неготовой схеме] → точная причина сохраняется в журнале CodeBase; stdout не используется для внепротокольной диагностики.
- [Параллельный `init/update` сериализуется и может ждать] → ожидание управляется context и корректно отменяется.

## Migration Plan

1. Выпустить бинарник с сериализованным `InitSchemaCtx`, текущим schema-marker и read-only checker.
2. Для существующей БД один раз выполнить `codebase update --config <path>`; проход схемы запишет текущий маркер.
3. После появления маркера запустить или перезапустить MCP-клиент; все профили выполнят только read-only проверку.
4. При rollback на предыдущий бинарник append-only записи `schema_migrations` не мешают старому коду; удаление маркера не требуется.
5. Если deployment нового бинарника нужно отменить до выполнения update, достаточно вернуть предыдущий бинарник: схема ещё не менялась через MCP startup.
