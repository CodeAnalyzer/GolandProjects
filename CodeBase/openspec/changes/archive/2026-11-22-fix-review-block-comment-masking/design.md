## Context

См. proposal.md (Why) — класс FP по закомментированному коду. Затронутые сканеры делятся на два семейства с разной механикой (проверено по коду на build 1712):

1. **Построчные сканеры** — читают контент (`fileContent` — сырой, `fileProcessedContent` — макро-расширенный), режут на строки, пропускают только строки, начинающиеся с `--`:
   - `checkInsertRowLock` (review_rules.go:3122) — собирает многострочный буфер INSERT до `;`/нового оператора; внутри буфера комментарии не вырезаются, поиск `insert` не учитывает состояние `/* */` (`isInComment` проверяет только `--` в той же строке);
   - `checkUseSelectAll` (review_rules.go:2493) — regex по строке; хвостовой `-- ...` в строке кода тоже не маскируется;
   - `checkTruncTbl` (review_rules.go:2528).

2. **Операторные сканеры на общем хелпере** `splitStatementsWithOffsets` (review_parser.go:1682) — хелпер отслеживает строковые литералы и вложенность скобок, но не комментарии. Ключевое слово `update`/`select`/`delete` внутри `/* */` или `-- ` стартует фантомный оператор; текст комментария попадает в `stmt`, который затем разбирают потребители:
   - `checkDeferredUpdate` (review_rules.go:4424), `checkMemoryUniqueIndexUpdate` (:4544), `checkInSubQuery` (:4620), `checkTooManyJoins` (:4225, postgre-requirements).

Эталоны в той же кодовой базе: `findInsertWithoutColumns` (review_parser.go:1965) — char-level FSM с `/* */`, `--` и литералами (эмпирически 0 FP у `columnInsert`); `stripLineComments` (review_helpers.go:1112) — построчная маскировка с переносом состояния; 12 сканеров из build 1711.

`checkVarUseAfterCursor` (review_rules.go:5181) работает через `fileProcessedContent` и парсеры курсора — пробел подтверждён по коду: внешний цикл `parseAllFetchIntoStatements` (review_parser.go:465-473) матчит `reParserFetchCursorStart` по сырой строке без состояния `/* */` (перенос `inBlock` есть только в сборе продолжений), `parseDeallocateStatements` (:435-443) и `parseCursorDeclarations` (:328-352) так же матчат сырые строки. Закомментированный `fetch`/`deallocate`/`declare cursor` считается оператором.

`fileContent`/`fileProcessedContent` возвращают текст, декодированный CP866→UTF-8 (`runner.go:163`): кириллица в комментарии занимает 2 байта на символ, `offset` сплиттера — байтовый индекс, `Line` потребителей считается по исходному `text[:offset]`. Существующий `maskBlockCommentsKeepLines` (review_parser.go:1183) работает в `[]rune` и байтовую длину не сохраняет — эталоном для offset-арифметики не годится.

## Goals / Non-Goals

**Goals:**

- Один механизм маскировки, закрывающий оба семейства: и многострочные `/* */`, и хвостовые `-- ...` в строках кода.
- Идентичность поведения для кода вне комментариев: 665 реальных findings измеренного корпуса сохраняются построчно (`rule:line`; `Object` — с нормализацией хвостовых комментариев, когда он производен от текста оператора); новые истинные находки (устранение FN) перечисляются явно.
- Сохранение арифметики номеров строк: length-preserving маскировка (длина текста и количество `\n` не меняются), центральный ремап expanded→original строк не затрагивается.

**Non-Goals:**

- Не менять правила с уже реализованной маскировкой: `apiExecOutsideFacade`, `debugProfileEnabled` (санитизация лексером), `columnInsert` (char-FSM), `ansiInJoin` и `modifyOutProc` (`maskBlockCommentsKeepLines`), `useEqColumn` и `varcharSize` (собственные блоки), `emptyReturn`/`rawTransactionControl` (`stripLineComments`), 12 сканеров из build 1711.
- Scope определён эмпирически по измеренному корпусу (247 файлов fa-contracts, 87 FP в 4 правилах); прочие raw-сканеры вне измеренного набора (например `emptyStringDate`) — отдельные кандидаты, не «пропуск».
- Не менять `shouldBeCP866` — проверяет кодировку файла по байтам, байты комментария легитимно входят в проверку.
- Не трогать ~27 правил на `parsed *sqlparser.ParseResult` (datatype-семейство и др.) — другой источник контента, эмпирических FP не зафиксировано; отдельный кандидат при обнаружении.
- Не извлекать общую инфраструктуру «маскированного контента» для всех 47 правил (кеш/прокидывание) — вне scope bug-fix'а.
- Не менять схему БД, CLI-контракт и MCP-контракт.

## Decisions

### D1. Единый байтовый length-preserving mask-хелпер `maskSQLComments(text) string`

Новый хелпер в `review_parser.go`: один проход по `[]byte`, отслеживает строковые литералы (`''` — экранирование, состояние переносится через `\n` — так же, как в `splitStatementsWithOffsets`), `/* ... */` (включая вложенные `/*` внутри блока как текст) и `-- ...` до конца строки; **каждый байт** комментария заменяется на `' '`, `\n` и `\r` сохраняются, инвариант — `len(результат) == len(вход)` в байтах. Байтовая инвариантность критична: контент декодирован CP866→UTF-8, кириллица в комментарии — 2 байта на символ, rune-маскировка сместила бы `offset`-координаты сплиттера и `Line` потребителей. Семантика автомата повторяет `findInsertWithoutColumns`, размещение — рядом с `sanitizeSQLForMacroScan` (см. D1a).

Почему единый хелпер, а не per-site FSM (стиль 1711):

- точек применения две: вход трёх построчных сканеров и вход `splitStatementsWithOffsets` (плюс вход `checkVarUseAfterCursor`);
- сохранение байтовой длины — централизованное свойство одного хелпера вместо инварианта в 8 местах;
- string-awareness: `stripLineComments` не различает `--`/`/*` внутри литералов — единый хелпер устраняет и этот нюанс.

Альтернатива — маскировать только `/* */`, не трогая `--`: отклонена, хвостовые `--` в строке кода дают тот же класс FP (regex `useSelectAll` по сыркой строке; фантомные операторы сплиттера из `-- select ...`).

Альтернатива — считать `Line` в каждом правиле по маскированному тексту (координаты не смешиваются): отклонена, центральный ремап expanded→original уже опирается на сохранение строк, а дублирование подсчёта по двум текстам расширяет дифф.

### D1a. Отношение к `sanitizeSQLForMacroScan`

В пакете уже есть байтовый length-preserving string-aware лексер `sanitizeSQLForMacroScan` (review_rules.go:1599-1655), но напрямую переиспользовать его нельзя: он заменяет содержимое строковых литералов на `?`, что испортит правила, читающие литералы и идентификаторы из `stmt` (`extractSetColumns`, `extractTablesFromFromClause`, `findInSubqueryPositions`). `maskSQLComments` — тот же класс автомата, но маскирует только комментарии, литералы сохраняет. Выделено общее ядро переходов `maskLexemes` в `review_parser.go` (рядом со сплиттером — его главным потребителем); санитайзер в `review_rules.go` делегирует ему (`maskStringLiterals=true`), так что две реализации не расходятся.

Принятое ограничение (как у существующих сканеров): bracket-quoted идентификаторы `[a--b]` и `"a--b"` не распознаются как литералы — `--` внутри них будет принят за комментарий. Вероятность в корпусе низкая, ограничение документируется; полная унификация обработки комментариев (`stripLineComments`, `maskBlockCommentsKeepLines`, `sanitizeSQLForMacroScan`, `maskSQLComments`) — отдельный рефакторинг-кандидат.

### D2. Точки применения

- `splitStatementsWithOffsets`: маскировать текст на входе. Один фикс закрывает 4 правила (`deferredUpdate`, `memoryUniqueIndexUpdate`, `inSubQuery`, `tooManyJoins`): фантомные операторы не стартуют, `stmt` не содержит текста комментариев, downstream-парсеры (`extractUpdateTargetTable`, `extractSetColumns`, `extractTablesFromFromClause`, `countTopLevelJoins`, `findInSubqueryPositions`) не меняются. `offset` и подсчёт `\n` для `lineNo` валидны благодаря length-preserving. Перед применением сверить полный список вызовов сплиттера — поведение меняется для всех вызовов консистентно.
- Построчные сканеры (`insertRowLock`, `useSelectAll`, `truncTbl`): маскировать контент один раз после `fileContent`/`fileProcessedContent` и до `strings.Split`; существующие циклы не меняются. Пустые (пробельные) строки после маскировки: `findKeywordPosition` не находит ключевых слов, префиксная проверка `--` становится no-op; для буфера `insertRowLock` пустые строки не завершают оператор (`isNewSQLStatement` на пустой строке ложен).
- `checkVarUseAfterCursor`: применить `maskSQLComments` на входе `text` (парсеры курсора получают чистый текст; строки сохраняются, `Line`-координаты валидны). Нюанс: расширение skip-спана по упоминанию переменной в комментарии (`fetchVariablesLineEnd`, review_parser.go:522-536) после маскировки становится неактуальным, но непротиворечивым — и парсер, и скан использования работают по одному маскированному тексту, FP не возвращается.

### D3. Тесты

- Table-driven по образцу `review_block_comment_test.go` (`ruleCase` + `newRuleTestFile`/`newRuleTestExec`): (а) триггер внутри `/* */` → 0 findings; (б) комментарий внутри реального оператора → finding по кодовым частям; (в) хвостовой `--` на строке кода → 0 findings; (г) незакрытый `/*` до конца файла → 0 findings; (д) код после `*/` → finding. Отдельный кейс: `;` внутри комментария не завершает буфер `insertRowLock`.
- Хелпер: кириллический комментарий **перед** триггером с проверкой, что `Line` после маскировки совпадает с исходным (ловит rune-регрессию); `\r`/CRLF; состояние литерала через `\n`.
- E2E: `FA/fa-generalledger/.../TmpTbl_GLReports.sql` с `--min-severity 1` → 0 findings.
- Приёмка на корпусе: регенерировать список fa-contracts файлов с `insert` внутри `/* */` (247 файлов), прогон 12 raw-правил с `--json --min-severity 1` до/после фикса: findings внутри `/* */`-спанов 87 → 0; сверка остальных построчная: `rule:line` идентичны, `Object` сравнивается с нормализацией хвостовых комментариев (у `tooManyJoins` `Object` — первая строка оператора, комментарий в ней после маскировки срежется `TrimSpace`); ожидаемые новые истинные находки (устранение FN вида `truncate /* c */ table t`) перечисляются явно до прогона. Урок из fix-review-macro-service-vars: сверка построчная, не по счётчикам.

`cmd/root.go` — `buildNumber` 1712 → 1713.

## Risks / Trade-offs

- [Избыточная маскировка скроет реальный код → потеря истинных findings] → приёмка D3 фиксирует построчную идентичность 665 реальных findings; маска меняет только байты комментариев.
- [`--` внутри строкового литерала ('a--b') при маскировке] → хелпер string-aware, семантика `''` та же, что у сплиттера; негативный тест.
- [Макро-расширенный контент `useSelectAll`/`varUseAfterCursor`: маска после раскрытия может скрыть сгенерированный макросом код с `--`] → препроцессорный комментарий в expanded-выводе остаётся комментарием для SQL Server; семантически корректно. Length-preserving сохраняет ремап строк.
- [Изменение `splitStatementsWithOffsets` затрагивает всех вызывающих] → список вызовов сверяется задачей 2.1; все потребители — правила review, для которых маскировка и есть цель.
- [Пустые строки после маскировки меняют поведение циклов] → кейсы (б)/(д) в D3; `isNewSQLStatement`/`findKeywordPosition` на пробельных строках нейтральны.
- [Производительность: 7 правил × O(len) маскировка на файл] → один линейный проход по KB-файлу несопоставим с DB-lookup'ами правил; кеш не требуется.
