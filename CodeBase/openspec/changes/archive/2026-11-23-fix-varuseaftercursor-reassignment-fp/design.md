## Context

`checkVarUseAfterCursor` (review_rules.go:5124) сканирует плоское текстовое окно между `DEALLOCATE` и следующей декларацией того же курсора; отслеживаемые переменные собираются из FETCH'ей текущей жизни. Гварды «переопределения» (set/select — review_rules.go:5236–5242, declare — 5232–5234) пропускают только текущую строку: `HasPrefix(lower, "set")` не срабатывает на отступах (мёртвый гвард во всём реальном коде), `select` + `Contains(var+"=")` ломается на выравнивающих пробелах перед `=` и не видит строки-продолжения многострочного select-присваивания. Даже корректно распознанное присваивание не снимает привязку переменной — последующие чтения флагуются. Сканер flow-insensitive: ветки if/else не различаются. Эталон FP — `pCardRegRelation_Load.sql` (build 1716): 4 findings во второй ветке `if @RegKind`, где обе переменные курсора переприсваиваются `select @var = ...` до любого чтения. Прецедент семантики «новой жизни» уже есть в правиле: переобъявление курсора (`nextDeclLine`) гасит окно целиком — здесь та же идея на уровне отдельной переменной.

## Goals / Non-Goals

**Goals:**

- Присваивание отслеживаемой переменной в окне ниже DEALLOCATE снимает её отслеживание для всех последующих строк окна (kill-семантика вместо построчных гвардов).
- Распознавание присваиваний: `set @v = ...` (с любым отступом), select-присваивание `@v = ...` (выровненный `=`, `select top N @v =`, строки-продолжения списка), `declare @v ...`, FETCH другого курсора в `@v`.
- Различение левой части присваивания и использования: RHS и сравнения (`if/where/and/when @v = ...`) остаются находками.
- Детекторы работают по маскированному комментарием тексту (`maskSQLComments`), как весь скан.

**Non-Goals:**

- Branch-aware анализ / мини-CFG (ветки, доминирование присваивания над чтением) — правило остаётся построчной эвристикой (зафиксировано в design `fix-cursor-redeclare-positional-scope`).
- Учёт GOTO/меток и порядка исполнения циклов `while` (чтение до присваивания по строкам, но после по исполнению).
- Изменение механики окон жизни, skip-спанов FETCH, дедупликации `seen`, per-line гвардов курсорных операций (`declare/open/close/fetch/deallocate` + имя курсора).
- Правило `varAssignInUpdate` и прочие правила — не затрагиваются.

## Decisions

- **D1. Kill вместо гвардов.** Окно сканируется последовательно; активное множество — копия списка `vars` для каждого DEALLOCATE, представленная сетом имён (дубликаты переменных из нескольких FETCH'ей одной жизни схлопываются). Строка-присваивание удаляет переменную из активного множества (и сама не флагуется по ней); строки ниже не проверяются по удалённой переменной. Чтения до присваивания флагуются как раньше. Альтернатива — CFG с доминированием — отклонена: скачок сложности против зафиксированной построчной философии; FN-риск sibling-веток принят явно (Risks). Kill локален окну одного DEALLOCATE — окна не влияют друг на друга, дедуп `seen` сохраняется.
- **D2. Детектор присваивания — позиционный, в контексте оператора.** Переменная считается переопределённой (word-boundary по имени), если её вхождение стоит в позиции левой части присваивания:
  - SET-строка: строка после отступа начинается с `set`, `@var` стоит непосредственно перед `=` или составным оператором присваивания (`+=`, `-=`, `*=`, `/=`, `%=`, `&=`, `|=`, `^=`).
  - SELECT-присваивание: заголовок — строка после отступа начинается с `select` (допускается `top N`) и содержит `@var` перед `=` после `select`/`top N`/запятой; список продолжается на следующих строках вида `^\s*,?\s*@var\s*=` и завершается строкой, начинающей новую секцию (`from`, `where`, `group`, `order`) или новый оператор (`exec`, `set`, `declare`, `if`, `while`, `insert`, `update`, `delete`, `print`, `fetch` и т.п.), а также standalone-вызовом макроса/профайлера. Строки-продолжения внутри открытого списка — kill соответствующих переменных.
  - EXEC-параметры: именованные аргументы `@param = значение [output]` переопределением не являются ни в заголовке, ни в продолжениях — контекст EXEC не открывает список присваиваний; вхождения переменных в EXEC-строках классифицируются как использование (значение параметра/RHS). `exec @ret = proc` (присваивание кода возврата) kill'ом не считается — задокументированное ограничение (Risks).
  - Сравнения `if @v =`, `where ... and @v =`, `select case when @v =` не матчатся — переменная не в позиции левой части присваивания.

  Альтернативы отклонены: «`select` в любом месте строки + `@v =`» — FN на `select case when @v = ...`; безусловное «начало строки/запятая» без контекста оператора — ложный kill на EXEC-параметрах вида `@FinOperID = @FinOperID output` (~2940 строк в fa-cards/Cards) и на `, @v =` внутри строковых литералов (см. D6).
- **D3. FETCH другого курсора — переопределение.** `parseAllFetchIntoStatements` уже возвращает все FETCH'и с переменными; FETCH ниже DEALLOCATE текущего курсора, чьи переменные пересекаются с активным множеством, удаляет эти переменные. Kill привязан к `fetch.LineStart` (заголовку FETCH), а не к строке с переменной — продолжения многострочного `into`-списка не успевают дать finding. Skip-спаны FETCH'ей того же курсора ниже DEALLOCATE сохраняются как есть (существующее поведение).
- **D4. `declare @var` ниже DEALLOCATE — переопределение.** Повторное объявление переменной перезапускает её жизнь (аналогично переобъявлению курсора); текущий declare-guard строки сохраняется, добавляется kill.
- **D5. Порядок обработки строки.** Сначала детекторы переопределения (kill) для всех активных переменных, затем поиск использований оставшихся. Строка может одновременно переопределять `@a` и использовать `@b` (`select @a = @b`) — `@b` флагуется; это сохраняет существующий сценарий `SET @Var = @FetchVar` (RHS — использование). Самоприсваивание (`set @a = @a`) убивает переменную до проверки RHS той же переменной — задокументированное ограничение (Risks).
- **D6. Маскирование литералов для kill-детектора.** Kill-детектор работает по length-preserving тексту с маскированными строковыми литералами (по образцу `maskLexemes(text, true)` / `sanitizeSQLForMacroScan`, review_rules.go:1601): содержимое литералов — в частности `, @var = %1!` в сообщениях профайлера (`CardAccRelation_MassLoad.sql:183` и др.) — не создаёт kill. Скан использований остаётся на текущем comment-masked тексте (`maskSQLComments`, литералы не маскируются — review_parser.go:1755) и подстрочным: устоявшееся поведение и якорь `@ChangedBrief:652` не меняются.

## Risks / Trade-offs

- [FN: присваивание в одной ветке if/else, чтение старого значения в соседней (`if c set @v=... else use @v`)] → принятый trade-off: severity 2, эмпирическая оценка масштаба класса в приёмке (задача 1.2/4.5) до вынесения вердикта о допустимости; при неожиданно большом масштабе — пересмотр решения D1.
- [FN: `while`-цикл — присваивание ниже чтения по строкам, но раньше по исполнению] → принято, соответствует существующим ограничениям построчного подхода.
- [Ложный kill на экзотической левой части (продолжение `where`-списка, начинающееся с `@v =`)] → практически не встречается (продолжения where начинаются с `and`/`or`/`on`); контроль — корпусный diff в приёмке: каждая исчезнувшая находка сверяется с фактом присваивания.
- [FN: `exec @ret = proc` — присваивание кода возврата EXEC kill'ом не распознаётся] → принято: паттерн редок, взаимное влияние с курсорными переменными минимально; задокументированное ограничение D2.
- [FN на самоприсваивании `set @a = @a` / `select @a = @a + 1` ниже DEALLOCATE: kill срабатывает раньше проверки RHS той же переменной (D5)] → принято; паттерн ниже DEALLOCATE экзотичен.
- [Новые находки класса «RHS на column-0 `set`» после снятия whole-line set-гварда (5236–5238): `set @lhs = @rhs` на строке в колонке 0 теперь флагует `@rhs`] → на реальном коде FA (с отступами) гвард был мёртв, класс ожидаемо пуст; приёмка 4.4 верифицирует каждую находку класса как реальное чтение.
- [Регресс существующих находок (эталоны `InstrumentSO_LoadStates.sql` @ChangedBrief:652, `Cons_*`)] → baseline до правок + повторный прогон, diff = 0 кроме класса «переопределено»; unit-тесты всех старых сценариев остаются зелёными.
- [Substring-дефект имён (`@ChangedBrief` ⊂ `@ChangedBriefs`) и якорь 4.3] → скан использований остаётся подстрочным `strings.Contains` (review_rules.go:5228) — без изменений; word-boundary применяется только внутри kill-детектора. Якорь `InstrumentSO_LoadStates.sql:652` дополнительно защищён unit-тестом: `select @ChangedBriefs = ...` kill не даёт (word-boundary), finding для `@ChangedBrief` сохраняется (подстрока).
- [Over-kill на inline-инициализации `declare @x int = @a` (R2 ревью кода): чтение `@a` в инициализаторе снимает отслеживание] → отложено: синтаксис T-SQL 2008+ в корпусе fa-contracts не встречается (0 вхождений); при появлении — ограничить declare-kill позициями объявляемых имён.
- [FN: `IF cond SELECT @v = ...` — select не в начале строки, заголовок D2 не матчится (R4 ревью кода)] → отложено: направление консервативное (finding остаётся, новых FN нет; класс новых находок в корпусе пуст — appeared = 0); в fa-contracts 369 строк-кандидатов, влияние на итоговый список находок не измерялось; кандидат на отдельную доработку.
