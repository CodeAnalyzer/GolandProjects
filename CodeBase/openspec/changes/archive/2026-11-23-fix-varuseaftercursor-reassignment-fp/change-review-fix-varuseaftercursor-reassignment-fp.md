## 3. Замечания

### B1 (блокирующее) — D2 ложно трактует EXEC-параметры `@Param = @Param` как переприсваивание

**Где:** `design.md:24` (D2), `tasks.md:10` (2.1), `spec.md:7` (описание переопределения), `spec.md:51-61`.

**Суть.** D2 считает переменную переопределённой, если `@var` стоит перед `=` «после начала строки, запятой или `select`». Правило «после начала строки / после запятой» применяется безусловно, без привязки к тому, что мы находимся в списке целей `SELECT`-присваивания. В T-SQL строки вида `@Param = @Param output,` — это **именованные аргументы EXEC**, а не присваивание локальной переменной. Под D2 они дают kill → реальное чтение переменной после DEALLOCATE подавляется (FN).

**Доказательство (реальный код из эталонного файла):** `FA/fa-cards/Cards/SERVER/Card/pCardRegRelation_Load.sql:325-326`

```
        exec FCD_CRD_FindListAction
               @FinOperID = @FinOperID
```

Линия 326 начинается с `@`, содержит `@FinOperID =` → по D2 это «многострочный select-список» и kill. Здесь `@FinOperID` не курсорная переменная, поэтому эталон 4.2 не ломается, но класс реален и массов.

**Масштаб в корпусе:** в `FA/fa-cards/Cards` (без `_materials`) найдено **2940** строк вида `^\s*@X\s*=\s*@X\s+output` — это типовые продолжения EXEC с OUTPUT. Любая из них, где имя совпадает с курсорной переменной, станет ложным kill.

**Рекомендация.** Ограничить детектор select-присваивания контекстом оператора: «продолжение списка» (строка с `@`/запятой) считается переопределением только если ближайший открывающий оператор — `SELECT`-присваивание (заголовок `select [top N] @v = ...`, список продолжается до начала нового оператора: `from/where/exec/set/...`). Как минимум — исключить строки, находящиеся в списке параметров `EXEC`. Добавить unit-тест: `exec P` / `@A = @A output,` не должен снимать `@A`; последующее чтение `@A` — finding. Обновить D2, task 2.1 и (при необходимости) формулировку требования.

### B2 (блокирующее) — детекторы работают по тексту без маскировки строковых литералов → ложный kill на сообщениях профайлера

**Где:** `design.md:12` («Детекторы работают по маскированному комментарием тексту (`maskSQLComments`)»), `tasks.md:12` (2.3).

**Суть.** `maskSQLComments` маскирует **только комментарии**, строковые литералы сохраняются (`review_parser.go:1755-1757`, `maskLexemes(text,false)`; `review_parser.go:1723` — содержимое литерала заменяется на `?` только при `maskStringLiterals=true`). Сообщения профайлера массово содержат текст `... , @Var = %1! ...`, где `@Var =` стоит после запятой или после `select` — ровно левый контекст D2. Итог: переменная курсора, упомянутая в тексте сообщения, получает ложный kill → реальное чтение ниже не флагается (FN).

**Доказательство (реальный корпус):**
- `FA/fa-cards/Cards/.../CardAccRelation_MassLoad.sql:183` — `PROFILE_TIME_VAR2('insert into tCardAccRelation, @RetVal = %1!, @RecCount = %2!', ...)` — `, @RecCount =` внутри литерала.
- `AddSMSServiceByCardProduct.sql:137` — `'... ProcCenterID @ContactType = %1!, @PhoneParam = %2!'`.
- `BranchConfigParam_Get.sql:113` — `'result: @NValue = %1!, @DValue = %2!, @SValue = %3!'`.

Дополнительно возможен вариант `select @X =` внутри литерала — левый контекст «select» также сработает.

**Рекомендация.** Для **kill-детектора** использовать текст с маскированными литералами (`sanitizeSQLForMacroScan` = `maskLexemes(s,true)`, `review_rules.go:1601-1602`) либо учитывать состояние кавычек при поиске `@var` перед `=`. При этом **скан использований** оставить на текущем `maskSQLComments`-тексте (иначе меняется устоявшееся поведение и якорь 4.3). Добавить тест: строка `PROFILE_TIME_VAR1('... , @A = %1!', @A)` не является переопределением, чтение `@A` — finding. Обновить design D-раздел и task 2.3.

### B3 (блокирующее) — противоречие «word-boundary vs Contains» ставит под угрозу якорь 4.3

**Где:** `design.md:35` (Risk), `design.md:24` (D2 word-boundary), `tasks.md:12` (2.3), `tasks.md:28` (4.3).

**Суть.** Risk утверждает: «kill-детектор наследует **word-boundary-поведение текущего использования `Contains`**». Это фактически неверно: текущее определение использования — `strings.Contains(lower, varLower)`, т.е. **подстрока**, без границ слова (`review_rules.go:5228`). Если исполнитель понят это как «перевести использование на word-boundary», изменится эталон 4.3: `InstrumentSO_LoadStates.sql:652` содержит только `@ChangedBriefs`, а finding `@ChangedBrief` там держится исключительно на подстрочном совпадении. Переход на word-boundary уберёт finding и нарушит ожидание «ровно 1 (@ChangedBrief, 652)».

**Рекомендация.** Явно зафиксировать: **скан использований остаётся подстрочным (`Contains`)**, word-boundary применяется **только** в kill-детекторе. Исправить формулировку Risk (убрать «word-boundary-поведение … Contains»), при необходимости добавить в тесты кейс `@ChangedBrief`/`@ChangedBriefs` как защиту якоря.

### M3 (важное) — утверждение «новых находок нет» (4.4) не учитывает снятие широкого `set`-гварда

**Где:** `tasks.md:29` (4.4), `tasks.md:10` (2.1), текущий код `review_rules.go:5236-5238`.

Старый `set`-гвард при строке в колонке 0 маскировал **все** переменные строки. После замены на kill: `set @lhs = @rhs` снимет только `@lhs`, а `@rhs` (RHS) станет finding. Это потенциально **новая** находка, что формально противоречит «новых находок нет». На реальном коде с отступами эффект почти нулевой (гвард был мёртв), но приёмка 4.4 должна это явно оговорить (класс «RHS на column-0 `set`») или исключить. Стоит также отметить в Risks.

### m1 (мелкое) — неточные ссылки на строки

- `design.md:3`, `proposal.md:24`, `tasks.md:10` указывают гварды `5231–5242`; фактические `set/select`-гварды — `5236–5242` (`5232` — declare-гвард). Косметика.
- `tasks.md:22` ссылается на диапазон тестов `3932–4750`; последний varUseAfterCursor-тест заканчивается на ~4752.

### m2 (мелкое) — не покрыто compound-присваивание `set @a += ...`

D2 требует `@var` **непосредственно** перед `=`; в `@a +=` между именем и `=` стоит `+`, поэтому reassignment не распознаётся (FN). Для Diasoft-корпуса редкость; зафиксировать как известное ограничение либо обработать `=?`/`+=` явно.

### m3 (мелкое) — D5 (kill→use) даёт FN на самоприсваивании

`set @a = @a` / `select @a = @a + 1` после DEALLOCATE: kill снимает `@a` раньше проверки RHS, чтение старого значения не флагается. Добавить в `Risks` как принятый trade-off (или проверять RHS до kill для той же переменной).

### m4 (мелкое) — D3: не зафиксирован якорь kill для FETCH другого курсора

Для многострочного `fetch c2` / `into @A` kill должен применяться на `fetch.LineStart` (а не на строке с переменной), иначе продолжения списка успеют дать finding. Уточнить в D3 явно, что kill привязан к `fetch.LineStart` и использует `fetch.Variables` из `parseAllFetchIntoStatements`.

### m5 (мелкое) — дубликаты в `vars`

`vars` может содержать повторы (несколько FETCH одной жизни); kill должен удалять все вхождения (реализация через множество/фильтр). Тривиально, но зафиксировать.
