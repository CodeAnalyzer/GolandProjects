# Delta: query/symbol-search

## MODIFIED Requirements

### Requirement: Дедупликация копий из веток

Поиск по unified symbols index SHALL возвращать не более одной строки на
символ одного продукта: строки, отличающиеся только веткой одного
продукта, схлопываются в одну по детерминированному приоритету
(default-ветка, затем больший id), выбранная строка SHALL содержать
`branch_used` (и `product`). Символы разных продуктов и разных типов, а
также одноимённые методы разных классов остаются отдельными строками.
Ключ владельца в ключе дедупликации SHALL читаться из материализованной
колонки `symbols.owner_name`: для `method` — имя класса, как оно записано
в исходном коде метода (регистр написания значим), для `component` — класс
родительской формы, для остальных типов — пустая строка. Одноимённые
методы разных классов SHALL оставаться отдельными строками независимо от
того, резолвнут ли класс в `pas_classes` — для символов с заполненным
`owner_name`. Легаси-строки, получившие пустого владельца от
backfill-миграции (методы с нерезолвнутым классом, имя класса-ссылки
которых не сохранено в индексе), дедуплицируются по пустому ключу
владельца до переиндексации их файлов.

#### Scenario: Символ в трёх ветках одного продукта

- **GIVEN** процедура `MyProc` проиндексирована в develop, `11-01-6` и `11-01-7` одного продукта
- **WHEN** выполняется поиск символа по имени
- **THEN** возвращена одна строка с `branch_used` = develop

#### Scenario: Одноимённые методы разных классов не схлопываются

- **GIVEN** методы `Execute` классов `TFormA` и `TFormB` в develop одного продукта
- **WHEN** выполняется поиск символа `Execute`
- **THEN** возвращены две строки (по одной на класс), обе с `branch_used` = develop

#### Scenario: Копия метода одного класса в другой ветке схлопывается

- **GIVEN** метод `Execute` класса `TFormA` объявлен в двух PAS-файлах одного продукта — в develop и в sp — с одинаковым написанием класса
- **WHEN** выполняется поиск символа `Execute`
- **THEN** возвращена одна строка ветки develop: обе записи имеют одинаковый ключ владельца и схлопываются веточным дедупом

#### Scenario: Методы нерезолвнутых классов не схлопываются между ветками

- **GIVEN** одноимённые методы `Execute` с различными заполненными `owner_name` (`TFormA` и `TFormB`), сами классы в `pas_classes` отсутствуют
- **AND** метод `TFormA.Execute` проиндексирован только в develop, `TFormB.Execute` — только в sp одного продукта
- **WHEN** выполняется поиск символа `Execute`
- **THEN** возвращены две строки — по одной из каждой ветки: ключ владельца каждого метода равен значению колонки `owner_name`, а не пустой строке

#### Scenario: Легаси-методы с нерезолвнутым классом дедуплицируются по пустому ключу

- **GIVEN** легаси-строки метода `Execute` двух нерезолвнутых классов в разных ветках одного продукта, заполненные backfill-миграцией с `owner_name = ''`
- **WHEN** выполняется поиск символа `Execute`
- **THEN** возвращена одна строка default-ветки: строки имеют одинаковый пустой ключ владельца и схлопываются веточным дедупом
- **AND** после переиндексации файлов методов `owner_name` заполняется именами классов и строки разделяются

## ADDED Requirements

### Requirement: Материализованный ключ владельца без per-row подзапросов

Поиск сущностей по имени (`SearchSymbol`, включая трёхполевой fallback
report_form) и поиск по содержимому (`SearchInContent`) SHALL вычислять
ключ владельца дедупликации напрямую из колонки `symbols.owner_name` без
коррелированных подзапросов к таблицам сущностей (`pas_methods`,
`pas_classes`, `dfm_components`, `dfm_forms`). Планы выполнения этих
запросов SHALL NOT содержать per-row SubPlan вычисления владельца;
состав результатов для символов с резолвнутыми классами и формами
MUST сохраниться прежним.

#### Scenario: План без SubPlan вычисления владельца

- **GIVEN** проиндексированная мультиветочная БД масштаба FA
- **WHEN** анализируется план `EXPLAIN (ANALYZE, BUFFERS)` поиска символа метода по имени (`query symbol --name DoAction --type method`)
- **THEN** план не содержит SubPlan и коррелированных подзапросов к `pas_methods`/`pas_classes`/`dfm_components`/`dfm_forms`
- **AND** ключ владельца читается из колонки `symbols` одним проходом

#### Scenario: Холодный поиск частого имени метода без таймаута

- **GIVEN** холодный кеш БД и тысячи одноимённых символов-методов
- **WHEN** выполняется `query symbol --name DoAction --type method`
- **THEN** результат возвращается за интерактивное время, без многосекундного ожидания и без обрыва по таймауту MCP

#### Scenario: Тёплый поиск частого имени метода

- **GIVEN** прогретый кеш БД и тысячи одноимённых символов-методов
- **WHEN** выполняется `query symbol --name DoAction --type method`
- **THEN** время ответа укладывается в десятки миллисекунд

#### Scenario: Состав результатов сохраняется для резолвнутых владельцев

- **GIVEN** БД, где backfill-миграция owner_name выполнена семантически эквивалентно прежнему runtime-выражению
- **WHEN** поиск символа по имени выполняется до и после перехода на материализованный ключ
- **THEN** для методов резолвнутых классов и компонентов резолвнутых форм возвращаются те же строки с той же дедупликацией
