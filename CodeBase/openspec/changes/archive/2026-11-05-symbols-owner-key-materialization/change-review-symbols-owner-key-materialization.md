## Замечания

1. **[Medium] `query/symbol-search` требует «не схлопывать» нерезолвнутые классы, а backfill по построению оставляет у легаси-строк `''`.**
   - Дельта `infrastructure/database-schema` (spec.md:20-21) и design D2 (design.md:38-50) предписывают для нерезолвнутых строк пустую строку — так сохраняется эквивалентность прежнему runtime-выражению.
   - Индексатор же для новых строк пишет имя класса как записано (design D3/D4.1, дельта `indexing`). Причина разницы объективная: `pas_methods` хранит только `class_id`, имя класса-ссылки нигде не сохранено, поэтому backfill физически не может восстановить его для нерезолвнутых методов.
   - Следствие: после миграции легаси-методы с нерезолвнутыми классами сохраняют `owner_name=''` и **по-прежнему схлопываются** (особенно заметно при кросс-веточном дедупе), а требование `query` («SHALL оставаться отдельными строками независимо от того, резолвнут ли класс», spec.md:13-19) и сценарий «Методы нерезолвнутых классов не схлопываются» (spec.md:39-43) для них не выполняются. `update` не переиндексирует неизменённые файлы (pre-filter mtime+size), поэтому состояние может сохраняться неопределённо долго.
   - Дополнительно: задача 4.1 сравнивает «до/после» на неизменённой БД — для нерезолвнутых легаси-строк расхождения не будет вовсе (old collapse == new collapse), то есть проверить D4.1 в таком прогоне нельзя.
   - Рекомендация: квалифицировать требование/сценарий («для строк, записанных индексатором после v5; легаси-строки — после переиндексации»), явно зафиксировать в design/proposal ограничение backfill для нерезолвнутых, а в 4.1 добавить прогон после переиндексации файла (и пин backfill: легаси-нерезолвнутый → `''`).

2. **[Medium] В design/tasks указан вызов `sanitizeUTF8String` из пакета `internal/indexer`, но функция не экспортирована.**
   - `sanitizeUTF8String` объявлена в `internal/store/db_nullable.go:6` (lowercase, пакет `store`). Задачи 2.2/2.3 и design D3 (design.md:56-57) предписывают `OwnerName = sanitizeUTF8String(...)` в `indexer_sql_pas.go` / `indexer.go` — дословно это не компилируется.
   - Локальный `sanitizeUTF8Lookup` (`internal/indexer/indexer_spec.go:17`) не эквивалентен: он делает только `strings.ToValidUTF8` и не удаляет `0x00`, который PostgreSQL отвергает.
   - Рекомендация: в индексаторе класть «сырое» `method.ClassName` / `formClassByID[...]`, а санитизацию выполнять в `insertSymbolsBatch` (`db_insert_j.go`) рядом с остальными полями символа (существующий паттерн). Поправить формулировки design/tasks, чтобы не закреплять некомпилируемый вызов.

3. **[Medium] Task 3.3 / новый сценарий не различают схлопывание из-за двухфазного дедупа.**
   - В `SearchSymbol` сначала `chosen` выбирает одну ветку на ключ, затем финальный SELECT возвращает **все** строки `base` выбранной ветки с этим ключом (`query.go:462-478`). Поэтому два одноимённых метода в **одной** ветке сохраняются в любом случае, даже при одинаковом `owner_key` (это же подтверждает существующий `TestSearchSymbolSameNameInOneBranchSurvives`, `query_branch_dedup_integration_test.go:255-272`).
   - Существующая фикстура кладёт `TMyForm.Execute` и `TOther.Execute` в develop (`query_branch_dedup_integration_test.go:139-150`) — при `owner_name=''` у обоих тест всё равно вернёт 2 строки и пройдёт, не поймав over-collapse.
   - Рекомендация: для регресса класть методы разных нерезолвнутых классов в **разные ветки** так, чтобы один класс отсутствовал в выигрывающей (default) ветке (например, `TFormA` только develop, `TFormB` только sp). Добавить контр-кейс «оба `owner_name=''` → схлопываются», чтобы доказать, что тест действительно чувствителен к владельцу.

4. **[Low] Task 1.3: не сказано, как триггерить backfill, и есть непроверяемое «не сканирует symbols».**
   - Ориентир — `TestFilesIsGenerated_BackfillIdempotent` (`db_lookup_spec_mentions_integration_test.go`, функция с :232, диапазон 239-288 в задаче указан неточно): вставить легаси-строки `method`/`component` с `owner_name=''`, удалить маркер текущей версии **и** `symbols_owner_name_backfill_v1`, вызвать `InitSchema`, проверить заполнение; затем повторить и проверить, что значения не перезаписаны.
   - «Не сканирует symbols» напрямую не ассертится; заменить на проверку «маркер есть → UPDATE не выполнился» (например, вручную изменить `owner_name` у строки и убедиться, что повторный прогон его не вернул).

5. **[Low] Backfill в design D2 — self-join `symbols s` ↔ `symbols s2`; формулировка «один hash-join проход» неточна.**
   - Запрос сканирует `symbols` дважды и содержит CASE + `s2`; это корректно, но не «один проход». На FA-масштабе дешевле и понятнее два type-scoped UPDATE: `method` — напрямую `pas_methods → pas_classes`, `component` — `dfm_components → dfm_forms`, без `s2`/CASE. Не блокер; либо упростить миграцию, либо поправить описание в design/дельте.

6. **[Low] Уточнения формулировок дельт.**
   - `query/symbol-search` сценарий «backfill-миграция owner_name выполнена по прежнему runtime-выражению» (spec.md:79) противоречит design D2, где коррелированная форма явно отвергнута во имя set-based. Заменить на «семантически эквивалентно прежнему runtime-выражению».
   - Сценарий «Методы одного класса в разных файлах схлопываются» (spec.md:33-37) не учитывает D4.2: при разном регистре написания класса в двух файлах новые `owner_key` различаются и строки не схлопнутся. Добавить «при одинаковом написании класса».
   - `indexing`-требование говорит «без обрезки пробелов», хотя парсер берёт имя класса/формы из regex без окружающих пробелов (`pas_parser.go:1543`, `dfm_parser.go:285-304`) — формулировка безвредна, но не несущая; можно оставить.

7. **[Info] Migration Plan п.2 (откат старым бинарём) описан неверно.**
   - Маркеры в `schema_migrations` не удаляются и накапливаются: после v5 в таблице остаётся и v4. Старый бинарь (`CurrentSchemaVersion=codebase_schema_v4`) увидит v4 в `CheckSchemaVersion` (`db_schema_version.go:15-28`) и будет работать; `owner_name` он просто не читает. Откат схемы для совместимости не требуется. Стоит поправить текст Migration Plan (или осознанно удалять старые маркеры, но это ухудшит обратную совместимость).

8. **[Info] Бамп buildNumber `1669 → 1672` пропускает 1670/1671 без пояснения.** Если номера зарезервированы — ок; иначе логичнее 1670 (task 5.1, tasks.md:30).
