## Context

См. `proposal.md — Why`. Текущее устройство, важное для дизайна:

- `cmd/review.go` — Cobra-команда с `Args: cobra.ExactArgs(1)`; собирает
  `review.Options` и вызывает `reviewsvc.ExecuteCtx`, который на каждый вызов
  читает конфиг, открывает `store.DB`, делает `CheckSchemaVersion` и закрывает
  соединение.
- `review.Runner.RunSQLFileCtx` на каждый файл: сбрасывает файловые кэши,
  делает `getIndexedFile`, `buildReviewScope` (2 запроса списков продуктов/веток
  + резолв dsinfo), читает/декодирует файл, парсит, прогревает кэши, гоняет
  правила.
- JSON-контракт одиночного review: `success`, `format_version`, `command`,
  `count`, `items[]` (finding содержит `file`), `summary`, `meta`.
- `cmd.Execute()` при ошибке `RunE` в JSON-режиме сам печатает error-envelope;
  повторная печать в `RunE` дала бы два JSON-документа в stdout.
- Замеры на реальном FA: холодный запуск ~20 с, горячий ~1–1.4 с/файл.
  Основная экономия пакетного режима — один холодный старт, одно соединение,
  однократная проверка схемы и переиспользование scope-инвариантных lookup'ов.

## Goals / Non-Goals

**Goals:**

- Один процесс/соединение на весь список, изоляция ошибок по файлам.
- Побайтовая эквивалентность findings для файла в пакете и в одиночном режиме.
- Единый агрегированный JSON-конверт и человекочитаемый вывод с прогрессом.
- Обратная совместимость одиночного CLI и MCP.

**Non-Goals:**

- `--dir`/glob-обход, чтение списка из stdin, рекурсивный обход ФС.
- Параллельная обработка файлов (worker-пул на файл уже есть внутри Runner).
- Пакетный MCP-инструмент и изменение `codebase_review_sql`.
- Сквозной шаринг файловых кэшей (colType/index/proc) между файлами: они
  зависят от scope/содержимого конкретного файла.
- Изменения схемы БД и миграции.

## Decisions

### D1. Флаг `--files` на существующей команде, без подкоманды

`review` получает `StringVar --files`; `Args` меняется на `cobra.MaximumNArgs(1)`,
а валидация режима выполняется в `RunE`:

- `--files` задан → позиционный аргумент запрещён (0 аргументов);
- `--files` не задан → требуется ровно один позиционный путь (как раньше).

Альтернативы: отдельная подкоманда `review batch` (ломает привычный UX и
дублирует флаги) и `--dir` (не покрывает произвольные списки из БД/CI).
Выбран флаг: минимальная поверхность, легко комбинируется с существующими
`--rules/--min-severity/--dsinfo/--json`.

### D2. Пакетное выполнение в сервисном слое, один `Runner`

Новый API:

- `reviewsvc.ExecuteBatchCtx(ctx, paths []string, opts review.Options, progress)` —
  открывает конфиг/БД/схему один раз (как `ExecuteCtx`), затем вызывает
  пакетный метод Runner;
- `review.Runner.RunSQLFilesCtx(...)` — цикл по путям поверх выделенного из
  `RunSQLFileCtx` ядра одного файла; публичный `RunSQLFileCtx` остаётся без
  изменений и переиспользует то же ядро.

`Runner` переиспользуется между файлами, но файловые кэши
(`colTypeCache`, `macroTypeCache`, `indexCandCache/indexFieldsCache`,
`memoryTableCache`, `viewNameCache`, `procParamsCache`, `procProductIDCache`,
`tableProductIDCache`, `tableCreatorCache`) сбрасываются перед каждым файлом —
это уже делает `RunSQLFileCtx`. При выделении ядра (задача 1.1) важно сохранить
все сбросы, включая `r.exec` (deferred `nil`) и перезапись `r.scope` на каждый
файл: замыкания правил держат `r`, и утечка состояния даёт ложные/потерянные
findings.

Новые scope-инвариантные кэши на время пакета:

- `ListDSProductIDs` и `ListDSProductBranches` — один раз на пакет;
- `dsinfosvc.ResolveAnalysisContext` — по ключу `explicitID` (включая `0`).

Такие кэши фиксируют состояние индекса/профиля на старте пакета. Для длинных
списков это осознанный trade-off: эквивалентность одиночному запуску
гарантируется при неизменном состоянии индекса и dsinfo-профиля во время
прогона (зафиксировано в спеке).

Альтернативы: новый `Runner` на файл с общим `DB` (проще, но теряются
переиспользуемые lookup'ы и добавляется аллокация кэшей); параллельные файлы
(давление на БД/CPU, недетерминированный порядок, сложный прогресс) —
отложены.

### D3. Ошибки файлов — данные, а не прерывание

`RunSQLFilesCtx` возвращает `BatchResult` и инфраструктурную ошибку только для
отказа всего пакета (конфиг/БД/схема). Ошибки отдельных файлов попадают в
`BatchFileResult{Status:"error", Error:{Code,Message}}`.

Чтобы коды были стабильными, в `internal/review` вводятся sentinel-ошибки с
сохранением текущего текста сообщений:

- `ErrFileNotIndexed = errors.New("file is not indexed")`,
- `ErrProductNotSet = errors.New("ds_product_id is not set for file")`.

`reviewsvc` маппит их в коды `not_indexed` / `missing_product`; остальные
ошибки файла → `review_failed` (с сохранением текста). `classifyReviewError`
из `cmd/review.go` переезжает в `reviewsvc.ClassifyError`, CLI и пакетный режим
используют один классификатор.

Новые ошибки уровня аргументов (0 аргументов без `--files`, конфликт режимов,
отсутствующий/нечитаемый/пустой список) вводятся как
`errs.ErrInvalidArguments` и маппятся в `invalid_arguments`; `ClassifyError`
проверяет `errors.Is` до строковых эвристик. Существующие одиночные коды
(`invalid_arguments`, `database_unavailable`, ...) не меняются.

Альтернатива: классифицировать по строке в `cmd` — хрупко и дублирует логику.
Альтернатива для аргументов: подгонять тексты под `containsAny` — неявно и
легко сломать при редактировании сообщений.

### D4. Один агрегированный конверт; `success=false` при частичном сбое

Пакетный JSON-ответ — отдельная структура в `cmd/review.go` (не встраивание
одиночной, чтобы не менять порядок/набор полей одиночного ответа):

```
{
  "success": false,            // failed == 0
  "format_version": "1.0",
  "command": "review",
  "mode": "batch",
  "count": 3,                   // всего findings по успешным файлам
  "items": [Finding...],        // плоский, в порядке списка и файла
  "summary": {total, by_rule, by_severity},
  "files": {
    "total": 2, "succeeded": 1, "failed": 1,
    "results": [
      {"file": "fa-contracts/.../A.sql", "status": "ok", "count": 1, "summary": {...}},
      {"file": "fa-contracts/.../B.sql", "status": "error",
       "error": {"code": "not_indexed", "message": "..."}}
    ]
  },
  "meta": {"rules": [...], "min_severity": 3}
}
```

`total` — число уникальных файлов после дедупа, `succeeded + failed = total`;
`results[]` содержит только уникальные файлы (порядок первого вхождения).
`results[].file` — нормализованный (`normalizePath`) путь в форме из списка,
чтобы ошибочные/непроиндексированные пути оставались узнаваемыми;
`items[].file` — индексный путь, как в одиночном режиме.
`items` собираются из успешных файлов; агрегат `summary` считается по ним же.
Одиночный конверт не получает `mode`/`files`.

### D5. Ненулевой exit code без второго JSON-документа

`RunE` печатает пакетный конверт сам. Если `failed > 0`, он возвращает
`fmt.Errorf("%w: %d file(s) failed", errs.ErrAlreadyReported, failed)`.
В `cmd.Execute()` перед `writeReviewErrorResponse` добавляется проверка
`errors.Is(err, errs.ErrAlreadyReported)` → вернуть ошибку как есть (exit code
ненулевой, повторный envelope не печатается). В не-JSON режиме достаточно
обычного возврата ошибки после печати итога.

Альтернативы: `os.Exit` из `RunE` (ломает deferred-логирование) и «всегда
успех» (CI не увидит частичный сбой).

### D6. Разбор списка — CLI-уровень

`readReviewFileList` живёт в `cmd/review.go` (это контракт CLI, не домена):
`bufio.Scanner` с увеличенным буфером, срез BOM у первой строки, `TrimSpace`,
игнор пустых и `#`-строк, снятие парных `'`/`"`, дедуп с сохранением порядка.
Относительные пути передаются в Runner как есть и резолвятся от CWD — так же,
как позиционный аргумент. Пустой/нечитаемый список — ошибка `invalid_arguments`.

### D7. Прогресс пакета

Колбэк `func(completed, total int, current string)`; в не-JSON режиме
используется тот же spinner, но строка объединяет оба уровня прогресса:
`review [i/N] <basename> rules k/m`, где `i/N` — файлы пакета, `k/m` —
правила текущего файла (если RuleRunner уже сообщил прогресс). Блок результата
файла печатается сразу после завершения файла. В `--json` прогресс не выводится
вовсе; stdout содержит только один JSON-конверт.

## Risks / Trade-offs

- [Двойной JSON при частичном сбое] → sentinel `ErrAlreadyReported` + guard в
  `Execute()`; отдельный cmd-тест проверяет ровно один документ в stdout.
- [Протечка состояния между файлами] → существующий сброс файловых кэшей
  сохраняется; регрессионный тест сравнивает batch и single для файлов из
  разных продуктов/веток.
- [Рост памяти на больших списках] → агрегат хранит все findings; рекомендация
  в документации — дробить списки; при необходимости позже добавить стриминг.
- [Медленный «хвост» из-за per-file prewarm] → пакет не обещает кратное
  ускорение; выигрыш даёт амортизация старта/подключения/глобальных lookup'ов.
  Дальнейшая оптимизация (агрегированный prewarm) — отдельное изменение.
- [Разные кодировки/CRLF в списке] → срез BOM и `\r`, тесты на CRLF.
- [Порядок и детерминизм] → результаты строго в порядке списка; findings —
  в порядке одиночного запуска; map-поля JSON сортируются `encoding/json`.
- [Долгий пакет и закэшированный профиль/индекс] → scope-кэши фиксируются на
  старте; эквивалентность одиночному запуску гарантируется при неизменном
  индексе/профиле, что зафиксировано в спеке. При частых `update` во время
  длинных прогонов — дробить списки.
- [Новые ошибки аргументов уходят в `internal_error`] → `ErrInvalidArguments` +
  явные тесты классификатора для всех веток валидации.

## Migration Plan

Изменение аддитивное: новый флаг, новые поля только в пакетном ответе, схема
БД не меняется. Откат — удаление флага/пакетной ветки; одиночный и MCP-режимы
не затронуты.
