## Context

Review-пайплайн (`internal/review`): правила выполняются параллельным worker-пулом
над expanded-контентом файла (после `replaceMacros`), строки finding'ов ремапятся
обратно через SourceMap. Каждое правило — константа в `types.go`, запись в
`ruleCatalog` (`catalog.go`), реализация `check*` в `review_rules.go`; DB-backed
правила юнит-тестами не покрыты (прецедент: `deferredUpdate`), тестируются
хелперы парсинга. Интеграционных тестов в `internal/review` нет — новый путь
данных получает их по образцу `indexer_lst_integration_test.go` (см. задачи).

Структурный прецедент нового правила — `checkDeferredUpdate`
(`review_rules.go:3673`): `splitStatementsWithOffsets` → отбор `UPDATE` →
`extractUpdateTargetTable` → `extractSetColumns` → сравнение SET-колонок с полями
индекса. Отличия нового правила: индекс не обязан быть хинтованным, зато
таблица обязана быть in-memory.

Данные в индексе уже есть, схема БД не меняется:

- Признак in-memory: `memory_tables` (v7, `indexing/lst-parsing`) — крошечная
  таблица (26 деклараций в FA), join по имени без product-scope (прецедент D3
  из `memory-tables-flag`).
- Уникальные индексы обычных `p*`-таблиц: `sql_index_definitions.is_unique`
  (источники: `CREATE UNIQUE INDEX`, `M_CRT_INDEX('UNIQUE',...)`, dsxml
  `IndexType=2` → `InternalPTableIndexes`) + `sql_index_definition_fields`.
- Уникальные индексы `pAPI_*`: `api_business_object_table_indexes.index_type`
  (INTEGER) + `api_business_object_table_index_fields`.

Живые данные рабочего индекса FA (change-review 2026-11-09 + дообверка):

- Признак уникальности API-индексов: `index_type` 2 и 3 дают уникальный индекс
  в рабочей БД (проверено вручную по БД). Распределение по всей БД согласуется:
  `3` → XPK 5829 (unique clustered), `2` → XPK 437 + XAK 222 + XKP 1 + XIE 9,
  `0`/`1` — без признака уникальности (XPK 3088/750, XAK 40, XIE 2222).
- Покрытие memory-таблиц критерием «`is_unique=TRUE` ИЛИ `index_type IN (2,3)`»:
  **7 из 26** — `pRuleDoc_QtyStack` (SQL `UNIQUE`) и 6 API-таблиц с XPK вида 2/3
  (`pAPI_LstTpl`, `pAPI_AutoNum_ExtraAttr`, `pAPI_ExtraAttrib_SaveNTF`,
  `pAPI_FO_TemplateExtraAttr`, `pAPI_Property_Value`, `pAPI_RuleAcc_TypeID`).
  Остальные 19 имеют только индексы без признака уникальности — правило для них
  неактивно по объективной причине (уникальных полей нет).
- Контрпример конвенции имён: `pObjectForRight` — `XPK` объявлен
  `M_CRT_INDEX('', ...)` и неуникален; `XPK*`/`XAK*` по имени не гарантируют
  уникальность.
- Ограничения SQL-распознавания: `M_CRT_INDEX('_UNIQUE_', ...)` даёт
  `is_unique=false` (987 строк по всей БД, парсер сравнивает `EqualFold` с
  `UNIQUE`); inline `UNIQUE`-constraint в `CREATE TABLE` в индекс не попадает
  вовсе (парсер пропускает эти строки). Среди memory-таблиц `_UNIQUE_`-деклараций
  нет — на покрытие правила не влияет.
- Живого true-positive `UPDATE` по уникальным колонкам memory-таблиц в текущем
  FA нет (`pRuleDoc_QtyStack` обновляет только `ID`/`Qty`; `UPDATE pAPI_LstTpl`
  отсутствует) — верификация правила требует синтетической фикстуры.

## Goals / Non-Goals

**Goals:**

- Finding `memoryUniqueIndexUpdate` (severity 1) на каждый `UPDATE`, чья
  SET-колонка входит в уникальный индекс таблицы, объявленной in-memory.
- Покрытие обоих источников уникальности (`p*` и `pAPI_*`) через расширение
  существующего кэша индексов, без новых N+1-запросов.

**Non-Goals:**

- Семантика runtime-таблицы `tTableInmemory` целевой БД — признак декларативен
  (границы `indexing/lst-parsing`).
- Конвенция имён (`XPK*`/`XKP*`/`XAK*` = уникальный) — отвергнута данными:
  `XPKpObjectForRight` реально неуникален; конвенция дала бы severity-1 false
  positive. Уникальность — только по явному признаку индекса.
- Расширение SQL-парсера (`_UNIQUE_`, inline `UNIQUE`/PK в `CREATE TABLE`,
  `M_CRT_INDEX('')` для `XPK`) — отдельный change: 987 затронутых строк требуют
  собственной валидации и переиндексации; покрытие memory-таблиц от этого не
  зависит (среди них нет `_UNIQUE_`-деклараций).
- Анализ изменения уникальных колонок через `INSERT`/`DELETE`+`INSERT` — только
  `UPDATE SET`.
- Product-scope или alias-маппинг продуктов декларации (D4 `memory-tables-flag`).

## Decisions

### D1: Структура проверки — по образцу `checkDeferredUpdate`

`splitStatementsWithOffsets` по expanded-контенту (`r.fileContent`) → отбор
операторов с префиксом `update` → `extractUpdateTargetTable` → skip `#`-таблиц
→ `extractSetColumns` (уже срезает alias-префикс цели и отфильтровывает
`@`-переменные) → сравнение с полями уникальных индексов. Номер строки —
подсчёт `\n` до `s.offset`, ремап в expanded→original делает runner.
Альтернатива (парсинг через `parseUpdateSetStatement` по fragment'ам) отвергнута:
прецедент `deferredUpdate` работает на уровне операторов и уже решает ту же
задачу извлечения цели и SET-колонок.

### D2: Резолв алиаса цели — ДО проверки in-memory, с единой нормализацией

`extractUpdateTargetTable` для `UPDATE x SET ... FROM pT x` вернёт `x`. Порядок
обязателен: сначала резолв реальной таблицы через `extractTablesFromFromClause`
+ `sameTableReference(t.TableName, target) || sameTableReference(t.Alias,
target)` (как в `deferredUpdate`), и только затем проверка признака in-memory
по реальному имени. Нормализация имени при обращении к множеству memory-таблиц
и кэшу индексов — та же, что у `sameTableReference`/`normalizeIdentifier`:
LOWER + снятие `[]`/`"` и схемного префикса (`dbo.`) — дешёвая страховка против
вариантов записи имени.

### D3: Признак in-memory — lazy-load всего множества имён одним SELECT, с флагом загруженности

`memory_tables` ограничена размером `.lst` (десятки строк): одно
`SELECT DISTINCT LOWER(table_name) FROM memory_tables` в множество под
мьютексом Runner'а при первом обращении правила (правила бегут параллельно).
Обязателен флаг `memoryTablesLoaded bool` — признак «множество уже запрошено»,
отдельный от «множество пусто»: без него пустая `memory_tables` (риск
«`.lst` не проиндексирован») заставляла бы повторять SELECT на каждый UPDATE.
Флаг и множество сбрасываются в `RunSQLFileCtx` рядом с остальными кэшами.
Ошибка запроса кэшируется как «загружено-пусто»: правило инертно до конца
запуска, шторма запросов нет (прецедент толерантности к lookup-ошибкам —
`cachedLookupTableProductIDs`). Альтернатива (prewarm batch по целям UPDATE,
по образцу `prewarmTableProductIDs`) отвергнута: потребовала бы дублирования
извлечения целей UPDATE до правил ради экономии на запросе по 26 строкам.

### D4: Уникальность — расширение общего кэша `tableIndexCandidate`, не отдельный lookup

`tableIndexCandidate` получает `IsUnique bool`; SQL#1 (`sql_index_definitions`)
добавляет колонку `i.is_unique`, SQL#2 (`api_business_object_table_indexes`) —
`(i.index_type IN (2, 3))`: оба значения дают уникальный индекс в рабочей БД
(проверено по БД; вид 3 — уникальный кластерный, вид 2 — уникальный
некластерный). Оба запроса уже batch по `ANY($1)` и кэшируются; расширение даёт
уникальность будущим правилам без новых запросов и без расщепления кэша.
Union-семантика при дублях из разных веток: кандидаты агрегируются по
`(table, indexID, normName)` — определение уникального индекса в любой ветке
делает колонку «уникальной» глобально (наследуемый прецедент неразветвлённых
lookup'ов, см. Risks). Альтернатива (отдельный `lookupUniqueIndexFields`)
отвергнута: дублировала бы SQL и кэш.

### D5: Finding, дедупликация и формулировка сообщения

`Object` — имя целевой таблицы; сообщение в стиле `deferredUpdate`: колонка,
таблица, имя уникального индекса, режим in-memory (изменение полей уникального
индекса in-memory таблицы). Формулировка привязана к «изменению полей
уникального индекса» и НЕ утверждает конкретный сценарий отказа (swap) —
правило консервативно флагует любое изменение уникальной колонки (см. Risks).
Дубли кандидатов одного индекса из разных файлов/веток (агрегация по
`indexID`) дедуплицируются: один finding на пару (нормализованная колонка,
`LOWER(index_name)`).

## Risks / Trade-offs

- [Покрытие 7/26 memory-таблиц] → Следствие данных, не дефект критерия: у
  остальных 19 таблиц нет индексов с признаком уникальности. Числа зафиксированы
  по живому индексу (change-review 2026-11-09) и перепроверяются задачей контроля.
- [`index_type` 0/1 у XPK: если такой индекс в целевой БД фактически уникален —
  молчаливый false negative] → Контрольная задача верификации по рабочей БД
  (как ручная проверка видов 2/3); при обнаружении таких случаев — расширение
  критерия отдельным решением.
- [`M_CRT_INDEX('_UNIQUE_', ...)` (987 строк в БД) и inline `UNIQUE` в
  `CREATE TABLE` не распознаются → false negative за пределами memory-таблиц]
  → Зафиксировано как ограничение; парсер-фикс — отдельный change; среди
  memory-таблиц `_UNIQUE_`-деклараций нет (проверено по индексу).
- [Деплой без `*.lst` в `include_patterns` или до v7 → `memory_tables` пуста,
  правило молча неактивно] → Наследуемый риск `memory-tables-flag` (D6);
  активность правила на стенде проверяется одним SQL.
- [Кросс-веточная union-семантика кэша индексов: уникальное определение в
  любой ветке делает колонку уникальной глобально] → Наследуемый прецедент
  (`lookupIndexExists`); для нового правила фиксируется осознанно.
- [Ложные срабатывания на легальные UPDATE: одиночное изменение уникальной
  колонки на неконфликтующее значение на in-memory таблице формально легально]
  → Осознанная консервативность severity-1 правила (аналогично `deferredUpdate`);
  фильтрация «только swap-паттернов» статически ненадёжна.
- [Пересечение с `deferredUpdate` на одном операторе] → Осознанно: триггеры
  разные (хинтованный индекс vs уникальный индекс in-memory таблицы), оба
  finding'а информативны.
- [Производительность] → Один дополнительный SELECT из 26-строчной таблицы на
  файл (с флагом загруженности); индексы — из существующего batch-кэша
  (cache-miss fallback уже в `lookupTableIndexCandidates`).

## Migration Plan

1. Схема/конфиг не меняются — только код. Правило включается дефолтным набором
   (`DefaultEnabledRules` = весь каталог).
2. Отключение точечное: существующий механизм `--rules` (перечислить все,
   кроме `memoryUniqueIndexUpdate`).
3. Предусловие активности на стенде: БД схемы v7+ с проиндексированным
   `ModuleTableInMemory.lst` (деплой `memory-tables-flag`).
4. Bump `buildNumber` + пересборка `CodeBase.exe` + smoke-прогон review
   (задача в tasks).
