# Дизайн: warm-up probe при старте MCP

## Context

`RunStdio` (`internal/mcp/server.go:22-52`) строит `registry` через
`buildToolRegistryForProfile` и регистрирует SDK-обёртки; хендлеры имеют сигнатуру
`toolHandler(ctx, map[string]interface{}) (interface{}, error)` (`registry.go:23`)
и могут вызываться напрямую, минуя SDK-обёртку. Конкурентный доступ к `*sql.DB`
(lib/pq) безопасен. Конфиг-паттерн опциональных параметров: `*int` + `secOrDefault`
(`server.go:122-128`), валидация в `config.go:370`. Логирование tool-вызовов —
`logMCPToolCall` через `logger` (nil = отключено).

Данные исследования (живая БД FA, 2026-10-13): горячий набор `relations` ≈ 1.35 ГБ
(индексы 969 МБ, 7 шт.), `symbols` ≈ 1.26 ГБ, `query_fragments` ≈ 1.25 ГБ при
`shared_buffers = 1 ГБ` — превышение ~4×, полный прогрев невозможен. `callers`
для `FCD_GL_Audit_Insert` обходит 1090 прямых + 2904 косвенных строк `relations`
(полосы листьев `idx_relations_target_type_id` + `idx_relations_source_type_id`,
PK `sql_procedures`/`files`). Зазор `initialize` → первый реальный вызов ≈ 1 мин
(IDE стартует opencode при своём запуске).

## Goals / Non-Goals

**Goals:**

- Перенести цену холодного старта (буферы PG/OS + ленивые LSA/embeddings-кэши)
  из первого пользовательского вызова в фоновую горутину при старте.
- Нулевое влияние на транспортный контракт и результаты tool-вызовов.
- Отключаемость и ограничение по времени.

**Non-Goals:**

- `pg_prewarm`-ветка (даже для малых таблиц) — отложена; полный prewarm
  `relations`-индексов исключён навсегда (969 МБ).
- Изменение SQL-планов query-инструментов (микро-оптимизации по эталону бьют по
  тёплому 19-мс запросу — не нужны).
- Аудит избыточности 7 индексов `relations` — отдельная работа.
- Профили `rti`/`trc`/`review` — проб нет (no-op), расширение списка позже по
  мере накопления логов.

## Decisions

1. **Проба = реплей реального tool-хендлера из `registry`, не отдельный SQL.**
   Гарантирует прогрев тех же путей доступа (индексов) и автоматически грузит
   LSA/embeddings через `desc_search`/`spec_search`. Альтернатива «отдельные
   SQL-запросы» отвергнута: рассинхрон с реальными планами, дублирование логики.

2. **Асинхронный запуск (`go warmupForProfile(...)`) до `server.Run`.**
   Синхронный вариант задержал бы `initialize` и рисковал клиентским таймаутом.
   Race probe ↔ первый вызов не страшен: зазор ~1 мин, а невыигранные пути
   остаются в прежнем (холодном) состоянии — регресса нет.

3. **Только при `logger != nil`.** Без логов probe — нефункциональная фоновая
   нагрузка без наблюдаемости. nil → не запускать (зафиксировано в спеке).

4. **Общий таймаут пачки `warmup_timeout_sec` (дефолт 60), а не попробно.**
   60 с хватает на самую дорогую часть (холодная LSA-загрузка ≈ 32 с в логе);
   попробные таймауты усложняют семантику и не дают гарантии завершения списка.
   Явный `0` = без таймаута; отрицательное — ошибка конфигурации.

5. **Порядок проб фиксирован: LSA-зависимые → `callers` → лёгкие name-пробы →
   `sql_fragment` (последняя).** Обоснование: (а) самые дорогие и не подверженные
   вытеснению (in-process кэши) — первыми; (б) полосы листьев `relations` —
   ценный ограниченный след; (в) FTS-скан `query_fragments` (547 МБ GIN) может
   вытеснить прогретое — последней, чтобы не навредить; ожидание — она редко
   успеет, что приемлемо (точечные trgm-запросы агентов греют себя сами).

6. **Аргументы проб — константы в коде (`internal/mcp/warmup.go`, одно место
   правки).** Имя для пробы `callers` — `FCD_GL_Audit_Insert` (выбрано по данным:
   средняя полоса fan-out 1090+2904; «хаб» `ReturnCode_Insert` на 7557
   вызывающих отвергнут — probe сам стал бы тяжёлым; динамический выбор «самой
   вызываемой» отвергнут — сам требует холодного скана). Аргументы обязаны
   проходить required-валидацию хендлеров (пустое имя, как в исходном предложении
   №1, отклоняется `requiredString` до касания БД).

7. **Список проб только для профиля `query`** (и для пустого профиля = все
   инструменты? — нет: пустой профиль обрабатывается как no-op вне списка).
   Профили без списка проб — no-op без единого вызова хендлера.

8. **Состав проб (профиль `query`, в порядке выполнения):**

   | # | tool | args | прогревает |
   |---|---|---|---|
   | 1 | `codebase_query_desc_search` | `{"text":"договор","limit":1}` | desc FTS + LSA/embeddings (in-process) |
   | 2 | `codebase_query_spec_search` | `{"query":"договор","layer":"semantic","limit":1}` | spec FTS + LSA/embeddings (in-process) |
   | 3 | `codebase_query_callers` | `{"procedure":"FCD_GL_Audit_Insert","limit":1}` | полосы листьев `relations`-индексов + PK `sql_procedures`/`files` |
   | 4 | `codebase_query_symbol` | `{"name":"Insert","like":true,"limit":1}` | `symbols` (btree) |
   | 5 | `codebase_query_relations` | `{"relation_type":"references_table","limit":1}` | `relations` (верхушки) |
   | 6 | `codebase_query_api_contract` | `{"name":"API","like":true,"limit":1}` | `api_contracts` |
   | 7 | `codebase_query_table` | `{"name":"tConsSalePortfolio"}` | `sql_tables` |
   | 8 | `codebase_query_form_component` | `{"name":"dl","like":true,"limit":1}` | `dfm_components` |
   | 9 | `codebase_query_sql_fragment` | `{"text":"select","limit":1}` | `query_fragments` (GIN) — последняя |

9. **Лог: одна строка по итогам** — `profile=<p> warmup probes=N done=M
   elapsed=... errors=K` через тот же `logger`. Ошибки отдельных проб не
   логируются построчно (шум), только счётчиком.

## Risks / Trade-offs

- **Race с первым реальным вызовом** → первый вызов частично холодный; хуже не
  становится (пути без probe остаются прежними). Митигировано зазором ~1 мин.
- **Фоновая нагрузка на БД при старте** → разовая, ограничена таймаутом,
  отключается `warmup_enabled=false`.
- **Имена-аргументы не существуют в чужом продукте** → прогрев страниц всё равно
  происходит (скан индекса); при необходимости — правка одной константы.
- **`shared_buffers` (1 ГБ) меньше горячего набора** → полосы могут вытесняться
  между сессиями; probe повышает вероятность тёплого пути, но не гарантирует её
  вечно. Параллельная административная задача — увеличение буфера.
- **Тесты, считающие лог-строки** → добавляется одна строка warm-up; учесть в
  `warmup_test.go` и существующих тестах логирования.

## Migration Plan

Обратная совместимость полная: дефолт `warmup_enabled=true` меняет только
тайминги первых вызовов. Откат — `warmup_enabled=false` в конфиге без пересборки.
