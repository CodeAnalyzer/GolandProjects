# Design: fix-spec-doc-drift-batch

## Context

BUG-spec-doc-drift-batch-20261009 (все 7 пунктов перепроверены на коде 2026-10-10 и подтверждены). Спеки — источник истины, но шесть из них содержат устаревшие счётчики, неверные атрибуции вызовов и неверное описание структуры выдачи. Ключевые факты верификации:

- `internal/rti/symbols.go` — `moduleIDMap` содержит **438** записей (спеки: «94 записи», причём в трёх местах: тело требования, Related code, Notes).
- `internal/mcp/registry.go` — **65** инструментов: 4 base + 29 query (включая `desc_search`) + 7 spec (включая `spec_config`) + 12 rti + 12 trc + 1 review (спека: «55», списки без `desc_search`/`spec_config`; в сценариях профилей — устаревшие ~17/~30/~14/~5).
- `SetPaginationTTL` вызывается в `cmd/root.go:284` (bootstrap, при загрузке конфига, guard `ttl > 0`), а не в `RunStdio`; `RunStdio` (`server.go:28–32`) делает только `globalPages` + `startGCLoop` — эта часть атрибуции в спеке верна.
- `ExecuteSpecByCode` (`specsvc.go:400–470`) возвращает плоский `Hits` c `ORDER BY cap.capability_name, m.line_number` — без группировки.
- `ExecuteSpecDeps` (`specsvc.go:481–490`) нормализует `outgoing`→`depends_on`, `incoming`→`depended_by`; канонические значения принимаются напрямую. CLI Use-string (`cmd/query_spec.go:70`) — единственное место с `outgoing|incoming`; флаг-описание (`:156`) уже говорит «depends_on or depended_by», MCP-описание инструмента — тоже.
- `ParseFileToDB` (`parse_to_db.go:29`) — в trc-storage спеке «ParseToDB».
- `indexAPIMacros` определена в `indexer.go:1600`, вызывается из `indexer_sql_pas.go:376`; `macro_type` в БД — lowercase (`create_proc`/`init_event`/`exec_contract`, `apimacro/parser.go:68,71,74`).

Ограничение механизма: дельта-файлы оперируют только требованиями (`ADDED/MODIFIED/REMOVED Requirements`); секции `Related code` и `Notes` дельтами не покрываются — их правки выполняются прямыми правками основных спек в рамках tasks.

Важно: номера строк из баг-репорта частично устарели (после архива `fix-timeout-zero-unreachable` mcp-transport-tools вырос до 442 строк: «55» теперь на 313, список Spec-инструментов на 401). Правки искать по содержимому.

## Goals / Non-Goals

**Goals:**

- Привести 6 спек в соответствие с фактическим поведением кода без изменения самого поведения.
- Устранить класс «магических счётчиков» из тел требований (счётчики гниют: 94→438, 55→65 доказано дважды).
- Единый словарь направлений `depends_on|depended_by` между спекой, CLI help и MCP-описанием (алиасы сохраняются).

**Non-Goals:**

- Группировка `SpecByCodeResult` по capability в коде (вариант (б) баг-репорта отвергнут: потребители CLI/MCP адаптированы к плоскому списку).
- Изменение набора MCP-инструментов, профилей, таймаутов, пагинации — только тексты.
- Введение lint-правила «магические числа в спеках» — зафиксировано как принцип формулировками без счётчиков; автоматический контроль вне скоупа.

## Decisions

1. **Счётчики убираем, а не обновляем.** Альтернатива — «94 → 438 записей», «55 → 65» — отвергнута: справочник `moduleIDMap` пополняется с обновлениями DEALMAIN.H, реестр инструментов растёт с каждым новым инструментом; любой новый счётчик устареет при следующем change. Формулировки становятся структурными: «полный реестр инструментов: базовые, query, spec, rti, trc и review». В rti-parsing добавлена фраза «количество записей сознательно не фиксируется» — фиксирует принцип, а не значение.

2. **П4 — вариант (а): спека описывает плоскую структуру.** `SpecByCodeResult` уже упорядочен по `capability_name, line_number` — формулировка «плоский список упоминаний, упорядоченный по имени capability и номеру строки» сохраняет полезную часть старого текста («capability рядом») и убирает ложную группировку. Вариант (б) — группировка в коде — поведенческое изменение JSON-структуры без запроса потребителей.

3. **П3 — хирургическая правка атрибуции.** Переносится только `SetPaginationTTL` → «bootstrap CLI (`cmd/root.go`) при загрузке конфигурации, до входа в `RunStdio`». Атрибуция `globalPages` init и `startGCLoop` за `RunStdio` остаётся (соответствует `server.go:28–32`). Сценарий «Кастомный TTL из конфига» переписан с учётом реального порядка: сначала `SetPaginationTTL` в bootstrap, затем `RunStdio`. Попутно исправляется Notes:133 — «меняет TTL для уже созданного store» ложно (TTL устанавливается до создания store).

4. **П5 — правка CLI Use-string + документирование алиасов в спеке.** `cmd/query_spec.go:70`: `[--direction outgoing|incoming]` → `[--direction depends_on|depended_by]`. Это help-текст, поведение не меняется; нормализация в `specsvc.go` остаётся. В spec_deps добавлена фраза про алиасы и сценарий «Алиас направления нормализуется» — алиасы остаются частью контракта, и спека обязана их фиксировать (иначе после правки help возникнет обратный вопрос «валиден ли outgoing?»). Альтернатива «оставить help как есть, алиасы задокументировать в спеке» отвергнута: help — первое место, куда смотрит пользователь, и он должен совпадать со словарём спеки и MCP-описания.

5. **П7 — дельта для тела требования, Notes для lowercase.** Атрибуция `indexAPIMacros` (определение `indexer.go`, вызов `indexer_sql_pas.go`) — в MODIFIED-теле требования. Факт lowercase-представления `macro_type` — прямой правкой Notes api-macros-t01: это представление данных, а не поведение; формулировка различает имя макроса в исходнике (`API_CREATE_PROC`) и значение столбца (`create_proc`). Сценарии «макрос сохранён с типом API_CREATE_PROC» оставлены: читаются как указание вида макроса.

6. **Related code/Notes — прямые правки в tasks.** Пункты, живущие вне требований (rti-parsing:151,163; mcp-pagination Related code/Notes; trc-storage:105; api-macros-t01 Notes), выполняются прямыми правками основных спек на этапе реализации; дельта-файлы их не выражают. trc-storage не входит в Modified Capabilities (его требования не меняются) — файл правится только в Related code.

## Risks / Trade-offs

- [Строки спек продолжают смещаться до реализации] → правки по содержимому, не по номерам строк; в tasks номера указаны как ориентиры «на 2026-10-10».
- [MODIFIED воспроизводит полные тексты — при ручном переносе легко потерять сценарий] → дельты собраны копированием актуальных блоков из основных спек; после правок — `openspec validate fix-spec-doc-drift-batch` и сверка количества сценариев.
- [Правка Use-string меняет текст, который может попадать в тесты help-вывода] → после правки — `go build ./...` + `go test ./cmd/...`; grep по `outgoing|incoming` в cmd/ для полноты (ожидается единственное вхождение на :70).
- [Убранные из сценариев профилей ~N-счётчики снижают точность проверки] → trade-off осознанный: структурная формулировка («базовые + RTI инструменты») проверяема по составу групп, а не по числу, и не дрейфует.
