# Design: tableFullScan — derived tables и INSERT…SELECT

## Context

Парсинг FROM-части правила `tableFullScan` устроен как конвейер: `findTopLevelFromClauseBounds` (скобко- и строко-aware, корректен) → `parseTablesInFromClause` (замена JOIN на запятые, split по запятым с учётом скобок) → `parseTableWithAlias` (первый whitespace-токен = имя таблицы). Узкое место — последний шаг: для derived table `(select …) t` токен №0 = `(select`, `strings.Trim(tokens[0], "()")` даёт «таблицу» `select`, алиасом становится мусор `ct.LoanID,`. Полный разбор — в `Bug-reports/BUG-tableFullScan-derived-table-false-positive-20261015.md`.

Второй дефект: `findStatementStart` знает только `select|delete|update|merge` — INSERT…SELECT ловится со строки `select` (line смещён, цель INSERT не анализируется).

Важно: `extractTablesFromFromClause` используется и другими правилами (`tableHintExists`, `indexWrong` и др.) — правки обязаны быть обратно совместимыми для обычных таблиц.

## Goals / Non-Goals

**Goals:**

- Derived table `(subquery) alias` распознаётся как сущность: алиас после парной закрывающей скобки; внутренние таблицы анализируются рекурсивно со своим WHERE/ON.
- Finding никогда не несёт `object` из SQL-ключевых слов (`select`, `from`, …).
- INSERT…SELECT: оператор начинается с `insert`, `line` — начало оператора; анализируется только SELECT-часть.
- Поведение для обычных (не derived) таблиц и для других правил-потребителей FROM-парсера не меняется.

**Non-Goals:**

- НЕ переписываем SQL-парсинг на полноценный токенизатор/AST — точечные правки существующего строкового конвейера.
- НЕ трогаем CTE (`with … as (…)`), табличные переменные `@t`, `openrowset(...)` — вне репро, отдельные паттерны.
- НЕ распространяем требование фильтрации на цель INSERT (она пишется, не читается).
- НЕ чиним прочие независимые баги `tableFullScan` из старых BUG-отчётов (word-boundary и пр. — уже закрытые/отдельные истории).

## Decisions

### 1. Derived tables: рекурсия, а не пропуск

Вариант «пропускать derived tables целиком» (минимальный, допускался багрепортом) убирает ложные срабатывания, но прячет реальные нарушения внутри подзапросов. Выбран полный вариант: в `parseTablesInFromClause` часть, начинающаяся с `(`, обрабатывается отдельно:

- находим парную закрывающую скобку (с учётом строковых литералов — тот же алгоритм, что в `findTopLevelFromClauseBounds`);
- алиас = первый токен после скобки (до конца части / `on`);
- внутренности `( … )` прогоняются через тот же конвейер `findTopLevelFromClauseBounds → parseTablesInFromClause`, но WHERE/ON для их фильтрации берутся из текста подзапроса (у подзапроса свой WHERE), а не из внешнего WHERE. Таблицы подзапроса добавляются в общий список `tables` для последующей проверки `isTableFiltered`.

Внешние WHERE/ON продолжают применяться к обычным таблицам и к алиасам derived tables (внешний `where t.x = …`/`on g.… = t.…` сам по себе не делает derived table «отфильтрованной» — фильтрация внутренностей определяется внутренним WHERE).

### 2. Guard на SQL-ключевые слова в `TableName`

В `parseTableWithAlias`: если `Trim`-результат — зарезервированное слово из фиксированного набора (`select`, `from`, `where`, `on`, `as`, …), таблица отбрасывается (`TableName = ""`). Дешёвая страховка от whole-class артефактов при будущих сломах парсинга. Набор — компактный map, не полный SQL-стандарт.

### 3. INSERT: точка входа и scope

`findStatementStart` получает `insert` (как уже сделано в `findStatementStartForTableHintExists` — там insert есть). В `analyzeStatementForFullScan` для `stmtType == "insert"`: цель INSERT не добавляется в анализируемые таблицы (только SELECT-часть), `Line` = строка `insert`. INSERT…VALUES не имеет FROM — конвейер естественно даст пустой список таблиц → нет finding.

Альтернатива «не добавлять insert, оставить как есть» отклонена: line=857 вместо 855 — реальный дефект навигации по finding'ам.

### 4. Совместимость с другими правилами

`parseTableWithAlias` общий. Изменение сигнатуры не требуется; derived-aware логика живёт в `parseTablesInFromClause` (уровень выше). Для правил, которым derived tables не нужны, поведение меняется только в сторону «меньше мусорных записей `select`» — это строго улучшение; регресс-тесты существующих правил обязательны (см. Risks).

## Risks / Trade-offs

- [Рекурсия зацикливается на некорректном SQL / очень глубокой вложенности] → ограничение глубины рекурсии (константа, ~10) + при исчерпании — пропуск уровня (лучше FN, чем ложный FP с `object=select`).
- [Изменение поведения других правил-потребителей FROM-парсера] → полный прогон `go test ./internal/review/...` + сравнение findings на контрольном наборе FA-файлов до/после (diff должен содержать только исчезающие ложные `object=select`).
- [Парная скобка ищется в already-lowercased тексте со строковыми литералами] → переиспользовать строко-aware сканер (`'…'` с `''`-эскейпом), не сырой `strings.Index`.
- [Внутренний WHERE у derived table сложный (CASE, OR)] → `isTableFiltered` уже обрабатывает неквалифицированные условия и ref-алиасы; на первом этапе не углубляемся в SARGability внутри подзапросов — только наличие фильтра по алиасу/имени, как для обычных таблиц.

## Migration Plan

Чисто кодовое изменение без схемы/данных. Откат = revert коммита. Версия бинарника по стандартному циклу сборки.
