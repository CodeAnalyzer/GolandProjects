## Why

Жёсткая карта «расширение → кодировка» врёт для части корпуса FA: 2545 описаний процедур из 32 441 (7.8%, концентрируются в `fa-administrator/**/*.SQL`) хранятся в CP1251, а декодируются как CP866 — комментарии и header-описания превращаются в mojibake, полнотекстовый и семантический поиск по ним не работает. Существующая эвристика `DetectEncodingFromContent` — мёртвый код (считает кириллицей любой байт ≥ 0x80), а сигнатура mojibake, верифицированная побайтовой таблицей CP866, позволяет детектировать реальную кодировку по содержимому с надёжностью ~100% и практически нулевой ценой (один проход счётчиков по уже прочитанному буферу). Анализ: `Modifications/fix-sql-encoding-detection.md`.

## What Changes

- Детекция кодировки по содержимому становится **универсальным механизмом** для всех single-byte legacy-форматов индексатора: `.sql`, `.h`, `.tpr`, `.pas`, `.inc`, `.js`, `.smf`, `.dfm`, `.rpt`. Карта расширений из «истины» превращается в **prior** (tie-breaker при неубедительном сигнале содержимого).
- Алгоритм: один проход по сырым байтам (счётчики маркерных диапазонов, проверка валидности UTF-8) → выбор между UTF8/CP866/WIN1251 → ровно один decode. Артефакт-набор mojibake (байты CP1251-кириллицы, дающие руны в CP866-декоде: 0xC0–0xDF, 0xF2–0xF7, 0xF9–0xFE без легитимных №/°) расширяет маркерные диапазоны существующего `DetectFromBytes`.
- Точка применения — walk-воркер (после ReadFile+SHA-256, по горячему буферу; прецедент — `.md`). Определённая кодировка пишется в `FileInfo.Encoding` → в `files.encoding` БД (persisted-метаданные остаются истиной).
- ASCII fast-path: файл без байт ≥ 0x80 пропускает детекцию (decode — identity в любой кодировке).
- Прозрачность: счётчик перекодированных файлов `EncodingRefined` в `ScanStats` + печать в сводке прогона.
- `.md` (DetectMarkdownEncoding), `.xml` (DetectXMLEncoding), `.yaml`, `.t01` — без изменений.
- Требуется полная пересборка индекса (`codebase update --modified=false`): pre-filter по mtime+size не видит смены правила декодирования.

### Modified Capabilities

- `infrastructure/encoding-cli`: требование «Детекция кодировок» — расширенные маркерные диапазоны (артефакт-набор 0xF2–0xFF) и параметризация prior-ом расширения; требование «Кодировки по типам файлов» — карта расширений становится prior-ом, кодировка определяется по содержимому.
- `indexing/file-walking`: новое требование — детекция кодировки по содержимому в walk-воркере для single-byte форматов, счётчик `EncodingRefined`, взаимодействие с pre-filter.

## Impact

- **Код**: `internal/encoding/encoding.go` (детекция, расширение `DetectFromBytes`), `internal/fswalk/fswalk.go` (вызов детекции в воркере рядом с `.md`-веткой), `internal/model/model.go` (`ScanStats.EncodingRefined`), точка печати сводки (`cmd/update.go`/`cmd/init.go`), тесты `internal/encoding` + `internal/fswalk` (fixture-файлы CP866/CP1251/UTF-8).
- **Существующие потребители `DetectFromBytes`** (RTI-парсер, review): поведение сохраняется — prior по умолчанию CP866 эквивалентен текущему tie-break.
- **БД**: без изменений схемы; `files.encoding` начинает хранить детектированное значение.
- **Миграция**: полная пересборка обязательна; после неё mojibake-описания в `sql_procedures` → 0, пластырь `isMojibakeText` в `internal/store/db_fts.go` остаётся страховкой (retire — вне scope).
- **Производительность**: +1 линейный проход счётчиков по горячему буферу (~1–3% бюджета файла на фоне SHA-256/парсинга/COPY), параллельность в существующих walk-воркерах, sамплинг не требуется.
