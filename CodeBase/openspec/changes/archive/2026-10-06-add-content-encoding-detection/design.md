## Context

Детекция кодировки сегодня — жёсткая карта расширений в `internal/fswalk/fswalk.go:372-407` (`getEncodingAndLanguage`): `.sql/.h/.tpr/.t01` → CP866, `.pas/.inc/.js/.smf/.dfm/.rpt` → WIN1251. Walker читает файл, считает SHA-256, присваивает кодировку по карте; индексер декодирует `file.Content` через `DecodeBytes` в `decodeIndexedFileContent` (`internal/indexer/indexer.go:416-420`); `files.encoding` пишется в БД (`indexer.go:1604`). Прецедент контентной детекции в воркере — `.md` (`fswalk.go:287-290`, `DetectMarkdownEncoding`).

Эвристика `DetectFromBytes` (`internal/encoding/encoding.go:184-221`) уже реализована и используется RTI-парсером и review: ASCII → CP866; valid UTF-8 → UTF8; «почти UTF-8» (≥80% высоких байт в валидных последовательностях) → UTF8; затем счёт диапазонов 0x80–0x9F (cp866) vs 0xC0–0xDF (cp1251), tie → CP866. Функция `DetectEncodingFromContent` (`encoding.go:79-104`) — мёртвый код: `hasCyrillic` считает кириллицей любой байт ≥ 0x80.

Анализ корпуса FA (change add-description-search, замер 2026-10-05): 2545/32 441 (7.8%) описаний процедур — mojibake (CP1251-байты в CP866-декоде), концентрируются в `fa-administrator/**/*.SQL`. Сигнатура mojibake верифицирована побайтовой таблицей CP866: байты 0xC0–0xDF → руны U+2500–U+259F, 0xF2–0xF7 → украинские ЄєЇїЎў, 0xF9–0xFE → ∙·√№¤■ (№ 0xFC и ° 0xF8 легитимны в CP866 и в артефактный набор не входят); в легитимном русском тексте эти руны не встречаются, mojibake-документ распознаётся с ~100% вероятностью. Полный анализ: `Modifications/fix-sql-encoding-detection.md`.

## Goals / Non-Goals

**Goals:**

- Универсальная детекция по содержимому для всех single-byte legacy-форматов индексатора с картой расширений как prior.
- Нулевая деградация производительности индексации: один линейный проход счётчиков по уже прочитанному буферу, одно декодирование.
- Сохранение поведения существующих потребителей `DetectFromBytes` (RTI, review).
- Прозрачность: метрика `EncodingRefined` в `ScanStats` и сводке прогона.
- Правдивое `files.encoding` в БД (persisted-метаданные).

**Non-Goals:**

- Retire пластыря `isMojibakeText` в `internal/store/db_fts.go` (остаётся страховкой; отдельное решение после корпуса без mojibake).
- Версионирование правила декодирования в pre-filter ключе (автоматический перерид при смене правила) — механизм `update --modified=false` достаточен; если правила детекции будут эволюционировать часто, вернуться.
- Детекция для `.md` (уже есть `DetectMarkdownEncoding`), `.xml` (`DetectXMLEncoding`), `.yaml`, `.t01` (генерируемые копии, CP866 по определению препроцессора).
- Полноценная языковая модель (chardet-класс): выбор бинарный CP866/CP1251 плюс UTF-8 — структурных сигнатур достаточно.
- Удаление мёртвого `DetectEncodingFromContent` — выполняется попутно, если не всплывут скрытые вызовы (аудит в задачах); иначе отдельный рефакторинг.

## Decisions

### D1. Детекция по сырым байтам до декодирования (detect → decode), а не decode-repair-redecode

Сигнатура mojibake — биекция с сырыми байтами: «есть руны U+2500–U+259F в CP866-декоде» ≡ «есть байты 0xC0–0xDF в сырых данных». Поэтому вариант из исходного предложения (декодировать CP866 → сканировать руны → перекодировать при сигнатуре) сводится к подсчёту байтовых диапазонов без первого декода.

- Выбрано: один проход счётчиков по сырым байтам → выбор кодировки → ровно один decode. Все файлы по одной цене.
- Альтернатива (decode-repair): +1 полный decode для всех файлов, +2-й decode для ~8% flipped, rune-scan медленнее byte-scan. Отвергнуто по стоимости без потери точности.

### D2. Расширение `DetectFromBytes` prior-параметром вместо новой функции

`DetectFromBytes(data)` сохраняет сигнатуру и семантику tie→CP866 (RTI-парсер `internal/rti/parser.go:81` и review `internal/review/review_helpers.go:2135` не меняются). Новая точка входа принимает prior (CP866|WIN1251|UTF8): prior используется как результат для ASCII-файлов, tie-breaker при равенстве счёта и фолбэк при слабом сигнале.

- Альтернатива: отдельная функция `DetectIndexedFileEncoding`. Отвергнута — дублирование алгоритма, риск расхождения версий.
- Альтернатива: поменять сам `DetectFromBytes(data)` на prior-обязательный. Отвергнута — ломает существующих потребителей ради синтаксической чистоты.

### D3. Счёт диапазонов с артефакт-набором, а не бинарная сигнатура «≥1 артефакт → WIN1251»

`cp866Score` += байты 0x80–0x9F (заглавные А-Я в CP866; в CP1251 — типографский мусор, редкий в legacy-SQL). `cp1251Score` += байты 0xC0–0xDF (заглавные А-Я в CP1251, псевдографика в CP866) и 0xF2–0xFF **кроме** 0xFC (№) — артефакт-набор: в CP1251 это строчные р–я (частые), в CP866 — украинские буквы и спецруны (в русском тексте редкие); 0xFF (я в CP1251 / nbsp-подобное в CP866) включается. Диапазоны 0xA0–0xBF и 0xE0–0xF1 амбигуальны (строчные в обеих кодировках / частая пунктуация) — не голосуют.

- Рамки в легитимных CP866-комментариях не переворачивают результат: артефактные байты рамок конкурируют с кириллицей 0x80–0x9F/0xA0–0xAF, а счёт видит весь файл.
- Альтернатива: порог «≥1 артефакт» (шаг 1 исходного предложения). Отвергнут из-за ложных срабатываний на легитимной псевдографике; счёт поглощает эту эвристику — файл mojibake набирает десятки артефактных байт и выигрывает счёт с запасом.
- Калибровка весов/порога отложена до корпусной валидации (T1 в tasks); стартовая гипотеза — равные веса, решение по большинству, tie → prior.
  **Результат корпусной валидации (2026-10-05, FA 104 860 файлов, отчёт `internal/encoding/corpus_encoding_report.txt`, запуск `go test ./internal/encoding/ -tags corpus -run TestCorpusEncodingValidation`)**: 2 963 flip-а (2.8%), 0 подтверждённых ложных. Разбивка: `sql/h/tpr CP866→WIN1251` 1 584 (mojibake-зона, все превью читаемые, cp866=0); `→UTF8` 1 243 (реально UTF-8 файлы: 780 PAS fa-administrator — современный Delphi-клиент, 413 SQL, H/TPR/JS); `inc/pas/smf/js WIN1251→CP866` 135 (глобально CP866 .inc Archiver/DataLoad, единичные Diasoft PAS/SMF/JS — превью читаемые; 18 third-party PAS — английские комментарии со stray CP1252-байтами, сегодня одинаково искажены под WIN1251, не регрессия); 6 бинарных DFM (обе кодировки бессмысленны, парсер не затронут). CP1251 SQL распределены по всем модулям (top: fa-reports 197, fa-contracts 182, fa-payments 92, fa-administrator 87) — оценка add-description-search о «концентрации в fa-administrator» была неточной. Веса оставлены равными.

### D4. Точка применения — walk-воркер (прецедент `.md`), не `decodeIndexedFileContent`

`files.encoding` пишется в БД из `FileInfo.Encoding`; детекция в воркере делает persisted-метаданные истиной, а decode-hook остаётся нетронутым. ASCII fast-path и `.md`-ветка уже живут там же.

- Альтернатива: детект в `decodeIndexedFileContent`. Отвергнута — в БД попадало бы значение по карте, детекция выполнялась бы при каждом декодировании (H-файл декодируется один раз, но точка менее очевидна), метаданные лгали.

### D5. Производительность: без сэмплирования, без новых горутин, ноль аллокаций

Проход счётчиков — простой `switch` по байту над буфером, уже находящимся в L1/L2 после `os.ReadFile`+SHA-256. Выполняется в существующих walk-воркерах — параллельность бесплатна. Замер (`encoding_bench_test.go`, Ryzen 5 3600): «почти UTF-8»-проверка и маркерные счёты слиты в один проход (`scanUTF8AndScore`); worst-case синтетика (30% высоких байт) — ~0.5 ГБ/с, ASCII fast-path — ~3.7 ГБ/с, 0 аллокаций; SHA-866-ориентир SHA-256 ~1.9 ГБ/с. На реальном корпусе (кириллица только в комментариях) стоимость ближе к ASCII-ветке: ~0.2 мс на файл 100 KB, <1% wall-time прогона.

- Сэмплирование первых N KB отвергнуто:_header-комментарии наверху, но кириллица бывает и внизу; полный проход по горячему буферу дешевле рисков.
- Слияние прохода детекции с циклом SHA-256 отвергнуто: связывает несвязанные функции ради микроэкономии, SHA-256 через crypto.Sum не даёт хук на байт.

### D6. Метрика и логирование

`ScanStats.EncodingRefined` — счётчик файлов, где детект отличался от prior; печать в сводке прогона рядом с `Pre-filtered: N`. Per-file логирование перекодировок — debug-уровень/выгрузка SQL-запросом по `files.encoding` после прогона (специальный лог не заводится).

## Risks / Trade-offs

- [Ложные перекоды CP866-файлов с богатой псевдографикой и бедной кириллицей] → корпусная валидация до фиксации весов (T1): полный прогон детектора по FA-дереву офлайн, сверка flip-ов с известными 2545 mojibake, ручная вычитка flip-ов вне fa-administrator. Спасает prior: при слабом сигнале остаёмся на карте.
- [Кириллица в CP866 только в нижнем регистре (0xA0–0xAF + 0xE0–0xEF — амбигуальные диапазоны) даёт cp866Score ≈ 0] → артефакт-набор голосует за CP1251 только при реальных CP1251-байтах; файл с чистым CP866-нижним-регистром набирает нули в обоих счётах → tie → prior (CP866 для .sql). Корректно по построению.
- [Смена поведения review/RTI незаметно] → `DetectFromBytes(data)` без prior сохраняет tie→CP866; тест-двойник регрессии в задачах (T5).
- [Двойная цена на pre-filtered файлах: старый прогон декодировал по карте, новый — по содержимому; hash одинаков] → необходима полная пересборка `codebase update --modified=false` (механизм уже существует, см. `indexing/file-walking`, «Полная пересборка»); инкрементальный update после деплоя нового бинарника не подхватит перекодировку для неизменённых файлов.
- [Украинскоязычные файлы в CP866 (легитимные ЄєЇїЎў в 0xF2–0xF7) голосуют за CP1251] → в корпусе FA не наблюдалось (замер add-description-search); при появлении — калибровка весов по корпусной валидации, fallback остаётся prior.

## Migration Plan

1. Деплой нового бинарника (старый бинарник корректно работает со старыми данными — read-only MCP-профили не затронуты).
2. Полная пересборка: `codebase update --modified=false` (reset таблиц кодовой базы + init-пайплайн; RTI/TRC-сессии и история сохраняются).
3. Проверка: SQL-запрос количества mojibake-описаний в `sql_procedures` → 0; `EncodingRefined` в сводке ≈ масштабу перекода (ожидание порядка тысяч файлов fa-administrator + одиночные).
4. Пересбор LSA-модели desc-слоя происходит штатно в init-пайплайне (порог изменений будет превышен).
5. Откат — бинарный: предыдущий бинарник + `update --modified=false` возвращает старое правило декодирования.

## Open Questions

- Точная калибровка весов артефакт-набора (равные веса vs повышенный вес 0xC0–0xDF против 0xF2–0xFF) — решается корпусной валидацией (T1) без изменения спек: стартуем с равных весов.
- Удалять ли мёртвый `DetectEncodingFromContent` в этом change — зависит от аудита вызовов (T4); решение локальное, на спеки не влияет.
