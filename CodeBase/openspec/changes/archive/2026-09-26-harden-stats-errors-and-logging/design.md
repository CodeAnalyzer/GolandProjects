## Context

См. `proposal.md` — Why. Текущее состояние:

- `store.DB.GetStats(ctx, lsaGeneration)` (`internal/store/db_stats.go:13`) считает 41 агрегат живым `COUNT(*)`; вызывается из `systemsvc.ExecuteStats` (`internal/systemsvc/runtime.go:56`) на каждый `codebase stats` / `codebase_stats`.
- `query.GetProcedureResult(ctx, name)` (`internal/query/query_sql.go:508`) возвращает `*SQLProcedureResult`; при отсутствии строки `QueryRowContext` даёт `sql.ErrNoRows`, который доходит до CLI/MCP как ошибка. Этим методом пользуются не только query-команды, но и обогащение RTI/TRC (`internal/rti/enrich.go:51`, `internal/trc/enrich.go:37`), для которых ошибка = «не найдено».
- `formatToolArgs` (`internal/mcp/server.go:189`) возвращает один аргумент: перебор списка приоритетов, иначе первый ключ `map`; маскировки нет.
- Схема инициализируется идемпотентно (`InitSchema`), миграций нет.

## Goals / Non-Goals

**Goals:**
- Убрать 41 `COUNT(*)` с горячего пути `stats`: снапшот по завершении `init`/`update`, чтение без пересчёта.
- `query procedure` / `codebase_query_procedure`: отсутствие процедуры — пустой результат, не ошибка.
- Логи MCP: все аргументы, детерминированный порядок, маскировка `text`/`sql`.

**Non-Goals:**
- Не менять контракт `GetProcedureResult` для обогащения RTI/TRC (ошибка = «не найдено» сохраняется).
- Не оптимизировать сами `COUNT(*)` (инкрементальные счётчики по ходу индексации) — снапшота достаточно.
- Не менять форму хранения LSA-поколений и sidecar-state.
- Не вводить ограничения по времени/таймауту на `stats`.

## Decisions

**D1. Отдельная таблица `stats_snapshot`.** Снапшот хранится в одной актуальной строке таблицы `stats_snapshot` (payload + `lsa_generation` + `created_at`), создаваемой в `InitSchema`. Поколение LSA хранится рядом с payload, потому что счётчики `spec_vocab_terms`/`spec_embeddings` от него зависят. Альтернатива — колонка `stats_json` в `scan_runs` — отклонена: `scan_runs` описывает прогресс сканирования, а `stats` включает и спеку-метрики, не привязанные к скану; отдельная таблица чище и переживает `update --modified=false`.

**D2. Запись снапшота — в конце `init`/`update`.** После успешного `idx.InitCtx`/`idx.UpdateCtx` (`cmd/init.go`, `cmd/update.go`) вызывается `RefreshStatsSnapshot`, который один раз прогоняет живой подсчёт (текущий `GetStats`) и перезаписывает строку снапшота. LSA-поколение разрешается тем же helper'ом, что и в `systemsvc`, чтобы `spec_vocab_terms`/`spec_embeddings` были generation-осведомлёнными уже на момент записи.

**D3. Чтение — снапшот, фолбэк — живой подсчёт.** `GetStats` читает снапшот, только если его `lsa_generation` совпадает с запрошенным поколением; иначе (снапшота нет, БД пустая/старая, поколение сменилось или state недоступен) выполняет живой подсчёт и сохраняет результат в `stats_snapshot` вместе с запрошенным поколением. Ошибка чтения снапшота не заваливает `stats` — деградирует в живой подсчёт.

**D4. P7 — обработка на границе команды.** `GetProcedureResult` **не меняет** сигнатуру/семантику (ошибка при отсутствии), чтобы не ломать обогащение RTI/TRC. Вместо этого CLI `cmd/query_commands.go` и MCP-обработчик `codebase_query_procedure` (`registry.go:447`) перехватывают `errors.Is(err, sql.ErrNoRows)` и возвращают пустой срез `[]SQLProcedureResult{}` → envelope `count: 0`, `items: []`. Форма ответа становится массивом 0/1 (BREAKING для потребителей, ожидавших объект).

**D5. A1 — канонический формат аргументов.** `formatToolArgs` логирует **все** аргументы: ключи сортируются, значение форматируется компактно (`fmt` для скаляров, JSON для составных), пары `k:v` соединяются `,`; значения ключей `text` и `sql` заменяются маской. Пустой набор — `args=-`. Порядок детерминирован (сортировка), что делает логи пригодными для группировки.

**D6. Снапшот — best-effort.** Падение записи снапшота логируется как предупреждение и не отменяет успешную индексацию; следующий `init`/`update` или фолбэк покроют чтение.

## Risks / Trade-offs

- [Снапшот устаревает, если БД меняется вне `init`/`update`] → `stats` считает только индексные и спека-таблицы, которые меняются именно при индексации; RTI/TRC-таблицы в статистику не входят. Риск принят; фолбэк покрывает отсутствие снапшота.
- [Изменение формы `query procedure` (объект → массив 0/1)] → зафиксировано как BREAKING; покрыто сценарием спеки.
- [Маскировка `text`/`sql` скрывает содержимое при отладке] → компромисс в пользу приватности; при необходимости задаваемый список маскируемых ключей расширяется без смены формата.
- [Отдельная таблица схема-изменение] → `CREATE TABLE IF NOT EXISTS` в `InitSchema` идемпотентен; старые БД получают таблицу при следующем запуске.
- [41 `COUNT(*)` теперь в конце init/update] → одноразовая стоимость там, где индексация и так доминирует; на `stats` путь переносится с горячего на холодный.

## Migration Plan

Схема расширяется идемпотентно. После обновления бинарника: старые БД работают через фолбэк, пока не пройдёт `init`/`update`; затем `stats` читает снапшот. Откат — revert коммита (таблица безвредна).
