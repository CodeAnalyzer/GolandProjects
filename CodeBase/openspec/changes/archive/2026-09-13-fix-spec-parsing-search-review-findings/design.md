## Context

См. `proposal.md` — Why. Текущий update-конвейер удаляет исчезнувшие файлы после spec-постпроцессинга, а LSA имеет быстрый выход по `corpusDelta == 0`, поэтому удаление и предыдущая неуспешная попытка могут не привести к повторной проверке корпуса. Публикация LSA последовательно изменяет один файл модели, vocab, embeddings и state без общего поколения. Лексический слой хранит невзвешенные `tsvector`, trigram-запрос сравнивает короткое имя с длинным агрегированным текстом, а `by-code` выбирает snippet через `COALESCE(CONCAT_WS(...))`, где пустая строка блокирует подходящую ветвь.

Изменение пересекает индексатор, PostgreSQL-схему, файловую модель, query service, CLI/MCP и Markdown-парсер. Новые внешние зависимости не нужны; PostgreSQL остаётся источником индексированных сущностей, а бинарная LSA-модель — файловым артефактом.

## Goals / Non-Goals

**Goals:**

- Гарантировать, что semantic-поиск использует согласованное поколение модели и embeddings и что удаление попадает в следующий опубликованный корпус.
- Сделать повтор после любой незавершённой LSA-публикации обязательным и наблюдаемым.
- Сохранить действующие CLI/MCP-вызовы и привести README со спецификацией к фактическим параметрам `query`/`--query`.
- Сопоставить SQL поиска с реально созданными FTS/trigram-индексами.
- Возвращать точные исходные границы Markdown-блоков и корректный контекст `by-code`.

**Non-Goals:**

- Изменение токенизатора, формулы TF-IDF, SVD или порогов качества LSA.
- Добавление semantic embeddings уровня requirement/scenario/usecase.
- Изменение семантики остальных spec-инструментов (`deps`, `coverage`, `history`, `config`, `usecase`).
- Поддержка новых форматов Markdown помимо исправления границ уже распознаваемых блоков.

## Decisions

### D1. Удалять исчезнувшие файлы до spec-постпроцессинга и всегда проверять fingerprint корпуса

После завершения workers оба cleanup-шага — старые версии изменённых файлов и исчезнувшие пути — выполняются до `runPostProcessingParallel`. Это даёт всем spec-постпроцессорам актуальный граф и позволяет LSA сразу увидеть удаление. Счётчик `FilesDeleted` обновляется до запуска LSA.

Небезопасный быстрый выход до загрузки корпуса удаляется. LSA всегда загружает детерминированный корпус и вычисляет fingerprint, но SVD и публикация по-прежнему пропускаются при совпадении fingerprint/параметров/версии и отсутствии незавершённой публикации. Это увеличивает стоимость идемпотентного прогона на чтение корпуса, но исключает недетектируемые удаления и ложный успех после ошибки.

Альтернатива — передавать в LSA только `removedPaths` и сохранять быстрый путь. Она отклонена, потому что не обнаруживает внешнюю рассинхронизацию state/БД и сохраняет две конкурирующие модели определения актуальности.

### D2. Публиковать LSA поколениями с атомарным файловым переключением

Каждое обучение получает `generation`, равный fingerprint корпуса и параметров. Модель содержит generation. В `spec_vocab` и `spec_embeddings` добавляется колонка `generation`; уникальность vocab становится `(generation, term)`, embeddings индексируются по `(generation, spec_id, embed_level)`.

Протокол публикации:

1. До вычислений атомарно записать в state `retry_fingerprint` текущего корпуса, не меняя fingerprint/generation активной публикации; непустой маркер принудительно включает retrain независимо от порога.
2. Рассчитать vocab, TF-IDF, SVD и новую модель полностью в памяти.
3. Записать модель во временный файл рядом с целевым `lsa_model_path`, выполнить close/sync.
4. Одной транзакцией вставить vocab и embeddings нового generation, не удаляя активное поколение.
5. После commit атомарно заменить целевой файл модели временным через rename; модель является указателем на активный generation.
6. Записать state с тем же generation/fingerprint и пустым `retry_fingerprint` атомарной заменой файла.
7. Только после успешного переключения удалить устаревшие поколения из БД; ошибка cleanup не влияет на активность модели.

Поиск загружает generation из модели и выбирает embeddings только этого generation. Если вычисление, подготовка, транзакция или rename завершаются ошибкой, старый файл модели продолжает указывать на сохранённое старое поколение БД, а `retry_fingerprint` остаётся в state и заставляет следующий прогон повторить обучение. Подготовленные, но неактивные строки нового generation безопасно очищаются при повторе. Serving использует поколение из модели и не зависит от retry-маркера.

Для миграции существующие строки получают generation `legacy`; существующая модель без generation читается как `legacy`. Первое успешное переобучение публикует fingerprint-generation и затем удаляет legacy-данные.

Альтернатива — очищать и заменять текущие таблицы в транзакции, затем заменять файл. Она отклонена: транзакция PostgreSQL и rename файловой системы не образуют общий atomic commit и оставляют окно рассинхронизации.

### D3. Разрешать путь модели одной конфигурационной функцией

В `internal/config` добавляется функция, возвращающая абсолютный путь LSA-модели: пустое значение означает `spec_lsa_model.bin` рядом с активным конфигурационным файлом, относительное значение разрешается относительно того же каталога, абсолютное сохраняется. Индексатор, state path и query service используют только эту функцию.

Альтернатива — исправить относительный путь только в индексаторе. Она отклонена как дублирование правил, способное снова разойтись.

### D4. Формировать weighted `tsvector` и выполнить миграционный пересчёт

Для capability, requirement, scenario и usecase используются конкатенации `setweight(to_tsvector(...), 'A'|'B')` согласно delta-спеке. Одна store-функция содержит выражения и применяется как при индексации файла, так и при миграционном backfill всех существующих строк. GIN-индексы остаются на колонке `search_vector`.

Миграция schema init обновляет существующие векторы до нового состава независимо от `IS NULL`; чтобы не выполнять полный backfill при каждом запуске, вводится версия spec search schema в служебной миграции либо идемпотентный versioned migration существующего механизма схемы.

### D5. Разделить лексический поиск текста и технических mentions

`tsvector` остаётся основным поиском бизнес-текста. Trigram-ветвь строится как `UNION ALL` совместимых результатов:

- поля/выражения capability, requirement, scenario и usecase, для которых существуют соответствующие `gin_trgm_ops` индексы;
- `spec_code_mentions.mention_name` с приоритетом регистронезависимого точного совпадения и fallback similarity.

Mention преобразуется обратно к capability/entity через `source_type` и существующие связи requirement→capability, scenario→requirement→capability, usecase→`usecase_involves`. Результаты дедуплицируются по `(level, entity_id)`, при этом лучший rank сохраняется. Порог similarity остаётся централизованным; точное совпадение не зависит от порога.

Альтернатива — снизить порог similarity для агрегированного `search_text`. Она отклонена из-за шума, последовательных сканов и зависимости результата от длины документа.

### D6. Явно классифицировать ошибки semantic-слоя

`ExecuteSpecSearch` различает отсутствие активной модели и операционные ошибки:

- `layer=both` + model-not-found: exact возвращается, `semantic_meta.reason = "unavailable"` и содержит диагностическую подсказку;
- `layer=semantic` + model-not-found: возвращается `ErrSpecModelNotFound`;
- ошибка чтения/декодирования модели, несовпадение generation или ошибка БД: возвращается как ошибка для обоих режимов.

Ошибки не подавляются общим `if err == nil`. Это сохраняет graceful degradation только для ожидаемого отсутствия ещё не обученной модели.

### D7. Выбирать snippet `by-code` по source_type

SQL использует `CASE m.source_type` и отдельную текстовую сборку для capability, requirement, scenario и usecase. `NULLIF(..., '')` применяется как защитный fallback. Путь берётся из `m.file_id`, поэтому mention из usecase продолжает указывать на usecase-файл.

Альтернатива — переставить аргументы существующего `COALESCE`. Она отклонена: `CONCAT_WS` возвращает пустую строку и проблема повторится для любого неподходящего alias.

### D8. Передавать фактическую строку закрытия в Markdown-парсеры

`closeScenario` принимает `lineEnd`, который вызывающая state machine передаёт как `lineNo - 1` при следующем структурном заголовке и `len(lines)` в конце файла. Подсчёт по количеству распознанных GWT-строк удаляется. Delta-парсер при первом scenario завершает сохранённый body с `lineNo - 1`, а не `delta.LineStart`.

Границы включают строки исходного блока, даже если их содержимое не сохраняется в GWT-полях. Это соответствует навигационной семантике line_start/line_end.

### D9. Исправить документацию без расширения публичного интерфейса

Фактические интерфейсы уже согласованы: MCP использует обязательное поле `query`, а CLI — обязательный флаг `--query`. Упоминания `text` и `--text` в README и основной спецификации являются ошибкой документации и заменяются на канонические имена. Код CLI и MCP по этому пункту не изменяется.

Альтернатива — добавить alias ради совместимости с ошибочной документацией. Она отклонена: подтверждённых клиентов alias нет, а второй способ передачи одного параметра усложнит валидацию и дальнейшее сопровождение API.

## Risks / Trade-offs

- [Загрузка LSA-корпуса на каждом update увеличит длительность идемпотентного прогона] → измерить отдельную стадию load/fingerprint; оптимизировать позднее только через проверяемый corpus revision, не через статистику одного прогона.
- [Generation-колонки временно увеличат объём vocab/embeddings] → очищать неактивные поколения после успешного переключения и в начале следующего обучения.
- [Смена FTS-весов изменит порядок exact-результатов] → закрепить integration-тестом приоритет A над B; это ожидаемое контрактное изменение.
- [Дополнительный UNION по mentions увеличит сложность SQL] → использовать индекс `mention_name gin_trgm_ops`, точный lower-index и отдельные CTE с проверкой плана на тестовом PostgreSQL.
- [Атомарный rename может различаться на Windows и Unix] → использовать существующий кроссплатформенный helper атомарной записи либо реализовать replace с тестами обеих поддерживаемых семантик; временный файл всегда размещать на том же томе.
- [Внешний клиент мог реализовать ошибочно документированный `text`] → считать фактическую MCP-схему и Cobra CLI источником совместимости; отдельно отметить исправление параметра в README и release notes.

## Migration Plan

1. Добавить nullable/default `generation = 'legacy'` в `spec_vocab` и `spec_embeddings`, заменить уникальные индексы на generation-aware варианты без удаления текущих данных.
2. Развернуть чтение legacy-модели как generation `legacy`, сохранив работоспособность semantic-поиска до переобучения.
3. Пересчитать weighted `search_vector` versioned-миграцией.
4. При первом успешном LSA-переобучении опубликовать fingerprint-generation по новому протоколу и удалить legacy-поколение после переключения.
5. При откате бинарника legacy-строки могут быть уже удалены, поэтому rollback выполняется вместе с восстановлением предыдущего файла модели и дампа `spec_vocab`/`spec_embeddings`; до подтверждения новой версии cleanup legacy-поколения можно отложить на один успешный последующий прогон.
