## Purpose

Полнотекстовый поиск по спецификациям в два слоя: лексический (tsvector 'russian' + pg_trgm по всем уровням сущностей спек) и семантический (TF-IDF + LSA на capability-уровне), с раздельными секциями результата. Управление LSA-моделью: обучение при пост-обработке индексации, пересчёт по порогу изменений, хранение словаря и векторов в БД, матрицы проекции — в файле рядом с БД.

## ADDED Requirements

### Requirement: Лексический слой поиска

Система SHALL обеспечивать точный полнотекстовый поиск по `spec_capabilities` (title A-вес, purpose/notes B), `spec_requirements` (requirement_name A, body_text B), `spec_scenarios` (given/when/then B), `spec_usecases` (title A, description B) через `tsvector`, конфигурацию 'russian' и GIN-индексы. Технические идентификаторы (`API_*`, `FCD_*`, имена таблиц) дополнительно ищутся через `pg_trgm` similarity — как в текстах спек, так и в `spec_code_mentions`. Поиск поддерживает фильтры: продукт, уровень сущности (capability|requirement|scenario|usecase), статус (для changes).

#### Scenario: Поиск по бизнес-термину
- **GIVEN** проиндексированные спеки с требованием «Арест аналитического счёта»
- **WHEN** выполняется поиск по запросу «арест счёта»
- **THEN** найдены capability и требования, содержащие термин, с указанием продукта, slug и границ строк

#### Scenario: Поиск технического идентификатора
- **GIVEN** спеки, упоминающие `API_CCred_BindClassifier` в текстах сценариев
- **WHEN** выполняется поиск по имени без точного совпадения падежа/контекста
- **THEN** trgm-слой находит упоминания в текстах спек, включая тексты сценариев, а не только секции Related code

### Requirement: Семантический слой — TF-IDF + LSA

Система SHALL строить семантический слой поиска через TF-IDF + LSA: токенизация с тремя категориями терминов (русские слова — нижний регистр и стемминг; технические идентификаторы — как есть, единым токеном; гибриды вида `758П`/`275-ФЗ` — как есть), словарь с фильтрацией minDF/maxDF, TF-IDF с log-нормализацией и smooth IDF, SVD-разложение (gonum). LSA применяется на уровне capability (embed_level = 'spec'): каждый capability получает k-мерный вектор (k=128); requirement-уровень покрывается только лексическим слоем.

#### Scenario: Семантическая близость через ко-встречаемость
- **GIVEN** корпус спек, где «арест» и «блокировка» встречаются в одних документах
- **WHEN** выполняется поиск «блокировка счёта» семантическим слоем
- **THEN** capability про арест счёта попадает в секцию семантически близких с косинусной оценкой

#### Scenario: Технический идентификатор как единый токен
- **GIVEN** тексты спек со словами `CON_STP_MassAccrual` и обычной русской лексикой
- **WHEN** строится словарь
- **THEN** `CON_STP_MassAccrual` — один токен словаря (не разбит на части), русский текст — стеммированные токены

### Requirement: Обучение и пересчёт LSA-модели

Система SHALL обучать LSA-модель при пост-обработке индексации и пересчитывать её по порогу: модель пересобирается, когда с момента последнего обучения изменилось число сущностей спек сверх порога (настраивается в конфигурации; при нулевом пороге — после каждого прогона). Словарь (term, doc_freq, idf) и векторы документов хранятся в таблицах `spec_vocab` / `spec_embeddings`; матрица проекции Vᵀ сериализуется в файл модели рядом с БД. Пересчёт детерминирован: одинаковый корпус даёт одинаковую модель.

#### Scenario: Пересчёт после массовых изменений
- **GIVEN** обученная модель и `codebase update`, изменивший 50+ capability
- **WHEN** выполняется пост-обработка
- **THEN** модель переобучена на актуальном корпусе, векторы в `spec_embeddings` обновлены

#### Scenario: Порог не достигнут
- **GIVEN** обученная модель и `codebase update`, изменивший 1 spec.md (порог 50)
- **WHEN** выполняется пост-обработка
- **THEN** модель не пересчитывается, поиск использует прежние векторы

### Requirement: Раздельные секции результата

Система SHALL выдавать результат поиска двумя раздельными секциями — «точные совпадения» (лексический слой, ранжирование ts_rank + trgm similarity) и «семантически близкие» (LSA, косинусная оценка) — без слияния ранжирований; документы, найденные обоими слоями, показываются в обеих секциях. Каждый результат содержит продукт, slug/имя, уровень сущности, границы строк и текст-фрагмент.

#### Scenario: Двухсекционный ответ
- **GIVEN** обученная модель и спеки, где часть совпадений точные, часть — только семантические
- **WHEN** выполняется `codebase query spec search --text "ограничение расходных операций"`
- **THEN** ответ содержит секцию точных совпадений (с ts_rank) и секцию семантически близких (с cosine score), перекрывающиеся документы видны в обеих

#### Scenario: Модель не обучена
- **GIVEN** индекс спек, но LSA-модель ещё не построена
- **WHEN** выполняется поиск
- **THEN** возвращается только секция точных совпадений с пометкой, что семантический слой недоступен

### Requirement: Доступ через CLI и MCP

Система SHALL предоставлять поиск через MCP-инструмент `codebase_query_spec_search` и зеркальную CLI-подкоманду `codebase query spec search` с параметрами: текст запроса, слой (exact|semantic|both, по умолчанию both), фильтры продукта/уровня, лимит. Большие ответы MCP проходят существующую пагинацию; CLI поддерживает `--json`/`--ndjson` envelope как прочие query-команды.

#### Scenario: MCP-вызов поиска
- **GIVEN** запущенный MCP-сервер и проиндексированные спеки
- **WHEN** вызывается `codebase_query_spec_search` с `text = "отключение SMS-уведомлений"`
- **THEN** возвращены доменные данные (count, items с секциями exact/semantic) без CLI envelope
