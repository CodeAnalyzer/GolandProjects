## Context

См. proposal.md — Why.

Текущая реализация `extractCapabilityDeps` в `internal/indexer/indexer_postprocess_spec_deps.go` использует 6 маркеров для извлечения `depends_on_capability`:

1. `reMDSpecLinkDeps` — markdown-ссылки `](../slug/spec.md)` — работает в fa-cards
2. `reLinkedDomains` — "Связан с доменами: `slug`" — работает в fa-contracts (частично)
3. `reSeeAlso` — "(см. `slug`)" — работает в fa-warranty, fa-reports (только в скобках)
4. `reSubdomains` — "поддомену/поддоменам: `slug`" — работает в fa-contracts
5. cci:-хвост — не используется ни в одном продукте FA
6. `ExtractSpecReferences` — пути `openspec/specs/slug/spec.md` — работает при наличии полных путей

Реальные spec-файлы FA используют как минимум 6 дополнительных форматов, не распознаваемых ни одним из существующих маркеров. Подробный анализ паттернов и продуктов — в proposal.md.

## Goals / Non-Goals

**Goals:**

- Распознать все 6 дополнительных паттернов, обнаруженных в реальных spec-файлах FA
- Сохранить обратную совместимость: существующие relations не должны измениться
- Новые relations получают `confidence: "notes"` (или `"inline"` для расширенного "см."), как текущие notes-паттерны
- Минимальное изменение кода: новые regex + новые блоки в `extractCapabilityDeps`

**Non-Goals:**

- Стандартизация форматов в spec-файлах FA — это задача продуктовых команд, не индексатора
- Извлечение зависимостей из семантического анализа текста (NLP) — только pattern matching
- Изменение схемы БД или API `codebase_query_spec_deps`
- Обработка cross-product зависимостей (между разными DS-продуктами) — отдельная задача

## Decisions

### Decision 1: Plain-text slugs в круглых скобках vs backtick-wrapped

**Решение:** Для паттернов "Связи с доменами: slug (desc)" и "Связи с другими spec: slug (desc)" извлекать slug как первое слово (до пробела или открывающей скобки) после двоеточия, а также из круглых скобок в формате `(slug, slug)`.

**Альтернатива:** Требовать backtick-обёртку для всех slugs. Отвергнуто: fa-generalledger и fa-cards не используют backticks в Notes, и заставлять продуктовые команды переписывать десятки spec-файлов нереалистично.

**Риск false positives:** Plain-text slugs могут совпасть с обычными словами. Снижение: slug резолвится через `resolveSlug` — если slug не найден в `slugToID`, relation не создаётся. Это естественный фильтр: только реальные capability names становятся relations.

### Decision 2: Расширение `reLinkedDomains` vs новый regex

**Решение:** Оставить `reLinkedDomains` без изменений ("Связан с доменами") и добавить отдельные regex для новых маркеров. Не объединять.

**Обоснование:** `reLinkedDomains` извлекает slugs из backtick-обёрток (`reBacktickSlugs`). Новые паттерны "Связи с доменами:" и "Связи с другими spec:" извлекают slugs из plain text и круглых скобок — другой механизм извлечения. Объединение создаст сложный regex, трудный для поддержки.

### Decision 3: Slug extraction из круглых скобок

**Решение:** Для паттернов с круглыми скобками `(slug, slug)` использовать regex `reParenSlugs = regexp.MustCompile(`\(([a-z0-9_\-/]+(?:\s*,\s*[a-z0-9_\-/]+)*)\)`)` и парсить запятые внутри.

**Альтернатива:** Извлекать всё содержимое скобок и сплитить по запятой. Отвергнуто: внутри скобок могут быть описания с запятыми, например `(card-proccenter, card-race-export) — загрузка рейсов`. Regex с ограничением на slug-символы надёжнее.

### Decision 4: Slug extraction из plain text "slug (desc)"

**Решение:** Для паттерна "Связи с другими spec: slug (desc)" извлекать slug как последовательность slug-символов перед открывающей скобкой. Regex: `rePlainTextSlug = regexp.MustCompile(`([a-z0-9_\-/]+)\s*\(`)`.

**Риск:** Может совпасть с обычными словами перед скобкой. Снижение: `resolveSlug` отфильтрует нерезолвённые имена.

### Decision 5: Расширение `reSeeAlso` для "см. `slug`" без скобок

**Решение:** Заменить текущий `reSeeAlso = (?i)\(см\.\s*\`([A-Za-z0-9_\-/]+)\`\)` на `reSeeAlso = (?i)(?:\(?\s*)?см\.\s*(?:spec\s+)?\`([A-Za-z0-9_\-/]+)\`(?:\s*\)?)?`. Это распознаёт "(см. `slug`)", "см. `slug`" и "См. spec `slug`".

**Альтернатива:** Отдельный regex для "См. spec `slug`". Отвергнуто: избыточно, `reSeeAlso` уже ищет "см." — достаточно сделать скобки опциональными и добавить "spec" как опциональное слово.

## Risks / Trade-offs

- **[False positives в plain-text извлечении]** → Mitigation: `resolveSlug` отфильтрует нерезолвённые slug'и; только реальные capability names станут relations. Дополнительная защита: slug должен содержать хотя бы один дефис или быть известным slug'ом (эвристика может быть добавлена позже, если false positives станут проблемой).

- **[Увеличение количества relations]** → После переиндексации количество `depends_on_capability` relations значительно возрастёт. Это может замедлить `codebase_query_spec_deps` при больших depth. Mitigation: существующая дедупликация и cycle-safe traversal уже справляются; при необходимости можно добавить лимит на размер дерева.

- **[Перекрытие паттернов]** → Некоторые spec-файлы могут использовать несколько паттернов одновременно (например, markdown-ссылки + "Связи с доменами:"). Mitigation: существующая дедупликация через `depSeen` map отсеивает дубликаты.

- **[Регрессия существующих тестов]** → Расширение `reSeeAlso` может изменить поведение существующих тестов. Mitigation: все существующие тест-кейсы должны пройти; новые тесты добавляются для новых паттернов.
