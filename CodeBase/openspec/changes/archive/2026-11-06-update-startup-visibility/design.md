# Design: update-startup-visibility

## Context

Тихое окно `update` до первого кадра спиннера (см. proposal.md — Why) состоит
из фаз `UpdateCtx` до `startProgressReporter` (runner.go:214): CreateScanRun →
BackfillAPIContractSearchVectors → discoverGitSources (последовательная
git-детекция + backfill привязок) → reconcileStaleFileGenerations →
GetLatestFilesByRootPath. Механизм именованных стадий уже существует
(`stats.Stage`, префикс до «: » = фаза, индер.go:1938-1970): стадии
`spec-lsa`/`desc-lsa` живут на собственной строке со спиннером. Индекса на
`files(path)` нет; предикаты backfill используют не-sargable `left()`.

## Goals / Non-Goals

Goals:

- Убрать «немоту» между баннером и спиннером: каждая подготовительная фаза
  видна как именованная стадия (переиспользование механизма `Stage`).
- Сжать окно: параллельная git-детекция пулом = effective parallel.
- Сжать окно: индекс `files(path)` + sargable-предикаты трёх pre-walk запросов.
- Атрибутировать окно пост-фактум: отдельные тайминги фаз в `Stage timings`.

Non-Goals:

- Чтение `.git/HEAD`/`.git/config` напрямую вместо git CLI (отклонено
  пользователем; worktree-семантика требует CLI).
- Параллелизация DB-upsert'ов discovery (resolve/UpsertDSProductBranch):
  остаются последовательными — детерминизм порядка и отсутствие contention;
  их стоимость (~160 roundtrip) на порядок меньше git-спавнов.
- Ускорение `GetLatestFilesByRootPath` при полном корне: LIKE root/% при
  root = весь FA покрывает все ~624k строк — seq scan + sort там легитимен,
  стоимость фазы в передаче строк, а не в скане. Индекс помогает backfill'у
  (80 узких префиксов) и подпутевым `update -p`.
- Стриминг-счётчик внутри `load state` (блокирующий SELECT): именованное
  ожидание без счётчика.

## Decisions

### D1. Ранний старт репортера, prep-фазы одной строкой через механизм Stage

`statsCollector` + `startProgressReporter` переносятся к началу `UpdateCtx`
(до BackfillAPIContractSearchVectors) и в `runInitPipeline` (до discovery).
Подготовительные фазы устанавливают `stats.Stage` через collector, всегда в
форме «фаза: деталь» — с ОБЩИМ префиксом `preparing`, поэтому репортер (фаза =
префикс до «: », фиксация `\n` только при смене фазы) держит их на ОДНОЙ
строке прогресса: деталь сменяется перезаписью на месте, без переводов строки
между фазами подготовки (UX-доводка по итогам рабочего прогона: пять
отдельных строк стадий делали вывод грязным):

- `preparing: git detection N/M` — счётчик инкрементируется только по
  завершении `detector.Detect` каталога; деталь живёт ровно до конца
  детекции;
- `preparing: source registry upsert` — пост-детекционная работа
  (resolve/upsert линий, SetDefaultBranch, bulk-backfill привязок); статичная
  деталь, чтобы счётчик N/M не «висел» на 80/80 во время backfill'а;
- `preparing: safety-net duplicates` — статичная деталь;
- `preparing: load state files` — статичная деталь (блокирующий SELECT).

Первая деталь prep-строки печатается ещё в cmd до старта репортера:
`preparing | schema check/migrations... ` (без перевода строки) до
`NewDB`/`InitSchema`, `done` — по завершении; затем cmd очищает строку
(`\r` + пробелы + `\r`), и репортер продолжает её же деталями — очистка
обязательна: кадры репортера короче строки схемы, `\r`-перезапись оставила бы
видимый хвост. Репортер дополнен флагом «первый кадр»: перевод строки перед
первой фазой не печатается (строка прогресса ещё пуста) — иначе prep-строка
началась бы с пустой строки, а при живой схемной строке cmd зафиксировала бы
её с несрезанным хвостом.

Переход prep→счётчики walk — штатная смена фазы (фиксация prep-строки `\n`).
CreateScanRun и FTS-backfill деталей не получают — их время атрибутируется
таймингом D4 (`PrepMiscMs`), а не отображением.

Альтернатива — прямые `fmt.Printf` строк фаз до спиннера — отклонена
пользователем: разрыв вывода при старте репортера и две механики отображения.

### D2. Параллельная git-детекция: пул воркеров, последовательные upsert'ы

`discoverGitSources(ctx, rootPath, detector, parallel)`, размер пула —
`normalizeParallel(parallel)` (indexer.go:199, существующая нормализация
worker-пулов; `-j 0` не должен подвешивать прогон пулом из 0 воркеров):

1. Кандидаты: последовательный `os.ReadDir` + `os.Stat(.git)` — дёшево (80
   stat'ов), даёт детерминированный порядок.
2. Детекция: пул из `parallel` воркеров, каждый выполняет
   `detector.Detect(ctx, dir)` — детектор уже потокобезопасен (mutex + кэш на
   время скана). Результаты собираются в слайс по индексу кандидата
   (не по каналу) — порядок сохраняется. Завершение каталога инкрементирует
   счётчик стадии D1 (atomic).
3. Главная горутина последовательно, в порядке ReadDir: `resolveDSProductID`
   (кэш) + `UpsertDSProductBranch`, затем `SetDefaultBranch` для всех продуктов,
   публикация реестра, bulk-backfill — как сегодня.

`parallel` = effective parallel прогонa (флаг `-j`/конфиг `indexer.parallel`,
дефолт 4), то же значение, что у воркеров walk/индексации. Ошибка exec
(git недоступен) воркером — как сегодня: warning, каталог на эвристику пути.
Идемпотентность: результат не зависит от порядка завершения воркеров —
upsert'ы последовательны и детерминированы.

Для теста конкурентности (максимум одновременных детекций = размер пула)
детектор принимается за минимальным интерфейсом
(`Detect(ctx, dir) (*GitSource, error)`), текущий `*gitDetector` — его
реализация; подставной счётный детектор проверяет наблюдаемое свойство без
тайминговых ассертов.

### D3. Индекс `idx_files_path` (text_pattern_ops) + sargable-предикаты

- DDL: `CREATE INDEX IF NOT EXISTS idx_files_path ON files(path
  text_pattern_ops)` — колонка объявлена `TEXT` (db_schema.go:92), канонический
  pattern-opclass для неё `text_pattern_ops` (`varchar_pattern_ops` на PG18
  принимается через бинарную совместимость и даже используется планировщиком,
  но это неканоническая связка с версионно-зависимым поведением; продукт
  заявляет PG14+). `CurrentSchemaVersion` v5 → v6 (readonly-schema-policy:
  без bump fast-path молча пропустит DDL на существующих БД). Миграция идёт
  штатным `applyMigrationTx` в транзакции — `CREATE INDEX` (не CONCURRENTLY)
  берёт SHARE-блокировку: запись `files` блокируется на время построения
  (~секунды на 624k строк, разовое окно при первом `update` после апгрейда).
- Предикаты выравниваются в единый sargable-вид (экранирование — общий
  существующий хелпер `escapeLikeAll`, db_reconcile_relations.go):
  - `GetLatestFilesByRootPath` и `FindDuplicateFileGenerations`:
    `WHERE path = $1 OR path LIKE $2` → `WHERE path LIKE $2` с экранированием
    корня. Ветка `= $1` семантически мёртвая: root — каталог, `files.path`
    всегда глубже. (Не мотивация планировщиком: на PG18 pattern-индекс
    обслуживает и `=`, и `OR` через BitmapOr — но поведение версионно-зависимо
    и на него не опираемся; плюс сегодня `FindDuplicateFileGenerations`
    экранирует LIKE-параметр через `escapeLikeAll`, а
    `GetLatestFilesByRootPath` подставляет корень без экранирования —
    корень с `%`/`_` перематчивается.)
  - `BackfillFilesFromSources`: `left(f.path, length(s.prefix)) = s.prefix AND
    (…substring… IN ('/','\'))` → `(f.path LIKE s.prefix || '/%' OR f.path
    LIKE s.prefix || '\%')` с экранированием LIKE-метасимволов префикса.
    Ветку «длина равна префиксу» (f.path = каталог источника) убираем — файл
    не может иметь путь каталога. Нормализация путей (`filepath.ToSlash`)
    делает `\`-границу практически недостижимой, но шаблон сохраняем для
    симметрии.
- Ожидаемый эффект (подтверждён живым EXPLAIN на PG18, 200k строк):
  полнокорневой `LIKE '<root>/%'` → Seq Scan + Sort (LIKE покрывает все строки
  — это легитимный план, стоимость фазы в передаче строк); узкий префикс с
  параметром (`LIKE $1`, `update -p <подпуть>`) → Bitmap/Index Scan.
  Production-форма backfill (один UPDATE с N-строчным VALUES-джойном) —
  Nested Loop + Seq Scan по `files`: PG не извлекает индексный диапазон из
  LIKE-паттерна, вычисляемого из колонки джойна (для `text_pattern_ops` нужен
  план-константный префикс), и это легитимный план bulk-операции — префиксы
  источников покрывают всё дерево, индексные проходы по всем строкам были бы
  дороже одного seq scan; UPDATE-сторона уже ограничена `IS DISTINCT FROM`.
  Per-source переписывание (80 отдельных UPDATE с параметром) отклонено:
  выигрыша нет (тот же объём строк через менее предсказуемый доступ) и
  меняет атомарность одного statement'а. Спека требует индекс только для
  план-константных узкопрефиксных LIKE; поведение backfill-формы
  зафиксировано канарейка-тестом плана (если будущий PG начнёт извлекать
  диапазон — тест упадёт и спеку можно ужесточить).
- `DISTINCT ON … ORDER BY path` не использует pattern-индекс для сортировки
  (pattern-порядок ≠ collation-порядок) — явный Sort поверх scan; принято.

### D4. Тайминги фаз

`ScanStats` +`DiscoveryMs`/`SafetyNetMs`/`StateLoadMs`/`PrepMiscMs`;
`PrepMiscMs` покрывает CreateScanRun + BackfillAPIContractSearchVectors —
на легаси-БД FTS-backfill может затронуть много строк, без тайминга окно было
бы недоатрибутировано. Четыре тайминга суммарно покрывают всё подготовительное
окно. `WalkSaveMs` начинает отсчёт от фактического старта walk (снимок времени
перед `WalkParallelCtx`), а не от старта `UpdateCtx`. `printPipelineTimings`
печатает новые поля при значении > 0 (init без load state не печатает нуль).
Тайминги независимы от отображения стадий (D1) — работают и в `--json`.
Знаменатель `Parallel efficiency` ((SaveMs+ParseMs)/(WalkSaveMs+ProcessMs))
меняет базу — сравнение с историей прогонов требует пере-замера.

### D5. Баннер и индикация схемы до `InitSchema`

`InitSchema` выполняется в `cmd/update.go`/`cmd/init.go` до печати баннера —
миграция v6 (CREATE INDEX по ~624k строк) создала бы новое тихое окно ДО
баннера, вне зоны репортера, ровно в первый прогон после замены бинаря.
Баннер («Updating started»/«Indexing started» + rootPath/parallel) переносится
выше `store.NewDB`/`InitSchema`; индикация схемы — первая деталь ЕДИНОЙ
prep-строки (см. D1): `preparing | schema check/migrations... ` без перевода
строки, `done` по завершении, затем очистка строки и продолжение репортером.
Время схемной работы входит в `PrepMiscMs`.

## Risks / Trade-offs

- [CREATE INDEX без CONCURRENTLY — SHARE-блокировка записи `files` при первом
  update: секунд-десятки секунд без индикации] → закрыто D5 (баннер и строка
  схемы до `InitSchema`); замер фактического окна — в bug-report-очередь
  (прецедент owner_name ALTER).
- [После замены бинаря v6 read-only команды возвращают ErrSchemaUpdateRequired
  до первого `update` — все `query`/`stats`/`health`/`review`/`rti`/`trc`]
  → неизбежная цена bump'а версии по readonly-schema-policy; явно
  документировано в proposal Impact.
- [Изменение семантики `WalkSaveMs` и знаменателя `Parallel efficiency` —
  старые сравнения прогонов поплывут] → зафиксировать до/после на одном корне
  (task 5.2); новые поля делают отчёт строже.
- [Убрана ветка `path = $1` — теоретический file row с path == root перестаёт
  матчиться] → такой row не создаётся walker'ом (каталоги не эмитятся);
  интеграционный тест на эквивалентность предикатов.
- [12 параллельных git.exe на AV-окружении] → суммарно меньше работы для AV,
  чем 240 последовательных спавнов; pool = parallel ограничен настройкой.
- [LIKE-экранирование в backfill и полнокорневых запросах] → юнит-тесты на
  префиксы/корни с `%`, `_`, `\`.

## Migration Plan

1. Бамп `CurrentSchemaVersion` → v6, DDL индекса в списке `InitSchema`.
2. Первый `codebase update` на существующей БД применяет миграцию (fast-path
   по маркеру версии уже отработан прецедентом v5 owner_name); до него
   read-only команды нового бинаря возвращают ErrSchemaUpdateRequired.
3. Откат старым бинарём бесшовный: `applyMigrationTx` только вставляет маркеры
   и не удаляет прежние — маркер v5 остаётся, старый v5-бинарь проходит
   `CheckSchemaVersion` (индекс для него обратно совместим; повторный прогон
   нового бинаря пересоздаст ничего — `IF NOT EXISTS`). Вручную при
   необходимости `DROP INDEX idx_files_path` — маркер версии при этом не
   трогаем.
