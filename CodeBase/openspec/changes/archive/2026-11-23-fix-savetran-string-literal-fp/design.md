## Context

`checkSaveTran` (`internal/review/review_rules.go:949`) сканирует expanded-контент построчно: вырезает блочные `/* */` и строчные `--` комментарии, затем передаёт строку в `hasSaveTran` (`review_helpers.go:1473`) — чистый substring-матчер `save tran`/`save transaction` с word-boundary. Строковые литералы не вырезаются, поэтому подпись профилировщика `PROFILE_TIME_EX('BEGIN tran and SAVE tran trnCardAccRelation_MassLoad...')` даёт FP (мотивация — proposal.md, Why).

В пакете уже есть два работающих механизма пропуска литералов:

- инлайн-скип в `hasRawTransactionControl` (`review_helpers.go:1845-1859`) — правило `rawTransactionControl` этому FP не подвержено;
- `stripQuotedSegments` (`review_rules.go:1866`) — удаляет `'...'` из строки с учётом `''`; используется хелпером `onlyQuotedOccurrence` (`review_rules.go:1922`), обслуживающим `tableExistsInMetadata`.

## Goals / Non-Goals

**Goals:**

- Устранить FP `saveTran` на вхождениях внутри однострочных литералов, включая литералы-аргументы макросов.
- Минимальная аддитивная правка с переиспользованием существующего хелпера.

**Non-Goals:**

- Не трогать `rawTransactionControl` — он уже корректен.
- Не переписывать `hasSaveTran` и не менять его контракт (чистый матчер).
- Не аудить другие построчные правила (`truncTbl`, `useDrop`, `deferredUpdate` и др.) на тот же класс уязвимости — отдельная работа при появлении реальных FP.
- Многострочные литералы не поддерживаются: в T-SQL литерал не может содержать перевод строки, пер-строчная обработка достаточна.

## Decisions

- **D1. Правка в `checkSaveTran`, а не в `hasSaveTran`.** После чистки комментариев применяем `stripQuotedSegments(line)` перед `hasSaveTran` (одна строка: `lower := strings.ToLower(stripQuotedSegments(line))`). Вырезание литералов — ответственность построчного сканера, как уже принято в `tableExistsInMetadata`. Альтернатива — сделать `hasSaveTran` quote-aware по образцу инлайн-скипа `hasRawTransactionControl` — отклонена: дублирует уже существующую логику пропуска в двух местах.
- **D2. Пер-строчная обработка.** Литералы T-SQL однострочные; состояние «внутри литерала» между строками не переносится. Ремап номеров строк не нужен — вырезание не меняет нумерацию строк, finding остаётся на исходной строке.
- **D3. Порядок фильтрации: комментарии → литералы.** Существующий порядок чистки комментариев сохраняется; `stripQuotedSegments` применяется последним, к уже очищенной от комментариев строке. Апострофы внутри `--`-комментариев (например `-- don't`) на результат не влияют: строка уже отброшена/обрезана. Остаточное ограничение (pre-existing, данным change не ухудшается): маркеры `--`/`/*` **внутри** литерала по-прежнему вырезаются как комментарии до вырезания литерала; порядок не меняется — на него завязаны существующие тесты блочных комментариев.

## Risks / Trade-offs

- [Незакрытый литерал на строке → хвост строки скрыт, возможен FN] → Валидный T-SQL всегда имеет сбалансированные кавычки в пределах строки; тот же эвристический риск уже принят для `tableExistsInMetadata`. Реальные незакрытые литералы — синтаксическая ошибка, review по ним не гарантирован.
- [SAVE TRAN в динамическом SQL (`sp_executesql N'save tran x'`, `exec('...SAVE TRAN...')`) перестаёт флаговаться → новый FN] → Принятый trade-off: согласуется с семантикой `rawTransactionControl`, который литералы тоже пропускает; savepoint через динамический SQL в кодовой базе — экзотика.
- [FP исчезают только у `saveTran`, асимметрия с прочими построчными правилами остаётся] → Зафиксировано в Non-Goals; при появлении реальных FP у других правил — отдельные точечные изменения по тому же образцу.
