# Design: lsa-semantic-cache

## Context

Семантические слои обоих корпусов (spec: `specsvc.searchSpecSemantic` на
`internal/specsvc/specsvc.go`; desc: `query.searchDescriptionsSemantic` на
`internal/query/desc_query.go`) выполняют при **каждом** вызове: gob-декод модели
(`specfts.LoadLSAModel`), проверку поколения в БД (`HasSpecLSAGeneration` /
`HasDescLSAGeneration` — уже есть) и загрузку эмбеддингов. У desc эмбеддинги идут
из бинарного кэша `desc_lsa_embeddings.bin` (`internal/query/desc_embeddings_cache.go`,
формат: JSON-header с generation + строки метаданных + float32 LE блок, инвалидация
по поколению, атомарная перезапись); у spec — напрямую из БД (`float8[]` как текст,
`parsePGFloatArray`), тот же bottleneck, который кэш desc уже решил.

MCP-сервер (`mcp.RunStdio`) живёт долго; профили (`registry.go: profileToolSets`)
влияют только на регистрацию инструментов — LSA-артефакты и так не читаются при
старте ни в одном профиле (ленивая загрузка внутри tool-вызовов). Масштабы живого
индекса: spec — 2 356 эмбеддингов (БД-путь ~0.25 c), desc — 54 556 × ~512 dim
(кэш-файл ~110 МБ, ~0.2 c на чтение).

## Goals / Non-Goals

**Goals:**

- Повторный semantic-вызов в том же процессе не декодирует модель и не читает
  кэш/БД повторно: только дешёвая проверка поколения.
- Первый вызов после рестарта процесса (CLI-команда или холодный MCP) для spec
  тоже ускоряется — через `spec_lsa_embeddings.bin` по образцу desc.
- Корректность при переиндексации: смена поколения заменяет закэшированные данные.
- Единый формат/механизм файлового кэша для обоих корпусов.

**Non-Goals:**

- Предварительная (при старте) загрузка моделей/эмбеддингов в MCP — остаётся ленивой;
  профили не получают специальной логики загрузки.
- Изменение схемы БД, формата моделей, результатов поиска или API инструментов.
- Кэширование exact-слоёв (FTS/trgm) — они и так быстрые (SQL-запросы).

## Decisions

### 1. Общий binary-cache helper в `internal/specfts`

Параметризованный helper (generic по типу строки метаданных): write/read файла
формата «JSON-header {version, generation, dim, count} + строки метаданных +
плотный float32 LE блок», атомарная публикация (temp + rename, как
`ActivateLSAModel`), инвалидация по generation из header.

- Почему: `desc_embeddings_cache.go` уже реализует этот формат локально для
  `descEmbeddingRow`; spec нуждается в том же с другой строкой метаданных (включая
  поле `product`).
- Альтернатива — копировать ~200 строк кэш-кода в specsvc: дублирование формата
  и двойная правка при эволюции. Отклонена.

### 2. Кэш в памяти: holder с RWMutex, ключ — generation

Структура вида `struct { mu sync.RWMutex; gen string; model *LSAModel; rows []Row }`
на процесс (пакеты-владельцы: `specsvc` для spec, `query` для desc; либо общий
тип в `specfts` с generic-строкой). Протокол вызова:

```
semantic-вызов
  ├─ LoadLSAModel?                ← нет: сначала RLock holder
  ├─ holder: gen совпадает? ──да──▶ переиспользуем model+rows
  └─ нет ─▶ LoadLSAModel + HasXLSAGeneration + загрузка rows
            (файловый кэш → БД → перезапись файлового кэша)
            Lock: замещаем gen/model/rows
```

- Проверка поколения в БД остаётся в пути загрузки; повторные вызовы с тем же gen
  не ходят в БД за эмбеддингами вовсе (EXISTS-проверка уже дешёвая — оставляем её
  только на пути загрузки; закэшированное поколение не может «протухнуть» незаметно:
  модель-файл перезаписывается только вместе со сменой поколения, а БД-поколение
  проверяется при несовпадении gen — компромисс: один EXISTS на cold-path).
- Почему не `sync.Once`: смена поколения после переиндексации требует перезагрузки.
- Почему map поколений, а не один слот: держим только активный слот (одна запись),
  чтобы не копить память старых поколений.

### 3. Порядок потоков: модель → поколение → эмбеддинги

Существующий порядок сохраняется: сначала модель (быстрый отказ при отсутствии —
graceful degradation без БД), затем EXISTS поколения, затем эмбеддинги. Модель
загружается до holder-проверки только при промахе — при хите модель из памяти.

### 4. `spec_lsa_embeddings.bin` пишется query-стороной, не индексатором

Файл пересобирается и перезаписывается лениво при первом semantic-поиске после
смены поколения (как `desc_lsa_embeddings.bin`). Индексатор не пишет его; единственная
точка индексатора — `removeLSASidecars` (runner.go:377) добавляет файл в список
удаляемых при `--modified=false`.

### 5. Фильтр по продукту — в памяти

Кэш spec-строк хранит `product` (LEFT JOIN `ds_products` уже есть в текущем SQL);
фильтр `$1 = '' OR dp.product_name = $1` применяется при сканировании строк в памяти.
Точный и полный SQL-фильтр (`generation`, `embed_level='spec'`) остаётся в
загрузчике из БД.

## Risks / Trade-offs

- [Память MCP query-профиля: ~110 МБ (desc) + единицы МБ (spec) после первого
  semantic-вызова] → Mitigation: ленивое заполнение; непрофильные сценарии не платят;
  при необходимости — будущий флаг конфигурации (вне scope).
- [Параллельные tool-вызовы (MCP) одновременно промахиваются → двойная загрузка]
  → Mitigation: singleflight-паттерн внутри holder (один загрузчик, остальные ждут);
  даже без него — корректность не страдает, только лишняя работа.
- [Устаревшее поколение в памяти при переиндексации на лету] → Mitigation: проверка
  gen при промахе holder-а + EXISTS в БД на пути загрузки; расхождение gen модели
  (файл) и БД обрабатывается существующей логикой gracefully.
- [Формат кэша эволюционирует] → Mitigation: `version` в header; неизвестная версия =
  промах = пересборка (не фатально).
- [Windows rename поверх открытого файла] → Mitigation: атомарная публикация уже
  обкатана в `ActivateLSAModel`; чтение кэша — короткая транзакция в памяти.

## Migration Plan

1. Обратная совместимость: отсутствие `spec_lsa_embeddings.bin` — штатный промах,
   пересборка из БД; старые `desc_lsa_embeddings.bin` остаются валидными (формат не
   меняется, меняется только владелец кода сериализации).
2. Откат: удаление новых файлов + revert кода; БД-путь работает всегда как фолбэк.

## Open Questions

- Вынести ли holder как generic-тип в `specfts` или дублировать маленькую структуру
  в `query` и `specsvc` — решается при имплементации по объёму дженерика.
