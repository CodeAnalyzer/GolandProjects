## ADDED Requirements

### Requirement: Признак is_generated в схеме файлов

Таблица `files` SHALL содержать колонку `is_generated BOOLEAN NOT NULL DEFAULT FALSE`. Миграция схемы MUST быть идемпотентной (`ADD COLUMN IF NOT EXISTS`) и MUST выполнять backfill: существующие записи, соответствующие конвенциям генерируемых копий (сегмент пути `UPLOAD` без учёта регистра, расширение `t01`), помечаются `is_generated = true` без требования полной переиндексации. Backfill MUST быть безопасен для повторного запуска.

#### Scenario: Новая инициализация

- **GIVEN** пустая база данных
- **WHEN** выполняется `codebase init` и создание схемы
- **THEN** таблица `files` создана с колонкой `is_generated`, новые записи получают признак от индексатора

#### Scenario: Существующая база после update без переиндексации

- **GIVEN** база данных с ранее проиндексированными копиями `*/UPLOAD/*.sql` и `*.t01`, у которых `is_generated` ещё не заполнен
- **WHEN** выполняется миграция схемы (в том числе при `codebase update`)
- **THEN** записи копий помечены `is_generated = true`, записи канонических исходников остались `false`
- **AND** повторный запуск миграции не меняет результат

### Requirement: Пакетный name-based lookup с приоритетом канона

Пакетные lookup-функции store, сопоставляющие имена сущностям по всему индексу (процедуры, таблицы, формы, SMF-инструменты, PAS-методы, API-контракты, отчётные формы, а также карты продукт/параметры процедур), SHALL выбирать кандидата по приоритету: не-генерируемый источник (`is_generated = false`) → источник того же продукта, что и контекст запроса → стабильный детерминированный tie-break для остаточных дублей. Регистр имён не значим. Нулевой (не заданный) продуктовый контекст допустим: в этом случае продукт-предпочтение не применяется, но приоритет не-копий сохраняется. Мультикарта контрактных таблиц (`api_table` → контракты-владельцы) SHALL возвращать только контракты-не-копии, если среди владельцев есть хотя бы один не-копия, и всех владельцев — иначе.

#### Scenario: Копия с большим id проигрывает источнику

- **GIVEN** в индексе процедура `P` из канонического источника `SERVER/.../P.sql` (`is_generated = false`) и одноимённая копия `.../UPLOAD/P.sql` (`is_generated = true`), id копии больше
- **WHEN** выполняется пакетный lookup процедуры по имени `P` с продуктовым контекстом
- **THEN** возвращён id канонического источника, а не копии

#### Scenario: Кросс-продуктовый кандидат проигрывает продукту контекста

- **GIVEN** в индексе процедура `P` существует в продукте A (не-копия) и в продукте B (не-копия), контекст запроса — продукт B
- **WHEN** выполняется пакетный lookup по имени `P`
- **THEN** возвращён кандидат продукта B

#### Scenario: Продуктовый контекст не задан — копии по-прежнему проигрывают

- **GIVEN** в индексе процедура `P` из канонического источника и из копии `UPLOAD`, продуктовый контекст не задан
- **WHEN** выполняется пакетный lookup по имени `P`
- **THEN** возвращён id канонического источника

#### Scenario: Карта продуктов процедур не берёт продукт от копии

- **GIVEN** процедура `P` существует в каноническом источнике продукта A и в копии `UPLOAD` продукта B (id копии больше), запрошена карта «имя → продукт»
- **WHEN** выполняется пакетный lookup продуктов по имени `P`
- **THEN** для `P` возвращён продукт A

#### Scenario: Контрактные таблицы фильтруют копии при наличии не-копий

- **GIVEN** контрактная таблица `T` декларирована в контракте-копии (`is_generated = true`) и в каноническом контракте (`is_generated = false`)
- **WHEN** выполняется lookup контрактов-владельцев по имени таблицы `T`
- **THEN** возвращён только канонический контракт
