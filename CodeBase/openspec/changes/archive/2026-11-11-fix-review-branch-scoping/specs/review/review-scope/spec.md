## Purpose

Область видимости review: какая ветка и продукт используются для DB-lookup'ов при проверке конкретного SQL-файла, как разрешается ветка чужого продукта по профилю dsinfo и какие режимы scope применяются к правилам каталога.

## ADDED Requirements

### Requirement: Область видимости review по продукту и ветке

Система SHALL определять область видимости review по проверяемому файлу:
продукт — из индексированной записи файла (`ds_product_id`), ветка — из
`ds_product_branch_id`. Все DB-lookup'и review MUST выполняться в этой области
с учётом правила разрешения ветки чужого продукта. Если у проверяемого файла
`ds_product_branch_id` не задан, область видимости MUST трактоваться как
product-scope без ветки: поиск идёт по всем веткам продукта, как до перехода
на многоветочную модель. Если файл не проиндексирован или у него не задан
продукт, review MUST завершаться ошибкой (поведение не меняется). Для
EXT-продуктов область существования дополнительно расширяется по требованию
«Область видимости EXT-продуктов».

#### Scenario: Файл develop-линии

- **GIVEN** проиндексированный файл `fa-contracts/Consumer/SERVER/Accrual/Cons_BlockLimitAuto_Check.sql` с продуктом `fa-contracts` и веткой `develop`
- **WHEN** выполняется review этого файла
- **THEN** DB-lookup'и выполняются в области `fa-contracts`/`develop`

#### Scenario: Файл релизной линии

- **GIVEN** проиндексированный файл `fa-contracts-11017/Consumer/SERVER/Accrual/Cons_BlockLimitAuto_Check.sql` с продуктом `fa-contracts` и веткой `fa-contracts-11-01-7`
- **WHEN** выполняется review этого файла
- **THEN** DB-lookup'и выполняются в области `fa-contracts`/`fa-contracts-11-01-7`

#### Scenario: Файл без ветки

- **GIVEN** проиндексированный файл с продуктом `fa-contracts` и незаданной веткой
- **WHEN** выполняется review этого файла
- **THEN** lookup'и ищут в пределах продукта `fa-contracts` без фильтра по ветке

#### Scenario: Файл не проиндексирован

- **GIVEN** SQL-файл, отсутствующий в индексе
- **WHEN** выполняется review этого файла
- **THEN** review завершается ошибкой «file is not indexed»

### Requirement: Область видимости EXT-продуктов

Для EXT-продуктов — продуктов, у которых есть ветки с ключом `prj/*`
(поставка в банк = default-ветка `develop` ∪ ветка банка `prj/<банк>`) —
система MUST определять область видимости как объединение, отражающее
фактическую поставку:

- для проверяемого файла в ветке `prj/*` своего EXT-продукта область MUST
  включать ветку файла и default-ветку продукта;
- для проверяемого файла в default-ветке своего EXT-продукта область MUST
  включать default-ветку и все ветки `prj/*` продукта;
- для чужого EXT-продукта разрешённая область MUST включать default-ветку и
  все ветки `prj/*` этого продукта; если профиль dsinfo указывает `prj/*`-линию
  этого продукта, область MUST включать default-ветку и указанную
  `prj/*`-ветку.

Сущность, созданная в любой ветке разрешённой области, MUST считаться
существующей (режим existence) и доступной для разрешения значения (режим
value). Имена между `develop` и `prj/*`-ветками дизъюнктны, поэтому
объединение не порождает конфликтов значений и ложных дублирований. Ветки
`prj/*` других банков и ветки вне разрешённой области MUST NOT подтверждать
существование.

#### Scenario: prj-файл использует таблицу из ext-develop

- **GIVEN** файл ветки `prj/novikom-persform` продукта `fa-contracts-ext` обращается в DML к таблице, созданной в ветке `develop` этого продукта
- **WHEN** выполняется review
- **THEN** finding `tableExistsInMetadata` не формируется

#### Scenario: prj-файл вызывает процедуру из ext-develop

- **GIVEN** файл ветки `prj/novikom-persform` продукта `fa-contracts-ext` содержит `EXEC`-вызов процедуры, созданной в ветке `develop` этого продукта
- **WHEN** выполняется review
- **THEN** finding `execNotExistsProc` не формируется

#### Scenario: develop-файл ext-продукта использует prj-таблицу

- **GIVEN** файл ветки `develop` продукта `fa-contracts-ext` обращается в DML к таблице, созданной в ветке `prj/novikom-persform` этого продукта
- **WHEN** выполняется review
- **THEN** finding `tableExistsInMetadata` не формируется

#### Scenario: prj-ветка другого банка вне области

- **GIVEN** EXT-продукт с ветками `develop`, `prj/bank-a` и `prj/bank-b`, файл ветки `prj/bank-a` обращается к таблице, созданной только в `prj/bank-b`
- **WHEN** выполняется review
- **THEN** сформирован finding `tableExistsInMetadata`: таблица вне поставки банка A

### Requirement: Разрешение ветки чужого продукта по профилю dsinfo

Для продукта, отличного от продукта проверяемого файла, система SHALL
разрешать ветку по цепочке убывания приоритета: явный `--dsinfo <id>` (CLI) /
`dsinfo_id` (MCP) > `CODEBASE_DSINFO_ID` > активный профиль (`dsinfo use`) >
отсутствие профиля. Если профиль содержит продукт и его линия проиндексирована,
MUST использоваться эта линия; если линия не проиндексирована или продукт
отсутствует в профиле, MUST использоваться default-ветка продукта
(`ds_products_branch.is_default`). При отсутствии профиля MUST использоваться
default-ветка продукта. Несуществующий или некорректный явный идентификатор
MUST завершать review ошибкой без молчаливого fallback. Ветка продукта
проверяемого файла MUST браться из файла и не MUST переопределяться профилем.
Для чужого EXT-продукта результатом разрешения является область по
требованию «Область видимости EXT-продуктов» (default ∪ `prj/*`, либо
default ∪ профильная `prj`-ветка).

#### Scenario: Флаг перекрывает окружение и активный профиль

- **GIVEN** активный профиль 1, `CODEBASE_DSINFO_ID=2`, вызов `review --dsinfo 3`
- **WHEN** разрешается ветка чужого продукта
- **THEN** используется профиль 3

#### Scenario: Окружение перекрывает активный профиль

- **GIVEN** активный профиль 1, `CODEBASE_DSINFO_ID=2`, вызов без флага
- **WHEN** разрешается ветка чужого продукта
- **THEN** используется профиль 2

#### Scenario: Продукт вне профиля

- **GIVEN** профиль без продукта `fa-payments`
- **WHEN** review обращается к сущности продукта `fa-payments`
- **THEN** используется default-ветка продукта `fa-payments`

#### Scenario: Линия профиля не проиндексирована

- **GIVEN** профиль с линией `fa-agreement-9-01-1`, а у продукта проиндексирована только develop-линия
- **WHEN** review обращается к сущности продукта `fa-agreement`
- **THEN** используется default-ветка продукта `fa-agreement`

#### Scenario: Несуществующий идентификатор профиля

- **GIVEN** вызов `review --dsinfo 999`, профиль 999 не существует
- **WHEN** выполняется review
- **THEN** review завершается ошибкой, fallback не применяется

#### Scenario: Профиль не переопределяет ветку своего продукта

- **GIVEN** проверяемый файл продукта `fa-contracts` в ветке `fa-contracts-11-01-7` и профиль с линией `fa-contracts-11-01-6`
- **WHEN** выполняется review
- **THEN** для продукта `fa-contracts` используется ветка `fa-contracts-11-01-7` из файла

### Requirement: Режимы DB-lookup review

Система SHALL применять к DB-lookup'ам review один из трёх режимов:

- **existence** — сущность считается существующей только в разрешённой
  области своего продукта (для продукта проверяемого файла — ветка файла,
  для EXT-продуктов — объединение по требованию «Область видимости
  EXT-продуктов»; для чужого продукта — разрешённая ветка, для чужого
  EXT-продукта — объединённая область). Режим MUST применяться к правилам
  `execNotExistsProc`, `tableExistsInMetadata`, `indexExistsInDB`.
- **value** — выбирается одно определение по приоритету: определение из
  проверяемого файла, затем из продукта и ветки, затем из разрешённой
  области продукта-кандидата, затем из продукта, затем из default-ветки
  продукта, затем самое свежее. Режим MUST применяться к разрешению типов
  колонок, параметров процедур, индексов и их полей, типа макроса для правил
  `datatype`, `dateIntoString`, `emptyStringDate`, `isNullSameTypes`,
  `diffTypesComparison`, `floatToStringConvert`, `excessProcParams`,
  `duplicateOutputVariable`, `indexWrong`, `deferredUpdate`,
  `memoryUniqueIndexUpdate`, `useFuncInIndCol`.
- **identity** — принадлежность продукту определяется без учёта ветки:
  сущность, созданная в продукте проверяемого файла в любой его ветке, не
  считается чужой. Режим MUST применяться к правилам `foreignTablesUsing`,
  `foreignPTablesUsing`, `foreignProcedureUsing`; для процедур свой продукт
  MUST проверяться раньше объявления процедуры чужой.

Исключения: декларации in-memory таблиц (`memory_tables`) и определения
`#define` (`h_files_defines`, правило `statementsWithJoinsRequireAliases`)
MUST проверяться глобально по имени, без веточного скоупинга: физическая
in-memory сущность одна на БД, а константы `#define` объявляются общими.
Тип макроса при этом разрешается в режиме value.

Определение, найденное только в ветке того же продукта вне разрешённой
области, MUST NOT использоваться как значение в режиме **value**, если в
разрешённой области есть определение, и MUST NOT подтверждать существование
в режиме **existence**.

#### Scenario: Существование только в чужой ветке своего продукта

- **GIVEN** процедура `Cons_Calc` создана только в ветке `develop` продукта `fa-contracts`, а проверяется файл ветки `fa-contracts-11-01-7` того же продукта
- **WHEN** выполняется review
- **THEN** `execNotExistsProc` формирует finding: в целевой ветке процедуры нет

#### Scenario: Значение из целевой ветки приоритетнее чужой

- **GIVEN** колонка `pList.QtyType` объявлена в ветке `fa-contracts-11-01-7` как `DSIDENTIFIER`, а в `develop` — как `DSINT_KEY`
- **WHEN** проверяется файл ветки `fa-contracts-11-01-7`
- **THEN** тип колонки разрешается как `DSIDENTIFIER`

#### Scenario: Таблица своего продукта из другой ветки не чужая

- **GIVEN** таблица `tContract` создана в продукте `fa-contracts` только в ветке `develop`, а проверяется файл ветки `fa-contracts-11-01-7`
- **WHEN** выполняется review
- **THEN** `foreignTablesUsing` не формируется (продукт свой)
- **AND** `tableExistsInMetadata` формируется, так как в целевой ветке создателя нет

#### Scenario: Кросс-продуктовый дубликат DDL не даёт ложного типа

- **GIVEN** p-таблица `pList` объявлена в `fa-contracts`/`fa-contracts-11-01-7` с `QtyType DSIDENTIFIER` и в `fa-reports` с `QtyType DSINT_KEY`
- **WHEN** проверяется файл `fa-contracts`/`fa-contracts-11-01-7`
- **THEN** тип `pList.QtyType` разрешается из целевой ветки `fa-contracts`

#### Scenario: Процедура чужого продукта только в неразрешённой ветке

- **GIVEN** файл продукта `fa-contracts` вызывает `EXEC Util_X`, процедура `Util_X` чужого продукта существует только в его неразрешённой ветке (не в default-ветке и не в ветке профиля)
- **WHEN** выполняется review
- **THEN** сформирован finding `execNotExistsProc` severity 1: в разрешённой области чужого продукта процедуры нет
- **AND** finding `foreignProcedureUsing` (severity 3) не маскирует его: допустимы оба finding'а одновременно

### Requirement: Дублирование процедур в области продукта и ветки

Система SHALL обнаруживать дублирование имени процедуры в пределах
разрешённой области своего продукта (для файлов вне EXT-веток это продукт и
ветка проверяемого файла; для EXT — объединение по требованию «Область
видимости EXT-продуктов») и формировать finding `procDuplicate` severity 1.
Дублированием MUST считаться как несколько `CREATE PROCEDURE` с одним именем в
одном файле, так и одинаковое имя в разных файлах одной области. Копии того
же имени вне разрешённой области — в других ветках того же продукта, не
входящих в область, и в других продуктах — MUST NOT считаться
дублированием. Источники `upload` и `.t01` MUST исключаться.
Finding MUST формироваться на каждое дублированное имя с указанием файла и
строки.

#### Scenario: Одна и та же процедура в трёх ветках

- **GIVEN** процедура `Cons_BlockLimitAuto_Check` создана в develop, `fa-contracts-11-01-6` и `fa-contracts-11-01-7` продукта `fa-contracts`
- **WHEN** проверяется файл ветки `fa-contracts-11-01-7`
- **THEN** finding `procDuplicate` не формируется

#### Scenario: Дублирование в разных файлах одной ветки

- **GIVEN** процедура `MyProc` создана в двух разных файлах одной ветки одного продукта
- **WHEN** проверяется файл этой ветки
- **THEN** сформирован finding `procDuplicate`, severity 1

#### Scenario: Дублирование в одном файле

- **GIVEN** SQL-файл содержит два определения `CREATE PROCEDURE MyProc`
- **WHEN** выполняется review
- **THEN** сформирован finding `procDuplicate`, severity 1

#### Scenario: Одно имя в разных продуктах

- **GIVEN** процедура `Util_DateFmt` создана в продуктах `fa-contracts` и `fa-payments`
- **WHEN** проверяется файл `fa-contracts`
- **THEN** finding `procDuplicate` не формируется

#### Scenario: Одно имя в prj-ветке и develop одного EXT-продукта

- **GIVEN** процедура `Ext_Proc` создана в ветках `prj/novikom-persform` и `develop` продукта `fa-contracts-ext`
- **WHEN** проверяется файл ветки `prj/novikom-persform`
- **THEN** сформирован finding `procDuplicate` severity 1: в поставку банка входят обе ветки

### Requirement: Поверхности review принимают контекст профиля

CLI-команда `review` SHALL принимать необязательный флаг `--dsinfo <id>`, а
MCP-инструмент `codebase_review_sql` — необязательный параметр `dsinfo_id`
(целое число). Контекст MUST разрешаться по цепочке из требования «Разрешение
ветки чужого продукта по профилю dsinfo» и MUST применяться только к lookup'ам
чужих продуктов; ветка продукта проверяемого файла всегда берётся из файла.
Несуществующий или некорректный идентификатор MUST завершать review ошибкой.

#### Scenario: CLI с профилем

- **GIVEN** профиль с линией `fa-contracts-11-01-7`
- **WHEN** выполняется `codebase review file.sql --dsinfo 3`
- **THEN** ветки чужих продуктов разрешаются по профилю 3

#### Scenario: CLI без флага

- **GIVEN** активный профиль 2
- **WHEN** выполняется `codebase review file.sql`
- **THEN** ветки чужих продуктов разрешаются по профилю 2

#### Scenario: MCP с профилем

- **GIVEN** запущенный MCP-сервер и профиль 3
- **WHEN** вызывается `codebase_review_sql` с `file_path` и `dsinfo_id = 3`
- **THEN** ветки чужих продуктов разрешаются по профилю 3

#### Scenario: Несуществующий профиль на CLI

- **GIVEN** вызов `codebase review file.sql --dsinfo 999`
- **WHEN** профиль 999 не существует
- **THEN** review завершается ошибкой

## Notes

- Профиль задаёт приоритет ветки, а не жёсткий фильтр: для чужих продуктов
  допускается default-ветка, если линия не проиндексирована.
- Для продукта проверяемого файла профиль не применяется: ветка файла
  авторитетна.
- Режим **identity** намеренно не учитывает ветку: иначе таблица/процедура,
  созданная в своём продукте в другой ветке, ошибочно объявляется чужой.
- Асимметрия исключений осознанна: существование константы `#define`
  проверяется глобально, а тип макроса (`lookupMacroSignature`) разрешается
  в режиме value — факт объявления константы един, а сигнатура может
  отличаться между ветками.
- При отсутствии ветки у проверяемого файла (`branch_id NULL`) в режиме
  value веточные тиры своего продукта схлопываются: все кандидаты своего
  продукта получают приоритет тира «продукт», далее разрешённая область
  чужих продуктов, затем default-ветки чужих, затем самое свежее.
