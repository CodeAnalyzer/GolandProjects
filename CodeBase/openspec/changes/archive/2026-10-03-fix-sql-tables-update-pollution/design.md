# Design: fix-sql-tables-update-pollution

## Context

SQL-парсер извлекает таблицы построчным state-machine (см. proposal.md — Why):
после матча `tableNameRe` (`FROM|JOIN|INTO|UPDATE <id>`, `sql_parser.go:34`)
безусловно включается режим списка таблиц (`inFromTableList = true`, :1422), внутри
которого `continuedTableRe` (:35) готов взять любой идентификатор в начале строки.
Стоп-лист режима (:1443–1455) не содержит `set`/`values`, а `isKeyword` (:1860)
глотает `set`, не сбрасывая флаг — отсюда попадание LHS-колонок многострочного
`UPDATE ... SET` в `sql_tables`. Отдельный вектор: хинт-макросы `M_*`/`#M_*`
(`M_FORCEORDER`, `M_KEEPPLAN`) на отдельной строке после последнего `JOIN` (когда
между ними нет `WHERE`, сбрасывающего флаг). Сопутствующий дефект: колонки `SET`
извлекаются только при `UPDATE` и `SET` в одной строке (`updateColumnsRe` :39
заякорен; механизм разбора assignments :1396–1420).

Ограничение миграции (уточнено при реализации, 2026-10-02): `codebase update` в
дефолтном режиме (`--modified=true`) инкрементален; при этом в `UpdateCtx`
(`runner.go:161`) pre-filter ставится **безусловно**, а флаг `--modified=false`
отключает только hash-проверку (:201) — файлы с неизменным mtime+size всё равно
пропускаются (`Hash==""` → skip :197), полный перепрох невозможен. `codebase init`
на существующей БД отклоняется («primary initialization has already been
completed»). Для полной очистки индекса в этот change добавлен минимальный фикс
семантики флага: pre-filter устанавливается только при `--modified=true`, тогда
`codebase update --modified=false` перепроходит все файлы с каскадным удалением
старых строк (:250–254).

## Goals / Non-Goals

**Goals:**

- Устранить три класса мусора в `sql_tables`: LHS-колонки `SET`, хинт-макросы,
  продолжения после однострочного `UPDATE ... SET`.
- Сохранить полезные данные: колонки многострочного `SET` — в `sql_columns`.
- Не регрессировать валидные формы: списки `FROM t1, t2, t3`, `INSERT INTO ...
  VALUES`, `UPDATE ... FROM` (список за `FROM`).
- Дать воспроизводимую процедуру очистки и верификации индекса на FA.

**Non-Goals:**

- Нормализация регистра имён (`tEntattrValue`/`tEntAttrValue`) — отдельная тема.
- Полноценный SQL-парсер (AST/tokenizer) — остаёмся в построчной state-machine.
- Чистка векторов мусора вне скоупа этого change (UPDATE-SET, `M_`-хинты,
  `##`-плейсхолдеры): например, прочие артефакты макро-шаблонов.

## Decisions

1. **Не включать list-режим после `UPDATE`-строки.** В ветке `tableNameRe` (:1422):
   `inFromTableList = !p.updateRe.MatchString(line)` — `updateRe` (`^\s*update\b`,
   :45) уже существует, учитывает регистр/отступы и надёжнее проверки префикса из
   баг-репорта (`HasPrefix(upper, "UPDATE ")` — эквивалентна, но дублирует логику).
   Обоснование: после `UPDATE <t>` синтаксически идёт `SET` (или `FROM` с новой
   строки, который матчится своим ключевым словом); запятого списка таблиц после
   `UPDATE` в T-SQL не бывает. Альтернатива «ничего не менять, только стоп-лист»
   отклонена: не покрывает `update t set a = 1,` + продолжения.

2. **Стоп-лист: добавить префиксы `set ` и `values `.** Defense-in-depth: закрывает
   UPDATE в середине строки (`exec ...; update t ...` — флаг включится, но
   `set`-строка остановит) и `INSERT INTO ... VALUES` на следующей строке. Только
   стоп-лист не решает однострочный кейс — поэтому вместе с решением 1.

3. **Хинт-макросы: префиксный фильтр в `isIgnoredTableName`.** Идентификаторы,
   совпадающие с `^#?M_[A-Za-z0-9_]+$`, не считаются кандидатами в таблицы.
   Размещение в `isIgnoredTableName` (а не `isKeyword`): это не ключевые слова SQL,
   а «имена, не являющиеся таблицами». Верификация по живому индексу (2026-10-02):
   в `context='create'` имена с префиксом `M_`/`#M_` отсутствуют (0 строк) —
   легитимных таблиц с таким префиксом нет, fallback не требуется. Запрос по всем
   контекстам вернул только хинты: `M_ISOLAT`/`#M_ISOLAT` в select-контексте,
   `M_FORCEORDER`, `M_KEEPPLAN` в update/insert — фильтр действует на все ветки
   извлечения (`tableNameRe` :1355, `continuedTableRe` :1475, `selectTempRe`
   :1326). Альтернатива «только явный список» отклонена: набор хинтов пополняется,
   префикс стабилен в конвенции Diasoft.

4. **Макро-плейсхолдеры `##...##`: фильтр в извлечении таблиц.** Токены подстановки
   имени таблицы в шаблонах DDL (`##M_TABNAME##`, `##_TABLENAME_##`, `##OUT_*_TABLE`,
   `##mTableName`) попадают в `sql_tables` с `context='create'` (`createTableRe` :20
   допускает `#` в классе символов; `isTemporaryTableName` :1704 помечает их
   `is_temporary=true`, но строки остаются в индексе). Фильтр в `isIgnoredTableName`:
   имена, начинающиеся с `##`, не считаются кандидатами в таблицы. Отдельно
   проверить распределение `##`-имён по контекстам запросом к индексу; если
   обнаружатся легитимные глобальные временные таблицы (`##temp`-стиль, lowercase) —
   сузить паттерн до плейсхолдер-конвенции (обёрнутые `##x##` и ALL-CAPS `##[A-Z0-9_]+`).

5. **Многострочный `SET` → `sql_columns`: аккумуляция SET-части.** При построчном
   обходе накапливать текст присваиваний update-стейтмента (от строки с `set` до
   `from`/`where`/конца стейтмента) и разбирать assignments существующим механизмом
   (split по запятым + поиск `=`, :1396–1420), привязывая колонку к таблице
   `UPDATE` и строке присваивания. Альтернатива «многострочный regex» отклонена —
   хрупок к регистру/отступам/вложенным скобкам. Качество разбора значений с
   запятыми верхнего уровня — best effort: приоритет — таблицы чистые, колонки —
   что удалось извлечь достоверно.

6. **Очистка индекса — итог реализации.** Фикс семантики флага выполнен
   (pre-filter только при `onlyModified`, `runner.go:161`), но полная
   пересборка через `update --modified=false` на практике непрактична:
   update-ветка платит per-file каскадными DELETE по ~40 таблицам сущностей —
   134 738 файлов за 4ч39м (scan 27), повторный прогон прерван на 47 тыс. за
   ~2.5ч. Финальная пересборка выполнена через `codebase init` на чистой БД
   (старая переименована, build 1549, 22:04:31–23:40:05, errors=0, ~1ч35м).
   Проблема скорости `--modified=false` зафиксирована отдельной доработкой
   `Modifications/update-full-rebuild-truncate-c41d7f.md` (InitSchema +
   `TRUNCATE` кодовых таблиц с сохранением RTI/TRC-сессий + init-пайплайн).
   После пересборки: воронки из баг-репорта — only-update имена 8 011 → 102,
   хинты ~9 000+ → ~161, `##`-плейсхолдеры → 22, целевые имена-мусор
   (`TemplateSysName`, `M_FORCEORDER`, ...) → 0 (детали в tasks 4.2).

## Risks / Trade-offs

- [Ложное срабатывание `M_`-фильтра на легитимной таблице] → верификация по
  индексу выполнена (2026-10-02: `context='create'` пуст; по всем контекстам
  только хинты); фильтр действует только на извлечение таблиц из стейтментов,
  `CREATE TABLE`-ветки не трогаем; fallback (явный список хинтов) задокументирован
  в D3 на случай будущих находок.
- [Регресс валидных списков таблиц] → юнит-тесты на сценарии дельты (FROM-список,
  INSERT VALUES, UPDATE...FROM); регресс-сценарии включены в спеку.
- [Неточность разбора колонок при сложных SET (CASE, подзапросы с запятыми)] →
  split по запятым верхнего уровня уже отлажен (:1396–1420); в спеке — привязка к
  таблице UPDATE, колонки best effort.
- [Изменение выдач потребителей (покрытие спек, review)] → исчезновение ложных
  сущностей и есть цель; интерфейсы и схемы БД не меняются.
- [Мусор остаётся в индексе до перепрохода] → миграция: полная пересборка
  выполнена через `codebase init` на чистой БД (см. D6/Migration Plan);
  верификационные запросы как acceptance.
- [Остаточные векторы вне скоупа change (верификация 2026-10-02, ~40 строк)]
  → задокументированы: `dfm_embedded`/`pas_embedded` экстракторы не применяют
  `isIgnoredTableName` (склейка `pAPI_User_FindLst#M_NOLOCK_INDEX`,
  `#M_FORCEORDER_WO_LOOPJOIN`), underscore-токены `__M_JOIN_PARTS__`,
  mixed-case `M_ISOlAT`; ~22 `##`-плейсхолдера в delete-контексте. Кандидат в
  отдельный баг-репорт/изменение.

## Migration Plan

1. Реализация фикса + тесты (юнит-сценарии дельты).
2. Финальная пересборка индекса FA выполнена через `codebase init` на чистой
   БД (старая переименована; build 1549; 22:04:31–23:40:05 2026-10-02,
   errors=0). Путь `update --modified=false` для пересборки отклонён по
   замерам — см. D6 и `Modifications/update-full-rebuild-truncate-c41d7f.md`.
3. Верификация SQL-запросами: пустые воронки мусора, кейс
   `Cons_GetDocToProcess.sql:813–821` — `TemplateSysName` отсутствует в
   `sql_tables`, колонки `SET` присутствуют в `sql_columns`.
4. Откат: git revert парсера + `codebase update --modified=false`
   (схема БД не менялась).
