# Proposal: fix-sql-tables-update-pollution

## Why

SQL-парсер загрязняет таблицу `sql_tables` ложными именами таблиц: при многострочном
`UPDATE ... SET` имена колонок левой части присваивания попадают в индекс как таблицы
(`context='update'`), а строки-хинты (`M_FORCEORDER`, `M_KEEPPLAN`) захватываются как
«таблицы» после последнего `JOIN`. По живому индексу FA это **31 416 строк / 8 011 имён**
мусора (имена, существующие только в `context='update'`; верхняя оценка с учётом
легитимных p-таблиц без DDL — 67 860 строк / 10 768 имён). Мусорные имена видят все
потребители индекса: покрытие спеками (`specsvc`, ветка `sql_table`) выдаёт ложные
«непокрытые» сущности, review-правила (`foreignTablesUsing`, `foreignPTablesUsing`)
работают на недостоверных данных, поиск сущностей шумит.

Источник: `Bug-reports/BUG-sql-tables-update-set-columns-as-tables-20260930.md`
(верифицирован: кейс `Cons_GetDocToProcess.sql:813-821` воспроизводится, анализ кода
`sql_parser.go` подтверждён построчно).

## What Changes

- Парсер больше не включает режим «списка таблиц» (`inFromTableList`) после строки
  `UPDATE <table>` — колонки `SET`-присваиваний перестают попадать в `sql_tables`.
- Стоп-лист продолжения списка таблиц дополняется префиксами `set ` и `values `
  (защита от смежных форм).
- Идентификаторы хинт-макросов Diasoft (`M_*`, `#M_*`: `M_FORCEORDER`, `M_KEEPPLAN`,
  `M_NOLOCK_INDEX`, ...) игнорируются при извлечении таблиц — закрывает второй вектор
  (хинт на отдельной строке после последнего `JOIN`; по данным индекса мусор
  охватывает update, select и insert контексты).
- Идентификаторы макро-плейсхолдеров (`##NAME##`, `##_TABLENAME_##`, `##OUT_*_TABLE` —
  токены подстановки имени таблицы в шаблонах DDL) не сохраняются в `sql_tables` —
  закрывает третий вектор (`createTableRe` допускает `#` в имени, плейсхолдеры
  попадают в индекс с `context='create'`).
- Многострочный `UPDATE ... SET`: колонки левой части присваиваний извлекаются в
  `sql_columns` (устраняется потеря полезных данных — сейчас `updateColumnsRe` требует
  `UPDATE` и `SET` в одной строке).
- Флаг `--modified` команды `update` получает корректную семантику: при
  `--modified=false` mtime+size pre-filter отключается и все файлы перепроходятся
  заново с каскадным удалением старых строк. Сейчас (build 1545) pre-filter
  ставится в `UpdateCtx` безусловна, а флаг отключает только hash-проверку —
  полный перепрох индекса невозможен без пересоздания БД.
- Очистка существующего индекса выполняется перепроходом (`codebase update
  --modified=false`) — без изменений схемы БД.

## Capabilities

### New Capabilities

(нет)

### Modified Capabilities

- `indexing/sql-parsing`: требование «Извлечение SQL-таблиц и колонок» — добавляются
  ограничения на извлечение таблиц из `UPDATE`-статементов (не-табличные идентификаторы
  `SET`-присваиваний и хинт-макросы не попадают в `sql_tables`) и извлечение колонок
  многострочного `SET` в `sql_columns`.
- `indexing/file-walking`: требование «Pre-filter по fingerprint (mtime + size)» —
  pre-filter применяется только при `--modified=true` (дефолт); при `--modified=false`
  все файлы перепроходятся заново.

## Impact

- **Код**: `internal/parser/sql/sql_parser.go` — ветка `tableNameRe` (:1341–1422,
  установка `inFromTableList` :1422), ветка продолжения списка (:1423–1493, стоп-лист
  :1443–1455), `updateColumnsRe` (:39), `isIgnoredTableName` (:1802); возможно
  `setClauseRe`. Изменения локальны, контракт `model.SQLTable`/`model.SQLColumn` не
  меняется. Дополнительно (фикс семантики флага, решение от 2026-10-02):
  `internal/indexer/runner.go` — установка pre-filter в `UpdateCtx` только при
  `onlyModified` (`walker.SetPreFilter` :161); `internal/fswalk` не меняется.
- **Индекс**: после фикса требуется перепроход индексации (`codebase update`) для
  очистки существующих мусорных строк в `sql_tables`/`symbols`; ожидаемое сокращение —
  ~31 тыс. строк.
- **Потребители**: покрытие спеками (`internal/specsvc/specsvc.go`, ветка `sql_table`),
  review-правила `foreignTablesUsing`/`foreignPTablesUsing`, `tableFullScan`, query
  table/symbol — качество данных улучшается, интерфейсы не меняются.
- **Риски**: регрессия на валидных списках таблиц (`FROM t1, t2, t3`) и на
  легитимных p-таблицах — покрывается тестами и верификацией на FA.
