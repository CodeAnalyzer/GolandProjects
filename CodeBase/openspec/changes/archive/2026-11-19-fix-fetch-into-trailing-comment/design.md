# Design: fix-fetch-into-trailing-comment

## Context

Разбор FETCH INTO идёт по двум путям (см. proposal.md — Why):

- **Fragment-level**: `checkCursorFetchArguments` (review_rules.go:5803) и `checkDatatypeFetchInto` (:112) вызывают `parseFetchIntoStatement(fragment.QueryText)` — текст фрагмента содержит комментарии как есть (эталонный FP: `@AccountsRequestID --используется внутри макроса...`).
- **File-level**: `checkVarUseAfterCursor` (:5079) использует `parseAllFetchIntoStatements(content)` — строки оператора собираются сырыми (review_parser.go:448–458), склеиваются через `\n` и передаются в тот же `parseFetchIntoStatement`.

Переменные извлекаются `splitTopLevelCSV` + анкорным `reParserFetchIntoVar` (`^\s*(@var)\s*$`, review_parser.go:20): любая не-переменная лексема в CSV-части (хвостовой `--комментарий`, `/*...*/`) отбрасывает переменную целиком. Стриппинг комментариев уже существует и применяется в `parseCursorDeclarations` для строк-продолжений (`stripLineComments`, review_helpers.go:1106, с inBlock-состоянием), но пути FETCH его не используют.

Существенное ограничение снизу: `checkVarUseAfterCursor` сканирует **сырые** строки окна DEALLOCATE и матчит переменные через `strings.Contains` (review_rules.go:5130–5167) — упоминание переменной в комментарии для него неотличимо от использования. Skip-спаны FETCH (`LineStart..LineEnd`) — единственный механизм, защищающий строки-продолжения FETCH ниже DEALLOCATE; **сжимать спаны нельзя** (см. Decision 2).

Ограничение по координатам: нумерация строк не меняется — стриппинг построчный, строки не удаляются и не сливаются, поэтому `LineStart`/`LineEnd`/`Line` остаются в координатах expanded-контента.

## Goals / Non-Goals

**Goals:**

- Переменные FETCH извлекаются из текста без комментариев (`--` и `/* */`) на обоих путях разбора.
- Границы сбора оператора FETCH (`isCursorDeclarationBoundary`/`isFetchStatementStopLine`) определяются по стрипнутому тексту: строка внутри многострочного блочного комментария, начинающаяся с ключевого слова оператора, не обрывает сбор.
- Строка FETCH в правилах (`fetchIntoStatementLine`) вычисляется по тому же стрипнутому тексту, что и разбор переменных.
- Skip-спаны `varUseAfterCursor` не сжимаются: комментарий-упоминание внутри FETCH не создаёт новый finding.

**Non-Goals:**

- Распознавание закомментированных FETCH-операторов (`-- fetch c into @a`) как несуществующих: определение старта оператора (`reParserFetchCursorStart`) остаётся на сырых строках — pre-existing поведение, эвристика построчная.
- Comment-aware сканирование в `checkVarUseAfterCursor` (стриппинг сканируемых строк): меняет наблюдаемое поведение правила (комментарий перестал бы быть «использованием» в любом месте окна, не только внутри FETCH) — кандидат в отдельный follow-up вместе с substring-дефектом `@ChangedBrief`; в этом change поведение окна неизменно.
- Quote-aware стриппинг (учёт `--` внутри строковых литералов): в списке переменных FETCH INTO строковых литералов не бывает; переиспользование хелпера для общего SQL-текста не предусматривается.
- Блочный комментарий, начавшийся до фрагмента/оператора (inBlock известен только внутри): старт inBlock=false на границе оператора — то же ограничение, что у `parseCursorDeclarations`.
- Незакрытый `/*` внутри оператора FETCH (битый/обрезанный SQL, на валидном недостижим): inBlock остаётся true до EOF, boundary/stop-проверки не срабатывают, сбор уходит до конца файла и последующие FETCH-операторы пропускаются — принято как риск (по итогам code review, C3); защитный предел на размер оператора не вводится, т.к. добавляет эвристику ради синтаксически невалидного входа.
- Полная симметрия с `parseCursorDeclarations`: декларации стриппят только продолжения, `remainder` первой строки добавляется сырым (review_parser.go:327–329) — pre-existing, не влияет на этот change (follow-up-кандидат).

## Decisions

1. **Стриппинг в `parseFetchIntoStatement` на входе — единая точка (choke point).**
   Новый приватный хелпер `stripCommentsFromText(text string) string`: построчный проход `stripLineComments` с переносом inBlock между строками текста, склейка через `\n`. Применяется первым действием в `parseFetchIntoStatement`. Альтернатива — стриппить `fragment.QueryText` в обоих правилах — дублирует логику и оставляет дверь открытой для новых вызовов; хелпер покрывает оба существующих пути (fragment-level вызовы + file-level сборка через `:464`) без правок правил.
   Побочный эффект: `fetch`-лексемы внутри комментариев фрагмента перестают матчиться префиксом `reParserFetchIntoPrefix` (сегодня phantom-FETCH из комментария распознаётся) — строго к улучшению.

2. **`statementLines` остаются сырыми; спаны FETCH не сжимаются (по итогам ревью, F1).**
   `parseAllFetchIntoStatements` хранит строки оператора как есть; стриппинг происходит только внутри `parseFetchIntoStatement` при извлечении переменных. `fetchVariablesLineEnd` (review_parser.go:482) продолжает считать `LineEnd` по сырым строкам: строка-продолжение, где переменная упомянута только в комментарии, может продлевать skip-спан — это безопасное перекрытие (скрываемая строка — комментарий, реальным использованием быть не может).
   Отвергнутая альтернатива (предыдущая редакция design) — хранить стррипнутые строки и сжимать `LineEnd`: `checkVarUseAfterCursor` сканирует сырые строки и матчит переменные `strings.Contains`-ом (review_rules.go:5165) — сжатие спана вскрыло бы матчинг `@var` в комментарии FETCH'а ниже DEALLOCATE и создавало **новый FP `varUseAfterCursor`**, противореча требованию main spec («строки-продолжения многострочного FETCH MUST NOT классифицироваться как использование»).

3. **Границы сбора — по стрипнутой копии строки с переносом inBlock (по итогам ревью, F2).**
   В цикле сбора продолжений ведётся inBlock-состояние: для каждой строки-кандидата вычисляется `stripped, nextInBlock := stripLineComments(rawLine, inBlock)`; boundary/stop-проверки (`isCursorDeclarationBoundary`, `isFetchStatementStopLine`) выполняются по `strings.TrimSpace(stripped)` — строка внутри многострочного `/* ... */`, начинающаяся с `select`/`set`/..., границей не является. В `statementLines` кладётся **сырая** строка (Decision 2). inBlock инициализируется false на старте оператора (Non-Goal про комментарий до оператора).

4. **`fetchIntoStatementLine` работает по стрипнутому тексту (по итогам ревью, F3).**
   Оба вызова (review_rules.go:119, :5810) ищут префикс FETCH в сыром `fragment.QueryText`: после choke point `parseFetchIntoStatement` выбирает реальный FETCH, а поиск строки мог бы найти phantom-FETCH в комментарии выше — расхождение строки с разобранным оператором ломает `nearestCursorDeclaration`. `fetchIntoStatementLine` применяет тот же `stripCommentsFromText` перед поиском префикса: стриппинг сохраняет количество `\n`, смещения строк не меняются. Альтернатива — возвращать offset из `parseFetchIntoStatement` — меняет сигнатуру без необходимости.

5. **Пустые строки внутри оператора хранятся в `statementLines` (по итогам ревью, F4).**
   Сегодня пустые строки пропускаются (`continue`, review_parser.go:452–454) и не попадают в `statementLines`, а `fetchVariablesLineEnd` считает `lineStart + k` — пустая строка внутри многострочного FETCH смещает `LineEnd`. Пропуск заменяется на добавление `""` (индекс k ↔ физическая строка сохраняется); на разбор переменных пустые строки не влияют (`\s`-aware регэкспы), хвостовые пустые строки безвредны (`LineEnd` выбирает последнюю строку с переменной).

6. **CRLF-поведение стриппера зафиксировано тестом (по итогам ревью, F7).**
   `stripCommentsFromText` собирает `strings.Split(text, "\n")` и `Join(..., "\n")`: `\r` в конце строк сохраняется внутри «строк» (CRLF round-trip), теряется только хвост комментария после `--` (включая завершающий `\r`) — безвредно, все регэкспы разбора `\s`-aware. `parseAllFetchIntoStatements` нормализует CRLF→LF до разбора (review_parser.go:428–429); фрагментный путь CRLF не нормализует — поведение покрывается тестом. Кириллица в комментариях дополнительной обработки не требует: контент — expanded-текст в Unicode, `stripLineComments` работает по ASCII-маркерам `--`, `/*`, `*/` и кодировко-независим.

## Risks / Trade-offs

- [Сжатие skip-спанов создавало бы FP `varUseAfterCursor` для комментария-упоминания в FETCH ниже DEALLOCATE] → Decision 2: `statementLines` сырые, спаны стабильны; тест «FETCH ниже DEALLOCATE + завершающая строка `-- @var` → 0 findings».
- [Границы по сырой строке обрывали бы сбор внутри многострочного `/* */`] → Decision 3: проверка по стрипнутой копии с inBlock; тест с `select`-строкой внутри блок-комментария в FETCH.
- [Расхождение `fetchLine` с разобранным оператором при phantom-FETCH в комментарии] → Decision 4: стриппинг в `fetchIntoStatementLine`; тест «комментарий с `fetch ... into ...` выше реального FETCH в одном фрагменте».
- [Сдвиг `LineEnd` при пустых строках внутри многострочного FETCH (pre-existing)] → Decision 5: пустые строки хранятся; тест с пустой строкой внутри FETCH.
- [Стриппинг в choke point изменит распознавание FETCH с комментариями и для `varUseAfterCursor` — переменные из комментария больше не попадают в окна] → приёмка на эталоне `InstrumentSO_LoadStates.sql`: ожидаются ровно 11 находок с прежней разбивкой (FETCH без комментариев).
- [`stripLineComments` не знает строковых литералов] → в списке переменных FETCH INTO литералы запрещены синтаксисом; риск принят, задокументирован в Non-Goals.
- [Регрессия существующих тестов разбора FETCH] → прогон `go test ./internal/review/`; комментарии в существующих тест-фикстурах FETCH отсутствуют.
- [FP на файлах, где «комментарий» — часть имени курсора/переменной] → имена не содержат `--`/`/*` (лексика `@[A-Za-z_]\w*`), коллизий нет.

## Migration Plan

Изменение локально для `internal/review` + тестов; схема БД и CLI-контракты не затрагиваются. Развёртывание — обычная сборка; откат — git revert без миграций.
