# Design: add-review-debug-profile-disabled-rule

## Context

Каталог review (`internal/review/`) построен по схеме «check-функция на правило»: константа rule ID в `types.go`, регистрация в `catalog.go` (severity фиксируется в Finding при срабатывании), реализация в `review_rules.go`. Правило `apiExecOutsideFacade` из change `add-review-api-proc-direct-call-rule` ввело паттерн textual-правила поверх однопроходного лексера `sanitizeSQLForMacroScan` (states normal/inString/lineComment/blockComment): содержимое строковых литералов заменяется на `?` с сохранением `\n`/`\r`, комментарии `--` и `/* */` забиваются пробелами, длина текста неизменна — номера строк сохраняются. Этот лексер переиспользуется данным правилом без изменений.

Механика пайплайна (критично для правила): `RunSQLFileCtx` читает файл, но в `reviewExecContext.content` кладёт результат `replaceMacros`, при этом `stripMacroDeclarations` вырезает из текста все строки `#define` — accessor `fileContent` возвращает expanded-контент, в котором директив физически нет. В конце `RunSQLFileCtx` все findings безусловно ремапятся `mapExpandedLineToOriginal`; `SourceMap` содержит только сохранившиеся строки — для удалённых define-строк обратного отображения нет. Тест-хелперы по образцу `newAPIRuleRunner` кладут в `exec.content` сырой текст, поэтому юнит-тесты прямого вызова check-функции production-дефект контента не выявляют — обязателен e2e-прогон через `RunSQLFileCtx`.

Препроцессорная семантика профилирования (по `MACROS.H` из fa-commonfiles): рубильник — `#define PROFILE` (обычно в начале файла, до `#include <macros.h>`); при отсутствии макроса `PROFILE` все `PROFILE_*` разворачиваются в пустую строку (`#else`-ветка, MACROS.H:578-588). Профилировочный вызов может попасть в файл не только явным `PROFILE_*` вызовом, но и транзитно — через каркасные макросы, тела которых содержат `PROFILE_*` (MACROS.H:592-2388). Ключевая цепочка нейтрализации на «чистом» стенде — `MACROS.H:5-15` (без `local.h`/`PROFILE_AVAILABLE` define убивается) — не гарантирует выключенность на отладочных стендах, поэтому маркер «активный define в файле» трактуется как нарушение сам по себе.

## Goals / Non-Goals

**Goals:**

- Детектировать файлы, в которых отладочное профилирование включено активным `#define PROFILE` и реально материализуется (в файле есть точка профилирования).
- Нулевые ложные срабатывания на трёх безопасных состояниях: define отсутствует / закомментирован / активен, но разворачивать нечего.
- Переиспользовать `sanitizeSQLForMacroScan` и конвенции каталога (severity 1, один finding на файл, DefaultEnabledRules).

**Non-Goals:**

- Резолв include-цепочек (продуктовые хедеры `CardTran_ProcessService.h`, `aml.h` могут приносить точки профилирования в includer — не детектируется per-file; включая обход переопределений макросов вида `RedirectProfile.h` в fa-cards, перенаправляющих `PROFILE_*` в `pDebugStack`).
- Учёт `#define PROFILE_AVAILABLE` в скриптах: директива мертва (убивается `MACROS.H:5` до include `local.h`).
- Проверка парности `PROFILE_BEGIN*`/`PROFILE_END*`, полноты списка носителей вне `MACROS.H`, эмуляция препроцессора.

## Decisions

### D1. Триггер: активный define + точка профилирования в файле (вариант B′)

Finding формируется только при совместном выполнении трёх условий: активный define, точка профилирования в файле, положение первого активного define **до** первого `#include <macros.h>` (если такой include в файле есть). Третье условие отражает линейность препроцессора: `MACROS.H` раскрывает `PROFILE_*` по состоянию макроса `PROFILE` на момент обработки заголовка; define после include ничего не включает (3 файла `tag13_PsExtendActions.sql` ×3 ветки). Отвергнутая альтернатива — принять эти 3 FP как known-issue: правило заявляет нулевые FP на безопасных состояниях, а define-after-include — именно безопасное состояние. Альтернативы триггера, отвергнутые на фактуре FA:

- «Буквальный» (только явные `PROFILE_*` вызовы, 93 файла) — пропускает 77 файлов, где профилирование приходит транзитно через каркас (`DCL_PROC_BODY` → `PROFILE_BEGIN_EX('begin NAME')`).
- «Include-триггер» (`#define PROFILE` + `#include <macros.h>`, 167 файлов) — 17 ложных срабатываний на файлах, где после include нет ни одной точки профилирования и профилирования фактически не будет (кейс пользователя: `__BEGIN_PROCEDURE__`/`__END_PROCEDURE__` отсутствуют).
- «Любой активный define» (~169 файлов) — 20 ложных на файлах без точек и 3 ложных на define после include.

Список носителей фиксирован и выведен из `MACROS.H`: прямые `PROFILE_BEGIN/TIME/END(_EX)`, `PROFILE_TIME_VAR1/2/3`; каркасные `RETURN_PROFILE(_EX)`, `DCL_PROC_BODY`, `DCL_PROC_END`, `COMMIT_TRAN`, `__END_TRAN__`, `__BEGIN_PROCEDURE__`, `__END_PROCEDURE__`, `__CHECK_ERROR__`, `M_TRACE_DCL_PROC_END_START`. `DCL_PROC_BEGIN` носителем не является (drop/create-обёртка без профилировочных вызовов), как и `GOEND`, `M_TRACE_DCL_PROC_END_FINISH`.

### D2. Проверка идёт по исходному тексту файла (до replaceMacros)

Оба условия проверяются на **исходном** содержимом файла, доступном правилу через новый accessor `rawFileContent()` (поле `rawContent` в `reviewExecContext`, заполняется в `RunSQLFileCtx` из прочитанного файла до `replaceMacros`). Существующий `fileContent` непригоден: он возвращает expanded-контент, из которого `stripMacroDeclarations` уже вырезал все `#define`-строки — правило дало бы 0 findings на всех сценариях. Альтернатива «читать файл в правиле через `encoding.ReadFile`» отвергнута: дублирование I/O и обход контракта exec-контекста (кодировка, путь, активная цель).

К исходному тексту применяется `sanitizeSQLForMacroScan`. Паттерн директивы: `(?i)^[ \t]*#[ \t]*define[ \t]+PROFILE\b` построчно; `\b` отсекает `PROFILE_AVAILABLE`; совпадение в маскированной зоне (комментарий/литерал) невозможно по построению лексера. Finding — первая строка совпадения (original-пространство, см. D6). Условие порядка: строка первого активного define сравнивается со строкой первого вхождения `#include <macros.h>` (регистронезависимо; если include в файле нет — условие не применяется, транзитивная семантика вроде `teg13_ConvertPaySchedule.sql` ← `dcUtil.h` остаётся корректной). Наивный скан сырого текста без санитизации отвергнут: ложное срабатывание на `-- #define PROFILE`, на define внутри блочного комментария и на директиву внутри строкового литерала.

### D3. Точки профилирования ищутся в том же санитизированном тексте, без блоков-определений

Поиск вхождений носителей как слов (`\b`, case-insensitive) в санитизированном тексте отсекает упоминания в комментариях и литералах (например, `-- DCL_PROC_BODY here` в комментарии). Дополнительно **блок определения макроса** — строка `^\s*#\s*define\s+` (независимо от определяемого имени) вместе с продолжениями по `\` — точками не считается. Иначе определение helper-макроса с носителем в теле (`#define DBG1(...) PROFILE_TIME_VAR1(...)`) или многострочное определение с `\`-продолжением, где носитель стоит на строке-продолжении, флаговались бы из-за самих определений (гибридные продуктовые хедеры с собственными определениями и активным define). На фактуре FA таких кейсов среди 170 файлов нет (0), мера — упреждающая; семантика блока совпадает с `collectMacroDefinitions`.

### D4. Guard расширений: `.sql` и `.h`, сравнение без учёта регистра

Фильтра расширений в review-пайплайне нет: `*.h` входит в `include_patterns`, `getIndexedFile` не фильтрует по расширению, tolerant-парсинг `.h` возвращает nil error — правило выполнялось бы на любом переданном файле. В check-функцию добавляется guard: расширение пути сравнивается с `.sql`/`.h` через `strings.EqualFold`. Без учёта регистра обязательно: в fa-generalledger 4 боевых файла с `.SQL` (`LastDateCalc_New.SQL`, `RulAddrAbbreviation_{Update,Insert,Delete}.SQL`) входят в ожидаемые findings — точное сравнение `filepath.Ext(path) == ".sql"` их потеряло бы. Реальные `.h`-риски, проверяемые задачей 2.5: файл должен быть в индексе с заполненным `ds_product_id`, CP866-чтение, tolerant-парсинг. Прочие расширения (`.inc` и т.п.) — вне области, с активным define не встречались.

### D5. Rule ID `debugProfileEnabled`, severity 1, дедупликация

Конвенции каталога: фактическая severity 1 (DeployStopper) задаётся полем `Severity: SeverityDeployStopper` в `Finding` при срабатывании — поле `Severity` в записи `ruleCatalog` пайплайном не читается (это метаданные каталога). Один finding на файл на строке первого активного define (аналог конвенции `apiExecOutsideFacade`). Сообщение указывает оба условия (define + найденная точка) и способ выключения (закомментировать директиву или удалить).

### D6. Строка finding — в original-пространстве, ремап пропускается

Строка первого активного `#define PROFILE` берётся из исходного текста, но `RunSQLFileCtx` в конце безусловно ремапит `Finding.Line` через `mapExpandedLineToOriginal`; для удалённой define-строки обратного отображения в `SourceMap` нет — строка сдвинулась бы на число `#define`-строк выше (пример: `#define PROFILE` в строке 1 → `SourceMap[0] = 2`). Решение: служебное поле `Finding.LineInOriginalSpace bool` (`json:"-"`, наружу не сериализуется); runner пропускает ремап для findings с этим флагом. Альтернативы отвергнуты: сохранение define-строк в `SourceMap` (изменение `replaceMacros`/`stripMacroDeclarations` затрагивает все правила и инвариант expanded-текста); вынос проверки в отдельный pre-parse шаг до `replaceMacros` (перемешивает поток runner, дублирует контекст выполнения). Правило — единственный потребитель флага в рамках change.

## Risks / Trade-offs

- [False negative: точки через include] файл с активным define, чьи точки профилирования приходят из продуктового include-хедера, не флагуется → осознанное ограничение per-file анализа. На фактуре FA Reload-кластеры прикрыты: хедеры-компаньоны (`INS/FCT_AllSync_Reload_proc.h` ×3, `FCT_AllSync_Reload_proc.h` ×1) содержат и define, и точки — флагуются сами. Будущее расширение — резолв include через граф relations индекса.
- [False negative: define через include] скрипт с точками профилирования и `#include <dcutil.h>` (хедер сам содержит `#define PROFILE` + `#include <macros.h>`), но без собственного define, не флагуется; `dcutil.h` собственных точек не имеет и тоже не флагуется — кластер conv-consumer «прикрытым» не является. Файловому паттерну «точки + `#include <dcutil.h>` + нет своего define» соответствует до 37 Test-кандидатов (многие подключают `macros.h`/`link_macros.h` раньше `dcutil.h`, тогда define в нём неэффективен — точное число требует include-резолва, вне области change). Закрытие — тот же резолв include-цепочек.
- [Ограничения лексера] `sanitizeSQLForMacroScan` не поддерживает вложенные блочные комментарии T-SQL (define во внешнем комментарии после внутреннего `*/` может дать ложное срабатывание), не маскирует двойные кавычки и bracket-идентификаторы (`[a--b]` может сорвать разбор строки), не знает `#if 0`/`#ifdef`. На FA кейсов не выявлено (проверено репликой лексера, change-review 2026-11-13); расширение лексера вне области — затронет `apiExecOutsideFacade`.
- [Список носителей может устареть] новый каркасный макрос с `PROFILE_*` в `MACROS.H` не попадёт в список → правило даст false negative; список — часть требования спеки, изменение списка = новая дельта спеки.
- [Redirect-переопределения] продуктовое переопределение `PROFILE_*` (fa-cards `RedirectProfile.h`, вставки в `pDebugStack`) может активировать профилирование без `#define PROFILE` → вне области (нет надёжного per-file детектора; файл-сирота, в FA не включается).
- [Условие порядка — только прямой include] эвристика сравнивает define с первым прямым `#include <macros.h>`; если `macros.h` приходит косвенно (например, `#include <dealmain.h>` или `link_macros.h` до `#define PROFILE`), define фактически неэффективен, но правило этого не увидит. На FA косвенных кейсов не выявлено (все 3 define-after-include — с прямым `macros.h`); закрытие — тот же резолв include-цепочек.
- [Масштаб первого прогона] фактический полный свуп (build 1694): 147 findings на 170 кандидатах, 23 пропуска — 3 подавлены условием порядка (`tag13_PsExtendActions.sql` ×3), 20 без точек профилирования (включая `tag13_PsExtCreate.sql` ×3: define предшествует include, но точек в файле нет; `dcutil.h` ×3, Reload-обёртки ×4 и др.). Отклонение от оценки change-review (~146): +1, расхождение методик (реплика лексера vs production-правило). Ожидаемый шум, включая branch-копии и Test-каталоги; зафиксировано в proposal Impact.
