# Design — Improve Spec Mention Coverage

## Context

Парсер спек (`internal/parser/openspecmd/mentions.go`) извлекает упоминания двумя режимами: Related code (бэктики + маркеры + bare-идентификаторы) и inline (бэктики + однозначные маркеры). Классификация `classifyMention` знает 6 kind'ов (procedure/api/table/form/smf/method/unknown). Постпроцессор (`internal/indexer/indexer_postprocess_spec.go`) резолвит 6 kind'ов batch-lookup'ами в relations `references_code`.

Замер по 2200 spec.md FA-продуктов (см. proposal) выявил потери: report-пути дропаются ещё на классификации (`.tpr`/`.rpt` не в switch → токен с точкой отвергается `bareAllowed`), события ловит `reUnderscoreIdent` как procedure (промах по `sql_procedures`), GIVEN не сканируется (`indexer_spec.go:577` — только `When + "\n" + Then`), `.pas` резолвится только в `pas_methods`, строчные процы падают в unknown без второй попытки, `pAPI_*` матчится `reTableName` как таблица.

Существующая спека `indexing/openspec-parsing` уже декларирует резолв в `report_forms` — реализация от неё отстаёт.

## Goals / Non-Goals

**Goals:**

- Закрыть шесть измеренных пробелов покрытия упоминаний (report ~2210, event ~979, GIVEN, .pas→form ~425, unknown-процы ~244, шум pAPI_ ~1662).
- Сохранить общий механизм: staging `spec_code_mentions` → batch-resolve → `references_code`, confidence `spec_mention`.
- Нулевые миграции: новые значения `mention_kind` — текстовая колонка, схема БД не меняется.

**Non-Goals:**

- Bare-идентификаторы в inline-прозе без бэктиков (кроме уже одобренных маркеров API_/FCD_/таблиц/путей/report/event) — высокий риск шума, отдельное решение.
- Резолв `.xml`-контрактов вне `Event/` (сервисные контракты, datamart-XML) — отдельная нить.
- Резолв `.js`/`.bpl` упоминаний (объёмы ~104/~40, низкий приоритет).
- Классификация VB-функций отчётов (2929 в индексе) — нет надёжного текстового маркера в спеках.

## Decisions

### D1. Report: новый kind `report` + регекс путей

`rePathReport = \b[A-Za-z0-9_/\\]+\.(?:tpr|rpt)\b` — в списке «всегда безопасных» маркеров обоих режимов (как `rePathSQL`). `classifyMention`: суффиксы `.tpr`/`.rpt` → `report`, имя — базовое имя файла без расширения.

*Альтернатива:* резолвить по полному пути — отклонено: `report_forms.report_name` хранит базовое имя (`form651`), совпадение по имени достаточно (коллизии имён отчётов редки, MAX(id) как у форм).

### D2. Event: маркер по префиксу идентификатора, не по расширению

`reEventName = \bOn(?:After|Before)[A-Z][A-Za-z0-9_]*` — в списке безопасных маркеров обоих режимов. Для путей: если токен-путь содержит сегмент `Event` и заканчивается `.xml`, kind = `event`, имя — последний сегмент без расширения (сегмент `Event` снимает неоднозначность с сервисными `.xml`-контрактами). Резолв — `FindAPIContractIDsByNames` (события лежат в `api_contracts` с kind event/callback_event).

*Альтернатива:* тянуть все `.xml` — отклонено: 478 упоминаний включают datamart/шаблоны, резко растёт шум.

### D3. GIVEN: включить в сканирование

В `insertSpecMentions` конкатенация `s.Given + "\n" + s.When + "\n" + s.Then`. Изменение одной строки; номер строки сценария уже считается от `s.LineStart` — корректен для любой части блока.

### D4. `.pas` — двухфазный резолв, классификацию не трогаем

`classifyMention` оставляет `*.pas` → `method`. В постпроцессоре: методный lookup промахнулся → `FindDFMFormIDsByNames` по тому же имени → ребро к `dfm_form`. Обоснование: в FA `.pas` — преимущественно юнит формы; в `pas_methods` лежат методы, а не юниты, поэтому сегодня хит почти невозможен.

*Альтернатива:* менять kind на «unit» — ломает резолв настоящих одноимённых методов и требует нового целевого типа.

### D5. Unknown — second-chance резолв вместо ослабления регекса

`reUnderscoreIdent` остаётся с требованием заглавной первой буквы. В постпроцессоре: собрать уникальные имена kind=unknown → `FindLatestSQLProcedureIDsByNames` → хиты дают рёбра. Так покрываются строчные процы (`r8938_prc`, `rpt_f1417u_proc` — наличие в индексе проверено).

*Альтернатива:* ослабить регекс до `[A-Za-z]` первой буквы — чинит ещё и извлечение bare-строчных из Related code, но добавляет false-positive «процедур» (`my_param`, служебные токены) уже на этапе классификации; отложено: сначала меряем эффективность second-chance.

### D6. `pAPI_*` — контрактовый резолв (kind `api_table`)

`pAPI_*` — TVP-таблицы, декларированные в контрактах: `api_contract_tables` → `contract_id` (и service, и callback_event контракты), `api_business_object_tables` → business_object, поля в `api_contract_table_fields`. Сегодня упоминания классифицируются как `table` и резолвятся в `sql_tables`, но там лежат usage-записи SQL-парсера (TVP создаётся per-spid в каждом callback-проце) — ребро указывает на последнюю usage-запись, то есть семантически произвольную сущность. Решение: в `classifyMention` префикс `pAPI_` (case-insensitive) → kind `api_table` (проверка до табличной эвристики); постпроцессор ищет имя в `api_contract_tables` и создаёт рёбра `references_code` ко всем DISTINCT контрактам-владельцам; дедуп по source|target уже встроен в `buildSpecMentionRelations`, мультиребро от одного mention механически допустимо.

*Альтернативы:* дроп упоминаний (v1 этого дизайна) — потеря трассируемости контрактных таблиц, отклонено: сущности полноценные, объём 1662 упоминания; связка с business_object — в relations нет целевого типа business_object; оставить table-резолв в `sql_tables` — ребро на произвольную usage-запись сохраняется.

Мультивладелец (`pAPI_Accrual_ObjDate` — ≥5 контрактов): ребро к каждому DISTINCT-владельцу; на шаге верификации меряем среднее число контрактов на таблицу — при среднем >10 пересматриваем (фильтр `contract_kind`).

### D7. Все новые lookup'ы — batch, одним постпроцессорным проходом

Новые kind'ы добавляются в существующую схему `collectMentionNamesByKind` → один batch-lookup → `buildSpecMentionRelations`. Фолбэки (.pas→form, unknown→procedure) выполняются после основных lookup'ов, только для имён без хита.

## Risks / Trade-offs

- [Ложные event-совпадения: `OnXxx` встречается в именах клиентских обработчиков Delphi] → Резолв по `api_contracts` точным именем: клиентские обработчики не контракты — промах, остаётся unknown в staging.
- [Коллизии коротких имён отчётов (`N1.rpt`)] → Резолв MAX(id), как у форм; риск неверной привязки тот же, что в существующих kind'ах, отдельного ухудшения нет.
- [Second-chance unknown может связать спеку с процедурой-совпадением по имени, но другим по смыслу] → Имена процедур в Diasoft уникальны по соглашению; риск оценён как низкий, эффект ограничен объёмом unknown (244 инстанса).
- [Рост relations (~5 тыс. новых рёбер) замедлит spec-запросы] → Рёбра пишутся тем же batch-путём с теми же индексами; `spec_by_code` уже использует trgm-индекс по `mention_name`.
- [Двойной резолв `.pas` может дать ребро к форме там, где имелся в виду метод] → Фолбэк срабатывает только при промахе методного lookup'а; неодносмысленность нулевая, т.к. имя не найдено как метод.
- [Мультивладельные TVP (`pAPI_*` принадлежат многим контрактам) раздуют граф рёбер] → Рёбра только к DISTINCT-владельцам, дедуп встроен; среднее число контрактов на таблицу замеряется на верификации, при >10 вводится фильтр `contract_kind`.

## Migration Plan

Без миграций схемы. Порядок внедрения: парсер (новые kind'ы + GIVEN + исключение pAPI_) → store-lookup (`report_forms`) → постпроцессор (report/event/фолбэки) → интеграционные тесты → полный пере-скан (`codebase init`/`update`), постпроцессинг пересобирает `references_code` идемпотентно (delete+insert). Откат — reverting изменений кода; staging-записи новых kind'ов без резолва безвредны.
