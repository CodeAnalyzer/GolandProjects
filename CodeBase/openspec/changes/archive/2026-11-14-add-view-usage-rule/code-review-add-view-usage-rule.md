## 2. Оценка реализации

Реализация соответствует design:

- **Ленивый кэш** `isViewTable` (`internal/review/review_lookup.go:731`)
  повторяет паттерн `isMemoryTable`: один `SELECT DISTINCT` под мьютексом,
  `viewNamesLoaded` различает «не запрошено» и «запрошено и пусто», при
  ошибке/`db == nil` кэш пуст и помечен загруженным (fail-open), повторных
  запросов нет.
- **Нормализация** выполняется в Go одной точкой — `normalizeTableKey`
  (`review_lookup.go:675`): lower, срезание схемы до последней точки, снятие
  `[]`/`""`. SQL возвращает сырые имена, `NULL` из `regexp_match`
  пропускается через `sql.NullString`. Это закрывает замечание F5
  предыдущего ревью артефактов.
- **Правило** `viewUsageInServerCode` (`review_rules.go:2098`) использует те же
  DML-контексты (`tableExistsDMLContexts`), фильтры шума
  (`isTableExistsNoiseName`), фильтр строковых литералов
  (`onlyQuotedOccurrence`), дедупликацию `name:line` и `CurrentProductID` —
  единая точка фильтрации с `tableExistsInMetadata`.
- **Подавление** `tableExistsInMetadata` (`review_rules.go:2070-2076`)
  выполняется после проверки создателя и до формирования finding; при
  ошибке загрузки view-множества имя не распознано и работает прежняя
  ветка (fail-open, старое поведение сохраняется).
- **Каталог/CLI/MCP**: правило зарегистрировано с `SeverityDeployStopper`
  (`catalog.go:425`), попадает в `DefaultEnabledRules` автоматически,
  `RuleListString()` подхватывает его без ручных правок; README дополнен
  (`README.md:1068-1069`).
- **Тесты**: unit покрывает nil-DB/fail-open, нормализацию (регистр,
  `dbo.`/`public.`), регистрацию/severity, SELECT/UPDATE, обычную таблицу,
  `#`-таблицу, курсор, view-поверх-view, подавление `tableExists` и
  незагруженный кэш; integration — ленивую загрузку из `query_fragments`,
  `public.` в определении, `create or replace`, отрицательный контроль
  (`select`-фрагмент не view) и совместную работу с `tableExists`.
- **Схема/индексация** не менялись, bump `CurrentSchemaVersion` не требуется;
  buildNumber поднят до 1697.

## 3. Замечания

### C1 — MEDIUM. Схемный префикс в *обращении* не реализован на уровне парсера; спека и код расходятся

**Где:**
- `internal/parser/sql/sql_parser.go:35` — `tableNameRe`:
  `(?i)\b(?:FROM|JOIN|INTO|UPDATE)\s+([A-Za-z_#][A-Za-z0-9_#]*)` — после
  `FROM` захватывается только первый токен, точки не входят в класс.
- `internal/review/view_usage_integration_test.go:66-68` — комментарий
  прямо фиксирует: «парсерный `tableNameRe` срезает qualified-имя до первого
  токена (`dbo.`/`public.` в ссылке не резолвится ни одним правилом)».
- `openspec/changes/add-view-usage-rule/specs/review/deploy-stoppers/spec.md:14-15`
  — требование: «Схемный префикс в определении и в обращении (`public.`,
  `dbo.`) MUST отбрасываться».
- Там же `:52-57` — сценарий «Схемный префикс отбрасывается» проверяет
  `create or replace view public.tinstracclink`, но обращение в сценарии —
  **bare** `tinstracclink`.

**Проверка:** пробный парсинг `create proc P as select ID from dbo.tfund`
даёт `TABLE name="dbo" context="select"` — не `tfund`. То есть при реальном
`from dbo.tView`:
- `viewUsageInServerCode` не сформирует finding (false negative);
- `tableExistsInMetadata` может сформировать finding на имя `dbo`
  (false positive), если `dbo` не попадёт в шум.

**Текущий корпус:** квалифицированных ссылок на view-имена — 0 (проверено
по индексу), поэтому приёмка на FA не затронута. Но требование с `MUST` в
обращении фактически не выполнено и не покрыто тестом; отклонение
зафиксировано только комментарием в integration-тесте, но не в design/tasks
и не в формулировке спеки.

**Рекомендация:** до архивации выбрать одно:
1. **Сузить спеку/сценарий:** «схемный префикс отбрасывается в определении;
   в обращении — если парсер сохранил префикс; текущий парсер срезает
   qualified-имена до первого токена (известное ограничение)», — и добавить
   это ограничение в design/tasks.
2. **Починить парсер** (отдельным change): разрешить точки в `tableNameRe`
   и/или добавить пост-обработку qualified-имён; тогда `normalizeTableKey`
   уже готов принять `dbo.tFund`, а сценарий можно оставить как есть.
3. В любом случае добавить тест, фиксирующий текущее поведение
   (`from dbo.tfund` → ожидаемый результат), чтобы расхождение не осталось
   незамеченным.

### C2 — LOW. Новое правило не учитывает таблицы, созданные в самом файле (`created`/`SELECT INTO`)

**Где:** `review_rules.go:2112-2148` (`checkViewUsageInServerCode`) не строит
`created`-множество, которое есть в `checkTableExistsInMetadata`
(`review_rules.go:2013-2029`). Если анализируемый файл создаёт локальную
таблицу с именем, совпадающим с view из другой ветки/продукта, правило
сформирует ложный `viewUsageInServerCode` — ссылка идёт на локальную таблицу,
а не на view.

**Текущий корпус:** коллизий view-имён с `CREATE TABLE`, `SELECT INTO`,
API- и memory-таблицами — 0, поэтому сейчас ложных срабатываний нет. Риск
растёт из-за generic-имён в наборе view (`Account`, `Balance`, `Branch`,
`Fund`, `Operation`, `Task`, `Host`, `Node`, `Instrument`, `Resource` и т.п.).

**Рекомендация:** перед `isViewTable` пропускать имена из `created`
(`CREATE TABLE` в файле) и `select_into` из `parsed.ColumnDefinitions`, как в
`tableExistsInMetadata`; добавить unit-тест «локальная таблица с именем view
не даёт finding».

### C3 — LOW. Извлечение имён view не учитывает комментарии/строки и берёт только первое совпадение на фрагмент

**Где:** `review_lookup.go:741-745` — `regexp_match(...)` возвращает первое
совпадение; `WHERE query_text ~* ...` не исключает комментарии и строковые
литералы.

**Текущий корпус:** фрагментов, где `create view` встречается только в
line/block-комментарии, — 0; фрагментов с 2+ `create view` — 0. Поэтому
текущие 156/105 корректны. Но при появлении, например, комментария
`-- create view Fake` перед реальным `create view Real` в одном фрагменте
кэш получит `Fake`, а `Real` потеряется (false negative), плюс возможен
ложный `Fake`, если на него есть ссылка.

**Рекомендация:** либо зафиксировать assumption в design («один view на
фрагмент, без комментариев перед определением»), либо использовать
`regexp_matches(..., 'g')` и/или предварительно вырезать комментарии;
добавить тест на комментарий/два определения.

### C4 — LOW. `isViewTable` игнорирует `rows.Err()` и помечает частичный кэш загруженным

**Где:** `review_lookup.go:747-759`: цикл `rows.Next()` завершается, ошибка
итерации не проверяется, после чего `viewNamesLoaded = true`. Если ошибка
произошла в середине выборки, кэш останется частичным, но «загруженным» —
до конца файла возможны false negative без повторной попытки.

`isMemoryTable` устроен так же, но для нового бан-правила контракт fail-open
лучше сделать явным: ошибка итерации — это не «пусто», а «неполные данные».

**Рекомендация:** проверять `rows.Err()`; при ошибке либо очищать кэш и
оставлять `viewNamesLoaded = false` с защитой от шторма (например,
отдельный флаг «пробовали»), либо явно логировать/документировать, что
частичный кэш — принятый fail-open. Добавить тест с закрытой БД/сломанным
соединением.

### C5 — LOW (приёмка/документация). Числа приёмки не воспроизводятся из артефактов; `grant` — ложный `tableExists`

**Числа.** В proposal/design зафиксировано 49 обращений в 30 файлах
(33 уникальных после свёртки ветвей); в отчёте о реализации — 45 находок в
26 файлах. Независимый проход по построенному мной набору путей из индекса
(36 файлов, `regexp_matches` по view-именам) дал **43 `viewUsage` в 24
файлах** и **0 остаточных `tableExists` на view-именах**. Это не
опровергает приёмку (набор файлов/дедупликация/фильтры могли отличаться), но
методика 45/26 в change не зафиксирована, поэтому результат не
воспроизводится следующим ревьюером.

**`grant`.** В `view_trash.sql` на строке 52 (`grant select on
CtrConditionContent to public`) `tableExistsInMetadata` выдаёт finding с
`object=grant`. Пробный парсинг подтверждает: парсер извлекает `grant` как
таблицу в контексте `select`; `sqlKeywordsMap` (`internal/review/types.go:162`)
не содержит `grant`, а `isTableExistsNoiseName` (`review_rules.go:1992`)
опирается на этот map. Это **предсуществующее** поведение, не регрессия
данного change (новое правило `grant` не флагает — его нет в view-наборе),
но утверждение приёмки «16 подлинных `tableExists` сохранены» неточно:
фактически 15 подлинных + 1 ложный `grant`.

**Рекомендация:**
- приложить к change точный запрос/список файлов/правило дедупликации для
  45/26 (или заменить числа на воспроизводимые 43/24 с оговоркой);
- поправить формулировку приёмки по `view_trash.sql`;
- отдельной задачей добавить `grant`/`revoke` в шум `tableExistsInMetadata`
  (или исправить парсер), чтобы ложный finding не маскировал реальные.

### C6 — LOW (тесты). Сценарий «ошибка БД» проверен только через `db == nil`

**Где:** `view_usage_test.go:33-50` (`TestIsViewTable_NoDB_FailOpen`) —
это отсутствие БД, а не ошибка запроса. Спека
(`spec.md:65-70`) требует, чтобы ошибка получения множества не валила
review; код это делает (`err != nil` → пустой кэш, `viewNamesLoaded=true`),
но реальный путь `QueryContext` с ошибкой не покрыт.

**Рекомендация:** добавить тест с закрытым/недоступным соединением или
временной БД без `query_fragments`; проверить, что review завершается
успешно, `viewUsage` молчит, а `tableExists` работает как раньше.

### C7 — INFO. «Для каждого обращения» vs дедупликация `name:line`

Спека (`spec.md:5-6`) говорит «для каждого обращения», реализация
дедуплицирует по `name:line` (`review_rules.go:2122-2126`) — так же, как
`tableExistsInMetadata`. Поведение разумное, но формулировку спеки стоит
уточнить: «для каждого обращения (дедупликация по имени и строке)».

### C8 — INFO. `CodeBase.exe` изменён в рабочем дереве

Бинарник tracked и пересобран (build 1697). Если это осознанная часть
поставки — ок; если бинарники не должны попадать в коммит, исключить.

## 6. Итог

Архитектурно и алгоритмически изменение корректно: ленивый кэш по образцу
`isMemoryTable`, единая нормализация, переиспользование фильтров шума,
fail-open и подавление старого правила работают; тесты и приёмка на реальных
файлах FA подтверждают замену ложных `tableExists` на `viewUsage` без
регрессий. Блокирующих дефектов кода нет. Перед архивацией нужно закрыть
C1 (расхождение спеки и парсера) и, желательно, C2–C5; остальное —
информационные улучшения.
