# Design: optimize-query-search-bottlenecks

## Context

Источник — `Bug-reports/BUG-query-search-performance-bottlenecks-20261103.md` и разбор от 2026-11-03: подтверждены B1, B2, B3, B5, B8, ANALYZE; отклонены B4 (склейка двух форм запроса; отдельное предложение `Modifications/symbols-owner-key-materialization.md`), B7-дедуп (архитектурный тред `Modifications/query-fragment-dictionary-versioned-lines.md`). B6 (состав проб warmup) выведен из scope: warmup — фоновая горутина, старт MCP не блокируется, а после фиксов B1/B2/B5 сами пробы подешевеют; при этом тяжёлые остатки (холодная загрузка 115 МБ desc-эмбеддингов ~14 с, `symbol LIKE "Insert"` ~5,5 с из B4) сохраняются, поэтому контроль времени MCP-старта включён в задачу 7.2. Все правки — query-side и пайплайн-хвост `update`; схема БД и данные не меняются, `CurrentSchemaVersion` не бампается.

Ключевые точки кода: `internal/specsvc/specsvc.go` (`ExecuteSpecSearch` :372, `searchSpecExact` :1302, `searchSpecTrgm` :1391), `internal/query/query.go` (`buildReportFormLookupCondition` :319, `SearchSymbol` :385, `SearchQueryFragment` :764), `internal/query/desc_query.go` (`searchDescriptionsSemantic` :255, displaced-выборка :293-314, кеш `descSemanticCache`), `internal/mcp/warmup.go`, runner завершения init/update.

## Goals / Non-Goals

**Goals:**
- `spec_search` exact-слой: единицы сотен мс вместо секунд (B1: 2,77 с → ~75 мс; B2: −6 с пустого trgm).
- `symbol --type report_form`: уход от полного перебора строк типа; интерактивное время на холодном кеше FA-масштаба (B3).
- `sql-fragment`: ограниченный худший случай, отсутствие обрывов по `query_timeout_sec`; диагностика усечения (B5).
- `desc_search` semantic: минус per-call SQL (~1 с) на вытесняющих контрактах (B8).
- Свежая статистика планировщика после массовых вставок/удалений (ANALYZE).

**Non-Goals:**
- Словарь `query_texts` и контент-дедупликация (versioned vs client lines) — отдельное направление.
- Материализация `owner_key` в `symbols` (B4) — отдельное предложение.
- Изменение состава проб MCP warmup (B6 — снят), `desc_search` displaced → EXISTS-подзапрос (закрывается кешем), `query table` enrichment (B9).
- Переименование значений `layer` у `spec_search` (только документация).
- Настройка окружения PG (`shared_buffers` и пр.) — вне кода.

## Decisions

### D1. B1: FTS-предикат проталкивается в каждую ветку CTE `artifacts`

В `searchSpecExact` предикат `search_vector @@ plainto_tsquery('russian', $1)` добавляется в `WHERE` каждой из четырёх веток UNION ALL внутри CTE; внешний предикат сохраняется (дешёвый фильтр по уже суженному множеству). CTE `chosen` и финальный SELECT не меняются — контракт дедупликации веток и ранжирование `ts_rank` сохраняются.

Альтернатива `NOT MATERIALIZED` отклонена: CTE референсится дважды, инлайн дублирует вычисление в двух местах и поведение зависит от версии планировщика; явный pushdown детерминирован и использует существующие GIN-индексы `idx_spec_*_fts` (никаких новых индексов).

### D2. B2: гейтинг body-trgm по числу word-токенов; tech-пути всегда

`searchSpecTrgm` разделяется на две части:
- **tech-часть** (выполняется всегда): trgm по `related_code`, точное `LOWER(mention_name) = LOWER($1)` и trgm по `mention_name` во всех четырёх source-ветках;
- **body-часть** (только для коротких запросов): similarity `%` по `body_text`, конкатенациям сценариев и usecases.

Гейт: запрос содержит ≤ 2 word-токенов, где word-токен — лексическая единица по правилу `specfts.lexicalUnits` (`internal/specfts/tokenizer.go:241`): последовательность букв/цифр/подчёркиваний длиной ≥ 2 рун, содержащая хотя бы одну букву (примеры: `Audit_Insert` — один токен; «создание user_profile» — два). Функция экспортируется и переиспользуется — собственная токенизация в specsvc не вводится. Правило — то же, каким гейт лексического покрытия распознаёт слова запроса. Больше двух токенов → body-часть пропускается целиком. Обоснование: similarity короткой фразы против длинного текста ограничена ниже порога 0.3 конструированием (union триграмм), recheck отбрасывает всех кандидатов — вычисления гарантированно пустые.

Альтернатива «ранний выход при exact ≥ limit» отклонена: теряет tech-name хиты, когда FTS заполнил лимит русскоязычными совпадениями (tech-путь — единственный способ найти спеки по `FCD_*`/`API_*`, русский стемминг их не покрывает).

Порог фиксируется константой (без конфиг-ручки — проблемы не наблюдалось, ручка добавится при необходимости). Семантика `layer=exact` («лексический: tsvector + tech-name trgm») уточняется в help CLI и описании MCP-инструмента без переименования значений.

### D3. B3: трёхполевой report_form-поиск через UNION ALL индексных ветвей

При `--type report_form` CTE `base` в `SearchSymbol` строится как `UNION ALL` трёх ветвей: совпадение по `LOWER(s.symbol_name)`, по `LOWER(rf.form_name)`, по `LOWER(rf.form_class)` (при `--like` — три ILIKE-ветви). Ветвь имени использует `idx_symbols_symbol_name_type_lower`; ветви form_name/form_class идут от `report_forms` (небольшая таблица) с выходом на symbols через `idx_symbols_entity_type_entity_id`. Дедуп `chosen`/финальный join не меняются; одна и та же строка, совпавшая по нескольким полям, может попасть в base дважды — финальный SELECT получает `DISTINCT` по `s.id`.

Альтернатива «нормализовать form_name/form_class в symbols при индексации» отклонена: смена схемы + переиндексация, по выигрышу эквивалентна owner_key-направлению; UNION ALL решает проблему без миграции.

### D4. B5: guard-потолок кандидатов + `meta.truncated`

`SearchQueryFragment`: внутренний подзапрос CTE `matches` получает `LIMIT $3` (cap+1); поверх — `count(*) OVER () AS total_matched` (окно строго снаружи внутреннего LIMIT, иначе окно форсирует полный проход). Ключевой эффект — ленивость: executor перестаёт тянуть строки из GIN/recheck после cap+1, `DISTINCT ON` сортирует ≤ cap строк. `total_matched == cap+1` → усечение.

Сигнатура расширяется: `SearchQueryFragment(...) ([]QueryFragmentResult, truncated bool, err)`; флаг прокидывается через querysvc в `meta` CLI (`--json` envelope) и MCP-ответ (`truncated: true` + hint «уточните шаблон»). `COALESCE(query_hash, md5(...))` сохраняется как есть (мёртвый на живых данных fallback, лениво вычисляется).

Конфиг: `[query] sql_fragment_match_cap`, дефолт 50000, `0` — без ограничения (внутренний LIMIT не подставляется), `< 0` — ошибка загрузки конфигурации. При cap ≤ 0 план эквивалентен текущему.

### D5. B8: кеш вытесняющих контрактов по ключу (поколение модели, эпоха индексации)

Displaced-множество зависит не только от модели, но и от данных (`relations` implements_contract, описания `api_contracts`), которые меняются каждым update — при этом переобучение desc-модели может пропускаться (`lsaDecisionSkipIdempotent`, fingerprint неизменен) или откладываться (`lsaDecisionDefer`, corpusDelta ниже `RetrainThreshold`), то есть поколение модели само по себе не маркирует изменения данных. Поэтому ключ кеша — пара «поколение модели + последний **завершённый** scan_run id (эпоха индексации)»: любое завершённое изменение данных кодовой базы создаёт новый scan_run. Эпоха — `SELECT MAX(id) FROM scan_runs WHERE status IN ('completed', 'completed_with_errors')` (идиома `HasCompletedInit`; PK-максимум, суб-мс): незавершённый `running`-прогон не является эпохой — semantic-вызов во время update, привязав частичный снимок к будущей эпохе, оставил бы кеш «свежим» с данными середины прогона после его завершения (выявлено ревью). Актуальность проверяется на каждом semantic-вызове дёшево — этим запросом и существующей проверкой поколения по паттерну `descSemanticHolder`; перевычисление — только при изменении любого из компонентов. Mutex/singleflight — по образцу существующего holder'а.

Альтернативы отклонены: «ключ только по поколению модели» — оставляет окно устаревания между update без переобучения (выдача отдаёт старое вытеснение, чего per-call SQL не делал; выявлено ревью F1); «EXISTS/semi-join в основном запросе» — главный запрос — in-memory скоринг LSA, а не SQL, кеш снимает 100% стоимости без изменения плана.

### D6. ANALYZE после init/update

Store-хелпер `AnalyzeCodebaseTables(ctx)` — один оператор `ANALYZE <список таблиц>` по фиксированному списку таблиц кодовой базы (symbols, query_fragments, relations, sql_tables, sql_procedures, files + крупные spec-таблицы при существенном изменении). Вызов — в runner после успешного завершения `InitCtx`/`UpdateCtx` (общая точка после фиксации итога прогона); ошибка — предупреждение в лог, статус прогона не меняется (идиома «VACUUM ANALYZE после массового удаления» из RTI/TRC-store). Read-only путь не задействован по построению.

`VACUUM ANALYZE` отклонен: мёртвые кортежи — зона autovacuum, для планировщика достаточно ANALYZE; VACUUM тяжелее и не выполняется в транзакции сctx прогона корректно.

## Risks / Trade-offs

- [B1: дублирование предиката в 4 ветках — расхождение с внешним условием] → внешний предикат сохранён как фильтр; тест-эквивалентность составов/рангов до/после на копии боевой БД.
- [B2: порог ≤2 токенов отсекает редкий полезный body-trgm для трёхсловных запросов] → tech-пути не затронуты; порог — константа в одном месте; при жалобах добавляется конфиг-ручка.
- [B3: UNION ALL дублирует строки при совпадении по нескольким полям] → `DISTINCT` по `s.id` в финальном SELECT; тест на форму, совпадающую и по имени, и по классу.
- [B5: усечённое множество недетерминированно (порядок обхода индекса)] → ниже потолка результат байт-в-байт прежний; усечение всегда помечено в meta; MCP-описание инструмента документирует флаг.
- [B5: window-count добавляет проход по ≤cap+1 строкам] → пренебрежимо против сэкономленной материализации/сортировки.
- [B8: кеш отдаёт устаревшее вытеснение между update без переобучения модели (skip-idempotent/defer)] → ключ включает эпоху индексации (последний завершённый scan_run): любой прогон, менявший данные кодовой базы, инвалидирует кеш; проверка эпохи — суб-мс PK-запрос на вызов; тест покрывает сценарий «update без переобучения перестраивает кеш».
- [B8: semantic-вызов во время активного прогона — недетерминированная смесь данных середины update] → эпоха считается только по завершённым прогонам: вызов во время update обслуживается снимком последней завершённой эпохи (консистентный вид), а не частичным снимком; после завершения прогона кеш перевычисляется (тест: `running`-скан не инвалидирует, `completed` — инвалидирует).
- [ANALYZE удлиняет update на секунды-десятки секунд на 5-млн таблицах] → один вызов после прогона, вне транзакций индексации; некритичность ошибки оговорена.
- [Тепловой прогон FA после фиксов меняет распределение буферов] → замеры verifikation выполняются и cold, и warm; пороги — в Verification bug-репорта.

## Migration Plan

Схема/данные не меняются — миграция не требуется. Откат — реверт кода; `sql_fragment_match_cap` в старых конфигах игнорируется новым кодом без ошибки (неизвестные ключи секции не фейлят загрузку), default 50000 применяется только после обновления бинарника.

- Формат hint в meta усечения (строка vs локализованные варианты) — при реализации вместе с существующими hint'ами semantic-диагностики.
