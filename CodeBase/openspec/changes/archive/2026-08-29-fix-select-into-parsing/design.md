## Context

SQL-парсер (`internal/parser/sql/sql_parser.go`) обрабатывает файлы построчно. Основной цикл (строка ~753) отслеживает блочные комментарии через флаг `inBlockComment`. При обнаружении `/*` без `*/` на строке устанавливается `inBlockComment = true`, но отсутствует `continue` — строка проходит дальше и может матчить `createTableRe` (строка ~1155), устанавливая `inCreateTableDefinition = true`. Последующие строки внутри комментария пропускаются (`inBlockComment`), но флаг `inCreateTableDefinition` не сбрасывается. После закрытия комментария строки SELECT-проекции обрабатываются как CREATE TABLE определения.

Дополнительно: `isKeyword` (строка ~1848) не содержит `ELSE`, а `splitSQLByTopLevelComma` (строка ~157) не фильтрует `--` комментарии.

## Goals / Non-Goals

**Goals:**
- Три точечных фикса в `sql_parser.go` для устранения описанных багов
- Регрессионные тесты, воспроизводящие сценарии из `patch7_2_1056.sql`

**Non-Goals:**
- Переписывание SQL-парсера на полноценный AST-разбор (out of scope)
- Улучшение `enrichSelectIntoDataTypes` для разрешения типов SELECT INTO колонок из CREATE TABLE в том же файле (отдельная задача)
- Обработка вложенных блочных комментариев `/* /* */ */` (редкий случай, не встречается в патч-файлах)

## Decisions

### Decision 1: Добавить `continue` после `inBlockComment = true`

**Решение:** На строке ~766 после `inBlockComment = true` добавить `continue`.

**Альтернатива:** Сбрасывать `inCreateTableDefinition` при входе в блочный комментарий. Отклонено — `continue` проще и обрабатывает все случаи (не только `createTableRe`, но и `selectIntoRe`, `insertRe` и т.д.).

### Decision 2: Добавить `ELSE` в `isKeyword`

**Решение:** Добавить `"ELSE": true` в карту ключевых слов на строке ~1856.

**Альтернатива:** Фильтровать `else` в `parseColumnDefinition` отдельно. Отклонено — `isKeyword` уже используется для фильтрации и это единое место для всех ключевых слов.

### Decision 3: Фильтровать `--` комментарии в `splitSQLByTopLevelComma`

**Решение:** В начале `splitSQLByTopLevelComma` (строка ~157) удалить `--` комментарии из входного текста перед разделением по запятым. Использовать уже существующий паттерн: поиск `--` и обрезка до него — но применить к каждому сегменту после split, а не к всему тексту до split (т.к. `--` может быть внутри строкового литерала с запятой).

**Уточнение:** Удалять `--` комментарии post-split, в каждом сегменте, через `inferSelectColumnName` (который уже это делает на строке ~209). Проблема в том, что `splitSQLByTopLevelComma` сплитит по запятым **до** того, как `inferSelectColumnName` фильтрует комментарии. Запятая в `--` комментарии создаёт лишний сегмент. Фикс: фильтровать `--` **внутри** `splitSQLByTopLevelComma` — обрезать текст от `--` до конца строки при обнаружении, не доходя до запятой.

**Альтернатива:** Переписать `splitSQLByTopLevelComma` с полным лексером. Отклонено — избыточно для точечного фикса.

## Risks / Trade-offs

- **[Risk] Строка с `/*` и `*/` на одной линии** → уже обрабатывается корректно: условие `!strings.Contains(line, "*/")` ложно, `inBlockComment` не устанавливается, `continue` не нужен. Фикс не ломает этот случай.
- **[Risk] `--` внутри строкового литерала** (например `'a--b, c'`) → `splitSQLByTopLevelComma` уже отслеживает `inSingleQuote`, но фильтрация `--` должна учитывать кавычки. Фикс: проверять `--` только вне `inSingleQuote`.
- **[Trade-off] `DSUNKNOWN` для SELECT INTO остаётся** → это by design, `enrichSelectIntoDataTypes` разрешает типы постфактум. Данный change не меняет эту логику.
