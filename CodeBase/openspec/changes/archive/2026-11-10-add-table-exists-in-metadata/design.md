## Context

См. `proposal.md` — Why. Review уже умеет проверять существование процедур и индексов, но не таблиц. Индекс уже содержит все нужные признаки создания таблицы, разбросанные по четырём источникам:

- `sql_tables.context='create'` — DDL из патчей (постоянные t-таблицы) и TmpTbl-скриптов (p-таблицы);
- `api_contract_tables` и `api_business_object_tables` — p-таблицы, объявленные в DSArchitect XML;
- `sql_column_definitions.definition_kind='select_into'` — таблицы, создаваемые через `SELECT ... INTO`.

Пилотный прогон по индексу показал, что простой фильтр «используется, но нигде не создаётся» даёт много шума: имена курсоров (`pAPI_ContractKind`), результаты `DROP_IF`, мусор парсера (`truncate`, `target`) и таблицы ядровых продуктов, которые не проиндексированы на конкретной машине. При этом найден реальный дефект: `pAPI_Account_MassClose` используется в `ContractMassLoad.sql`, а в метаданных объявлена `pAPI_Acc_MassClose`.

## Goals / Non-Goals

**Goals:**

- Новое правило `tableExistsInMetadata` (severity 1), доступное через CLI `review` и MCP `codebase_review_sql` без новых флагов.
- Проверка всех таблиц, к которым скрипт реально обращается в DML, с минимальным числом ложных срабатываний.
- Один batch-запрос к БД на файл вместо N+1.

**Non-Goals:**

- Не проверять существование колонок, индексов или прав — только таблиц.
- Не пытаться определять базовые таблицы по эвристикам или белому списку: на рабочем ПК ядровые продукты (`fa-fmcore` и др.) проиндексированы.
- Не менять схему БД индекса и не добавлять новые таблицы.

## Decisions

### D1. Набор контекстов использования

Правило обходит `parsed.Tables` и берёт только `context IN ('select','insert','update','delete','log')`. Контекст `unknown` игнорируется.

Уточнение (не вводить в заблуждение при реализации): `parsed.Tables` порождается только SQL-парсером review, который контексты `dfm_embedded`/`pas_embedded` не эмитирует — это признаки индекса (DFM/PAS-парсеры), в `parsed.Tables` они не встречаются и отдельного фильтра не требуют.

Эмпирическая поправка (замер по локальному индексу fa-contracts): контекстный фильтр сам по себе НЕ закрывает курсорный шум — `FETCH ... FROM <cursor>` даёт `context='select'`, а `WHERE CURRENT OF <cursor>` — `context='update'`. Поэтому курсоры обрабатываются отдельным фильтром в D6. Альтернатива «обходить все `parsed.Tables`» даёт сотни ложных срабатываний.

### D2. Единый источник «таблица создана»

Добавляется `store.BatchLookupTableCreators(ctx, names []string) (map[string]bool, error)`, который одним запросом объединяет источники. Предикат `LOWER(table_name) = ANY($1)` ставится **в каждой ветви**, а не снаружи (прецеденты: `BatchLookupTableProductIDs`, `findAPITableNames`) — проталкивание предиката сквозь UNION не гарантируется планировщиком, а внутриветвевой фильтр гарантирует использование индексов:

```sql
SELECT LOWER(table_name) FROM sql_tables
 WHERE context IN ('create','select_into') AND LOWER(table_name) = ANY($1)
UNION ALL
SELECT LOWER(table_name) FROM sql_column_definitions
 WHERE definition_kind = 'select_into' AND LOWER(table_name) = ANY($1)
UNION ALL
SELECT LOWER(table_name) FROM api_contract_tables
 WHERE LOWER(table_name) = ANY($1)
UNION ALL
SELECT LOWER(table_name) FROM api_business_object_tables
 WHERE LOWER(table_name) = ANY($1)
```

Обоснование деталей:
- `UNION ALL` без `DISTINCT` — дедупликация делается Go-мапой, серверный distinct не нужен;
- ветвь `sql_tables.context='select_into'`: значение парсером сейчас не пишется, но уже используется существующими lookup'ами (`BatchLookupTableProductIDs`) — включение бесплатно и устойчиво к будущим изменениям индексации;
- `sql_column_definitions` имеет индекс `idx_sql_column_definitions_lower_table_col`; `sql_tables` — `idx_sql_tables_table_name_lower`. У api-таблиц индекса по `LOWER(table_name)` нет, но они малы (тысячи строк), seq scan приемлем; при росте — добавить индекс отдельным изменением.

Альтернативы:
- Переиспользовать `BatchLookupTableProductIDs` — отклонено: там есть fallback на `dfm_embedded` и продуктовый scope, а для существования это неверно и дороже.
- Отдельные запросы по каждому источнику — отклонено: 2–4 round-trip на файл.

### D3. Учёт создания в самом анализируемом файле

Перед запросом к БД в множество созданных добавляются имена из `parsed.Tables` с `context='create'`. Это защищает от устаревшего индекса: файл читается с диска в актуальном виде, а метаданные могли не обновиться после добавления `CREATE TABLE`.

Дополнительно same-file `SELECT ... INTO` покрывается тем же способом — без БД: в множество созданных добавляются имена из `parsed.ColumnDefinitions` с `DefinitionKind='select_into'` (парсер пишет их при извлекаемой проекции).

Остаточный пробел: `created` не пополняется, когда парсер не извлекает из проекции валидное имя колонки — `SELECT * INTO tX`, проекции из `@`-переменных без алиаса-имени, пустые псевдонимы. Такая таблица не распознаётся созданной ни через parsed, ни через устаревший индекс; стиль редкий в FA, принимается как остаточный риск (см. Risks).

### D4. Кэш и предзагрузка в Runner

Как и для процедур/таблиц, в `Runner` добавляется кэш `tableCreatorCache map[string]bool` и предзагрузка в `prewarmTableCreators(ctx, parsed)` рядом с `prewarmTableProductIDs`, до старта параллельных правил (`runRuleTasks` исполняет задачи в до `NumCPU` горутин). Ключ — `normalizeIdentifier(name)` (lower + trim + снятие `[]`/кавычек). Кэш сбрасывается в начале `RunSQLFileCtx`.

Модель конкурентности (обязательна — правила идут параллельно):
- prewarm заполняет кэш **до** старта правил и записывает негативные записи (`false` для запрошенных и не найденных) — в проде ленивый путь не срабатывает вовсе;
- правило только читает кэш; при промахе (db-тесты, частичный prewarm) — индивидуальный lookup **без записи результата в общий map**, по паттерну `cachedLookupTableProductIDs` (review_lookup.go). Запись в общий map из горутины правила = data race;
- ошибка БД в ленивом пути трактуется fail-closed: возвращается false («не создана») — транзиентный сбой даёт ложный finding, а не пропуск дефекта severity 1; в проде путь не срабатывает благодаря негативному prewarm;
- альтернатива «мьютекс + флаг загруженности» (паттерн `isMemoryTable`) отклонена как избыточная при негативном prewarm.

### D5. Имя правила и место в каталоге

`RuleID = "tableExistsInMetadata"`, severity `SeverityDeployStopper` (1), описание «Таблица отсутствует в метаданных». Регистрация в `catalog.go` и `types.go`. Название симметрично существующему `indexExistsInDB`.

### D6. Фильтрация не-табличных имён

Дополнительно к фильтру контекстов:
- пропускаются имена с префиксом `#` и `##`;
- курсоры, объявленные в анализируемом файле: `parseCursorDeclarations(content)` (review_parser.go, уже используется правилами `varAssignInUpdate`/`cursorFetchArguments`) — закрывает `FETCH ... FROM` и `WHERE CURRENT OF` собственных курсоров файла; межфайловых курсоров в review нет (файл анализируется автономно);
- rule-local стоп-набор (общий `sqlKeywordsMap` не расширяем, чтобы не влиять на другие правила): `inserted`, `deleted`, `master`, `information_schema`, имена с префиксом `sys` (`sysobjects`/`syscolumns`/`sysindexes`/`systypes`/`sysconstraints`), плюс ключевые слова `open`/`fetch`/`goto`, отсутствующие в `sqlKeywordsMap`;
- placeholder-токены генераторов (regexp): имена из подчёркиваний (`^_+.*_+$`), содержащие `##` или начинающиеся с `__` (`__table__`, `_tablename_`, `t##__table__##`);
- шум из строковых литералов: DML-глаголы в профилировочных сообщениях (`PROFILE_TIME_EX('update contract')`) дают парсеру ложную пару (update, contract) — имя, встречающееся на строке обращения только внутри одинарных кавычек, таблицей не считается (найдено при ручной проверке 4.3 на ContractMassLoad.sql);
- пропускаются ключевые слова SQL (`sqlKeywordsMap`) и Diasoft-макросы (`M_*`);
- пустые имена и дубликаты отбрасываются.

Эвристика «имя должно начинаться с `t` или `p`» **не вводится**: базовые таблицы тоже t-префиксные, а p-префиксные имена курсоров уже отсекаются фильтром курсоров и контекстом.

## Risks / Trade-offs

- **Неполный индекс** (не все продукты скетчены, например `fa-fmcore`) → ложные finding'и на базовых таблицах. Митигация: правило можно отключить через существующий `--rules`; на рабочем ПК с полным индексом ложных быть не должно. Отдельный белый список не вводим — он быстро устаревает.
- **Шум не-табличных имён (измерен).** Пилотный замер по локальному индексу fa-contracts с фильтром только контекстов (D1) + `#`/`sqlKeywordsMap` (D6 без харденинга): 160 уникальных имён без источника создания, 662 из 35 691 файлов (1.9%) получили бы severity-1 finding. Классы шума: курсорные чтения (`FETCH ... FROM` → select, `WHERE CURRENT OF` → update), `inserted`/`deleted`, sys-каталоги, placeholder-токены, префиксы БД из cross-db ссылок, алиасы/derived-имена, парсерный мусор (`open`/`fetch`/`goto`). Митигация — D6 (курсоры файла, стоп-набор, placeholder-фильтр). До включения правила по умолчанию — обязательный повторный замер с полным набором фильтров (задача 4.5, см. Measurements); если шум остаётся систематическим — эскалация на пересмотр severity или default-off (решение согласовать: это противоречит proposal).
- **Устаревший индекс** для только что добавленных DDL в других файлах → ложный finding. Митигация: D3 покрывает создание в самом файле (включая `CREATE TABLE` и `SELECT ... INTO` с извлекаемой проекцией); для межфайловых случаев помогает `codebase update` перед review. Остаточный пробел: SELECT INTO с проекцией, из которой парсер не извлекает имена колонок (`*`, `@`-переменные без алиаса-имени) — редкий в FA стиль, осознанно принимаем.
- **Производительность**: один batch-запрос с `ANY($1)` по 4 источникам на файл, предикат в каждой ветви (индексы используются гарантированно); api-таблицы без lower-индекса сканируются, но они малы. При росте — индекс `LOWER(table_name)`.

## Measurements

Протокол замера (задача 4.5): по индексу отбираются файлы-кандидаты грубым SQL-фильтром (DML-контекст, без `#`, минус creators-UNION, минус стоп-набор/sys*/m_*/placeholder), затем на каждом кандидате прогоняется само правило `tableExistsInMetadata` с полным набором фильтров (end-to-end, включая курсоры файла и строковые литералы). Метрики — уникальные имена и файлы с ≥1 finding.

- Пилот (fa-contracts, локальный индекс, без харденинга D6): **160 имён / 662 файла (1.9%)** — неприемлемо для severity 1.
- Повторный замер с полным набором фильтров (2026-11-10, build 1684): SQL-грубый фильтр → 261 файл-кандидат; end-to-end прогон правила → **100 имён / 239 файлов (0.67% от 35 691 SQL-файлов)**. Снижение: файлы −64%, имена −38%.

Классы остатка (100 имён):

1. **Conversion/Test-утилиты** (`Test/Script_Utils/conv-*`): `cnv_KeyExt` (27 файлов, join в конверсионных скриптах), `tOperTemplateDoc` (18), `tPatch` (17) — таблицы окружения конвертации, существующие вне метаданных FA.
2. **Макросы генераторов отчётов**: `RESDEP_C_*` (14 имён), `SERVICETEMPLATE_*` (3) — runtime-таблицы генераторов.
3. **Парсерный шум**: `SEED_GEN`/`TARGET`/`drop`/`DROP_CREATE`/`truncate`/`isNull`/`TEST_END` (keywords вне `sqlKeywordsMap`), однобуквенные алиасы (`a`,`i`,`d`,`d2`,`p`,`cl`,`os`,`csl`,`iv1`), имена колонок (`ContractID`,`Subconto*`,`Direction`,`CDeal`,`cRisk`).
4. **Cross-db префиксы**: `nt72db`,`testdb4`,`testdb12` (имя перед `.dbo.`).
5. **Вероятные реальные необъявленные таблицы** (1–3 файла на имя, стиль FA): `pAPI_Account_MassClose` (подтверждённый дефект ContractMassLoad) + `pAPI_Acc_Mass*NTF/Protocol`, `p_MassInsertOrder*` (тот же файл), `pADC_LnAtr_*`, `pAPI_LoanExt_PTI*` (7 имён, один файл), `pAIC_*`, `pAPI_OperPart`, `pConsRB*`, `tIFRS*`, `tGuarantee`, `tLimit`, `tMenuItems` и др.

Вывод по гейту: ориентир «affected files сходятся к файлам с реальными дефектами» формально не достигнут (0.67% против единиц). Остаток доминируют классы 1–4 (утилиты конвертации и генераторов, не входящие в деплойный контур, + дешёво режущийся парсерный шум). **Решение (2026-11-10, согласовано): принять измеренный уровень 0.67% как есть** — правило остаётся severity 1 и включено по умолчанию; при необходимости точечные фильтры (точка-суффикс cross-db, `sqlFunctionsMap`/`sqlDataTypesMap`) добавляются отдельным изменением по факту эксплуатационного шума.

## Migration Plan

- Новых миграций схемы нет.
- Правило включается по умолчанию (как все правила каталога), отключается через `--rules`; включение — только после успешного замера 4.5 (гейт, см. Measurements).
- Откат: удалить правило из каталога (изменение обратно совместимо).
