# Review: параллельный запуск правил (минимальный риск)

План переводит `review` на внутреннее контролируемое распараллеливание правил с единым чтением файла, fail-fast/cancel при первой полученной ошибке и сохранением детерминированной выдачи findings.

## Цели и инварианты

- Не менять внешний контракт CLI/MCP (`codebase review`, `codebase_review_sql`).
- Параллелизм только внутренний, без новых флагов/аргументов.
- Лимит конкурентности: `min(runtime.NumCPU(), enabledRules, dbMaxOpenConns)`.
- Ошибки: отмена контекста при первой полученной ошибке, дождаться завершения воркеров, вернуть эту ошибку.
- Результат: детерминированная сортировка findings остаётся как сейчас.

## Этап 1: Единый контекст анализа файла

**Файлы:** `internal/review/types.go`, `internal/review/runner.go`, `internal/review/review_rules.go`.

1. Добавить внутреннюю структуру контекста выполнения review (например `reviewExecContext`):
   - `content []byte`
   - `contentStr string`
   - `lines []string`
   - при необходимости нормализованные/очищенные варианты текста, уже используемые несколькими правилами.
2. Выполнять `os.ReadFile(file.Path)` один раз в `RunSQLFile` после валидации файла.
3. Передавать контекст в правила, которые сейчас читают файл сами.
4. Удалить повторные `os.ReadFile(file.Path)` из правил и использовать данные из контекста.

## Этап 2: Абстракция rule task

**Файлы:** `internal/review/runner.go` (+ при необходимости `types.go`).

1. Сформировать список задач `ruleTask` на основании `enabledRuleSet(opts.Rules)`.
2. Каждая задача хранит:
   - `rule RuleID`
   - `run func(ctx context.Context) ([]Finding, error)`
3. Для задач, использующих `parsed`, передавать уже готовый `parsed` (как и сейчас — парсинг файла один раз).
4. Для задач, использующих текст файла, передавать общий `reviewExecContext`.

## Этап 3: Worker-pool + fail-fast cancel

**Файлы:** `internal/review/runner.go`.

1. Добавить `context.WithCancel` в `RunSQLFile`.
2. Реализовать worker-pool:
   - канал задач,
   - N воркеров (`N = min(runtime.NumCPU(), enabledRules, r.db.Stats().MaxOpenConnections)`),
   - канал результатов (`findings`/`err`).
3. Поведение ошибок:
   - при первой полученной `err` вызвать `cancel()`;
   - прекратить постановку новых задач;
   - дождаться завершения воркеров (`sync.WaitGroup`);
   - вернуть первую полученную ошибку.
4. На успехе собрать findings всех завершённых задач в общий срез.

## Этап 4: Детерминированный merge и пост-обработка

**Файлы:** `internal/review/runner.go`.

1. Сохранить существующую фильтрацию `MinSeverity` без изменений.
2. Сохранить текущую сортировку:
   - по `Line`,
   - при равенстве по `Rule`.
3. Не менять `Summary`/`Result` формат.

## Этап 5: Тесты

**Файлы:** `internal/review/runner_test.go` (и точечно соседние тесты при необходимости).

Добавить/обновить тесты:
1. `RunSQLFile` в параллельном режиме выдаёт детерминированный порядок findings.
2. Первая полученная ошибка из правила приводит к отмене и возврату ошибки.
3. Поведение `min-severity` не меняется.
4. Регрессия на subset правил (`--rules`) — выполняются только выбранные.
5. (Опционально) smoke на отсутствие повторного чтения файла через test double/инструментируемую функцию чтения.

## Этап 6: Проверка и приёмка

1. `go test ./internal/review/... ./cmd/...`
2. `go build ./...`
3. Ручной smoke:
   - `codebase review <sql-file>`
   - `codebase review <sql-file> --json`
   - `codebase review <sql-file> --rules datatype,indexWrong`

## Риски и как их снимаем

- **Конкуренция за БД:** ограничиваем пул воркеров через `MaxOpenConnections`.
- **Скрытые зависимости правил от последовательности:** сохраняем независимый merge + итоговую сортировку; порядок выполнения не используется в логике findings.
- **Утечки горутин/каналов при ошибке:** единый `cancel`, закрытие каналов только владельцем, `WaitGroup` перед выходом.

## Критерии готовности

- Время `review` на типичных больших SQL заметно ниже последовательного baseline.
- Контракт CLI/MCP неизменен.
- При ошибке поведение fail-fast сохранено (с учётом «первая полученная»).
- Все релевантные тесты и сборка проходят.
