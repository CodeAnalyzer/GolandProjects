# План: типизация select_into (итерация 1)

В первой итерации мы добавляем безопасный вывод `data_type` для простых `SELECT ... INTO` выражений, чтобы уменьшить долю `DSUNKNOWN` без попытки полноценно вычислять типы сложных SQL-выражений.

## Цель
- Для `definition_kind = select_into` заполнять `data_type` в очевидных случаях.
- Сохранить текущую устойчивость парсера: при сомнении оставлять `DSUNKNOWN`.

## Scope (что включаем)
1. Простые ссылки на поле:
   - `table.column`
   - `alias.column`
   - `column` (если однозначно в рамках текущего `FROM/JOIN` контекста).
2. Алиасы результата:
   - `expr AS Alias`
   - `expr Alias`
3. Простые обертки:
   - `ISNULL(x, ...)` / `COALESCE(x, ...)` — тип берется из первого аргумента `x`, если он распознан как ссылка на поле.

## Out of scope (итерация 2+)
- Полная типизация `CASE ... WHEN ... THEN ... ELSE ... END`.
- Вычисление типа арифметических/строковых выражений и функций общего вида.
- Глубокий межфайловый вывод типов через цепочки view/CTE/subquery.

## Изменения по коду
1. `internal/parser/sql/sql_parser.go`
   - Расширить обработку проекции `select_into`: извлекать не только имя колонки, но и тип кандидата.
   - Добавить helper-ы:
     - разбор выражения колонки (`expr`, `output_name`);
     - извлечение ссылок на поля внутри `expr` для простых кейсов;
     - приоритизация источника типа для `ISNULL/COALESCE`.
   - В `flushSelectIntoProjection` формировать `appendColumnDefinition(..., "<column> <type>", "select_into", ...)`, где `<type>` = вычисленный DS-тип или `DSUNKNOWN`.

2. Источник типов для полей
   - Использовать уже проиндексированные определения колонок (`sql_column_definitions`) как словарь `table.column -> data_type`.
   - На этапе парсинга файла строить in-memory lookup по доступным таблицам/алиасам из текущего запроса (`FROM/JOIN`).

3. `internal/store` / `internal/indexer` (если потребуется)
   - Добавить легковесный метод чтения типов колонок по имени таблицы/колонки для parser context.
   - Не менять формат хранения результата: использовать существующее поле `data_type` в `sql_column_definitions`.

## Тесты
1. `internal/parser/sql/sql_parser_test.go`
   - Позитивные кейсы:
     - `i.InstitutionID` -> тип из `tInstitution.InstitutionID`.
     - `i.Name` -> тип из схемы.
     - `isnull(i.Name1, "") as Name1` -> тип `Name1` от `i.Name1`.
   - Негативные/ограничения:
     - `case ... end as PropDealPart` -> пока `DSUNKNOWN`.
     - неоднозначная ссылка `column` -> `DSUNKNOWN`.

2. Регрессии
   - Сохранить уже добавленный тест на корректное извлечение колонок при `INTO` на отдельной строке.

## Критерии готовности
- В `query table-schema --name tConsInstitutionSync --json` для части колонок из `select_into` вместо `DSUNKNOWN` появляются конкретные `DS...` типы.
- Для сложных выражений остаётся `DSUNKNOWN` (осознанно).
- Существующие сценарии индексации не деградируют.

## Риски и контроль
- Риск ложной типизации при неоднозначных алиасах/колонках.
  - Контроль: strict-режим — тип ставим только при высокой уверенности, иначе `DSUNKNOWN`.
- Риск удорожания парсинга.
  - Контроль: кэш lookup-ов по таблицам в рамках файла/statement.
