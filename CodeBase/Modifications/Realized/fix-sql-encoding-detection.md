# Детекция кодировки SQL/H-скриптов по содержимому (CP866/CP1251)

> **Статус: реализовано** в change `add-content-encoding-detection` (расширенный
> вариант: универсальная детекция по содержимому для всех single-byte форматов
> `.sql/.h/.tpr/.pas/.inc/.js/.smf/.dfm/.rpt`, карта расширений → prior).
> См. `openspec/changes/add-content-encoding-detection/` (design D1–D6,
> корпусная валидация в D3). Ниже — исходный анализ.

Предложение (не реализовано). Для расширений `.sql`/`.h`/`.tpr` декодер жёстко
применяет CP866, но часть исходников FA (модуль fa-administrator, файлы `*.SQL`)
хранится в CP1251. Такие файлы декодируются в mojibake: кириллические комментарии
и header-описания процедур превращаются в рамки/спецсимволы. Вскрыто выгрузкой
словаря desc-LSA (`desc_vocab`) change-а add-description-search.

---

## Контекст (что есть сейчас)

- **Жёсткая карта расширение → кодировка** (`internal/encoding/encoding.go:25-30`):
  `.sql`/`.h`/`.tpr` → CP866, остальное → WIN1251. Содержимое файла не анализируется.
- **Фактура FA (замер 2026-10-05, change add-description-search)**:
  - 2545 описаний процедур из 32 441 (7.8%) — mojibake «╧ЁюЎхфєЁра…» (CP1251-байты
    в CP866-одежде); концентрируются в `fa-administrator/**/*.SQL`;
  - у этих же файлов mojibake все кириллические комментарии в `query_fragments`,
    defines и прочем текстовом экстракте (идентификаторы ASCII не страдают);
  - крайний случай: `fa-cards/.../Acq_Calculations.sql` содержит байт 0x98,
    не мапящийся в CP1251 — строгий декод падает, поведение на эвристике не определено.
- **Эвристика `DetectEncodingFromContent` — мёртвый код**: `hasCyrillic` считает
  «кириллицей» любой байт ≥ 0x80, поэтому для любого не-ASCII файла CP866 всегда
  выигрывает и WIN1251-ветка недостижима.
- **Сигнатура mojibake точна** (проверено побайтовой таблицей CP866):
  CP1251-кириллица в CP866-декоде даёт U+2500-U+259F (рамки/блоки, байты
  0xC0-0xDF), украинские ЄєЇїЎў (0xF2-0xF7), ¤■∙·√ (0xF9-0xFE). В легитимном
  русском тексте описаний эти руны не встречаются (№ 0xFC и ° 0xF8 — легитимны
  в CP866 и в артефактный набор не входят). Буквы CP1251 т-я (0xF2-0xFF, 14 из
  33 букв алфавита) дают те же артефакты — mojibake-документ целиком распознаётся
  с вероятностью ~100%.
- Тот же артефакт-набор уже используется фильтром корпуса desc-LSA
  (`isMojibakeText`, `internal/store/db_fts.go`) — пластырь change-а
  add-description-search; настоящее предложение чинит корень.

## Мотивация

1. **8% описаний процедур — мусор**: полнотекстовый поиск по ним не работает
   (искажённые термины), семантический корпус вынужденно их отбрасывает.
2. **Загрязнение текстового экстракта**: fragments/comments этих файлов
   нечитаемы и для человека, и для поиска.
3. **Универсальность**: детекция по содержимому снимает зависимость от
   соглашений конкретного модуля (CP866 у SERVER-скриптов, CP1251 у части
   администраторских) и будущих исключений вида Acq_Calculations.sql.

## Предлагаемое решение

### Шаг 1. Сигнатурное уточнение декодирования

В точке декодирования индексатора (для файлов, чья кодировка разрешена картой
как CP866):

1. Декодировать CP866 (как сейчас).
2. Проверить результат на артефакт-сигнатуру (набор рун из контекста выше,
   порог: ≥1 вхождение — сигнал; при необходимости калибровка долей).
3. Если сигнатура есть — перекодировать те же байты как WIN1251.

UTF-8 проверять раньше CP866 (valid UTF-8 с кириллицей → UTF-8), покрывая и
случай Acq_Calculations.sql: невалидные байты → не UTF-8 → сигнатурная схема.

### Шаг 2. Оживить `DetectEncodingFromContent`

Заменить `hasCyrillic` (b ≥ 0x80) на осмысленное сравнение: счётчик кириллических
букв против счётчика артефакт-рун для обоих кандидатов; вернуть кодировку с
лучшими показателями. Существующие вызовы (если есть вне индексатора) —
аудит на совместимость.

### Шаг 3. Прозрачность

- Счётчик перекодированных файлов в `ScanStats` (например `EncodingRefined`)
  + лог-строка с rel_path — чтобы прогон показывал масштаб.
- Release notes: «часть файлов теперь декодируется по содержимому; требуется
  полная пересборка».

## Затронутые файлы

- `internal/encoding/encoding.go` — сигнатурная детекция, правка `hasCyrillic`
- точка декодирования индексатора (`decodeIndexedFileContent` / вызовы
  `DetectEncoding`) — пропуск данных в детекцию
- `internal/model` (ScanStats) — счётчик перекодировок
- тесты `internal/encoding`, fixture-файлы CP866/CP1251/UTF-8

## Миграция и совместимость

- **Полная пересборка обязательна**: pre-filter по mtime+size не увидит
  изменения правила декодирования неизменённых файлов. `codebase update
  --modified=false` (или `init` на чистой БД).
- Все существующие поля/таблицы не меняются — меняется только содержимое
  текстовых колонок для части файлов.
- Откат — бинарный (предыдущее правило декодирования).

## Тесты

- Детекция: CP1251-файл с русской кириллицей → WIN1251; CP866-файл → CP866
  (без ложных срабатываний на рамках в легитимных CP866-комментариях —
  порог/калибровка); UTF-8 с кириллицей → UTF-8; файл с байтом 0x98 → не падает.
- Индексер: fixture fa-administrator-стиля → описание процедуры читаемо.
- Regression: существующие фикстуры парсеров (CP866) не меняют декодирование.
