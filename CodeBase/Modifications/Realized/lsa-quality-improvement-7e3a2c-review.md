# Заключение и рекомендации по улучшению LSA

## Заключение

Изменение `lsa-quality-improvement-7e3a2c.md` в целом направлено в правильную сторону и не нарушает заявленную модель OpenSpec: LSA по-прежнему работает на уровне capability, `embed_level = 'spec'`, а exact и semantic результаты остаются раздельными.

Однако план в текущем виде я бы оценил как **концептуально хороший, но не готовый к безусловной реализации**. Основные риски находятся не в совместимости со спецификацией, а в корректности ранжирования, переобучения модели и отсутствии проверяемых критериев качества.

## Основные находки

### 1. Критический риск: изменения requirements/scenarios не гарантируют переобучение LSA

В `internal/indexer/indexer_postprocess_spec_lsa.go:24-52` количество изменений определяется только через:

```go
changedCount := stats.SpecCapabilities
```

При этом в `internal/indexer/indexer_spec.go:285-287` отдельно считаются:

```go
stats.SpecCapabilities++
stats.SpecRequirements += len(reqs)
stats.SpecScenarios += len(scns)
```

То есть добавление или изменение требования может изменить текст LSA-документа, но не увеличить `changedCount`. При наличии уже существующей модели условие раннего выхода может пропустить переобучение.

Это особенно опасно для основной цели изменения: термин «заметка» будет добавлен в requirements, но старая модель останется на диске и поиск не изменится.

**Рекомендация:** определить надежную политику инвалидирования модели:

- считать измененными capability, если изменились их requirements/scenarios;
- либо использовать отдельный счетчик вроде `SpecTextChanged`;
- либо хранить fingerprint входных LSA-документов;
- fingerprint должен учитывать capability-текст, requirements, scenarios, параметры `min_df`, `max_df`, `k` и версию tokenizer.

Наиболее надежный вариант: вычислять hash агрегированного текста корпуса и параметров модели, сохранять его рядом с моделью и переобучать при изменении hash.

### 2. Относительный cutoff требует четкого порядка применения

Сейчас `internal/specsvc/specsvc.go:1084-1119`:

1. читает все embeddings;
2. отбрасывает значения `<= 0.01`;
3. сортирует результаты;
4. применяет `limit`.

Relative cutoff нужно применять до `limit`:

```text
получить все кандидаты
отфильтровать по абсолютному порогу
отсортировать по Rank DESC
вычислить relative cutoff от максимального Rank
отфильтровать по cutoff
применить limit
```

Рекомендуемая логика:

```go
if len(hits) > 0 {
	cutoff := cfg.Spec.LSARelativeCutoff * hits[0].Rank
	filtered := hits[:0]
	for _, hit := range hits {
		if hit.Rank >= cutoff {
			filtered = append(filtered, hit)
		}
	}
	hits = filtered
}
```

### 3. Новые параметры конфигурации нужно валидировать

Следует определить поведение для некорректных значений:

- `LSAMinCosine` должен находиться в диапазоне `[0, 1]`;
- `LSARelativeCutoff` должен находиться в диапазоне `[0, 1]`;
- нужно решить, допустимо ли явное значение `0` для отключения порога;
- некорректные значения должны приводить к ошибке загрузки либо к default с предупреждением.

Существующий подход с условием `<= 0` не позволяет отличить «значение не задано» от явного отключения фильтра. Это допустимо, только если такое поведение является осознанным контрактом.

### 4. Полный текст requirements/scenarios может исказить TF-IDF

Предлагаемый документ capability:

```text
title + purpose + notes + requirements + scenarios
```

оправдан для поиска терминов вроде «заметка», но сценарии могут быть длинными и содержать повторяющиеся шаблонные фразы. В `internal/specfts/vocab_tfidf.go:75-108` частота терминов внутри документа влияет на TF-вес, после чего строка нормализуется. Большие capability могут получить искаженный профиль по сравнению с короткими capability.

**Рекомендация:**

- включать `requirement_name`;
- включать `scenario_name`;
- ограничивать максимальную длину агрегированного текста;
- нормализовать markdown-служебные конструкции перед токенизацией;
- проверить влияние на длинные и короткие capability;
- при необходимости использовать веса: title повторять 2-3 раза, purpose 1-2 раза, requirements/scenarios включать один раз.

Минимально разумный состав:

```text
title title
purpose
notes
requirement_name body_text
scenario_name given when then
```

### 5. SQL-агрегация должна быть детерминированной

Предложенный SQL со `string_agg` требует доработки:

- нужен `ORDER BY` внутри `string_agg`;
- необходимо корректно обрабатывать `NULL` через `concat_ws`;
- в scenarios следует включать `scenario_name`;
- при большом корпусе стоит оценить стоимость двух коррелированных подзапросов на capability.

Рекомендуемый фрагмент:

```sql
string_agg(
    concat_ws(' ', req.requirement_name, req.body_text),
    ' ' ORDER BY req.req_order, req.id
)
```

Для сценариев:

```sql
string_agg(
    concat_ws(
        ' ',
        s.scenario_name,
        s.given_text,
        s.when_text,
        s.then_text
    ),
    ' ' ORDER BY req.req_order, s.scn_order, s.id
)
```

Индексы на `capability_id` и `requirement_id` уже присутствуют в `internal/store/db_schema.go:855-857`, поэтому базовая схема для такого запроса подходит.

### 6. `RelatedCode` переиспользовать не следует

План правильно предлагает отдельное поле вместо записи requirements в `RelatedCode`. `RelatedCode` имеет самостоятельный смысл и используется для code references.

Рекомендуется добавить отдельное поле:

```go
ReqText string
```

либо более явно:

```go
LSAText string
```

`LSAText` лучше отражает назначение агрегированного текста, если он используется только для обучения LSA.

### 7. Доменные стоп-слова слишком агрессивны

Слова `клиент`, `документ`, `объект`, `счет`, `операция`, `параметр` действительно могут быть частотными, но они также могут быть единственными предметными признаками запроса.

Например, удаление этих терминов может ухудшить запросы:

- «операция по счету»;
- «документ клиента»;
- «параметры объекта».

Ручной список словоформ также ненадежен, поскольку токенизатор применяет stemmer.

**Рекомендация:**

1. сначала получить статистику `df` по реальному корпусу;
2. использовать maxDF как основной механизм фильтрации;
3. добавлять стоп-слова только по результатам benchmark;
4. вынести доменный список в конфигурацию либо versioned-файл;
5. проверять влияние каждого слова на контрольные запросы.

Особенно важно проверить варианты `счет` и `счёт`, поскольку текущий корпус и тесты используют `ё`.

### 8. Снижение `maxDF` не решает проблему редких терминов

В `internal/specfts/vocab_tfidf.go:44-52` применяется `minDF`, равный по умолчанию `3`. Если «заметка» встречается только в одной capability, она не попадет в словарь, даже если requirements будут добавлены в документ.

Это противоречит ожидаемому эффекту, сформулированному в спецификации.

**Рекомендация:** проверить фактический `df` термина «заметка». Если он равен 1:

- снизить `LSAMinDF`;
- либо использовать отдельную стратегию для query terms;
- либо скорректировать ожидаемый результат и не обещать автоматическое попадание термина в словарь.

Также нужно учитывать округление:

```go
maxDFCount := int(maxDF * float64(nDocs))
```

Поведение на границах `maxDF` следует покрыть тестами.

### 9. Нет достаточных тестов для главного сценария

В текущем коде есть тесты токенизации, TF-IDF и общих функций `specsvc`, но нет теста, который проверяет заявленный результат:

```text
«Заметка по клиенту» -> legal в semantic top-N
```

Нужны тесты на:

- загрузку capability вместе с requirements/scenarios;
- полноту и порядок агрегированного текста;
- изменение LSA-документа после добавления requirement;
- абсолютный cosine cutoff;
- relative cutoff;
- применение `limit` после relative cutoff;
- defaults новых параметров;
- некорректные значения конфигурации;
- переобучение после изменения requirement/scenario;
- фильтрацию доменных стоп-слов;
- пустой query vector.

Один запрос «Заметка по клиенту» недостаточен. Нужен небольшой benchmark минимум из следующих запросов:

- «Заметка по клиенту»;
- «блокировка счета»;
- «лимит карточки»;
- «обработка платежного документа»;
- «параметры операции»;
- несколько запросов с техническими именами.

Для каждого запроса следует фиксировать ожидаемую capability, допустимый top-k, минимальный rank и количество нерелевантных результатов.

## Что в плане сделано правильно

- Сохранен capability-level embedding.
- Не предлагается создавать отдельные LSA embeddings для requirements.
- Exact search не смешивается с semantic search.
- Предлагается отдельное поле вместо перегрузки `RelatedCode`.
- Новые пороги предполагаются configurable.
- Изменения локализованы в `store`, `indexer`, `specsvc`, `specfts`, `config`.
- `cmd` менять, скорее всего, не требуется: команда `query spec search` уже передает параметры в `specsvc.ExecuteSpecSearch`.

## Рекомендуемый порядок реализации

### Этап 1. Исправить обновление модели

Сначала устранить риск устаревшей модели:

1. добавить агрегированный LSA-текст в модель;
2. загружать requirements и scenarios;
3. считать fingerprint полного корпуса;
4. переобучать модель при изменении текста или параметров;
5. добавить тест переобучения после изменения requirement.

### Этап 2. Добавить детерминированный агрегированный текст

Реализовать SQL с `concat_ws`, `ORDER BY`, включением `requirement_name`, `scenario_name` и корректной обработкой `NULL`. Добавить тест на содержимое агрегированного поля.

### Этап 3. Реализовать абсолютный порог

Добавить `LSAMinCosine` и проверить benchmark до и после изменения.

### Этап 4. Реализовать relative cutoff

Вынести фильтрацию в отдельную чистую функцию, например:

```go
func filterSemanticHits(
    hits []SpecSearchHit,
    minCosine float64,
    relativeCutoff float64,
    limit int,
) []SpecSearchHit
```

Это позволит тестировать логику без PostgreSQL.

### Этап 5. Настроить maxDF и стоп-слова по benchmark

Не следует одновременно менять состав документов, `maxDF`, стоп-слова и оба порога без промежуточных измерений. Иначе невозможно будет определить причину улучшения или ухудшения.

Оптимальный порядок:

1. расширить training-текст;
2. проверить `df` и ranking;
3. добавить абсолютный cutoff;
4. настроить relative cutoff;
5. оценить domain stop words;
6. изменить `maxDF`, если это подтверждено benchmark.

## Итоговая оценка по приоритетам

### Высокий приоритет

- исправить retrain/invalidation для requirements и scenarios;
- проверить, что термин «заметка» проходит `LSAMinDF`;
- определить порядок relative cutoff и `limit`;
- добавить regression-тест на semantic ranking;
- сделать агрегацию текста детерминированной.

### Средний приоритет

- валидировать диапазоны новых конфигурационных параметров;
- добавить scenario name в LSA-текст;
- ограничить или взвесить длинные документы;
- покрыть SQL-загрузчик интеграционным тестом;
- проверить поведение `maxDF` на границах.

### Низкий приоритет

- заменить ручной список словоформ на stem-based или конфигурируемый список;
- обновить документацию `Document.Text`;
- добавить диагностическую статистику LSA: число документов, размер словаря, min/max/avg cosine и количество результатов после каждого фильтра.

## Финальный вывод

Изменение стоит реализовывать, но не буквально по текущему плану. Шаг 1 является наиболее перспективным, однако его необходимо дополнить корректной инвалидизацией модели и проверкой `minDF`. Шаги 2-3 следует внедрять через отдельные тестируемые функции и benchmark, иначе есть риск заменить один вид шума другим и потерять релевантные результаты.
