# Шум semantic-слоя: пересмотренное предложение (ревизия 2)

Статус: **реализовано (этап 1)** — change `lsa-query-coverage-gate` архивирован
2026-10-17, build 1607. Этапы 2–3 (центрирование эмбеддингов и калибровка
порогов `lsa_min_cosine`) **не реализованы** и остаются отдельными задачами.

Причина пересмотра: проверка на живом индексе (PostgreSQL `codebase`, модели
`desc_lsa_model.bin` / `spec_lsa_model.bin`) показала, что исходный диагноз
«OOV-деградация запроса» **неверен**, а рекомендованный шаг 1 не даёт эффекта
на реальных данных. Ниже — проверенные факты, переформулированная проблема и
план, разделённый на независимые изменения.

---

## 1. Что изменилось относительно ревизии 1

| Ревизия 1 | Ревизия 2 |
|---|---|
| «`несуществующий` — OOV, остаётся только `запрос`» | **Ложно.** `несуществ` есть в обоих словарях (desc df=291, spec df=100) |
| TC-037: покрытие 1/3 ≈ 0.33 | **Фактически 2/2 = 1.0**: токенизатор даёт `[несуществ, запрос]`, `asdkjhasd`/`zzz` отбрасываются до словаря |

| Центрирование — шаг 3 того же изменения | **Отдельное изменение**: наивный mean даёт 138 ложных топ-хитов |
| «Укладывается в текущие требования» | **Противоречит спеке** `query/description-search` (строки 182–186) |

## 2. Проверенные факты

### 2.1. Токенизация и словарь

Запрос TC-037 `"asdkjhasd несуществующий запрос zzz"`:

```
Tokenize → 2 токена: [несуществующий → несуществ] [запрос → запрос]
           asdkjhasd, zzz — строчная латиница, отбрасываются до словаря
```

Запрос TC-119 `"asdkjhasd zzzzz несуществующее"` → 1 стем `[несуществ]`.

Словари (живая БД):

| Корпус | `запрос` | `несуществ` | Всего терминов |
|---|---|---|---|
| `desc_vocab` | df=863, idf=5.15 | df=291, idf=6.23 | 4465 |
| `spec_vocab` | df=375, idf=2.96 | df=100, idf=4.27 | 10271 |

Вывод: оба содержательных слова запроса **известны модели**. Утверждение
ревизии 1 об OOV не подтверждается.

### 2.2. Полностью мусорный запрос уже работает

```
codebase query desc-search --text "asdkjhasd zzz"   → count=0
codebase query spec search --query "asdkjhasd zzz"  → semantic=[], meta.reason=threshold
```

Проваливаются только **смешанные** запросы, где кроме мусора есть реальная
русская фраза «несуществующий запрос» (она встречается в описаниях FA —
exact-поиск находит реальные процедуры).

### 2.3. Текущие ранги

TC-119 (`spec search`, живые значения): `0.3736, 0.3140, 0.3066, 0.3059, 0.2882`.
При пороге 0.35 остаётся **один** хит — тест всё равно FAIL.

TC-037 (`desc-search`): `0.7693, 0.7604, 0.7508, 0.6791, 0.6675` — порог 0.35
не отсекает ничего.

### 2.4. Порог 0.35 сейчас не применяется

В `codebase.toml` **явно** заданы `lsa_min_cosine = 0.15` в секциях `[spec]`
(строка 84) и `[desc_lsa]` (строка 98). Смена Go-дефолта без правки конфига —
no-op.

### 2.5. Центрирование: симуляция на реальных эмбеддингах

Spec-корпус: 2661 документ, K=512. Симуляция воспроизвела живые ранги TC-119
до 4 знаков, т.е. модель поведения восстановлена корректно.

| Сценарий | TC-119 | «расчёт аннуитетного платежа» | «массовое создание плановых событий» |
|---|---|---|---|
| Сырые cosine | max 0.3736, 1 хит >0.35 | max 0.5609, 17 хитов >0.35 | max 0.3524, 1 хит >0.35 |
| Наивный mean по всем | **max 0.6359**, 138 хитов | max 0.5305, 151 хит | max 0.3343, 0 хитов |
| Mean без вырожденных + skip | max 0.3386, 0 хитов | max 0.5328, 14 хитов | max 0.3367, 0 хитов |

Причина: **138 из 2661 (5.2%) эмбеддингов имеют норму ≈ 0**. Это capability,
чей title — slug вида `accrual-core/base-algorithms/operation`: токенизатор не
находит в нём ни русских слов, ни техимён, ни гибридов → нулевой вектор.
После вычитания среднего все они превращаются в одинаковый `−mean` и занимают
весь топ с cosine 0.6359.

Отсюда два следствия:

1. Центрирование обязано **исключать вырожденные векторы** из расчёта среднего
   и из выдачи (guard по норме, epsilon).
2. После корректного центрирования средний cosine становится ≈ 0
   (`-0.001`), и порог 0.35 бьёт по позитивному запросу «массовое создание
   плановых событий» (max 0.3367). **Шаги «порог» и «центрирование» нельзя
   калибровать независимо.**

Симуляция выполнена только на spec-корпусе; для desc-корпуса центрирование
нужно проверить отдельно (45k+ документов, другой масштаб рангов: релевантные
0.52–0.67).

## 3. Переформулированная проблема

Исходная формулировка «OOV-деградация запроса» неверна. Реальных причин три:

1. **Смешанный запрос.** Мусорные токены молча исчезают, а оставшиеся реальные
   слова («несуществующий запрос») дают осмысленную для модели проекцию.
   Сигнал «часть запроса не распознана» теряется.
2. **Неточная мера покрытия.** Считать покрытие по стемам бессмысленно: OOV в
   такой метрике — только слова, которые дошли до стеммера. Отброшенная
   латиница в знаменатель не попадает.
3. **Фон косинуса + вырожденные документы.** В редуцированном пространстве
   косинус систематически положителен; нулевые эмбеддинги усиливают эффект при
   любом центрировании.

Пункт 1 — продуктовый вопрос: должен ли запрос с 50% нераспознанных слов давать
пустую semantic-выдачу? Пункт 3 — отдельная задача качества модели.

## 4. Развилка: что считать требованием

### Вариант A. Признать TC-037/TC-119 дефектом тест-кейсов

Чистый OOV уже возвращает 0. «Несуществующий запрос» — реальная фраза корпуса;
ожидать `count=0` от запроса, половина которого осмысленна, спорно.
Действие: переписать TC-037/TC-119 (чистый мусор + смешанный кейс с явно
заданным ожиданием), код не менять.

**Плюсы:** нет изменений в поведении, нет дельта-спек.
**Минусы:** проблема «полумусорных» запросов остаётся.

### Вариант B. Гейт по доле нераспознанных лексических слов (рекомендуется)

Считать не OOV-стемы, а **«сырые» word-токены**, которые токенизатор не смог
обработать. Стоп-слова считаются распознанными (они легитимны в запросе).

```
coverage = recognizedRawWords / totalRawWords

TC-037:  asdkjhasd | несуществующий | запрос | zzz   → 2/4 = 0.50
TC-119:  asdkjhasd | zzzzz | несуществующее          → 1/3 = 0.33
мусор:   asdkjhasd | zzz                             → 0/2 = 0.00
позитив: массовое | создание | плановых | событий    → 4/4 = 1.00
смешанный: asdkjhasd | аннуитетного | платежа        → 2/3 = 0.67
```

Порог по умолчанию — **0.6** (а не 0.5): TC-037 даёт ровно 0.5, и при `< 0.5`
граница не срабатывает; при 0.6 срабатывают оба кейса, а запрос 2/3 проходит.

**Плюсы:** закрывает оба TC, не зависит от minDF/maxDF словаря, прозрачен.
**Минусы:** эвристика; требует MODIFIED-дельты к спекам; строчная латиница
(легитимные английские слова) тоже считается нераспознанной — это уже текущее
поведение токенизатора, но его нужно явно зафиксировать.

### Вариант C. Не гейтить, а только центрировать + калибровать порог

TC-037 после корректного центрирования (spec) всё равно даёт max 0.478 — порог
придётся поднимать выше 0.48, что рискованно для позитивных кейсов. Само по
себе не закрывает TC-037.

**Рекомендация:** B как отдельное изменение + C как отдельное изменение
качества модели. A — если продукт решит, что смешанный запрос должен искать по
осмысленной части.

### Этап 1 (вариант B). Гейт по лексическому покрытию — реализовано

**Статус: реализовано** в change
[`lsa-query-coverage-gate`](../../openspec/changes/archive/2026-10-17-lsa-query-coverage-gate/)
(архивирован 2026-10-17, build 1607). Фактическая реализация:

- `specfts.QueryLexicalCoverage`, `UnrecognizedWords`, `QueryCoverageGate`;
  общий тип `specfts.SemanticDiagnostics` (алиас `SpecSearchMeta`).
- `lsa_min_query_coverage` в `[spec]` и `[desc_lsa]`: `nil` → 0.6, явный `0`
  отключает, значения вне `[0,1]` отклоняются при загрузке.
- `desc-search`: гейт до загрузки LSA-кэша; диагностика `semantic_meta`;
  MCP-ответ стал объектом `{items, has_more, semantic_meta}` (**BREAKING**).
- `spec-search`: гейт после загрузки модели (сохраняет приоритет диагностики
  недоступной модели); `reason=query_coverage`, `filtered_out` не заполняется.
- Интеграционные проверки: TC-037/TC-119, отключение нулём, граница 0.6,
  `loadCount=0` при гейте, exact-слой не подавляется.
- Оба корпуса используют один дефолт 0.6; секции настраиваются независимо.

**Новый API (`internal/specfts/tokenizer.go`):**

```go
// QueryLexicalCoverage возвращает число «сырых» word-токенов запроса
// и число распознанных: токенизатор дал токен, либо слово — стоп-слово.
// total == 0 → coverage = 0 (полностью нераспознанный запрос).
func QueryLexicalCoverage(query string) (recognized, total int)
```

Реализация — единая точка рядом с `Tokenize`: скан word-токенов (буквы,
длина ≥ 2), сопоставление с результатом `Tokenize` + `stopWords`/`stopStems`.
Не использовать `Vocab.Index` — minDF/maxDF иначе влияют на гейт.

**Конфигурация (`internal/config/config.go`, обе секции):**

```go
LSAMinQueryCoverage *float64 `toml:"lsa_min_query_coverage"`
// доля распознанных лексических слов; nil = 0.6, 0 = без проверки.
```

Геттер `MinQueryCoverage()` в `SpecConfig` и `DescLSAConfig` по образцу
`MinCosine()`.

**Интеграция:**

- `internal/query/desc_query.go` (`searchDescriptionsSemantic`): гейт **до**
  `descSemanticCache.get`: при `< MinQueryCoverage()` вернуть пустой semantic-слой
  и `SemanticDiagnostics` (`reason=query_coverage`, `coverage`,
  `coverage_threshold`, `oov_terms` = `UnrecognizedWords`, `hint`). Модель и
  кэш не загружаются; exact-слой не затрагивается.
- `internal/specsvc/specsvc.go` (`searchSpecSemantic`): гейт **после**
  `specSemanticCache.get` и до `ProjectQuery` (сохраняет приоритет диагностики
  недоступной модели); вернуть пустую секцию и `SpecSearchMeta` с
  `reason=query_coverage`, `coverage`, `coverage_threshold`, `oov_terms`.
  `filtered_out` и `threshold` для этой причины не заполняются — гейт
  применяется до скоринга.
- `vocab_tfidf.go` не меняется: `ProjectQuery` остаётся как есть.

**Дельта-спеки (фактически синхронизированы):**

- `query/description-search` — MODIFIED «Гибридный поиск exact + semantic» +
  ADDED «Диагностика semantic-слоя desc-search».
- `query/spec-search` — MODIFIED «Раздельные секции результата».
- `infrastructure/configuration` — ADDED «Настройки лексического покрытия
  LSA-запросов».

### Этап 2 (вариант C). Центрирование — отдельный change (не реализовано)

Не смешивать с этапом 1: меняются все ранги, другая матрица тестов, другая
перекалибровка.

1. **Вырожденные документы.** Перед обучением/центрированием вычислить норму
   эмбеддинга; документы с `‖emb‖ < ε` (например, 1e-6) исключить из расчёта
   mean и не скорить в semantic-слое. Причина: slug-title capability даёт
   нулевой вектор (5.2% spec-корпуса).
2. **MeanVec.** `mean[j] = avg(DocEmbedding(i)[j])` по невырожденным строкам;
   поле `MeanVec []float64` в `LSAModel` (gob обратно совместим).
3. **Fingerprint.** `AlgorithmVersion` 2 → 3 (`internal/specfts/lsa.go:39`) —
   иначе fingerprint не изменится и модель не переобучится. `MeanVec` в
   старых моделях = nil → центрирование выключено (поведение не меняется).
4. **Единая точка центрирования.** Либо центрировать при загрузке из БД и в
   кэше, либо хранить центрированными и БД, и кэш. Нельзя: БД — сырые, кэш —
   центрированные.
5. **Проекция запроса.** `query' = ProjectQuery − MeanVec`, `doc' = emb − MeanVec`;
   для вырожденных документов хит не создаётся.
6. **Переобучение** (`codebase update`) и проверка, что generation сменился.
7. **Калибровка.** Снять распределение рангов на размеченном наборе
   (TC-032…036, TC-113…118) до/после; только после этого выбирать пороги.

**Тесты:** mean не учитывает нулевые векторы; нулевые документы не попадают в
выдачу; позитивные кейсы сохраняются; golden-ранги; средний cosine по корпусу
≈ 0.

### Этап 3. Пороги — только после этапа 2 (не реализовано)

1. Не менять Go-дефолт `lsa_min_cosine` вслепую.
2. Если меняем — синхронно править `codebase.toml` (сейчас там явные 0.15),
   комментарии в `config.go` и документацию.
3. 0.35 не использовать как «универсальный»: на сырых рангах spec это
   отсекает позитивный «массовое создание плановых событий» (max 0.3524),
   на центрированных — тоже (max 0.3367).
4. Решение о пороге фиксировать таблицей «запрос → ожидаемый максимум/число
   хитов» из прогона, а не эмпирическим числом.

### Примечание: строчная латиница и `mass create`

`Tokenize` распознаёт русские слова, техимена (`API_*`, `CON_*`, `t[A-Z]`,
all-caps) и гибриды (`758П`, `1-4212U`). Слова `mass`, `create` не попадают ни в
одну категорию и не входят в стоп-словарь, поэтому дают покрытие 0/2 — гейт
срабатывает, semantic-слой пуст, а диагностика содержит
`reason=query_coverage`, `coverage=0`, `oov_terms=["mass","create"]`.

Это не регрессия: semantic-слой и раньше не мог построить для них проекцию;
изменение лишь сделало отказ явным. `lsa_min_query_coverage = 0` отключает
гейт, но **не** делает латиницу распознанной: `ProjectQuery` по-прежнему не
находит терминов, поэтому semantic остаётся пустым (причина `threshold`), а
exact-слой работает как обычно. Живой прогон build 1607: `desc-search
"mass create"` → exact 5 хитов, semantic 0, `reason=query_coverage`,
`coverage=0`, `oov_terms=["mass","create"]`; `spec search "mass create"
--layer both` → exact 100 (лимит), semantic 0, та же диагностика.

Для полноценной поддержки нужен отдельный change: расширить токенизатор
(категория строчной латиницы/английский стеммер), пересобрать словари и
LSA-модели, добавить тесты и перекалибровать пороги.

## 9. Открытые вопросы

**Решены в change `lsa-query-coverage-gate`:**

1. Смешанный запрос (2 распознанных слова из 4) подавляется гейтом при 0.6 —
   это принятое поведение.
2. Диагностика в `desc-search` добавлена: единый `semantic_meta` в обоих
   поисках; MCP `desc-search` возвращает объект, а не массив.
3. Стоп-слова считаются распознанными.
4. Отдельные пороги для desc/spec не вводятся: оба 0.6, но секции
   конфигурируются независимо.

**Остаются:**

1. Capability с title-slug и нулевыми эмбеддингами — исключать из LSA-корпуса
   или синтезировать текст из пути (этап 2).
2. Расширение токенизатора на строчную латиницу — отдельный change; до него
   `mass create` даёт coverage 0.

## Приложение. Как проверялось

```sql
-- словари
SELECT generation, term, doc_freq, idf FROM desc_vocab
 WHERE term IN ('несуществ','запрос');
SELECT generation, term, doc_freq, idf FROM spec_vocab
 WHERE term IN ('несуществ','запрос');
```

```
codebase query desc-search --text "asdkjhasd zzz"          → count=0
codebase query desc-search --text "asdkjhasd несуществующий запрос zzz"
                                                           → 5 semantic, 0.769…0.667
codebase query spec search --query "asdkjhasd zzzzz несуществующее"
                                                           → semantic 0.3736…0.2882
```

Симуляция центрирования: декодирование `spec_lsa_model.bin` (gob), чтение
`spec_embeddings` поколения модели (2661 × 512), проекция запроса по `VT`,
расчёт cosine до/после вычитания mean. Ранги TC-119 совпали с живой выдачей —
валидация методики. Наивное центрирование дало 138 хитов с одинаковым
cosine 0.6359 у документов с нулевой нормой.
