# Fix missing callback subscribers

План исправления: перенести формирование `subscribes_to_event` в обязательный глобальный пост-процесс после завершения индексации, чтобы убрать зависимость от порядка/параллельности обработки XML.

## Подтверждённая причина

- `subscribes_to_event` сейчас строится в `parseXMLFile(...)` сразу после вставки контрактов конкретного файла.
- В этот момент целевой `event` может ещё не существовать в БД (из-за параллельной индексации), и связь без ретрая пропускается.
- `query api-publishers` читает уже готовые relations и потому возвращает неполный список подписчиков.

## План изменений

1. **Убрать построение callback-relations из per-file этапа**
   - В `internal/indexer/indexer.go` исключить вызов `buildCallbackEventRelations(...)` из `parseXMLFile(...)`.
   - Это убирает недетерминированный момент создания связей.

2. **Добавить глобальный пост-процесс пересчёта `subscribes_to_event`**
   - Добавить отдельный шаг в индексаторе (по аналогии с `postProcessPASPending(...)`), который запускается после завершения worker pool.
   - Шаг выполняется и в `Init`, и в `Update` (включая `--only-modified`).

3. **Сделать пересчёт идемпотентным и полным**
   - Перед пересборкой удалить только старые callback-связи вида `api_contract -> api_contract` с `relation_type='subscribes_to_event'`.
   - Затем пересобрать их по всем актуальным `callback_event` контрактам, используя текущую логику матчинга:
     - `UsedObjectName` -> `event.contract_name`
     - приоритет `UsedModuleSysName` -> `event.owner_module`, с fallback по имени+типу.
   - Вставку выполнять батчами через существующий `BatchInsertRelations`.

4. **Добавить необходимые store-методы для массового пересчёта**
   - Получение набора callback-контрактов для пересборки (id, used object/module).
   - Удаление relations по типу/направлению для `subscribes_to_event`.
   - (Опционально) оптимизированный lookup events для снижения числа запросов.

5. **Верификация после фикса**
   - Прогнать `init` и `update --only-modified` на тестовом наборе с несколькими `CallbackEvent` на одно событие.
   - Сравнить `query api-publishers --event OnAfterRuleD_MassCrtDoc --json` до/после.
   - Проверить повторяемость результата на нескольких прогонах (исчезновение недетерминизма).

## Критерии готовности

- Для одного и того же события стабильно возвращаются все callback-подписчики.
- Результат не зависит от порядка/параллельности индексации.
- `update --only-modified` также восстанавливает ранее пропущенные `subscribes_to_event`.
